## 2. 任务目标（Goal）

用不含歧义的结果描述：

> 让系统角色库里内置 12 个经过统一评审的正式角色，每个角色只定义「它能做什么」这类长期稳定的能力，不绑定任何具体使用场景；内置角色只读、可查看、可基于它复制出自己的变体；旧 `dispatcher` 从内置降为自定义角色，但已经引用它的历史工作流照常能跑；原有的 5 个角色升级为正式版本后，引用不断。

拆成可观察结果：

- G1. 角色库「内置」分组**恰好**呈现 12 个角色，机器标识与中文名符合清单：通用 8 个（`requirements` 需求分析 / `designer` 方案设计 / `dev` / `review` / `test` / `evaluator` / `accept` / `closeout`），专业 4 个（`diagnose` 缺陷诊断 / `orchestrator` 探索统筹 / `researcher` 专家研究 / `synthesizer` 综合分析）。
- G2. 任一内置角色不可编辑、不可删除，但可从它创建自定义变体。
- G3. `dispatcher` 出现在「自定义」分组，引用它的历史工作流节点仍能正常解析并执行。
- G4. 原 `dev` / `test` / `review` / `accept` / `closeout` 的引用平滑映射到升级后的正式角色，行为连续、不失效。
- G5. `evaluator` 同时可被「优化」与「探索」两类流程引用；两类流程各自的评价结论枚举由**流程节点**定义，不写死进共享角色。
- G6. 角色机器标识为稳定英文，角色的正式说明为中文。

## 4. 关键实现约束（影响做法，不影响目标）

1. **运行时不读角色文件，只拼路径让 Agent 自己读**：生成器只产出一句「开工前先读取 `<roleDir>/<id>.md`」的提示。因此**角色定义文件必须真实存在**，否则节点执行时读不到内容。
2. **内置与自定义角色混装在同一目录**，靠「不在内置 id 集合内即视为自定义」来区分。这意味着 `dispatcher` 迁移只需把它移出注册表数组，**文件保留原位即可**，无需搬家。
3. **引用保护会拦截删除/重命名**：`dispatcher` 当前被 4 个节点引用，任何删除动作都会被引用数保护拦下 —— 这恰好是「历史引用不丢失」的现成保障。
4. **角色内容三级回退**：目录内文件 → 打包仓库内的同名文件 → 合成占位正文。新增角色时若文件缺失，会静默回退到占位正文而不报错 —— **这是个需要注意的静默失败点**，收口验证时应显式检查 12 个角色的文件都真实存在。
5. **加载目录优先级**：会话工作区仓库根下的角色目录优先。测试与开发模式下需注意这一点。

### 6.1 总体判断

**#81 技术上已可开工，且是 #82 的前置。** 它唯一的正式依赖 #58「角色库基础能力」已完成并交付（角色增删改、内置只读拦截、基于内置创建自定义变体、引用数保护均已落地）。技术路径还被 PR #70 完整验证过一次。

### 6.3 需要留意的风险

- 🟡 **静默回退**：新增角色若忘记建定义文件，系统不会报错，而是回退到占位正文。收口验证必须显式检查 12 个文件都真实存在（已列为验收第 14 条）。
- 🟡 **`evaluator` 语义冲突**：PR #70 留下的 `evaluator` 定义是探索专用的，与本 Issue 的「共享基础能力」定位相反。**可以直接复用 PR #70 素材的只有 `orchestrator` / `researcher` / `synthesizer` 三个**（评论给出「高度复用」评级），`evaluator` 需重写。
- 🟡 **并发动迁风险**：roadmap 规定「同一 Issue 同一时刻只有一个主责 Agent」。7 个角色若分给多个执行方并行做，容易在注册表数组与测试断言上互相覆盖。建议串行，或先做完工单 01 让扩充动作变成互不冲突的增量。
- 🟢 **意外之喜**：`dispatcher` 迁移是**零风险动作**——文件保留原位、模板不用改、引用保护自动生效，还能顺带验证「历史引用不丢失」这条验收标准。建议第一个做。
