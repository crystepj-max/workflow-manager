# Requirements Analysis（需求分析）

把一份原始输入（GitHub issue 或用户的自然语言描述）加工成「可直接执行」的需求资产。本 skill 是**自洽的编排能力**：分诊、澄清、定体量、拆解、探路所需的全部知识内联在本 skill 内，**不通过 `skill` 工具调用任何子 skill**。

> **为什么内联而不调用子 skill**：`triage` / `grill-with-docs` / `wayfinder` / `to-tickets` 是「仅限用户调用」的命令型 skill（frontmatter `disable-model-invocation: true`，对应 `allow_implicit_invocation: false`），刻意设计为人工键入 `/triage`、`/wayfinder` 等命令触发，**模型不可调用**（`skill` 工具会返回 `not available for model invocation`）。本 skill 将四者的等价知识内联于此。若用户希望交互式分诊 / 追问 / 探路，可提示其自行运行对应 `/` 命令；本 skill 的流程不依赖、也不调用这些命令。

## 流程

### 0. 输入识别

先判断需求源，这决定后续的「发布去向」：

- 输入是 GitHub issue（URL / `#编号` / `repo#编号`）→ 拉取 issue 全文 + 全部评论 + 标签 + 作者作为需求源；**发布去向 = 更新该 issue**
- 输入是自然语言 → 需求源 = 输入本身；**发布去向 = 创建新 issue**（GitHub 可用时）

### 1. 分诊（内联 triage 规则）

对需求做分类 + 状态判定，并为需求源打标签。

**分类标签**（恰好一个）：
- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

**状态标签**（恰好一个）：
- `needs-triage` — 维护者待评估
- `needs-info` — 等报告者补充信息
- `ready-for-agent` — 规格完整，可交 agent 施工
- `ready-for-human` — 需人工实现（判断/外部权限/设计决策/手动测试）
- `wontfix` — 不处理

**状态流转**：无标签 → 先 `needs-triage`；`needs-info` 收到回复后回到 `needs-triage`；维护者可随时覆盖（异常流转先确认再动）。

**分诊检查**：
1. **冗余性**：按领域概念（不是按措辞）搜索仓库中是否已有实现；已有 → `wontfix` 并指出位置，不写 `.out-of-scope/`（那是给「被拒绝」的需求用的）。
2. **历史拒绝**：读 `.out-of-scope/`（若存在），有相似需求先提示。

**标签应用**：以仓库实际标签为准——先 `gh label list` 查已存在的标签，存在则复用（如本仓库已有 `bug` / `enhancement` / `wontfix` / `needs-info` / `ready-for-agent` / `sized-m` / `sized-l`），缺失才新建；不要重复创建同名标签。

**发布规则**：发布到 issue tracker 的任何内容必须以 `> *This was generated by AI during triage.*` 开头（AI 生成免责声明）。

> 注意：**size 判定不在此步**——体量必须基于澄清后的完整信息来定，先澄清、后定大小（见 §3）。

### 2. 澄清（内联 grill-with-docs 规则）

需求**内容**层面存在歧义时（术语含糊、行为未定义、多解场景），向用户逐项追问澄清，边聊边沉淀决策：

- **追问方式**：每轮至多一轮针对性提问；问题必须具体可行动（不是「请提供更多信息」）。
- **沉淀决策**：落定的决策记为 ADR / 术语表，写入分析文档（或仓库 `docs/adr/` 等约定位置），避免重复提问。
- **边界**：此处澄清的是需求内容的歧义。若澄清后仍无法得出三要素中的某一项，**走 §5 缺口处理，不得继续追问**。
- **无人工受访者时**（后台 / 自动化执行，无人可问）：需求内容歧义**直接转 §5 缺口处理**——如实列入缺口清单（缺什么/由谁补/补在哪），不编造、不追问，由人工补齐后重新调度续接。

### 3. size 判定与路由（基于澄清后的完整信息）

澄清完成后信息已完整，**此时才判定体量**，打 `sized-s` / `sized-m` / `sized-l` 标签。

#### size 判定启发式

按优先级依次看三个维度：

1. **路径清晰度**：实现方案是否已明确？是否存在必须先决断的设计问题或未知领域？
   - 不清晰或存在未知 → 至少 M，倾向 L
2. **工作量**：能否在单个执行会话内完成（含测试与验证）？明显超出（多日、多人、多轮探索）→ L
3. **影响面**：涉及多少模块 / 服务 / 文件集合？单一 → S；2 个以上 → M 或 L

判定结果：

- **S**：路径清晰 + 影响面单一 + 单会话可完成 → 直接产出三要素分析（§4），作为单个任务
- **M**：路径清晰 + 需拆成多个依赖任务，但无需先期决策探索 → 产出三要素 + 按 §6.1 内联拆解规则产出带依赖顺序的任务清单（垂直切片、阻塞边、先做前置重构）
- **L**：路径不清晰（存在先决断问题）或明确超出单会话承载 → **必须拆分，禁止整块开工**，走下方 L 型路径

#### L 型路径：拆分 + 探路（内联 wayfinder 规则）

L 型 = 超出单会话承载，**必须拆分才能推进**；拆分的正确对象是「决策」而非「任务」：

1. **拆决策地图**：把需求拆成 N 张**决策工单**——每张对应一个「必须先决断的问题」（服务边界怎么划、数据一致性怎么做、对外契约怎么定……）。一张工单 = 一个问题 = 一个执行会话的容量。工单间用**阻塞关系**接线；未被阻塞且未认领的工单组成 **frontier**（可立即开工的边界）。
2. **逐张解决**：每张工单产出一个「决定」并关闭，直到全部解决、路径清晰。
3. **全部决断后出 OpenSpec**：把已决断结论综合成 OpenSpec 提案（模板见 `references/openspec-template.md`）；此后才按 §6.1 把执行拆成任务清单。
4. 🔴 **硬规则：L 型禁止直接开工**——任何阶段都不实施、不写实现代码，只产出「地图 + 工单 + OpenSpec + 三要素」。

**决策地图结构**：

- 地图是索引，含四段：`Destination`（目的地，一两行）/ `Notes`（领域、常驻技能、偏好）/ `Decisions so far`（已决索引，一行一条：工单标题 + 链接 + 一句话结论）/ `Not yet specified`（雾区）/ `Out of scope`（已排除，永不毕业）。
- 决策工单是地图的子项，每张 = 一个问题，正文为 `## Question`（精确到可开工单的问题），带类型标签。
- **工单类型**：`research`（AFK：读文档/外部资料查证事实，可并行）/ `prototype`（HITL：做廉价原型供人反应）/ `grilling`（HITL：对话，默认）/ `task`（为解锁决策而做的必要杂活，做了才决定）。
- **跟踪机制**：解决一张 → 在地图「Decisions so far」追加一行索引 → 关闭工单 → 原先「Not yet specified」雾区里能精确表述的问题毕业为新工单。frontier 工单可被多个会话并行**认领**（认领 = 指派给自己）。
- **雾区原则**：能精确表述的问题才开工单；说不清的留在「Not yet specified」，frontier 推进后毕业。别把雾区预切成工单。
- **会话纪律**：除 research 工单外，一次会话只解决一张工单。
- **落地形式**：有 GitHub 时用 issue：地图 = 一个带 `wayfinder:map` 标签的 issue，工单 = 其子 issue，阻塞用平台原生依赖关系（没有则用正文「Blocked by」约定）。无 GitHub 时降级为本地 markdown tracker：地图 = `decision-map.md`，工单 = `decision-tickets/<NN>-<slug>.md`。

### 4. 产出三要素（任何产出必须包含）

无论 size 大小、无论是否缺失，产出的需求文档必须声明以下三项（可复制到 issue 正文 / 评论 / 落盘文件）：

#### 任务目标（Goal）
交付什么结果、用户得到什么。用**不含歧义的结果描述**（动词 + 可观察结果），而非过程描述。

#### 涉及范围（Scope）
改动影响哪些**文件 / 模块 / 服务**；以及**明确哪些不做**（非目标）。

#### 验收标准（Acceptance）
怎样算完成。**可操作、可验证、可复现**的判定条件（最好能对应到可执行的验证步骤，如「执行 X 后观察到 Y」）。

### 5. 缺口处理（三要素完整性检查）

三要素中任一要素**无法**从澄清后的信息得出时：

- ✅ 如实判定并标注「缺失」及缺失的具体要素名
- ✅ 给出补齐建议（具体到缺什么信息、由谁补、补在哪）
- ❌ **不得自行编造补全**
- ❌ **不得向用户追问**
- 产出文档保留缺口，状态标注 `awaiting-human-input` 并落盘；人工补齐后**重新调度本 skill 续接**（重跑时读取落盘文档，只补缺口，不复述已定内容）

### 6. 落盘与发布

**关键状态必须落盘**（三要素、size、标签、决策、任务清单），不得只存在会话中。落盘位置约定：

| 产物 | 位置 |
|---|---|
| 需求分析（三要素） | `.scratch/<feature-slug>/requirements-analysis.md` |
| 任务清单（M） | `.scratch/<feature-slug>/issues/<NN>-<slug>.md`（内联拆解规则，本地模式） |
| 决策地图（L） | 内联 wayfinder 规则，本地模式：`decision-map.md` + `decision-tickets/<NN>-<slug>.md`（无 GitHub 时） |
| OpenSpec（L） | `specs/<slug>/proposal.md`（OpenSpec 标准布局） |

#### 6.1 任务清单拆解规则（内联 to-tickets 规则，M 型使用）

把计划/规格/对话拆成一组「追踪子弹」工单：

- **垂直切片**：每张工单切一条窄而完整的纵向路径（schema → API → UI → 测试），单张可演示 / 可验证，单张适配一个新上下文窗口；不是单层的水平切片。
- **阻塞边**：每张工单声明阻塞它的工单；无阻塞 = 立即可开工。多张无阻塞工单即 frontier，按依赖顺序推进。
- **宽重构例外**：机械性大范围改动（改列名、改共享类型，爆炸半径横跨全库）走 **expand–contract**——① 加新形态与旧形态并存（不破坏）；② 按影响面分批迁移调用点（每批一张工单，被 expand 阻塞，逐批保持绿）；③ 无调用方后删除旧形态（被所有迁移批阻塞）。
- **本地发布**：`.scratch/<feature-slug>/issues/<NN>-<slug>.md`，按依赖顺序从 `01` 编号（阻塞者在前），一工单一文件。模板：

```markdown
# <NN> — <工单标题>

**What to build:** 用户视角的端到端行为——不是分层实现清单。

**Blocked by:** 阻塞它的工单编号/标题，或「None — can start immediately」。

**Status:** ready-for-agent

- [ ] 验收标准 1
- [ ] 验收标准 2
```

- **真实 tracker**（GitHub 等）：一 issue 一工单，按依赖顺序发布（阻塞者先，拿到真实 id 后回填阻塞引用）；有原生阻塞/子 issue 关系就用，否则正文「Blocked by」；打 `ready-for-agent` 标签。
- **正文纪律**：避免具体文件路径 / 代码片段（易过期）；例外——原型产出的决策富片段（状态机、reducer、schema、类型形状）可内联并注明出自原型。
- **不关闭 / 不修改父 issue**。

#### 6.2 issue 回写

检测 GitHub 能力（gh CLI 已认证，或 GitHub 连接器可用）。

- **可用**：
  - **目标仓库**：优先取当前工作目录 git remote origin（若为 GitHub 仓库）；无关联仓库或无法确定时，需人工明确指定；无法确定 → 走降级
  - 输入来自 issue → 更新该 issue：发布分析评论（三要素 + 任务清单引用，必须带 AI 生成免责声明前缀），并更新标签（分类 / 状态 / size）
  - 输入来自原始输入 → 创建 issue：标题 = 任务目标摘要；正文 = 三要素 + 任务清单引用；应用标签
- **不可用 / 无法确定目标仓库** → **自动降级**：全部产物按上表落盘本地，并在分析文档顶部明确提示「需连接 GitHub 并指定目标仓库后执行 issue 创建 / 更新操作」，不阻塞分析主流程

## 硬规则清单

1. 🔴 **L 型禁止直接开工**：只产出地图 + OpenSpec + 三要素，不实施
2. 🔴 **关键状态必须落盘**：三要素、size、标签、决策、任务清单不得只存在会话中
3. 🔴 **三要素缺失不编造、不追问**：如实标注缺失 + 补齐建议，人工补齐后重新调度
4. 🔴 **发布到 issue tracker 的内容必须带 AI 生成免责声明**（`> *This was generated by AI during triage.*`）
5. 🟡 有歧义才澄清：需求清晰时跳过澄清，不浪费轮次；**先澄清后定 size**，不提前拍板体量；L 型必先拆决策工单，不跳过探路
6. 🟡 **不通过 `skill` 工具调用子 skill**：triage / grill-with-docs / wayfinder / to-tickets 为「仅限用户调用」的命令 skill，本 skill 的知识全部内联；需要交互式分诊 / 追问 / 探路时，提示用户自行运行对应 `/` 命令
