# 任务治理分层规范（通用流程 / 业务场景分离）

> **定位**：定义「哪些能力属于通用流程层、哪些属于项目业务层」，并记录三项已定决策。
> **状态**：分层决策于 2026-09-22 拍板；任务来源边界于 2026-10-21 按当前产品决定补充。
> **术语**：通用层 = 任何项目都能用的机制；业务层 = 本项目特有的判断标准与规则。

---

## 0. 三项已定决策

| # | 决策 | 内容 | 影响 |
|---|---|---|---|
| 1 | **真源 = Multica 任务数据库** | 当前 Task 的身份、状态、负责人、项目归属、依赖与执行历史以 Multica 为唯一事实源；仓库 registry / BOARD 不再承担可写状态账本。 | 废止《Multica 选型评估报告》§4.2 的保留意见 |
| 2 | **审查轮次控制器由项目自控** | 审查流程、轮次、额度、去重规则不进入通用层，各项目自行实现 | 平台不承担，通用层不含此能力 |
| 3 | **通用流程与业务场景分离** | 通用层只放跨项目可复用的机制；业务判断一律留在项目侧 | 决定门禁该放在哪、哪些该删 |

## 1. 分层原则

### 1.1 一句话原则

**通用层放「机制」，业务层放「判断」。**

- 机制 = 与具体业务无关、任何项目都一样的东西：谁领了任务、领了多久、卡住了怎么办、任务和代码改动怎么关联。
- 判断 = 与本项目产品形态相关的东西：什么算"定义完成"、什么算"验收通过"、审查几轮、收口要交什么。

### 1.2 判定方法（一条可操作的提问）

> 把这个能力原样搬到另一个完全不同的项目，它还成立吗？

- **成立** → 通用层
- **需要改写才能成立** → 业务层
- **只有一部分成立** → 拆开：成立的进通用层，其余留业务层

### 1.3 分层结果

| 层 | 承载 | 例子 |
|---|---|---|
| **通用层** | 平台原生能力 + 通用脚本 | 任务登记与发号、领取与占用、心跳与超时回收、阻塞退回与改派、执行日志与成本、任务与代码改动关联、字段完整性校验 |
| **业务层** | 各项目自建 | 定义质量的判断标准、验收标准与判决、审查流程与轮次、收口产物与归档规则、业务特有的风险规则 |

## 2. 硬门禁完整清单（实测自现有实现）

> 说明：此前口述的「七项硬门禁」是概括说法，**实际实现为 13 个字段上的 23 条校验规则**。以下是完整清单与逐条判断。这 23 条不是都要保留——判断标准见每列。

### 2.1 任务字段清单（13 个）

> 本节字段清单与后文校验规则是旧 registry 退役前的历史分析，不是 Multica 当前 Schema，也不要求新任务写入本地 registry / BOARD。

任务标识、任务名称、任务类型、当前状态、优先级、需求基线版本、前置依赖、任务规格位置、定义时间、施工环境组、施工环境角色、无人值守许可、GitHub 同步。

### 2.2 逐条判断

#### 🔴 必须保留（5 条）——拦的是"真会出错"

| # | 门禁 | 拦截的风险 | 在 Multica 上怎么落 |
|---|---|---|---|
| 1 | **Multica 当前状态与元数据满足开工条件** | 没定义完就开工 | 从 Multica 读取 Task 状态与必需元数据；服务不可用、工作区不符或关键字段缺失时停止，不回退本地登记册 |
| 2 | **无人值守许可 = 允许** | 需要人做决策的任务被自动启动，然后卡死 | 自定义属性（单选：允许 / 不允许），门禁查该属性 |
| 3 | **前置依赖已合并** | 依赖没就绪就开工，必然返工。**这是最有价值也最难的一条**（要跨任务、跨仓库查证据） | 查依赖任务的平台状态 + 其关联改动的合并事实 |
| 4 | **未决产品事项 = 0** | 带着未决问题开工，施工者要么卡住要么做错 | 变成任务上的一个数值/勾选属性，不再靠读文本 |
| 5 | **任务规格可取得** | 施工没有依据 | 规格放进任务描述或附件，天然满足 |

#### 🟡 保留但换实现方式（6 条）——方向对，做法要改

| # | 门禁 | 为什么保留 | 怎么改 |
|---|---|---|---|
| 6 | 定义检查清单无未勾选项 | 它是第 4 条的载体，是定义质量的把关 | 改为平台上的结构化检查清单，不靠文件勾选框 |
| 7 | 版本一致（任务卡 = 规格） | 防止施工看错版本 | 规格成为任务的唯一来源，版本自动带出，取消"两处比对" |
| 8 | 前置依赖有合并证据，且是当前基线的祖先 | 防止"声称已合并"实际没进主线 | 保留判断，实现改为查平台记录的合并事实 |
| 9 | 优先级合法（P0/P1/P2） | 只影响排序，填错不造成错误交付 | 降级：设为必填选项 + 缺失时给默认值并告警，不再拦开工 |
| 10 | 施工环境组 / 角色合法 | 防止任务写到错误的工作区 | **在 Multica 下由平台管环境，此条价值大幅下降**；改为可选记录 |
| 11 | 成员角色必须带环境上下文 | 防止同组串行被绕过 | 平台的目录锁已原生解决串行问题，此条可简化 |

#### ⚪ 建议取消或自动填充（5 条）——不该让人填，更不该因此拦开工

| # | 门禁 | 取消理由 |
|---|---|---|
| 12 | 定义时间非空 | **纯记录字段，应系统自动写入**。因为它拦开工属于用错力气 |
| 13 | 当前 Task 标识由 Multica 发放 | 使用 Multica Task ID；旧本地编号仅作历史追溯信息，不再作为新任务 ID |
| 14 | **GitHub 同步取值合法** | 这是"GitHub 不可用降级"时期的历史产物。真源改为平台后，**该字段的历史使命结束** |
| 15 | 规格正文必须显式写"未决产品事项：0" | 用文本匹配当门禁很脆弱——应改为结构化字段（见第 4 条） |
| 16 | 规格不得含"待决 / TBD / TODO 决策"字样 | **会误伤**：规格里写"本任务不涉及 TBD 场景"也会被拦。属正则匹配的固有缺陷 |

### 2.3 结论

| 分类 | 条数 | 处理 |
|---|---|---|
| 🔴 必须保留 | 5 | 迁移到平台属性 + 通用脚本 |
| 🟡 换实现方式 | 6 | 保留判断，改为结构化 |
| ⚪ 取消 / 自动填 | 5 | 删除或由系统自动补 |
| 其余（字段存在性等） | 7 | 随上述归类一并处理 |

**核心结论：现有 23 条校验里，真正"必须死"的只有 5 条。** 其余要么该换实现方式，要么本就该由系统自动完成、而不是拦人。把 23 条原样搬走是错的——它把"记录完整性"与"开工资格"混在了一起，后者才是门禁该管的事。

## 3. 真源改为平台数据库：含义与边界

### 3.1 什么变了

| 项 | 之前 | 之后 |
|---|---|---|
| 任务权威记录 | Git 仓库内的任务卡与规格文件 | **Multica**：当前 Task 身份、状态、负责人、项目、依赖和执行历史 |
| 版本历史 | 代码与版本化规格由 Git 保存；任务状态变化与执行历史由 Multica 时间线保存 | 两边各自负责不同事实，不复制可写任务状态 |
| 规格存放 | 项目产品/技术规格按仓库权威路径版本化保存，Task 描述记录范围、验收与引用 | Multica Task 关联规格；文档保留内容版本，不承担当前 Task 状态 |
| Multica 不可用时 | 本地 registry / BOARD 曾可降级开工 | 已退役：停止新 Task 登记、状态变更与依赖 Multica 的开工门禁，不回退旧账本 |

### 3.2 什么不变（必须留住）

- **代码与证据仍在 Git 仓库**：代码改动、测试证据、验收记录属于交付物，仍走仓库与合并申请，平台只做关联。
- **任务与代码改动关联**：在 Multica Task 中关联 PR，并在 PR 标题中写明 WFM Task key；不要使用可能自动关闭交付 Task 的 `Closes` 关键字，除非该关闭行为是本次明确目标。
- **项目全局视图**：使用 Multica 项目与任务视图；仓库 BOARD 是迁移历史，不再手工维护为第二份看板。

### 3.3 Multica 不可用时的当前边界

本地「已定义」降级状态已随旧任务登记流程退役。当前 Task 由 Multica 登记与管理；不能读取正确的 Multica 工作区、Task 或必需元数据时，依赖这些事实的开工门禁必须停止，且不得静默读取 `registry.json`、`BOARD.md` 或 GitHub Task 状态作为替代。

- 可以继续维护已有的产品规格、设计文档和代码证据，因为它们是版本化项目资料，不是任务状态账本。
- 不得离线新建、认领或推进 Multica Task，也不得把本地草稿自动当作已登记任务。
- 服务恢复后，先在 Multica 核实 Task、状态、负责人、项目、依赖与验收范围，再恢复对应工作。
- 历史 registry、BOARD 与任务卡保留为只读迁移记录；任何历史映射都必须有证据，不能据旧状态猜测当前 Task 状态。

该边界是治理要求；落地状态以当前 `main` 与 Multica WFM-342 任务/关联 PR 的实际证据为准，本文本身不证明代码已实现。

## 4. 审查轮次控制器的归属

**决策：由项目自控，不进通用层。**

理由：审查几轮、什么算收敛、额度耗尽后怎么办，这些取决于项目的质量要求与风险偏好，**换一个项目结论就会变**。按 §1.2 的判定方法，它属于业务层。

边界划分：

| 属于通用层 | 属于项目业务层 |
|---|---|
| 提供触发审查的通道（评论、接口） | 审查怎么触发（哪个命令、谁来发） |
| 记录审查发生的次数与时间 | 允许几轮、怎么算一轮 |
| 记录同一提交是否已审过 | 同一提交重复触发是拒绝还是重试 |
| — | 额度耗尽后的处置（转人工 / 追加 / 放弃） |

## 6. 落地含义（一句话版）

1. **门禁瘦身**：23 条 → 5 条必控 + 6 条结构化，其余取消。
2. **平台只做机制**：登记、发号、领取、心跳、接手、日志、关联。
3. **判断留在项目**：定义质量、验收、审查轮次、收口。
4. **服务不可用时 fail closed**：停止需要 Task 状态、依赖或归属校验的开工与状态写入；保留仓库内版本化规格和历史记录，但不把它们当作离线任务账本。
