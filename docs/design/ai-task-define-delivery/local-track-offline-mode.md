# 本地轨道方案（GitHub 不可用期间的替代流程）

> **状态**：已拍板（2026-09-08，松哥）并已落地。三个决策点全部按推荐 A 执行：① 新增「本地已定义」状态；② 一任务一提交合并；③ 本地镜像仓库备份（异地托管放第二阶段）。
> **适用**：GitHub 账户暂停、issue/PR 不可用的窗口期
> **影响范围**：需求分析入口（`dsh/skills/requirements-analysis`）+ 单任务交付（`dsh/skills/construction-bootstrap`）
> **设计原则**：不新建第二套流程，只在现有流程上做「入口扩展」与「落点切换」；GitHub 恢复后可原样回填，不需要重做。

---

## 1. 一句话结论

把「任务」从 GitHub issue 编号上解绑，改用**本地任务标识 `LOC-<序号>`** 作为唯一身份；任务卡从「写在 issue 里」改为「写成仓库内的一页文档并随合并提交入库」；每个任务仍然各自开一个独立工作区开发；验收通过后**一个任务合并为 main 上的一个提交**，提交信息携带任务标识、来源、范围与验收结果。

GitHub 恢复后，用本地登记册批量补建 issue / PR，已有历史不需要重来。

---

## 2. 现状盘点：到底哪些环节真的依赖 GitHub

先说清楚「断在哪里」，避免为了保险而大改。全链路只有 **4 处**真正依赖 GitHub：

| # | 环节 | 依赖点 | 断了会怎样 | 证据位置 |
|---|---|---|---|---|
| 1 | 需求入口 | 只认 issue 作为需求源 | 本地/口述需求无处落档 | `requirements-analysis/SKILL.md` §0 |
| 2 | 定义落档 | 「已定义」要求 issue 基本信息写入成功 | **任务永远无法进入「已定义」，无法开工** | `SKILL.md` §7.2、契约 §5 |
| 3 | 开工建工作区 | 建分支前先 `git fetch origin main` | 拉取失败，分支建不出来 | `scripts/cwf-run-init.mjs` L109–111 |
| 4 | 收口 | 「PR/合并按仓库规则」、issue 置为已完成 | 成果合不回主干，状态无处记录 | `construction-bootstrap/runbook.md` §7.3 |

**已经不依赖 GitHub 的环节**（无需改动）：证据记录、集成检查、证据链校验、返工记账、批量排程脚本（`cwf-record` / `cwf-checkpoint` / `cwf-evidence-verify` / `ai-task-execution-plan` 均无 GitHub 调用）。

> 业务含义：要改的只有「入口」「开工门槛」「合并出口」三处，中间的开发、审查、测试、验收流程原样不动。这是本方案能低成本落地的关键。

## 3. 任务标识设计

### 3.1 标识规则

> **2026-09-16 更新**：编号改为「类型前缀 + 远端发号」，本机不再自己算号。
> 依据：`task-id-and-remote-sync-proposal.md`（已拍板并执行）。

| 项 | 取值 | 说明 |
|---|---|---|
| 任务标识（新） | `FEAT-<远端号>` / `FIX-<远端号>` / `CHORE-<远端号>` | 号由 CNB 建 issue 时服务端分配，双机/多会话并行都不会撞号；编号即 issue 号，无需维护映射表 |
| 类型前缀 | `FEAT` 需求迭代 / `FIX` 缺陷修复 / `CHORE` 维护性（文档、脚本、口径收敛、测试补齐、验收活动） | 一眼看出这是什么性质的活 |
| 临时号（降级） | `TMP-<机器码>-<日期><序号>` | 远端不可达时开工用，`remote=pending`，联网后必须换取正式号 |
| 任务标识（历史） | `LOC-001`…`LOC-045`（三位递增，永不复用） | 2026-09-15 及以前分配，保留为历史别名；活跃任务通过登记册 `remote` / `legacy_id` 与远端号双向可查 |
| 任务规格目录 | `docs/tasks/specs/LOC-001-<slug>/`（**入库**） | slug = 任务名英文短写；禁止使用被忽略的 `.scratch/` |
| 工作分支 | `dev-loc-001-r1` | `r1` = 该任务第几次交付运行；重跑为 `r2` |
| 完成标记 | git 标签 `task/loc-001/v1` | 指向该任务在 main 上的合并提交 |
| GitHub 恢复后 | issue 正文中「任务标识」字段写 `LOC-001` | 双向可查：`LOC-001 ↔ #N` |

选「类型前缀 + 远端序号」而不是用 slug 或时间戳，原因：序号短、可口头引用、天然排序、不含中文与空格（可直接用作分支名与目录名）；远端发号消除了双机/多会话并行时的撞号；类型前缀让分支名、提交记录、看板都能一眼分辨需求与缺陷。

> **撞号实证（2026-09-15→16）**：本机与远端各自递增，产出三个同号不同物的任务（`LOC-034/035/036`）。本机是「验收清单前置条件补齐 / 交付链口径收敛 / prune 单测补齐」，远端是「WR-007 / WR-008 / WR-010」。三个本地任务已改用远端号 `CHORE-36/37/38` 恢复，旧号保留在 `legacy_id`。

### 3.2 与现有契约的关系（不推翻，只加字段）

现有公共契约 `public-task-contract.md` §1 的「Issue 基本信息」九字段全部保留，只是**载体从 issue 换成仓库内的一页文档**（下称「本地任务卡」），并新增一行：

| 新增字段 | 值 | 必填 |
|---|---|---|
| 任务标识 | `LOC-001` | 是 |
| 需求来源 | `github-issue` / `本地文档` / `会话录入` | 是 |
| 来源定位 | issue 号 / 文档路径 / 会话日期与摘要 | 是 |

> 好消息：实施前检查脚本已经预留了读取「任务标识」的能力（`scripts/ai-task-preflight-check.mjs` L74–77），只是契约里还没定义这一列。本方案属于补齐，不是硬塞。

## 4. 三类需求输入的识别与接入

### 4.1 判定顺序（写死，避免歧义）

输入进来后按下列顺序判定，**命中即停**；判定结果向用户复述一次，不再反复追问。

| 顺序 | 判定条件 | 识别为 | 接入方式 |
|---|---|---|---|
| 1 | 形如 `#123`、`123`、`owner/repo#123`、或含 `github.com/.../issues/` 的链接 | **GitHub issue** | 尝试拉取；拉取失败 → 转为「本地任务」并标注「来源=github-issue（暂不可读，需人工粘贴正文或改走会话录入）」 |
| 2 | 是一个真实存在的文件路径，且为 `.md` | **本地文档** | 直接读取；缺三要素（目标/范围/验收）时用决策卡补齐 |
| 3 | 其他，或一次口述/粘贴的多段文字 | **会话录入** | 进入渐进式分析循环，逐项补齐三要素与关键决策 |

补充规则：
- 一次输入里同时含「文件路径 + 补充说明」→ 以文件为主，说明作为补充约束。
- 一次输入里同时含「多个需求」→ 按现有规则先切片，每片一个 `LOC-` 号。
- 已有「已定义」任务的**实质变更**请求 → 走现有 V1→V2 升版流程，不重新分配新号。

### 4.2 三种来源对后续流程的影响

| 来源 | 落档内容 | 差异点 |
|---|---|---|
| GitHub issue | 同现状，另加「任务标识」行 | 无 |
| 本地文档 | 本地任务卡 + 任务规格；文档原文作为附件存档 | 需在任务卡记录原文档路径，便于回填时贴回 issue |
| 会话录入 | 本地任务卡 + 任务规格 + 决策记录 | 必须完整记录「谁在什么时候确认了哪一版基线」，因为除会话外没有第三方留痕 |

> 业务含义：三种来源最终产物完全一致（一张任务卡 + 一份规格 + 一份检查记录），下游的建设流程不需要关心需求是从哪来的。

## 5. 🔴 决策点一：GitHub 不可用时，能否算「已定义」并开工

这是本方案唯一需要松哥拍板的实质性问题。

**现状规则**（`SKILL.md` §7.2）：本地落档齐了也只能标「本地准备完成，待同步」，**不具备开工资格**。这条规则的本意是防止「没有留痕就悄悄开工」——在 GitHub 可用的前提下，它是合理的。

**现在的问题**：GitHub 长期不可用，这条规则会让所有任务卡在门口。

| 选项 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A（推荐）新增「本地已定义」状态** | 引入 `本地已定义（LOCAL_DEFINED）`，与「已定义」同等开工资格；登记册记 `github_sync=pending`，恢复后批量补 issue | 低：新增一个状态枚举 + 一个字段，不动现有语义 | 窗口期不中断；恢复后有明确的「待同步清单」，可机械核对不遗漏 | 若长期不恢复，本地状态与 GitHub 的偏差会累积（有清单，可控） |
| B 保持现状，改为人工值守施工 | 不标「已定义」，每个节点人工确认后推进 | 中：每个节点都要等松哥 | 契约完全不变，最保守 | 失去无人值守价值；多任务并行时人成为瓶颈 |
| C 直接放宽 §7.2，本地落档即算已定义 | 不改状态机，放宽门禁 | 极低 | 最快 | 丢掉「是否已同步 tracker」这一信息，恢复后无法分辨哪些还没补 issue；破坏现有契约语义 |

**推荐 A 的理由**：它把一个「临时绕行」变成「可追溯的正式状态」——只要登记册里有 `github_sync` 字段，恢复后就不会有人漏掉补 issue；而且它是**新增**状态，不是修改「已定义」的含义，GitHub 恢复后把该状态收回去即可，不留后遗症。

配套硬规则（推荐 A 时一并采纳）：
1. 「本地已定义」必须同时满足：Definition Check 全通过 + 未决产品事项 0 + 松哥明确确认基线 + 本地任务卡已入库；
2. 呈递确认时必须显式写明「此版本为本地轨道，GitHub 恢复后需补建 issue」，不能默认松哥知道；
3. 人工验收三态、返工上限 3、AI 不代签 —— 全部不变。

## 6. 保留「一任务一工作区」机制

现状机制不变：每个任务在自己的独立工作区（worktree）里开发，互不干扰；同组任务串行；全组验收通过后才清理。

**唯一需要改的**：建工作区时不再从远程拉取基线，改为以**本地 main 当前进度**为起点。

| 现状 | 改为 | 原因 |
|---|---|---|
| 开工前 `git fetch origin main`，以远程 main 为基线 | 窗口期内以**本地 main** 为基线，跳过远程拉取 | 远程不可达；本地 main 此时是唯一可信基线 |
| 基线版本记为 `origin/main` 的提交 | 记本地 main 的提交号，并记为「本地基线」 | 恢复后可与远程 main 比对，判断是否需要重新对齐 |

新增纪律（三条，缺一不可）：
1. **窗口期内本地 main 只能由「任务合并」推进**，禁止在 main 上直接改东西，否则任务之间会互相污染；
2. 每个任务开工时记录它基于 main 的哪个进度；合并前必须先把 main 的最新进展并入自己的工作区并**重跑测试**；
3. 两个任务改动到同一批文件时，后合并的那个必须人工确认冲突解决结果，不允许自动采纳任一侧。

## 7. 🔴 决策点二：合并回本地 main 的策略

### 7.1 合并门禁（三种策略都适用，是硬条件）

只有全部满足才能合并：

1. 人工验收结果为「通过」或「有条件通过」（退回的禁止合并）——沿用现有收口规则；
2. 需求基线版本三处一致：本地任务卡 = 任务规格 = 交付运行记录；
3. 证据链校验通过（现有脚本，不依赖 GitHub，可直接用）；
4. 已把 main 最新进展并入本任务工作区，且测试重跑通过；
5. 无未解决的冲突。

### 7.2 三种策略对比

| 选项 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A（推荐）一任务一提交** | 每个任务在 main 上合成一个提交，提交信息带任务标识/来源/范围/验收结果 | 低：一次标准合并动作 | main 保持一条直线；一眼能看出「哪个提交是哪个任务」；恢复后可一提交一 PR；出问题可整块回退 | 工作区里的过程提交不进 main（分支仍保留，需要时可查） |
| B 保留完整过程（带合并节点） | 把工作区的全部过程提交原样并入 main | 低 | 开发过程完整可查 | main 图形变复杂；多任务并行时主线很快变成一团；回退粒度变粗 |
| C 先汇入集成分支再进 main | 多任务先合并到一条集成分支，验证后再整体进 main | 中：多维护一条分支与一层状态 | 批量集成时冲突一次性解决 | 窗口期任务量不大时是纯额外成本；追溯链多一跳 |

**推荐 A**，理由：窗口期内最重要的诉求是「每个任务的成果边界清晰、可单独回退、可单独补 PR」——一任务一提交正好对应这个粒度，且松哥日后看历史时不需要理解分支图形。

### 7.3 提交信息模板（A 方案的核心可追溯载体）

```
<类型>(<范围>): <任务名称> (LOC-001 V1)

任务标识: LOC-001
需求基线: V1
需求来源: 会话录入 | 本地文档 <路径> | GitHub issue #N
任务范围: <一句话说清做了什么、明确没做什么>
验收结果: 通过 | 有条件通过
验收人: <松哥>
关联交付运行: loc-001-r1
任务卡: docs/tasks/LOC-001-<slug>.md
任务规格: docs/tasks/archive/LOC-001/task-spec-V1.md
GitHub 同步: 待补 issue / 已同步 #N
```

### 7.4 合并后的收尾动作（自动执行，不可省略）

1. 打标签 `task/loc-001/v1` 指向该提交；
2. 把本次任务的任务卡与对应版本规格**复制进仓库**（`docs/tasks/archive/LOC-001/`），确保合并进 main 后，任务的来源、范围、验收状态在仓库历史里永久可查——不能只留在不入库的临时目录里；
3. 更新本地登记册：状态改为「已合并」、记录合并提交号与合并时间；
4. **删除工作区、保留分支**（阶段一口径）：工作区由合并脚本在归档三件套入库后自动删除（不带 `--force`，脏则拒绝并登记遗留），随后 `git worktree prune` 兜底；分支不可再生，保留到 GitHub 恢复、对应 PR 处理完（阶段二）再删；
5. 若验收是「有条件通过」，把优化意见登记为**新的候选任务**（可分配新的 `LOC-` 号），不修改已合并的基线。

## 8. 跟踪机制：一本账 + 一页一任务 + 一张看板

### 8.1 本地任务登记册（唯一真源）

位置：`docs/tasks/registry.json`（**入库**，可备份、可比对、可恢复）

每条记录字段：

| 字段 | 说明 |
|---|---|
| `task_id` | `LOC-001` |
| `name` / `slug` | 任务名称 / 目录短写 |
| `source` | `github-issue` / `本地文档` / `会话录入` |
| `source_ref` | issue 号 / 文档路径 / 会话日期 |
| `baseline` | 当前基线版本 `V1` |
| `status` | 定义中 / 待确认 / **本地已定义** / 交付中 / 等待验收 / 执行受阻 / 已合并 |
| `priority` | P0 / P1 / P2 |
| `env_group` / `env_role` | 施工环境组 / 独立或成员（沿用现有机制） |
| `deps` | 前置依赖任务标识 |
| `branch` / `worktree` | 工作分支与工作区路径 |
| `runs` | 历次交付运行记录（run id、结果、返工次数） |
| `merge` | 合并提交号、合并时间、合并时 main 的位置 |
| `github_sync` | `not-applicable` / `pending` / `synced#N` |

### 8.2 一任务一页（人读）

位置：`docs/tasks/LOC-001-<slug>.md`，内容 = 现有「Issue 基本信息模板」九字段 + 新增三字段，另附变更记录（谁在什么时候改了什么状态）。

### 8.3 一张看板（总览）

位置：`docs/tasks/BOARD.md`，按状态分组列出所有任务及其来源、负责人（AI/松哥）、下一步动作。**每次状态变更自动重写**，不手工维护。

### 8.4 恢复后的回填流程

1. 筛 `github_sync = pending` 的任务 → 得到待同步清单；
2. 按「定义时间」顺序批量创建 issue，正文 = 任务卡全文 + AI 免责声明，并把 issue 号回填登记册；
3. 对每个已合并任务，推送其工作分支并开 PR（一任务一 PR），PR 描述沿用 §7.3 提交信息；
4. 全部回填完成后，把「本地已定义」状态收敛回标准「已定义」，退役本地轨道临时规则。

> 这一步是**机械的、可核对的**——清单来自登记册，不会凭记忆漏任务。

## 10. 🔴 决策点三：本地 main 是唯一副本，要不要加一道备份

窗口期内所有成果只存在于这台机器的本地仓库。机器故障或误操作 = 全部丢失。

| 选项 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A（推荐）加一个本地镜像仓库** | 在本机另一个磁盘位置建一个纯镜像仓库，每次合并后自动同步 | 几乎为零（一条命令，可挂到合并流程里自动执行） | 本机多一份完整副本，误删/误重置可救回 | 与本机同生共死，防不了整机损毁 |
| B 再加一个异地托管 | 在另一个代码托管服务上建私有仓库作为第二个远程 | 低（需注册与配置一次） | 防整机损毁；GitHub 恢复后仍可保留作为异地备份 | 需要信任另一个服务；窗口期结束后需决定去留 |
| C 什么都不做 | 只靠本地 | 零 | 无 | 单点故障，本方案所有可追溯性在丢数据时归零 |

**建议 A + B 都做**：A 成本为零立即做；B 视松哥对异地托管的接受度决定。至少做 A。

## 11. 本方案自身的验收标准

方案落地后，用下面几条验证是否真的可用（可逐条实测）：

1. 在会话里口述一个需求 → 能产出「本地已定义」的任务，且无需任何 GitHub 操作；
2. 指定一份本地 `.md` 需求文档 → 能识别并接入，缺三要素时会以决策卡形式追问；
3. 两个任务同时开工 → 各自独立工作区，互不干扰，各自状态独立可查；
4. 任务 A 合并后任务 B 仍能正确合并（含冲突场景的人工确认环节）；
5. 任一已合并任务，能从 main 的提交历史反查到：任务标识、需求来源、基线版本、验收结果、任务卡与规格原文；
6. 登记册能一键列出所有「待同步 GitHub」的任务，且数量与实际核对一致。

## 12. 明确不做（防止范围蔓延）

- 不做新的任务管理系统、不建第四套流程；
- 不改现有开发/审查/测试/验收节点的行为与规则；
- 不改返工上限（仍为 3）、不改验收三态、不改「AI 不代签」；
- 不在窗口期重构已有脚本结构，改动以满足本方案为限。
