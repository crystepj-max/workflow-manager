## 1. 需求背景

用户希望自己控制「哪些业务事件会打扰自己」。本轮只做**站内通知**偏好，不扩展到邮件/短信。经产品决策确认后形成本基线。

## 2. 用户问题

无法按事件类型开关站内通知，导致无关消息过多或重要消息被淹没。

## 3. 目标

用户能在「通知设置」中按事件类型打开/关闭站内通知，保存后立即生效；列表展示当前开关状态。

## 4. 非目标

- 不做邮件 / 短信 / 推送渠道（本轮明确排除）
- 不做通知内容编辑或模板管理
- 不做管理员代用户改偏好
- 不改通知发送底层队列实现细节（只要读取偏好生效）

## 5. 修改前

用户无按事件类型的站内通知开关；所有站内通知按系统默认全开策略送达。

## 6. 修改后

用户可在通知设置页看到事件类型列表与开关；保存后，关闭的类型不再产生新的站内通知；打开的类型保持原送达行为。

## 7. 功能范围

- 通知设置页：事件类型列表 + 开关 + 保存
- 偏好持久化到当前登录用户
- 发送站内通知前读取偏好并过滤
- 空状态：无事件类型配置时的说明文案

## 8. 不修改范围

- 邮件/短信/推送
- 通知文案与模板
- 历史已产生通知的删除/撤回（只影响新产生）

## 9. 业务规则

- 事件类型清单以产品给定的固定枚举为准（本轮：`订单状态变更`、`系统公告`、`互动提醒`）
- 默认值（产品已拍板）：新用户三类均为**开**
- 关闭某类型后：仅阻止**新**站内通知；已存在通知仍可见
- 未登录不可访问设置页
- 保存失败时保留编辑中的开关状态并提示重试，不静默丢改

## 10. 用户操作路径

1. 登录后进入「通知设置」
2. 查看三类事件开关（默认均为开）
3. 关闭「互动提醒」并保存
4. 触发一条互动类事件 → 不出现新的站内通知
5. 触发订单状态变更 → 仍出现站内通知

## 11. 异常和边界场景

- 保存时网络失败：提示失败，服务器侧不更新
- 中途登出：未保存更改丢弃
- 未知事件类型（未来新增）：默认按「开」处理，直到产品补进设置列表（已知限制）

## 13. 功能切片关系

本需求拆为两个可独立 UAT 的完整功能切片；**本规格对应切片 A**。切片 B 另单独立项（本示例同目录可附带说明，V0.1 无前置依赖故可并行定义）。

- 本切片 A：用户可查看并保存站内通知偏好（设置页主路径）
- 兄弟切片 B：发送链路按偏好过滤新站内通知（可独立 UAT：关开关后不再收到新通知）
- 拆分原则：最小可独立 UAT 的完整功能切片（非「先做存储再做页面」的内部层次）
- 前置依赖：无（B 可在 A 合并后验，但「未完成 A 不一定令 B 无法开工」——若共享契约已冻结；本示例记录为无强制前置）

> 说明：若团队认为 B 必须等 A 的设置页合并后才能正确验收，应把 B 的前置依赖写成 A 的任务标识。本示例拍板为「无」，以便 V0.1 可并行进入已定义。

## 15. 验收条件

- [ ] 通知设置页展示三类事件及开关，默认均为开
- [ ] 用户可改开关并成功保存
- [ ] 保存失败有提示且不丢本地编辑态误报成功
- [ ] （与切片 B 联验时）关闭类型后不再产生该类型新站内通知

## 16. UAT 场景

### UAT-01 查看与保存偏好

- 验收目的：确认用户能看到默认全开的三类开关并成功保存变更
- 前置条件：
  1. 已登录
  2. 可进入通知设置
- 操作步骤：
  1. 打开通知设置
  2. 确认三类默认开
  3. 关闭「互动提醒」并保存
  4. 刷新页面
- 预期结果：
  1. 「互动提醒」保持关闭
  2. 其余两类仍为开
- 建议人工关注：文案是否好懂、保存反馈是否清晰

### UAT-02 偏好对新通知生效（切片联验/切片 B）

- 验收目的：关闭后不再收到该类型新站内通知
- 前置条件：
  1. 已保存「互动提醒=关」
- 操作步骤：
  1. 触发一条互动类事件
  2. 触发一条订单状态变更
- 预期结果：
  1. 无新的互动站内通知
  2. 订单类站内通知仍出现
- 建议人工关注：是否误伤其他类型

## 17. 风险

- 默认全开可能仍偏吵：已接受，后续可用「有条件通过」沉淀优化为新定义输入
- 未来新事件类型默认开：已记入已知限制

## 18. 已知限制

- 本轮无邮件/短信/推送
- 未知新事件类型默认开，直到产品纳入设置列表
