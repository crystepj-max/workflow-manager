# 任务编号与远端同步优化方案（提案）

> 状态：**已拍板并执行**（2026-09-16，松哥按推荐方案批准；执行记录见 §10）
> 提出时间：2026-09-15
> 触发原因：任务编号在多机 + 多 AI 会话并行时存在撞号风险；编号本身不携带类型信息；远端无任何任务锚点
> 影响范围：任务登记册、看板、任务卡、分支与提交信息命名、需求分析入口流程

---

## 1. 一句话结论

把「编号谁说了算」从**本机算**改成**远端发**，把「这是什么活」从**看编号猜**改成**编号里就写着**。

具体：`LOC-037` → `FEAT-12`（需求迭代）/ `FIX-12`（缺陷修复）/ `CHORE-12`（维护性工作），号由 CNB 建 issue 时服务端分配，本机不再自己算号。

---

## 2. 现状诊断（先看清楚断在哪）

### 2.1 三个问题，逐个量化

| # | 问题 | 证据 | 业务影响 |
|---|---|---|---|
| 1 | **编号会撞** | 发号逻辑 = 读本机 `docs/tasks/registry.json` 现有最大序号 +1（`scripts/local-task-registry.mjs` 第 41、47 行）。两台机器各有一份登记册副本，各自算号 | Windows 本机与远程 Mac 同时开一个任务 → 都拿到 `LOC-037`；两个 AI 会话并行开工 → 同上。撞号后任务卡、分支、提交记录、归档目录全部串味，事后要人工拆解 |
| 2 | **编号不携带类型** | 现有字段只有 `task_id` / `name` / `source`(来源渠道) / `baseline` / `status`，没有「这是需求还是缺陷」 | 36 个任务混在一条序列里，看板按状态分组，无法一眼区分「在做新功能」还是「在补洞」；也无法统计缺陷占比 |
| 3 | **远端零锚点** | 登记册 36 条记录，`github_sync` 全部为 `pending`；CNB 仓库实测 issue 数为 **0** | 任务只活在一台机器的一个文件里。机器故障 = 任务清单全丢；跨机器协作无对账基准；GitHub 恢复后回填也是纯记忆活 |

### 2.2 现有编号的优点（要保留，不要推倒）

- 短、可口头引用、天然排序、不含中文与空格（可直接当分支名与目录名）——这条设计是对的，新方案保留。
- 一任务一页文档 + 一张看板 + 一本登记册的三件套结构运行良好，不动。

## 3. 业界成熟做法盘点

先说别人怎么解决同一个问题，再说我们抄哪几条。

| 来源 | 编号机制 | 类型怎么分 | 对我们的启发 |
|---|---|---|---|
| Jira（最主流的项目管理工具） | `项目缩写-序号`，如 `PROJ-123`；**序号由服务端统一发**，客户端从不自己算 | 类型是一等字段：Epic（大主题）/ Story（需求）/ Bug（缺陷）/ Task（杂活） | 「服务端发号」是根治撞号的标准答案；类型应该是编号的一部分或紧邻字段，而不是靠人读标题 |
| Linear（新一代研发管理工具） | `团队缩写-序号`，如 `ENG-123`；服务端发号 | 靠标签 + 优先级 + 周期（Cycle）分层 | 编号带「归属团队」前缀，一眼知道这活归谁 |
| GitHub / GitLab | 仓库内递增 `#12`；跨仓库引用写 `仓库名#12` | 无原生类型，靠标签（bug / enhancement）和 issue 模板；GitLab 额外有「事件」类型 | 编号 = 远端 issue 号，**不需要维护本地号与远端号的映射表**——这条直接省掉一整层同步成本 |
| Azure DevOps（微软研发管理） | 工作项编号 + **区域路径**（Area Path）区分团队与模块 | 工作项类型：Epic / Feature / User Story / Bug / Task | 「归属信息」可以放字段里，不必塞进编号——编号要短 |
| 约定式提交（业界通用的提交信息写法） | — | 提交信息前缀 `feat` / `fix` / `chore` / `docs` | 「这是什么性质的改动」在进入代码历史那一刻就该可读，我们现在只写在正文里，检索不到 |
| 分布式唯一编号（ULID 等） | 时间戳 + 随机数，不依赖任何中心节点 | — | 离线环境的兜底方案：绝对不撞号，代价是不可口述、不可排序 |

### 3.1 提炼成四条原则

1. **编号由唯一的发号方发出，任何机器都不自己算。** 撞号的根因是"各自计算"，不是"前缀不够长"。
2. **编号里要有类型。** 让人在分支名、提交记录、看板、聊天记录里一眼看出这是需求还是缺陷。
3. **本地可以离线干活，但联网必须能对账。** 本地保留完整任务卡（离线可用），远端是权威编号与状态。
4. **编号永不复用、只增不改。** 已发出的号即使任务作废也不回收，避免历史记录指向错人。

### 3.2 一条反向教训（避免踩坑）

业界对「把机器名/团队名塞进编号」是有分歧的：Linear 塞（团队前缀），Azure DevOps 不塞（放字段）。
**我们的选择：不塞。** 因为冲突已经由发号方解决了，塞进去只会让每个号变长、口头沟通更啰嗦。机器与 AI 会话归属改为登记册里的一个字段，事后追溯够用，平时不碍事。

## 4. 方案主体

### 4.1 🔴 决策点一：编号格式

| 选项 | 格式示例 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A（推荐）类型前缀 + 远端编号** | `FEAT-12`、`FIX-07`、`CHORE-03` | 中：改发号脚本 1 处 + 登记册加 2 个字段 + 更新 3 份文档；历史任务按需回填 | ① 号由远端发，双机多会话**物理上不可能撞号**；② 类型一眼可见；③ 编号 = CNB issue 号，**零映射成本**，点开 issue 就是任务卡全文；④ 分支/提交/归档目录全部自动带上类型 | 远端不可达时发不出号（需兜底，见 4.4） |
| B 保留 `LOC-`，加机器码 | `LOCM-001`（Mac）、`LOCW-001`（Windows） | 低：只改前缀生成规则 | 双机之间不撞号 | 只缩小冲突面，没根治：同一台机器上两个 AI 会话并行照样撞；类型仍然看不出来；改名后与历史 36 条割裂感强 |
| C 完全本地随机号 | `LOC-01J8XK9P...` | 低：无外部依赖 | 绝对不撞号，离线无忧 | 不可口头引用、不可排序、与 issue 号脱节、看板上像乱码 |

**推荐 A。** 理由：它同时解决三个问题（撞号、类型、远端锚点），而 B 只解决一个，C 解决一个但毁掉可读性。
A 的代价是"依赖远端"，用 4.4 的降级通道覆盖即可，且 CNB 实测可用。

**子选项（若想保留 LOC 品牌）**：
- A1 干净版 `FEAT-012`（推荐）
- A2 怀旧版 `LOC-FEAT-012`
两者能力完全相同，A2 多 4 个字符且口头念起来更长。**建议 A1**，历史 `LOC-0xx` 号全部保留为旧号别名（登记册加 `legacy_id` 字段），不销毁、不复用。

### 4.2 🔴 决策点二：分几类

| 选项 | 类别 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| A 两类 | `FEAT`（需求迭代）/ `FIX`（缺陷修复） | 最低 | 最小可用，符合松哥原始诉求 | 仓库里有一批"既不是新功能也不是缺陷"的活（工作区治理、口径收敛、文档模板维护、脚本补齐）无处安放，硬塞 FEAT 会稀释语义 |
| **B（推荐）三类** | `FEAT` / `FIX` / `CHORE`（维护性：文档、脚本、模板、清理、口径收敛） | 与 A 相同，只是多一个枚举值 | 覆盖度完整；可以按类型统计"我们有多少精力花在补洞和杂活上" | 多一个分类判断，偶尔有边界模糊的活（有争议时按"用户能不能感知到变化"判定：能感知=FEAT，坏了=FIX，感知不到=CHORE） |
| C 四类 | 再加 `SPIKE`（技术调研/探索） | 略高 | 区分"想清楚"和"做出来" | 当前任务量（2 个月 36 个）粒度已经够细，第四类一年用不了几次，属于过度设计 |

**推荐 B。** 三类是覆盖度与判断成本的最佳平衡点。

### 4.3 编号结构（A1 + B 组合后的样子）

```
FEAT-012
│    └── 远端顺序号（CNB issue 号，服务端分配，永不复用）
└─────── 类型（FEAT 需求迭代 / FIX 缺陷修复 / CHORE 维护性）
```

配套命名（自动跟随，无需额外记忆）：

| 用途 | 现在 | 改为 |
|---|---|---|
| 任务卡文件 | `docs/tasks/LOC-016-xxx.md` | `docs/tasks/FEAT-016-xxx.md` |
| 工作分支 | `dev-loc-016-r1` | `dev-feat-016-r1` |
| 交付运行标识 | `loc-016-r1` | `feat-016-r1` |
| 完成标记 | `task/loc-016/v1` | `task/feat-016/v1` |
| 提交信息 | `任务标识: LOC-016` | `任务标识: FEAT-016` + 新增 `任务类型: 需求迭代` |

### 4.4 远端同步机制（🔴 决策点三）

| 选项 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A（推荐）先远端后本地** | 建任务时先在 CNB 建 issue（标题=任务名，正文=任务卡全文）→ 拿号 → 用这个号写本地任务卡与分支 | 每次建任务多一次网络调用（秒级），对方服务不可用时有阻塞 | 编号即 issue 号，无需维护映射；远端永远是最新状态；双机天然对账；任务卡自动异地备份 | 远端不可达 → 需降级（下方通道） |
| B 本地先建，事后批量回填 | 维持现状，本地算号，联网后再批量补 issue | 零改动 | 离线可用 | 撞号问题原样保留，且回填时本地号与远端号需要一张映射表长期维护 → **不推荐作主路径** |

**推荐 A，并配一条降级通道**：
远端不可达时，允许用临时号 `TMP-<机器码>-<日期序号>`（如 `TMP-MAC-0916a`）开工，登记册标 `remote = pending`，看板顶部高亮显示"待换取正式号 N 个"，联网后 24 小时内换取正式号并回填。**临时号不计入正式序列，换取后本地文件与分支改名。**

### 4.5 CNB 侧字段怎么落（已实测能力）

CNB 的 issue 支持：编号（服务端分配）、标签、处理人、优先级（原生 `P0`–`P3`）、起止日期、自定义属性、任务集（可做版本/迭代容器）。落地映射：

| 我们的信息 | 放在 CNB 的哪里 |
|---|---|
| 任务编号 | issue 号本身（`FEAT-12` ↔ issue #12） |
| 类型 FEAT / FIX / CHORE | 标签（CNB 无原生"类型"字段，标签是标准做法，且可按标签筛选） |
| 状态（定义中 / 本地已定义 / 交付中 / 等待验收 / 已合并） | issue 开关状态 + 标签 |
| 优先级 P0 / P1 / P2 | CNB 原生优先级字段（我们现在的 P0–P2 正好对上） |
| 需求来源、基线版本、验收结果 | issue 正文（沿用现有任务卡模板） |
| 负责人 | 处理人字段 |
| 版本/迭代（可选，二期） | 任务集 |

> 一期只用「编号 + 标签 + 优先级 + 正文 + 处理人」，不用自定义属性与任务集——能力够用即可，避免为用不上的功能付维护成本。

### 4.6 机器与 AI 会话归属（不进编号，进字段）

登记册每条任务新增三个字段，用于事后追溯，不占用编号长度：

| 字段 | 取值示例 | 用途 |
|---|---|---|
| `origin_machine` | `mac-mini` / `win-pc` | 这个号是在哪台机器上开的 |
| `origin_agent` | `codex` / `workbuddy` / `人工` | 是哪个 AI 会话或人工开的 |
| `created_by_session` | 会话标识（可选） | 出问题时能回溯当时的对话 |

### 4.7 🔴 决策点四：历史 36 个任务怎么处理

| 选项 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| A 全量回填 | 36 个任务全部在 CNB 建 issue，旧号留别名 | 中：脚本批量约 10 分钟，但会一次性产生 36 条 issue（通知刷屏） | 台账完整，远端与本地 100% 对齐 | 已合并任务的成果已经固化在代码历史里，再建 issue 属于纯记录性工作；通知噪音大 |
| **B（推荐）只回填活跃任务** | 只回填未合并的 **16 个**（3 个定义中 + 13 个本地已定义），已合并的 19 个保持 `LOC-` 旧号不回填 | 低：16 条，一次搞定 | 正在推进的活全部有远端锚点，跨机器可见；不制造噪音 | 历史号与新型号并存一段时间（用 `legacy_id` 字段关联，看板可按"旧号/新号"筛） |
| C 完全不回填 | 只有新任务用新规则 | 零 | 最省事 | 当前 16 个活跃任务仍然锁在单机文件里，风险没解除 |

**推荐 B。** 原因：回填的目的是"让正在推进的活有异地锚点、可跨机对账"，已完成的活价值在代码历史里，回填不产生新收益。

## 5. 过渡期方案（方案批准前，今天就可执行）

编号规则改动需要半天到一天落地，但撞号风险**今天就有**。建议立即执行临时管制：

1. **按机器分号段**：远程 Mac 用 `LOC-037`–`LOC-060`，Windows 本机用 `LOC-061`–`LOC-090`。号段用完再申请，机器之间不重叠。
2. **同一台机器上的并行 AI 会话**：由会话自己先去登记册抢占（写在登记册里就算占住），不允许"先干活后补号"。
3. 新规则上线后，号段管制自动失效，全部切到远端发号。

> 这是权宜之计，只保证"不撞号"，不提供类型区分与远端锚点——所以方案本身仍要推进。

## 7. 验收标准（可逐条实测）

1. 同一时刻在 Windows 和 Mac 各建一个任务 → 拿到两个不同编号，且不冲突；
2. 任意一个新建任务，在 CNB 上都能点开对应 issue，正文就是任务卡全文；
3. 看板能按类型（需求 / 缺陷 / 维护）筛选与统计；
4. 断网时建任务 → 拿到临时号且看板高亮提示；恢复网络后能换取正式号，本地文件与分支同步改名；
5. 任一已合并任务，能从代码提交历史反查到：任务编号、类型、需求来源、验收结果、对应 issue 链接；
6. 历史活跃任务（16 个）全部能在 CNB 上查到，旧号 `LOC-0xx` 仍能检索到对应新号。

---

## 8. 明确不做（防止范围蔓延）

- 不引入新的任务管理系统，CNB 就是那个"远端"；
- 不改现有的开发 / 审查 / 测试 / 验收节点行为与规则；
- 不改返工上限（仍为 3）、不改验收三态、不改"AI 不代签"；
- 一期不启用 CNB 自定义属性与任务集（等真需要"按版本归堆"时再开）；
- 不为不可能出现的场景写兜底（例如同时有 5 台机器并发建号——CNB 服务端发号天然覆盖）。
