# 多工作区并行开发 · 目录组织约定（通用标准模板 v1.0）

> **这是通用模板，与具体项目无关。** 所有 `<尖括号>` 处为占位符，需按目标项目实际取值。
> 填充完成的实例见 `instance_example` 所指文件。
> 本模板分三部分：**Part 1 完整设计方案**、**Part 2 实施落地方案**、**Part 3 存量任务处理方案**。

---

# Part 1 完整设计方案

## 1.1 问题与根因

### 1.1.1 典型症状

当一个 Git 项目长期采用「一任务一分支一独立工作区（worktree）」的并行开发模式，且工作区由脚本或 AI Agent 自动创建时，通常会在数周内出现下列症状：

| 症状 | 表现 |
|---|---|
| 工作区分散在多个根目录 | 人工创建的、编辑器创建的、运行时自动创建的分布在互不相识的位置 |
| 每个工作区内部各自再生一份过程产物目录 | 产物数量随工作区数量线性复制 |
| 同一任务产物多处并存 | 一份在工作区内、一份在主检出、一份在归档处 |
| 过程产物命名形成多套体系 | 出现无任务含义的名字（如 `task`、`env-store`） |
| 工作区目录名与其分支名不一致 | 按目录名推断分支会全面出错 |
| 磁盘被过程产物吃掉 | 单个在制任务的过程产物可达 GB 级 |
| 过程产物漏网入库 | 本应忽略的临时目录被提交 |
| 孤儿工作区登记 / 指针错乱 | 登记指向不存在的路径，或两个工作区指向同一管理目录 |

### 1.1.2 三个根因（非「命名不整齐」）

**根因一：缺少单一锚点。**
所有工具用「当前工作目录 + 相对路径」推导产物位置。工作区本身是仓库的完整副本，于是同一个相对路径在每个工作区里各自成立一次，产物随工作区数量线性复制，嵌套也随之发生。

判据：只要存在「用相对路径推导工作区或产物位置」的代码，嵌套与复制就必然出现。

**根因二：没有生命周期。**
没有任何环节规定「任务结束时删什么、留什么、留多久」。归档脚本通常只处理一两个文件，过程产物与证据既未归档也未清理。

判据：只要「任务进入终态」与「过程产物被删除」之间没有因果关系，终态残留就必然累积。

**根因三：约束分散且互不覆盖。**
忽略规则覆盖了产物目录，但**没有任何一处禁止在工作区内部创建工作区**，也没有统一命名规则。

### 1.1.3 为什么值得治理

不是审美问题，而是三个实际后果：

1. **工具行为受损**：工作区嵌套会让「向上逐级查找仓库根」的机制产生歧义（编辑器、构建工具、包管理器均如此）。
2. **信息会丢**：过程产物目录通常被忽略规则排除，**对版本控制完全不可见**——一个「干净」的工作区内部可能躺着尚未归档的唯一副本。
3. **成本不可控**：单个在制任务的过程产物可达 GB 级，且无任何机制回收。

## 1.2 设计目标与非目标

**目标（可验收）**

1. **可定位**：任一任务的任一过程产物，可由任务标识唯一定位到一处。
2. **可清理**：任务结束后过程产物可整体删除，只留最终产出，且删除不造成信息损失。
3. **可追溯**：变更记录有明确、唯一的存放与维护方式。
4. **可丢弃**：任一工作区被删除都不损失任何不可替代的内容。
5. **可校验**：约定内容能被机器检查（见 §1.11），不依赖人工自觉。
6. **可复用**：约定本身与项目无关，换项目只需替换占位符与少数路径常量。

**非目标**

- 不改造外部运行时/工具链的内部实现，仅约定接口层。
- 不做跨机器同步、不做云端备份。
- 不改变 Git 本身行为，不使用非公开特性。
- 不重写项目已有的流程角色，只做对齐与补齐。

## 1.3 标识体系

### 1.3.1 任务标识（可配置）

| 项 | 要求 |
|---|---|
| 任务标识 `TASK_ID` | **必须唯一、稳定、可读**。由项目自定形态，例如 `<前缀>-<序号>` |
| 分配方式 | 由**任务登记册脚本**统一分配，禁止手工命名 |
| 多轨道支持 | 若同时存在本地任务与外部需求源（如代码托管平台 issue），每个轨道各用一个前缀区分 |

### 1.3.2 命名派生规则（其余全部派生，禁止自由命名）

| 对象 | 规则 |
|---|---|
| 运行标识 `RUN_ID` | `<TASK_ID>-r<n>`，n 从 1 递增（返工即 n+1） |
| 分支 | `dev-<任务标识小写>-r<n>`；一需求拆多切片时允许附加切片后缀 |
| **工作区目录名** | **必须等于其检出的分支名** |
| 过程产物目录 | `<主检出>/.task-runs/<TASK_ID>/<RUN_ID>/` |
| 归档目录 | `<归档根>/<TASK_ID>/` |

### 1.3.3 现有命名 → 正式版映射

治理存量时必须先建立「旧名 → 新名」映射表（见 Part 3 §3.7），否则历史产物无从对应。映射表要求覆盖：运行目录、过程目录、工作区目录、缓存目录、分支五类。

## 1.4 物理布局（推荐：相邻容器）

```bash
<工作区容器根>/
├── <项目>/                                  # 主检出（位置不变，.git 在此）
└── <项目>-worktrees/                        # 相邻容器：全部工作区平铺于此
    ├── dev-<任务标识>-r1/                   # 目录名 = 分支名
    └── dev-<任务标识>-r2/
```

创建方式（路径须按 §1.6 锚定到主检出后拼接）：

```bash
git worktree add ../<项目>-worktrees/<分支名> <分支名>
```

**硬约束**

- **平铺**：容器内不再按任务/批次分第二层。
- **禁止嵌套**：容器内不得出现工作区套工作区。
- **主检出内不再有工作区**：仓库目录内不得存在任何链接工作区。
- 容器在主检出之外，**不需要**忽略规则。

**三种布局的取舍**

| 布局 | 形态 | 适用 | 主要风险 |
|---|---|---|---|
| 纯相邻 | `../<项目>-<分支名>/` | 工作区数量少 | 污染上层目录，与其他项目混杂 |
| **相邻容器（推荐）** | `../<项目>-worktrees/<分支名>/` | 通用 | 几乎无 |
| 容器下沉 | `<容器>/base/` + `<容器>/worktrees/` | 追求最整洁 | **改变主检出绝对路径** → 所有指向主检出的既有链接失效（实测：运行时创建的工作区普遍以绝对路径指回主检出，搬迁后需逐个修复） |

> 选型判据：**只要存在以绝对路径指向主检出的既有链接（运行时的 `.git` 指针是最常见的一类），就不要选「容器下沉」**。相邻容器能以零迁移成本获得全部收益。

## 1.5 三类产物与生命周期

| 类别 | 内容 | 存放位置 | 入库 | 生命周期 |
|---|---|---|---|---|
| **过程产物** | 需求草稿、探针脚本、缺陷复现、实验目录、编译中间物、临时截图 | `<主检出>/.task-runs/<TASK_ID>/<RUN_ID>/scratch/` | 否 | 收口即删 |
| **证据** | 运行记录、各类交接包与校验存证、验收卡 | `<主检出>/.task-runs/<TASK_ID>/<RUN_ID>/evidence/` | 否 | 合并后压缩为一份摘要保留；明细按保留期删除 |
| **最终产出** | 任务卡、规格终版、决策记录、变更日志条目、生成结果 | 项目自定的文档根 | 是（可重生成物除外） | 永久 |

**保留期总表**

| 内容 | 保留期 | 执行者 |
|---|---|---|
| `scratch/` | 无保留期，收口即删 | 收口命令 |
| `evidence/` 明细 | 合并时间 + `<N>` 天（建议 7 天） | §1.8 的三个触发点 |
| 证据摘要 | 永久 | — |
| 工作区 | 任务进入终态（已合并 / 已取消）即删 | 收口命令 |
| 分支（暂停期） | 至外部托管恢复并完成同步 | 阶段二收口 |
| 失效工作区登记 | 每次清理动作末尾兜底 `git worktree prune` | 收口命令 |

## 1.6 锚定机制（本约定能成立的技术要点）

不论从哪个工作区执行任务，过程产物都必须落回**主检出**。Git 提供了这个锚点——所有工作区共享同一个「公共 git 目录」：

```bash
git rev-parse --git-common-dir      # 所有工作区返回同一路径，取其父目录即主检出
```

必须把**两处**相对路径都替换为「解析到主检出后拼接的绝对路径」：

1. 过程产物目录 `.task-runs/`；
2. **工作区自身的创建路径** —— 否则从工作区内部开工时相对路径仍会被解析到错误位置，嵌套复现。

**三个直接效果**

- 一个任务的产物**物理上只有一份**，可定位、可备份、可整体删除；
- 工作区变成完全可丢弃的；
- 工作区内部不再需要过程产物目录，**嵌套自然消失**。

> 若项目已有「收口时把证据复制回主检出」的逻辑，说明方向已被验证；本约定相当于从「收口时补一次」升级为「全程只写一份」。

## 1.7 收口两阶段（决策四类型）

当外部代码托管不可用时（无法创建 PR / 关闭 issue），收口需要分两个阶段。

### 1.7.1 两阶段动作

| 动作 | 阶段一：托管暂停期 | 阶段二：托管恢复后 |
|---|---|---|
| 环境/资源回收 | ✅ 必须 | ✅ 必须 |
| 归档必要文档入库 | ✅ 必须 | ✅ 必须 |
| 删除工作区 | ✅ 删 | ✅ 删 |
| 删除分支 | ❌ **保留** | ✅ 删 |
| 同步外部托管（PR / issue） | ⏭ 无法执行 | ✅ 每次完整同步 |
| 删除 `scratch/` | ✅ 删 | ✅ 删 |
| 删除证据明细 | ✅ 按保留期 | ✅ 按保留期 |
| `git worktree prune` | ✅ 兜底 | ✅ 兜底 |

### 1.7.2 判据：工作区可再生，分支不可再生

- **工作区可再生**：随时可用 `git worktree add <路径> <分支名>` 从分支重建，删除不损失任何不可替代的东西。
- **分支不可再生**：它是提交历史的载体。托管不可用时（无法建 PR），必须保留分支才能日后补登 PR。

因此暂停期只保留「不可再生」的那一部分：**删工作区、留分支**。

> 该判据可直接用于裁决任何「这个该不该删」的争议。

### 1.7.3 阶段一必须入库的「必要文档」

这是「托管恢复后能推送完整记录」的唯一保证：

1. 任务卡
2. 任务规格终版
3. 证据摘要
4. 决策记录（若本任务产生架构级决策）
5. 变更日志条目
6. 登记册中的保留分支名

其中 1–3 构成**归档三件套**，由校验项 D-8 强制。三者缺一即视为未收口。

**证据摘要的最小字段集**（存为 `<归档目录>/evidence-summary.json`）——它是明细被删除后唯一能回答「当时做了什么、谁签的字」的记录，故不存原文、只存可核对的事实：

| 字段 | 含义 |
|---|---|
| `task_id` / `run_id` | 任务标识与本次运行标识 |
| `task_name` / `branch` / `status` | 任务名、分支名、终态 |
| `decision` / `decided_by` / `decided_at` | 裁决结果、裁决人、裁决时间 |
| `merge` | 合并提交、合并时间、关联 issue |
| `stages` | 各阶段记录的类型、文件名、写入时间、产出者与关键结论（基线状态 / 设计决定 / 交接结果 / 审查结论 / 测试结论 / 验收裁决） |
| `evidence` | 明细的归档位置、文件数、总字节 |
| `generated_at` | 摘要生成时间 |

两条硬约束：

- **不得伪造证据**。任务若先于 Run 证据链机制落地（无分支、无明细），则 `evidence` 置 `null` 并加 `no_run_evidence: true` 与说明文字，而不是编造一个空的证据块。
- **摘要是删除明细的前置条件**（见 §1.8）：摘要不存在时，清理动作必须拒绝执行。

### 1.7.4 与既有流程角色的对齐

**不要新建并行机制。** 若项目已有收口角色/流程，应把本约定作为其补充，逐条对齐：

| 既有行为 | 处理 |
|---|---|
| 已有的资源回收步骤 | 保留，作为清理工作区**之前**的前置步骤 |
| 已有的工作区清理步骤 | 保留，作为**阶段二**动作（阶段一只删工作区、留分支） |
| 已有的证据归档逻辑 | 保留，升级为「全程只写一份」 |
| 已有的归档脚本（通常只归档 1–2 个文件） | **扩展**为三件（增证据摘要） |
| 过程产物无任何清理规定 | **新增**到期清理机制（§1.8） |
| 若收口未级联注销嵌套子工作区登记 | 🔴 **需补**：删父工作区后固定追加 `git worktree prune` |

## 1.8 到期清理机制（推荐方案 B）

**保留期不依赖「有人记得」**，执行挂到已有高频事件上。三个触发点：

| 触发点 | 时机 | 动作 | 为什么不会忘 |
|---|---|---|---|
| 开工顺带清 | 任何任务开工时 | 扫登记册中已到期的项，删明细 | 开工最频繁，积压上限 = 距上次开工的时长 |
| 收口顺带清 | 任何任务收口时 | 删本任务明细 + 扫其他到期项 | 收口每次都跑，天然搭车 |
| 校验闸门 | 项目的校验命令 | 存在超期未清项 → **校验失败** | 不清理过不了闸门，机器强制 |

到期信息写在任务登记册（一个 JSON 即可判定，无需扫盘）：

```json
"merge": { "commit": "<sha>", "merged_at": "<ISO8601>" },
"evidence_expires_at": "<merged_at + 保留期>",
"evidence_cleared_at": null,
"branch_retained": true
```

- 起算点 = 合并时间 + 保留期，**不是创建时间**。
- **删除前置条件**：证据摘要必须已存在，否则拒绝删除——防止误删唯一副本。

**三个方案对比（为什么不用定时任务）**

| | 定时任务 | **机会式 + 闸门（推荐）** | 终态即删 |
|---|---|---|---|
| 成本 | 需常驻调度 | 一个函数 + 一条校验 | 最低 |
| 主要风险 | 🟡 **失败是静默的**（调度挂了无人知）；跨机器与多环境难覆盖 | 积压上限为「距上次开工程序运行的时长」 | 放弃终态后的短期调试能力 |

## 1.9 变更记录的统一存放与维护

| 层级 | 载体 | 维护规则 |
|---|---|---|
| 交付事件 | 变更日志 `CHANGELOG.md` | 合并时追加一行：日期 + 任务标识 + 一句话影响 |
| 任务级 | 任务登记册 + 任务卡 + 归档目录 | 只由脚本写入；必须入库 |
| 架构级决策 | `docs/design/decisions/NNNN-<slug>.md` + 索引 | **已接受的不修改**；推翻时写新条目并标注 `Superseded by NNNN` |
| 研究过程 | `docs/research/<slug>.md` | 保持 |
| 阶段性决策票 | 决策票目录 + 索引 | 阶段完成后冻结，不再回改 |
| 需求分析与决策地图 | `docs/design/<主题>/` | 与正式规格目录配套；**不得留在过程产物目录** |

**三条硬规则**

1. **唯一位置**：同一层级的记录只有一个存放位置，不得两处并存。
2. **只新增不修改**：已接受的决策记录永不修改，推翻走新条目。
3. **入库**：变更记录必须进版本控制——放在 wiki 或忽略目录里的记录，结局是「被遗忘」。

## 1.10 外部运行时的例外条款

工作区根目录往往不止一个：除人工/脚本创建外，**外部运行时、编辑器也会自己创建工作区**。这些不在人工约定管辖内，但必须遵守三项接口约定：

1. 遵守 §1.3 命名规则与 §1.6 锚定规则；
2. 工作区销毁时**必须同时注销对应的 Git 工作区登记**，否则产生孤儿；
3. 纳入定期巡检（`git worktree list` 快照 → 与活跃工作区比对 → 报告孤儿）。

🔴 **高风险位置**：位于系统临时目录（`/tmp`、`/private/tmp`）的工作区应视为高危——系统可能随时清理该目录，而 Git 登记不会随之消失，直接退化为孤儿登记。此类工作区应迁出或删除。

## 1.11 机器校验标准

| 编号 | 检查项 | 判定 |
|---|---|---|
| D-1a | **工作区禁止嵌套**（红线） | 无任何工作区位于**另一工作区**内部 |
| D-1b | 工作区不得位于仓库目录内 | 全部工作区在相邻容器等仓库外位置 |
| D-2 | 工作区目录名 = 分支名 | 逐一比对，全部一致 |
| D-3 | 分支名符合派生规则 | 全部匹配 §1.3.2 规则 |
| D-4 | 过程产物位置 | 工作区内部不存在过程产物目录 |
| D-5 | 运行目录命名 | 全部可解析为 `TASK_ID` + `RUN_ID` |
| D-6 | 无漏网入库 | 版本控制的文件列表中不含过程产物路径 |
| D-7 | 终态任务已清理 | 登记册状态为「已合并 / 已取消」的任务，其工作区与 `scratch/` 均已删除 |
| D-8 | 归档完整性 | 每个已合并任务在归档目录下均存在任务卡、规格终版、证据摘要三件 |
| D-9 | 无超期证据残留 | 不存在已到期且未清理的项 |
| D-10 | 收口口径一致 | 登记册的「分支保留」标记与实际分支存在性一致 |

> ⚠️ **合并判据**：判定「某任务是否已合并」必须用登记册记录的合并提交是否在主分支上，**不得**用 `git merge-base --is-ancestor <分支> main`。若项目使用 squash 合并，分支祖先判定会把已合并任务**误报为未合并**。
> 判别方法：`git show --no-patch --format='%P' <合并提交> | wc -w`，结果为 `1` 即 squash。

## 1.12 生命周期所有者：谁在什么时候创建 / 回收

> 本节回答一个必须先定清的问题：**新任务来时，分支与工作区在什么时候创建、由谁处理。**

### 1.12.1 通用链路（四个环节，各有唯一所有者）

| 环节 | 时点（触发条件） | 执行者 | 前置门禁 |
|---|---|---|---|
| ① 分配任务标识 | 任务完成需求分析、进入「已定义」 | 任务登记册脚本 | 需求基线已确认 |
| ② 建分支 + 工作区 | **「已定义 → 开工」转换点**，即实施前检查通过之后 | **Run 引导脚本（唯一入口）** | 实施前检查通过 |
| ③ 环境/并发解析 | 紧接 ②，多任务并行时 | 环境解析**函数**（由 ② 调用，**不设独立入口**） | 同组前置任务已完成 |
| ④ 回收 | 任务进入终态（已合并 / 已取消） | **收口命令（唯一入口，与 ② 同一所有者）** | 归档核对通过 |

### 1.12.2 「什么时候建」的判据

必须**同时**满足，缺一不建：

1. 任务状态 = 已定义（需求基线已确认，未决产品事项为 0）；
2. 实施前检查通过（无阻塞项）；
3. 前置依赖已解除；
4. 基线可取得（能取到远程基线，或显式声明「以本地主分支为基线」）。

任一条不满足：**不建**，Run 状态置为受阻（`BLOCKED`）并停止。**不得先建后补。**

> 🟡 为什么不能在需求分析阶段就建：任务可能被取消、被合并、被调序。提前创建只会产生终态残留——实测中存在「任务已取消但工作区仍在」的案例（`LOC-010`）。**创建工作区是开工动作，不是登记动作。**

### 1.12.3 三条硬规则

1. **创建只有一个入口。** 任何工具不得各自拼接工作区路径；所有路径必须由**同一个解析函数**产出。多入口并存是产物散落的机制性原因。
2. **创建与回收必须是同一个所有者。** 创建方负责登记，回收方按同一份登记清单清理。二者分离必然产生孤儿。
3. **人只在两种情况下介入**：单次手工调用；以及人工确认门禁处。常规流程由脚本驱动。

### 1.12.4 为什么把「谁处理」写进约定

现状的典型病灶不是「没人建」，而是**建的入口和回收的入口都不唯一**：创建有 2 个脚本入口，回收有 4 个（环境回收、环境组清理、任务合并、收口角色），**没有任何一处掌握「全部产物的清单」**。

因此本约定要求：**创建与回收共用同一份登记清单**（写进任务登记册的运行记录）。创建时写入，回收时核对删除。这样孤儿在定义上就不可能出现。

## 1.13 定位：共享执行入口，不绑定任何单一工作流，也不绑定任何单一 Agent

### 1.13.1 它属于共享层

两条证据：

1. **规格层面**：v0.1 产品规格把「执行入口」与 Blueprint、Logical Run、角色、版本、人工交互、模型配置并列为四套正式工作流的**共享能力**。
2. **实现层面**：四套蓝图内**没有任何分支/工作区创建逻辑**——蓝图里出现的 `verified_branch` / `verified_head` 只是节点的校验字段；创建与回收都在蓝图之外的脚本层。收口能力也已被声明为多流程复用。

因此本约定的正确归属是「**执行入口的共享契约**」，而不是某一工作流的附属说明。

### 1.13.2 接入多套工作流的方式

| 层 | 内容 | 谁维护 |
|---|---|---|
| **共享契约（本约定）** | 命名与位置、产物锚定与三级生命周期、收口两阶段、到期清理、登记字段、D-1~D-10 | 一份，各工作流共用 |
| **流程层** | 各工作流特有的门禁、路由与节点编排 | 各工作流自己的 runbook，**只引用**共享契约 |

🔴 **反模式**：把共享契约的内容复制进每套工作流的 runbook。复制会产生分叉，分叉会导致「同一仓库里并存两套不同的工作区语义」。

### 1.13.3 跨 Agent 的定位

本约定对 Agent **中立**，但对执行者有最低要求，且存在一段必须按 Agent 适配的部分。

**最低要求（任何执行者都必须满足）**

1. 能读取仓库内文档（runbook / 项目根指南）；
2. 能执行命令行脚本；
3. 能遵守「工作区纪律」（命令一律显式指定工作区路径，并核对当前分支）。

**必须按 Agent 适配的接口点（由使用者自行解决，不在本约定内）**

| 接口点 | 说明 |
|---|---|
| **规则投递方式** | 各 Agent 的规则文件与技能发现根不同。本约定只要求「规则能被目标 Agent 读到」，如何投递不属本约定范围 |
| **权限 / 批准模式** | 无人值守要求「执行工作区类命令无需人工批准」。各 Agent 的默认批准与沙箱策略不同，需逐个声明并实测 |
| **资源与环境隔离** | 若执行者有自身的工作目录/会话/进程需要隔离，该隔离**是执行者专属的**，应作为可插拔适配段声明；🔴 **无适配器时退化为「不隔离」**，不得让它成为共享契约的必需依赖 |

> 依据：同一个 Run 的多个节点本就可能由不同 Agent 执行（异构执行体）。若工作区纪律依赖某一 Agent 的特有能力，换 Agent 即失效。**因此 Agent 中立是硬需求，不是优化项。**

### 1.13.4 与既有仓库级约定的关系

若仓库已有 Agent 中立的约定文件（如项目根指南 `AGENTS.md` 之类），工作区约定应**同时写入其中作为入口指引**，而不只活在某个 Agent 的技能目录里——这样任何 Agent 进入仓库都能拿到规则。

# Part 2 实施落地方案

## 2.1 落地原则

1. **先只读、后写入**：任何批量动作前先出只读报告，人工确认后分批执行。
2. **先脚本、后批量**：先把规则固化进脚本与校验，再动存量。否则同样的乱局会在一周内重建。
3. **先删后迁**：先删除终态工作区，再迁移在制工作区，避免迁移即将被删除的目录。
4. **禁止用 `rm -rf` 处理工作区**：一律用 `git worktree remove`。
5. **每批 ≤5 个目标**，执行后立即复核登记数与磁盘是否一致。
6. **不自动提交**：所有改动交人工确认后提交。

## 2.5 门控与回滚

**每批执行前的硬性前置条件**

1. 目标工作区 `git status --porcelain` 为空，或未跟踪文件已逐个人工确认；
2. **内部过程产物已归档核对**（见下）——两步都过才能删；
3. **无并发会话正在使用目标工作区**；
4. `git worktree remove` 被拒时**先查明原因**，不直接升级到 `--force`。

> 🔴 **删除前必做：内部过程产物归档核对。**
> `git status --porcelain` 为空 **≠** 工作区内没有有价值内容。过程产物目录被忽略规则排除，**对版本控制完全不可见**——实测中存在「检查时为 0 未提交改动、内部却有 21 个未归档证据文件」的案例。必须单独把内部过程产物与归档位置对照（**存在性 + 条目数一致**），未归档的先补归档再删。

> ⚠️ **并发作业风险。**
> 若存在其他会话/进程正在同一工作区作业，则：清理目标可能被对方先行删除；对共享文件（登记册、看板）的修改可能被对方脚本**重写覆盖**（实测发生过）。结论：**涉及共享文件或共享工作区的批次，必须在无并发写入时执行。**

**回滚策略**

- 删除工作区前不删分支 → 任何工作区都可用 `git worktree add` 重建（这是相邻容器 + 两阶段设计的核心保险）。
- 脚本改造保持一版向后兼容（旧路径仍可解析），确认新路径稳定后再移除兼容分支。
- 对已入库文件的改动独立提交，便于单独回滚。

# Part 3 存量任务处理方案（通用方法）

## 3.1 建立基线快照

治理存量前必须先定格两件事，且**只读采集**：

1. **任务基线**：全部任务及其状态（已合并 / 已取消 / 在制 / 未开工）。
2. **工作区基线**：`git worktree list` 全量 + 每个工作区的归属、分支、未提交改动数、体量。

## 3.2 分类处置矩阵（通用）

| 任务状态 | 工作区存在 | 处置 |
|---|---|---|
| 已合并 / 已取消 | 是 | **收口**：归档核对 → 删工作区 → `prune`；分支按阶段口径保留 |
| 已合并 / 已取消 | 否 | 检查分支保留状态与登记册字段一致性 |
| 在制 | 是 | **保留**，待其收口时按新约定处理（**不强制回改**，避免干扰在制工作） |
| 未开工 | 否 | **按新约定开工** |
| 无归属 | 是 | **待判定**：人工确认归属后归入上述某类 |
| 外部运行时创建 | 是 | **由运行时侧回收**，不手工删（避免绕过登记注销逻辑） |

## 3.3 存量清理批次模板

| 批 | 内容 | 风险 |
|---|---|---|
| **B0** | `git worktree prune` 清孤儿登记 | 无（幂等） |
| **B0.5** | 补归档：核对时发现未归档的内部过程产物 | 低（复制，不删源） |
| **B1** | 删终态工作区（每批 ≤5 个） | 低 |
| **B2** | 处理指针错乱目录 | 🟡 中（先确认无独有产出） |
| **B3** | 清过程产物目录中的可再生成残留 | 低 |
| **B4** | 外部运行时终态工作区回收 | 🟡 中（应由运行时流程执行） |
| **B5** | 在制工作区迁移到相邻容器 | 中（建议脚本化） |
| **B6** | 登记册数据卫生（悬空引用、未启用字段） | 低 |
| **B7** | 分支治理（独立议题，不与工作区收敛混做） | 中 |
| **B8** | 新任务收口后追加的工作区清理 | 低 |

> ⚠️ **B6 类操作（改共享文件）必须在无并发写入时执行**，否则会被并发脚本覆盖。

## 3.4 归档缺口与补救

清理前必须核对：**每个工作区内部的过程产物，是否已在主检出的归档位置留有副本。**

核对方法：把内部过程产物目录与归档位置逐一对照（存在性 + 条目数一致）。未归档的**先补归档再删**。

> 🔴 实测中多次出现「过程产物只在工作区内、从未入库」的情况——尤其是**最早期的任务**（后续任务收口时通常会归档，早期任务可能从未纳入归档流程）。治理时必须逐个核对，不能假定「已合并 = 已归档」。

## 3.5 命名修正映射

必须建立「旧名 → 新名」对照表，覆盖五类：运行目录、过程目录、工作区目录、缓存目录、分支。要求：

- 每一行给出旧名、新名、修改方式（改名 / 归并 / 删除）；
- 对无任务归属的旧名明确处置（归并到某任务，或标记为「运行时非任务产物」）；
- 对**非标识**的名字（如 `task`、`env-store` 之类泛名）直接判定为需删除。

## 3.6 存量收敛完成判据

以下条件全部满足，即视为存量收敛完成：

1. `git worktree list` 中不存在终态任务的工作区；
2. `git worktree prune --dry-run --verbose` 输出为空；
3. 不存在指针错乱的工作区目录（`.git` 与管理目录双向一致）；
4. `git ls-files` 中不含过程产物路径；
5. 每个已合并任务具备任务卡 + 规格终版（证据摘要随 P1 落地后补齐）；
6. 过程产物目录体量回落到约定上限以内；
7. D-1~D-10 校验项全部通过。
