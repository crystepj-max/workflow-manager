# Multica 选型评估报告

> **评估对象**：Multica（https://github.com/multica-ai/multica，文档 https://multica.ai/docs）
> **评估问题**：它能否替代在线电子表格，承担本团队的任务管理？
> **评估日期**：2026-09-22
> **评估口径**：Multica 作任务总账、GitHub 任务票保留为项目内镜像；自托管与官方云并列对比
> **证据原则**：每条判断标注依据；查不到依据的一律标「未找到依据」，不推测

---

## 1. 结论摘要

**结论：能替代在线表格，且覆盖面更大；但它替代不了本团队自有的交付治理规则层。**

把它拆成两句话：

- **「协调与可见性」这一半，它全面胜出。** 我们上一轮分析中认为"表格做不到、必须自建"的全部能力——原子领取、心跳、超时回收、阻塞接手、跨项目总账、任务号、人看得懂的视图——它都是原生开箱的，而且底层是 PostgreSQL（真正的数据库），在线表格的三个硬伤（乐观锁冲突、接口限流、弱一致性）全部不存在。
- **「治理规则」这一半，它完全空缺。** 定义门（七项硬门禁）、验收三态、返工上限、收口三件套、审查轮次控制器——平台没有任何原生原语，必须挂在外围自己实现。且其中一个缺口带**静默开工风险**（见 §4.1）。

因此这不是「采用 / 不采用」的二选一，而是**分工问题**：平台做执行与记账，规则仍归我们。

### 🟢 对你最有价值的四个事实

| # | 事实 | 对你的意义 |
|---|---|---|
| 1 | 有 **表格视图**（以及列表/看板/甘特/泳道，共五种） | 你想要的"打开就能看全局"直接满足，不用改习惯 |
| 2 | **26 种 Agent 工具自动识别**，含 DeepSeek Harness、Codex、Claude Code、Cursor、Kimi、OpenCode、Hermes、CodeBuddy、Pi、OpenClaw | 你现在用的 Agent 全在支持列表里，不需要换工具 |
| 3 | **阻塞后任务自动退回待办池，可改派**；重试保留上次已写入的文件 | 直接解决你"某个 Agent 卡住，其他 Agent 不能接手"的痛点 |
| 4 | GitHub 集成通过任务号自动关联 PR，合并后任务自动完成 | 上一轮讨论的「任务与合并申请一一对应」是它的内建行为 |

## 2. Multica 是什么

### 2.1 定位

官方原文（README）：**"Agents that show up on the board."**——一个开源、可自托管的工作空间，让你像给同事派活一样把工作派给 AI 编码 Agent。Agent 自己领活、回报进度、提出阻塞、交回审查。

团队规模与活跃度（2026-09-22 实测）：**5,432 次提交、2,622 个分支、167 个版本发布**，最新提交就在评估当天。单前端测试套件 6,503 个用例，具备完整持续集成、GoReleaser 与 Helm 发布链路。**成熟度属「活跃且工程化程度高」，不是实验品。**

### 2.2 组成形态

| 层 | 技术 | 说明 |
|---|---|---|
| 网页端 | Next.js 16 | 主界面 |
| 后端 | Go（Chi 路由 + WebSocket） | 协调中枢 |
| 数据库 | PostgreSQL 17 | **业务数据的唯一真源** |
| 执行端 | 本机守护进程（daemon） | 跑在你自己的机器上，**挨着你的代码** |

桌面端（macOS/Windows/Linux）、手机端（iOS，需自行构建）、命令行工具齐备；官方云与自托管两种形态并存。

### 2.3 任务是怎么流转的

🔴 **关键机制：Agent 不会自己开工。** 官方原文："Agents never start work on their own — every run is triggered by an explicit action"。四种触发方式：**给任务指定负责人、在评论里 @它、直接对话、定时自动化**。

一次执行的完整路径：

```
任务（含目标、讨论、负责人）
      ↓ 指定负责人
产生一次「执行记录」，进入队列
      ↓ 某台在线机器认领
在本机启动对应的 Agent 工具
      ↓ 本机执行（读写代码、跑命令）
进度与结果写回原任务的动态与执行日志
```

**执行状态与超时（这份表是理解它能力的核心）**：

| 状态 | 含义 | 超时与后果 |
|---|---|---|
| 排队中 | 等待某台机器认领 | **不会因等待过久而失败**——只要机器还在发心跳就说明它在忙、不是死了 |
| 已派发 | 已被认领，正在启动工具 | 停留超过 **5 分钟**判失败 |
| 等待本地目录 | 目标目录正被另一次执行占用，等锁释放 | 无自身超时，锁释放后回到启动流程 |
| 执行中 | Agent 正在工作 | **无固定时长上限**；靠心跳判活——**每 15 秒一次**，失联约 **3 分钟内**判离线，其名下执行一并失败 |

🟢 **「等待本地目录」这一条直接对应你的「30+ 工作副本失控」问题**：同一个目录不会被两次执行同时改写，平台层面就串行化了。

### 2.4 阻塞与接手（你最关心的一段）

| 机制 | 具体行为 |
|---|---|
| 阻塞上报 | Agent 卡住时**主动上报**，失败原因有专门分类：`agent_blocked` = "Agent 报告它无法继续"，处置动作是"提供它在评论里要求的东西" |
| 失败退回 | 当任务没有其他进行中的执行、也没有待执行的重试时，失败会把任务**从「进行中」退回「待办」** |
| 自动重试 | **仅覆盖基础设施故障**（机器离线、守护进程重启、执行超时、工具网络中断等），常规重试 2 次、网络中断最多 3 次；**Agent 自身的错误（凭证过期、额度耗尽、配置错误）不自动重试**，须先修因再手动重试 |
| 重试的连续性 | **重试保留上一次执行已写入本地目录的文件**；若原会话仍安全且同一台机器认领，还会**续接上次会话** |
| 改派 | 一个任务可以"被讨论、修改、反复改派"给不同 Agent；每次执行都有独立记录，**旧记录永不覆盖** |
| 手动重试的对象 | 🔴 注意：手动重试调用的是**当初处理那次执行的 Agent**，即使任务后来已改派他人也不会切到新负责人 |

### 2.5 失败原因分类（可直接用于排障）

平台侧 11 类（机器离线、排队过期、守护进程重启回收、环境准备失败、执行超时、迭代上限、**Agent 报阻塞**、请求非法、Codex 语义停滞等）+ 工具侧 15 类（模型凭证、额度、限流、服务端错误、网络、模型不可用、上下文溢出、配置缺失、可执行文件缺失、版本过旧等）。**这个分类粒度明显优于当前自建体系的「失败」黑箱。**

## 3. 能力逐条对照

对照我们需求清单的 10 项，分三类判定：

| # | 需求 | 判定 | 依据 / 缺口 |
|---|---|---|---|
| 1 | 27 类任务字段 | 🟡 可扩展实现 | 任务支持**自定义属性**，9 种类型（文本/数字/单选/多选/日期/勾选框/链接/人员/多人员）。27 类大体可映射（旧号→文本、远端锚点→链接、施工环境组与无人值守许可→单选、证据过期时间→日期）。**缺口**：属性类型创建后不可改；文档未记载数量上限，也**未找到「必填」能力的依据** |
| 2 | 自定义状态机 | 🟡 部分实现 | 可新增状态名，但必须归入平台固定的四个生命周期类别（未开始/进行中/已完成/已关闭），**类别创建后只读**；官方明示"状态之间没有固定流转"。**缺口**：只能得到「状态名」，得不到「状态机」 |
| 3 | 定义门（七项硬门禁） | 🔴 **不支持** | 全站找不到「字段必填」与「条件准入」的依据。门禁必须外置为脚本/技能 |
| 4 | 交付链门禁 + 验收三态 + 返工上限 3 | 🟡 可扩展实现 | 执行与任务状态分离，状态可被 Agent 用命令行显式写入；**「退回/有条件通过」三态与轮次计数无原生表达**。自动重试的能力存在但只覆盖基础设施故障 |
| 5 | 收口三件套 + 登记册 | 🟡 可扩展实现 | 有「每个任务一条分支 + 产物落仓库」与附件机制；**无「归档到固定路径」原语**；**合并提交号与合并时间：未找到原生字段依据** |
| 6 | 批量调度 | 🟡 可扩展实现 | **并发上限与排队补位是原生的**（单个守护进程上限 20、单个 Agent 上限 6，超限排队，空位自动被认领）。**缺口**：没有「按条件筛池 + 冻结快照 + 按序补位」的一体化能力；定时自动化只会「到点建任务或直接跑」，不会按优先级筛选。需自行拼装 |
| 7 | 多机多 Agent 协调 | ✅ **原生支持** | 每次执行记录触发来源/Agent/状态/时间；临时令牌绑定「用户+工作区+Agent+执行」并按 Agent 归属记账；团队（Squads）机制可避免对同一任务重复入队；有目录串行锁 |
| 8 | 人工可读全局 | ✅ **原生支持** | **五种视图：列表 / 看板 / 表格 / 甘特 / 泳道** |
| 9 | 审查门禁（控制器/轮次/去重/额度） | 🔴 **不支持** | 官方明示 GitHub 集成"从不推送提交、从不写评论、从不写状态检查"。审查控制器必须自建（**✅ 已决策：由项目自控，不进通用层**，见 `task-governance-layering.md` §4） |
| 10 | 本地文件为真源 | 🔴 **不支持** | 官方架构文档明确「**PostgreSQL 是业务数据的唯一真源**」；任务描述与规格存在服务端数据库，仓库里的 Markdown 无法成为权威，**也没有任务与文件的双向同步** |

**统计：原生支持 2 项、可扩展实现 5 项、不支持 3 项。**

## 4. 三个阻塞性缺口

### 4.1 🔴 门禁规则没有平台原语，且存在「静默开工」风险

平台没有必填字段、没有条件状态迁移。**更危险的是**：自定义的「未开始」类状态**不具备平台自带待办的"停车"语义**——官方对状态类别的说明与"指派即开工"的触发机制合在一起，意味着**一旦门禁漏执行，任务会直接开工**。

🟡 对你的影响：定义门从「系统兜底」退化为「靠流程约定」。也就是说，**现有七项硬门禁的拦截力在平台侧等于零**，必须在外围脚本或技能里重新做实。

这是本次评估最重要的一条——它不是"功能缺失"，而是**安全垫消失**。

### 4.2 🔴 「本地文件为真源」这条基石在平台上不成立

> **✅ 已决策（2026-09-22）**：真源改为 Multica 任务数据库。本节的"保留意见"已撤销，处理方式见 `task-governance-layering.md` §3（含平台不可用时的降级策略）。

官方架构文档明确以自身数据库为唯一真源。我们现有体系依赖三件事：任务卡与规格是 Git 仓库里的文件、可以对比差异、可以追溯历史。

在 Multica 上这条只能二选一：

- **放弃**：任务与规格的权威移入平台数据库；
- **降级**：文件仍存仓库，任务里只放指针，二者一致性**由脚本或 Agent 自行保证**（平台不提供任何保证）。

🟡 风险：一旦指针与文件不一致，没有任何机制会发现。

### 4.3 🔴 GitHub 只读，状态回写要自己写

它的 GitHub 集成是**单向只读**：只关联 PR、镜像 CI 状态与可合并性、合并后自动完成任务，**不推代码、不写评论、不改状态**。

你已确认的口径是「Multica 作总账、GitHub 任务票保留为镜像」——这意味着：

- **镜像同步脚本必须自建**（平台不会帮你回写 GitHub 任务票）
- 收口所需的**合并提交号与合并时间**，在平台上**未找到原生记录字段**（PR 卡片只记录状态、增删行数、CI、可合并性）

## 5. 部署形态对比

### 5.1 自托管（自有机器）

| 项 | 事实 |
|---|---|
| 前置 | 需要 Docker 与 Docker Compose（或 Kubernetes + Helm） |
| 服务数 | **3 个**：网页端（默认 3000）、后端（默认 8080）、PostgreSQL 17 |
| 数据边界 | **代码与任务数据都不出本机**；所有服务默认只绑本机端口（127.0.0.1），不暴露公网 |
| 单机可行性 | 官方文档面向"本机 localhost"场景，**单台笔记本运行属支持的典型用例**；但**未给出 CPU/内存下限**（唯一容量数字来自 K8s 模板：数据库 10Gi + 上传 5Gi 存储） |
| 需要自建的部分 | **自建 GitHub 应用**（回调地址、密钥、仓库权限、订阅事件） |
| 升级 | 拉新镜像 + 重启，数据库迁移**在后端启动时自动运行**；有回滚命令 |
| 已确认的坑 | ① **遥测默认开启**（每日一次匿名快照，可用环境变量关闭，端点编译在二进制内无法重定向）；② **企业微信智能机器人多副本会丢回复**，该配置下应单副本运行；③ 密钥必填，生产环境拒绝用默认值启动 |
| 维护负担 | 升级、备份、故障全部自担 |

### 5.2 官方云

| 项 | 事实 |
|---|---|
| 上手 | 邮箱注册 + 验证码即用，工作区自动创建 |
| 数据边界 | **任务状态与事件经过官方服务器**；官方 FAQ 原文："Agent execution happens on your machine... **Code never passes through Multica servers.**"——**代码不经过** |
| 需要配置的 | 无需自建 GitHub 应用 |
| 成本 | 🔴 **定价未公开**（官方定价页返回 404）——**属未查证项，不能作为决策依据** |
| 集成完整度 | 部分入口云端不提供（例如自托管 Git 平台的接入入口） |
| 维护负担 | 无 |
| 可退出性 | 中——项目开源，理论上可迁往自托管，但**数据迁移路径未找到依据** |

### 5.3 🟢 建议

**先自托管在自有机器。** 理由有三：① 数据完全自有，与你的既有偏好一致；② 官方云定价未公开，现在算不出成本；③ 自托管形态的功能更完整（云端部分入口缺失）。

代价是必须接受一次 Docker 环境搭建 + 自建 GitHub 应用。这个代价换来的是"标签一开就能整体撤走"的可逆性。

## 6. 「Multica 作总账 + GitHub 票保留」的可行性

你已选定这个口径。评估结论：**可行，但镜像层要自己维护，且有三处语义会打架。**

### 6.1 可行的部分

- 平台的任务号（工作区级）与 GitHub 的 PR 关联机制天然配合：把任务号写进分支名或标题，或用 `Closes <任务号>`，合并后任务自动完成。
- **这直接实现了你上一轮的「任务与合并申请一一对应」诉求**，且不需要自己写任何关联逻辑。

### 6.2 需要自己维护的部分

| 事项 | 说明 |
|---|---|
| 镜像同步脚本 | 平台不会回写 GitHub 任务票，需自建 |
| 合并证据补录 | 合并提交号与合并时间平台上无原生字段，需在收口时由脚本补记 |
| 门禁校验 | 定义门七项检查需外置 |

### 6.3 🟡 三处语义冲突（必须事先想清楚）

1. **编号体系**：平台任务是工作区级编号（如 MUL-123），会取代你现有的 `FEAT/FIX/CHORE-号` 体系。**改前缀后，旧号在已有的 PR 与分支里不会更新**——历史任务的追溯会断。
2. **状态语义**：「本地已定义」（远端不可用时的降级状态）在平台上无法通过状态本身表达——平台的自定义状态没有转移约束，也不区分"能开工"与"不能开工"。你现有体系中「本地已定义具备与已定义同等的开工资格」这条语义，需要放进自定义属性而非状态。
3. **两套真源**：平台数据库与仓库文件如果都写，就存在一致性风险；如果不写仓库文件，「文件可对比、可追溯」的能力就消失。→ **✅ 已决策：单一真源为平台数据库**，代码与证据仍留在仓库；处置见 `task-governance-layering.md` §3。

## 7. 风险与不确定项

### 7.1 🔴 已确认的风险

| 风险 | 说明 |
|---|---|
| 静默开工 | 门禁无平台兜底，漏执行即开工（§4.1） |
| 真源分裂 | 平台数据库与仓库文件两套真源，无一致性保证（§4.2） |
| 编号断层 | 切换编号体系会切断历史任务与 PR/分支的关联（§6.3） |
| 授权条款 | 许可为「Apache 2.0 + 附加条件」，**自己用、自己改、自托管都没问题；对外提供托管服务需要商业授权**。团队自用不受影响 |
| 企业微信丢消息 | 该集成在多副本下会丢回复，需单副本运行 |
| 遥测默认开启 | 默认每日上报一次匿名用量快照，可关闭 |

### 7.2 🟡 未查证项（不得作为决策依据）

| 项 | 状态 |
|---|---|
| 官方云定价 | 页面 404，未查到 |
| 自定义属性数量上限 | 未找到依据 |
| 自定义属性能否设为必填 | 未找到依据（这条直接决定定义门能否部分内建） |
| 表格 / CSV 导出 | **未找到原生能力依据**。特别提示：网上流传的「Add CSV and PDF export」是官方演示界面里的**示例任务标题**，不是功能——不要被误导 |
| 合并提交号与合并时间是否有原生字段 | 未找到依据 |
| 插件能力的正式文档 | 仓库中有示例（含界面面板与权限作用域），但**文档站无对应页面**，能力存在但依据不足 |
| 官方云转自托管的数据迁移路径 | 未找到依据 |

## 8. 建议与下一步

### 8.1 建议（明确表态）

**推荐采用，但定位必须校准为「执行与协调底座」，不是「治理体系」。**

- 采纳它来做：跨项目总账、任务号、人可读视图、多机多 Agent 协调、执行日志与成本、任务与 PR 关联。
- 不要指望它做：定义门、验收三态、返工额度、收口归档、审查控制器。这些留在外围。
- 形态上先自托管。

**如果这个定位你不接受**——即你要求"现有治理规则必须原样搬进去、由平台强制"——那么答案是**不推荐采用**，因为平台在规则层是空的，强行改造反而比现状更脆弱。

### 8.2 建议的验证动作（低成本、可逆）

在正式决定前，用最小代价验三件事：

1. **验视图是否合用**：它是否真能替代你"打开表格看全局"的习惯（表格视图是否满足）。
2. **验门禁能否外置**：用一个任务走完整流程，看外围脚本能否可靠拦住未过定义门的任务。
3. **验编号与追溯**：模拟一次编号切换，看历史任务的追溯是否可接受。

这三件事都不需要先迁移任何存量数据。

### 8.3 与既有设计文档的关系

本评估**取代**《任务治理能力外置方案》（`docs/design/task-governance-externalization.md`）中的这一部分：

- ✅ **被取代**：自建在线表格总账、自建租约服务（原子领取 + 心跳 + 超时回收）——Multica 原生具备，不必自造。
- ❌ **仍然需要自建**：交付门禁、验收三态、返工额度、收口归档、审查控制器、GitHub 镜像同步。
- ✅ **已决策**：该文档主张的「本地文件为真源」——经确认**改为以 Multica 数据库为真源**（见 §4.2 标注与 `task-governance-layering.md` §3）。
- ✅ **已决策**：审查轮次控制器**由项目自控，不进通用层**（依据「通用流程与业务场景分离」原则，见 `task-governance-layering.md` §4）。
- ✅ **不受影响**：《分支管理规范》（`docs/design/branch-management-policy.md`）——分支纪律与工具选型无关，仍然有效。
