# 任务治理能力外置方案（拆分 · 表格主源 · 多机协调）

> **定位**：在《分支管理规范》基础上，解决三个更上层的问题——① 项目管理能力与工作流插件仓库耦合过重；② 需要一个跨项目的统一任务总账；③ 多机多 Agent 并行时的重复施工与阻塞占坑。
> **状态**：草案 V1，含 §9 待拍板决策点。
> **术语翻译**：租约 = 带有效期的任务占有权（到期自动失效）；心跳 = 执行者定期发出的「我还活着」信号；幂等 = 同一件事重复做一遍不会产生额外副作用；熔断 = 连续失败到阈值后自动停止并转人工。

---

## 1. 结论先行

1. **拆分方向成立**：workflow-manager 的项目定位是「做 dsh 的工作流插件」，任务登记/发号/收口/调度属于项目管理，两者职责确实应该分离。
2. **在线表格当总账可行，但不能当锁**：表格适合做「发号源 + 跨项目总账 + 人工视图」；**不适合**承担并发领取的原子互斥。这一条有明确的技术依据（§3.4），是本方案最重要的判断。
3. **你担心的两个协调问题，现有系统只解决了半个**：防重复已有实现，阻塞后接手**完全没有**能力。补齐方式是引入租约 + 心跳 + 超时回收，这是业界标准做法。

## 2. 业界做法参考（四类，含适用判断）

### 2.1 多 Agent 共享看板 + 原子租约（Hypertask 团队实践）

公开分享的多 Agent 共板经验，核心主张与你的诉求高度吻合：

- **认领必须原子**：多个 Agent 可能同时读到「待办」再同时去改，必须有一个「向服务端申请认领、成功才开工」的原子动作。
- **租约四要素**：任务 + 认领者 + **认领实例号** + **到期时间**。认领实例号容易被忽略——没有它，一个旧 Agent 重试后可能把新 Agent 的租约误释放。
- **长任务要心跳续租**：Agent 死了，到期即自动可回收。
- **每个 Agent 独立身份**：共享账号会让审计无法追溯「到底是谁改的」。
- **人的注意力收口到一个收件箱**：状态变更安静，只有需要人决策/审查/解阻塞时才打扰人。

**适用判断**：这就是你要的机制的成熟形态，建议直接采纳其四要素定义。

### 2.2 任务租约 + 心跳 + 收敛条件（中文实践总结，与本项目场景最接近）

一篇面向多 Agent 协作的实践总结，四条主张与你的痛点逐条对应：

| 主张 | 对你的意义 |
|---|---|
| 领取用**租约**而非永久锁 | 进程崩溃、网络中断、容器回收后**无需人工解锁**，到期自动可接管 |
| 心跳只证明存活，**不能证明成功** | Agent 卡在错误推理里但进程还在的情况，需要单独检测「有心跳无进度」 |
| 接管前先核对**副作用是否已发生** | 租约过期 ≠ 上一位什么都没做；新接手者必须先用幂等键查执行记录，已成功就推进，明确失败才重做，结果未知转人工 |
| 设置**收敛条件** | 最大交接次数、最大尝试数、总耗时预算，到上限转人工，防止「复核退回→重做→再退回」无限循环 |

**适用判断**：这四条应当直接写入我们的协调规则，尤其第四条——本项目已有「自动返工上限 3」的概念，需与交接次数上限合并考虑。

### 2.3 Hermes Agent v0.12.0 看板多 Agent（已落地产品，可作对标）

- 任务放共享看板，每个 Agent 作为**独立进程**自行认领、并行执行。
- 整体围绕本地数据库运转，每次认领是**原子事务**，竞争时只有一个能拿到。
- Agent 崩溃或超时后，调度器通过**进程存活检测自动回收并重新分配**。
- **连续失败三次触发熔断**，任务自动锁定等待人工介入。

**适用判断**：它的「三次熔断转人工」和我们现有的「自动返工上限 3」是同一量级的经验值，可互为佐证。

### 2.4 文件 + Git 作为协调层（gptodo，反面参考）

有团队用「Markdown 文件 + YAML 头信息 + Git 提交」做多 Agent 协调，主张简单可调试。但他们**明确接受的前提**是：Agent 基本顺序执行（间隔 2 小时）、无真正文件锁、规模 4 个 Agent 以内、冲突靠 Git 合并暴露。

**适用判断**：❌ **不适用于你的场景**。你要的是多机、多会话、真正的并发抢活，该方案的前提条件与你完全相反。仅作为「不要过度设计」的提醒保留。

### 2.5 在线表格作为主源（含关键限制）

**支持的一面**：表格做任务总账是广泛且有效的实践——单一位置、人工可读、格式长期可移植、跨项目统一视图、无需为每个项目搭一套服务。

**反对/限制的一面（必须正视）**：

| 限制 | 具体依据 |
|---|---|
| 并发写写冲突 | 在线表格提供的是**乐观锁**并发控制，非事务性；多方同时改同一格会冲突 |
| 官方明确建议 | 飞书开放平台建议「对单一多维表格同时只请求一次 API 写操作」 |
| 接口频率限制 | 批量写约 50 次/秒、单次最多 1000 条；触发限流会报错 |
| 查询能力弱 | 无原生 JOIN，筛选排序能力受限 |
| 一致性 | 属「强一致性要求不苛刻」的适用场景 |

业界给出的稳妥架构是：**表格作展示/协作层 + 专业存储作持久层**的混合架构。

**适用判断**：✅ 表格可以做**总账与发号**，❌ 不能做**并发锁**。这两件事必须分层。

## 3. 现状对照：我们缺什么

| 诉求 | 现有能力 | 判定 |
|---|---|---|
| 防重复施工 | 已有：认领靠「打标签 + 留言标记 + 二次回读确认」，后到者主动让位，口径是「宁可少开工，不可重复施工」 | ✅ 已有 |
| 阻塞后可接手 | **无任何时间维度**：无领取时间、无到期、无心跳、无超时回收。Agent 崩溃或阻塞后占有权**永久保留**，只能人工清 | 🔴 缺口 |
| 登记创建人 | 有 `origin_agent` 字段，但存在为空的历史记录 | 🟡 部分 |
| 登记领取人 / 领取时间 | **登记册中没有这两个字段** | 🔴 缺口 |
| 区分「卡住」与「在跑」 | 无 | 🔴 缺口 |
| 接手前核对已完成的动作 | 无幂等键设计 | 🔴 缺口 |

现有登记册字段包括：任务号、类型、远端锚点、来源、状态、优先级、环境组、分支、运行记录、合并信息、创建/更新时间、规格位置等**共 27 类**，但**不含任何归属与时效字段**。

## 4. 方案一：项目管理能力拆分到新仓库

### 4.1 拆分边界

| 归属 | 内容 | 理由 |
|---|---|---|
| **留在 workflow-manager** | 工作流插件本体、工作流蓝图、运行时、模板、插件开发与发布、可视化编辑器 | 这是它的产品定位 |
| **迁到新仓库** | 任务卡与登记册、发号、需求分析与立票、施工 runbook、验收与收口账本、批量调度、分支与工作区规范、工作流定义与执行计划 | 这些是项目管理能力，与具体工作流产品无关 |

### 4.2 拆分后的使用形态（解决「其他项目得克隆一套」）

- 新仓库提供**独立命令行工具**与**配置模板**，其他项目只需：① 指明自己属于哪个项目；② 接入同一个在线总账；③ 调用工具。
- 其他项目**不再需要克隆 workflow-manager 的代码**，也不需要复制脚本与文档。
- workflow-manager 自身作为**第一个接入方**验证链路，不再同时是「产品」和「管理工具」。

### 4.3 迁移路径（三步，避免一次性大手术）

1. **第一步**：新仓库先承接「登记 + 发号 + 协调」三项最痛的能力，workflow-manager 保留兼容入口。
2. **第二步**：迁移需求分析与施工 runbook，旧入口改为转发。
3. **第三步**：清理 workflow-manager 中的历史任务目录与脚本，保留归档索引指向新仓库。

### 4.4 拆分风险

- 🟡 **历史数据迁移**：现有登记册已有 27 类字段、数十条任务记录与归档三件套，迁移需保证任务号不重编、归档可追溯。
- 🟡 **在途任务**：当前有 25 张未关闭的任务票、多张在制合并单，切换期需冻结新开工或双写。
- 🟡 **跨仓库引用**：现有文档与脚本中大量路径引用需批量替换。

## 5. 方案二：在线表格作发号源与总账

### 5.1 推荐架构（三层，职责分离）

```
【第一层】在线表格 —— 权威总账
  发号源 · 跨项目总登记簿 · 人工视图 · 冲突裁决方
        ↓ 单向同步（表格为准）
【第二层】租约服务 —— 并发互斥层
  原子领取 · 心跳续租 · 超时回收 · 幂等记录
        ↓ 投影
【第三层】各项目的任务票 —— 辅助登记簿
  项目内可读 · 存放施工产物与讨论 · 不参与裁决
```

### 5.2 为什么必须分三层（关键判断）

🔴 **不要试图把「领取」直接做在在线表格上。** 依据：在线表格是乐观锁、官方建议单表同时只一次写、有频率限制。把高频的原子领取压到表格上，会同时踩「并发冲突」与「限流」两个坑。

正确分工：

- **表格负责低频、人工视角的事**：发号、状态总览、归属归属、优先级、跨项目视图。人打开就能看懂全局。
- **租约服务负责高频、机器视角的事**：谁正在占用、占用到什么时候、是否还活着、能否接管。
- **项目任务票负责承载施工产物**：代码变更、评审讨论、证据链，留在项目里最自然。

### 5.3 冲突裁决

- 一切冲突**以在线表格为准**（你的既定口径，正确且必要）。
- 同步方向：表格 → 租约服务 → 项目任务票，**单向为主**。
- 项目任务票上的状态**不得反向覆盖**表格；如需变更，必须先改表格再同步。
- 每次同步记录时间与作用范围，冲突时保留双方快照供人工复核。

### 5.4 🔴 发号必须单独处理（表格发号的隐藏风险）

表格里「取当前最大号 + 1」在多 Agent 并发时会**撞号**——两个 Agent 同时读到最大值，写出同一个号。

三种解法，建议选 B：

| 选项 | 做法 | 评价 |
|---|---|---|
| A | 表格直接自增 | ❌ 并发撞号，不可靠 |
| B | **号段预分配**（推荐） | 表格批量预留号段给各机器/各项目，本地在号段内顺序使用，用完再申请；撞号概率为零，表格写入次数大幅下降 |
| C | 租约服务发号后回写表格 | 可靠，但发号权威转移到服务层，与「表格为准」口径略有张力 |

### 5.5 表格选型建议

- **腾讯文档**：当前已具备接入条件，可立即试点。
- **飞书多维表格**：能力更接近数据库（关联字段、视图、仪表盘），但**需先完成授权接入**，且限流与单表并发限制更明确。
- 建议先用**已接入的那一个**做试点验证字段与同步链路，跑通再决定是否迁移。选型是可逆决策，不建议在试点前花时间比选。

## 6. 方案三：多机多 Agent 协调机制

### 6.1 核心机制：租约 + 心跳 + 超时回收

| 机制 | 作用 | 解决你的哪个问题 |
|---|---|---|
| **租约**（带到期时间的占有权） | 领取时写入「谁、何时、到期时刻、第几次尝试」 | 谁领了、何时领的 |
| **心跳** | 执行中定期续期，报告阶段与进度 | 区分「卡住」与「在跑」 |
| **超时回收** | 到期未续期即视为释放，他人可接管 | Agent 崩溃/阻塞后能接手 |
| **主动释放** | 遇阻塞主动交还，并写明阻塞原因 | 主动交还比等待超时更快 |
| **熔断** | 连续失败达上限 → 锁定转人工 | 防止无限接力（建议阈值 3，与现有返工上限一致） |

### 6.2 登记字段设计（在现有 27 类基础上新增）

| 字段 | 业务含义 | 填空时机 |
|---|---|---|
| 创建人 | 谁提的需求 | 立票 |
| 创建机器/会话 | 从哪台机器、哪个会话提出 | 立票 |
| 领取人 | **当前谁在执行** | 领取 |
| 领取机器/会话 | 在哪台机器、哪个会话执行 | 领取 |
| 领取时间 | 何时开始占用 | 领取 |
| **租约到期时刻** | 占到什么时候 | 领取 + 每次心跳刷新 |
| **最后心跳时刻** | 最后一次报告还活着 | 心跳 |
| 当前阶段 | 定义/施工/审查/测试/验收/收口 | 每次阶段变更 |
| 尝试次数 | 第几次接手 | 每次领取累加 |
| 阻塞原因 | 主动交还时写明卡在哪 | 主动释放 |
| 版本号 | 防止旧的写覆盖新的 | 每次状态变更 |

### 6.3 四条硬规则

1. **领取必须原子**：只有「当前无人占用」或「租约已过期」两种状态才允许领取成功。同时申请时只有一个成功，其余重新排队选别的任务。
2. **心跳只证明活着**：必须在每次续租时校验**任务版本与持有者仍匹配**；一旦发现自己已不是持有者，**立即停止后续动作**，不得「把剩下步骤做完」。
3. **接管前先核对已完成动作**：租约过期 ≠ 上一位什么都没做。新接手者先用**幂等键**（任务号 + 步骤号）查执行记录——已成功则推进，明确失败才重做，结果未知转人工。
4. **收敛条件**：设置最大接手次数、最大尝试数、总耗时预算；任一触顶转人工，不再继续消耗资源。

### 6.4 与现有机制的衔接

- 现有的「防重复」实现（标签 + 留言标记 + 二次回读 + 后到者让位）**保留**，它解决的是「同时抢」；新增的租约解决的是「占了不放」。两者互补，不冲突。
- 现有的「自动返工上限 3」与建议的「熔断阈值 3」需合并为**同一个计数器**，避免两套额度各算各的。

## 7. 分支规范与本方案的关系

《分支管理规范》解决的是「一条任务线怎么走完」，本方案解决的是「多条任务线归谁、谁在跑、卡了怎么办」。两者是上下层：

- 分支规范：任务是**怎么落地的**（一票一线一单、主干稳定）
- 本方案：任务是**怎么分配与回收的**（发号、总账、租约、接手）

**新增衔接点**：任务分支的创建时机与领取动作绑定——**领到租约才建分支**，避免为一个没人认领的任务预先产生一堆分支（当前 30+ 工作副本的失控与此有关）。

## 8. 落地顺序建议

| 阶段 | 内容 | 前置 |
|---|---|---|
| 一 | 租约 + 心跳 + 超时回收机制（补最痛的缺口） | 无，可立即开工 |
| 二 | 在线表格总账试点（选一个已接入的平台，跑通发号与状态同步） | 阶段一的字段定稿 |
| 三 | 拆分新仓库，迁登记/发号/协调 | 表格链路跑通 |
| 四 | 迁需求分析与施工 runbook，清理旧仓库 | 阶段三稳定 |

**理由**：先补协调机制（最痛、最独立），再上表格（依赖字段定稿），最后拆仓库（依赖前两者稳定、改动面最大）。反过来做会在迁移中途反复改结构。

## 9. 待拍板决策点

### 🔴 决策一：表格是否承担并发领取

- **A · 分层（推荐）**：表格管发号与总账，另设租约服务管并发互斥 — 收益：规避限流与乐观锁风险；成本：多一层服务；风险：低
- **B · 表格全包**：领取也写表格 — 收益：架构最简单；成本：需实测限流；风险：**高**，并发冲突与限流双踩

### 🔴 决策二：发号方式

- **A · 号段预分配（推荐）**：零撞号、写入少
- **B · 服务发号回写表格**：可靠但发号权威转移
- **C · 表格直接自增**：❌ 不推荐，并发必撞号

### 🔴 决策三：拆分节奏

- **A · 先补机制后拆仓库（推荐）**：风险最低，每步可独立验收
- **B · 一次性拆分**：快，但在途 25 张票与多张在制合并单需全部冻结，风险高

### 🔴 决策四：表格选型

- **A · 先用已接入的腾讯文档试点（推荐）**：今天就能开始
- **B · 先接入飞书多维表格再开始**：能力更接近数据库，但需先完成授权
