# 分支管理规范（Branch Management Policy）

> **定位**：本文件是团队「多任务并行 + 主干稳定 + 一票一单」的协作规范，约束需求分析、立票、施工、验收、收口全链路。
> **业务翻译**：分支 = 一条独立的并行工作线（该任务的专属工作副本）；PR = 合并申请单；issue = 任务票；主分支（main）= 对外发布的正式版本线。
> **状态**：草案 V1，待负责人拍板 §8 三个决策点后生效。

---

## 1. 为什么需要这套规范（现状证据）

| 痛点 | 现状证据（2026-09-22 实测） | 业务后果 |
|---|---|---|
| 主干被在制内容污染 | 主检出 `main` 上存在 **20+ 项未落账改动**，横跨任务卡、登记册、归档目录、插件包 | 任何时刻都无法从主干切出一个干净版本对外发布；发布前必须先人工分辨哪些改动是"半成品" |
| 定义与施工挤在同一条主干上 | 需求分析产物直接落在主干工作目录，需靠后续合并单回收 | 多任务并行时改动互相夹杂，验收后难以单独摘出某一票的成果 |
| 一票多单，追踪断裂 | CHORE-286 对应合并单 #292（实施）+ #295（收口）；CHORE-110 对应 #255（代码）+ #294（收口）；FEAT-283 对应 #285（立票）+ #287（元数据修正） | 「这一票到底做了什么」要翻 2–3 个合并单才能拼出全貌；收口审计与回溯成本高 |
| 分支命名八套并存 | `dev-<票>-r1` / `chore/<slug>` / `fix/<slug>` / `docs/<slug>` / `diag/...` / `sync/...` / `vwf/run/*` / `dev-tmp-*` | 无法从分支名反查属于哪一票；自动化脚本与人工都对不齐 |
| 并行副本失控 | 本机同时存在 **30+ 个工作区副本**，含大量 `dev-tmp-*`、`diag/` 一次性副本 | 机器资源与人工注意力被稀释，收口时无法判断哪个副本还有效 |

---

## 2. 核心原则（三条，冲突时按此顺序裁决）

1. **主干永远可发布**：主分支只接受「已验收并收口」的成果。任何未验收的中间状态（含需求分析草稿、立票登记、施工半成品）禁止出现在主干。
2. **一票 · 一线 · 一单**：一张任务票 = 一条任务分支 = 一个合并申请单。任务的全生命周期产物（定义、代码、证据、收口账本）都在同一条线上累积，最终一次性合并。
3. **主干是共享资源，冲突必须前置消解**：任务线在开工前与合并前各对齐一次主干；中心账本类文件采用「合并瞬间自动重放」而非手工编辑（见 §6）。

---

## 3. 分支命名规范

统一为**一套**命名，删除其余全部历史形态：

| 类型 | 命名格式 | 示例 | 生命周期 |
|---|---|---|---|
| 任务主线 | `task/<票号>-<简短描述>` | `task/CHORE-293-github-82-epic` | 立票时创建，合并后删除 |
| 派生子票 | `task/<子票号>-<简短描述>` | `task/CHORE-294-d8-archive` | 同主线（子票即独立票，独立线） |
| 临时探针 | `scratch/<票号>-<用途>` | `scratch/CHORE-273-m4-probe` | **永不合并**，取证后 24 小时内删除 |
| 镜像回灌 | `sync/<来源>-<短标识>` | `sync/cnb-18bb0f84` | 保留现有形态（灾备通道专用） |

**硬性要求**：

- 分支名必须能反查票号；无法反查的分支（如 `dev-tmp-*`）一律视为临时副本，限期清理。
- 同一票的**第 2、3 轮返工不新建分支**，在原任务线上继续提交。轮次标识（如 `r1`/`r2`）只作为运行记录编号，不再进入分支名。
- 父票与其子票**各自独立分支**（子票本就是独立任务票，享有独立验收与合并）。父子关系靠任务票的「前置依赖」字段表达，不靠分支结构表达。

## 4. 四阶段流程

### 阶段一 · 立票与需求分析（定义）

| 步骤 | 动作 | 落点 |
|---|---|---|
| 1 | 建任务票，取得票号 | 远端任务票（唯一发号方） |
| 2 | 创建任务分支 `task/<票号>-<描述>`，**基线取主干最新** | 分支 |
| 3 | 需求分析与规格编写 | **任务票正文与评论**（对外可见的权威载体） |
| 4 | 规格文件落盘 | 任务分支上的 `docs/tasks/specs/<票号>-<slug>/` |
| 5 | 定义检查通过、人工确认基线 → 打「可开工」标签 | 远端任务票 |
| 6 | 🔴 **不提合并申请单** | — |

**关键变化**：定义产物不再单独进主干。「可开工」的判定信号是**远端任务票上的标签**，不是主干上的登记文件。因此定义阶段主干零改动。

> 若远端不可达（本地轨道），定义产物落在本机任务分支上，并在远端恢复后补建任务票；此期间该票对本机以外的协作者不可见，属于已知的可发现性降级。

### 阶段二 · 开工与施工

1. 开工前：把主干最新成果接到自己的任务线上（对齐一次）。
2. 施工全程只在该任务的工作副本内操作，禁止在主检出或其他任务副本里"顺手"执行任何写操作。
3. 施工期间如需调用共享设备（如开发用的可视化服务实例），必须带本票命名空间前缀登记，用完注销并释放。
4. **并行上限**：同一台机器同时激活的任务线 **≤ 3 条**，其余排队。超出上限时新任务不得开工——这是资源约束，不是建议。

### 阶段三 · 验收

1. 验收在任务分支上进行，验收证据落在该分支。
2. 验收三种结论：通过 / 退回 / 有条件通过。退回 → 在**原分支**继续修改，不新建分支、不新建合并单。
3. 自动返工上限 3 次；超出则停止自动循环，呈递人工。

### 阶段四 · 收口与合并

1. 收口三件套（任务卡、任务规格、证据摘要）与登记册更新**全部在本票的任务分支上完成**，不另开分支、不另开合并单。
2. 合并前再对齐一次主干，确认无冲突后发起**本票唯一的一个合并申请单**。
3. 合并申请单必须写明：对应票号（单内显式写 `#<票号>`，形成机器可解析的绑定）、验收结论、验证命令、是否影响主干对外行为。
4. 合并后：删除该任务分支；关闭任务票。
5. **例外**：合并后补登的纯账本修正（如发现登记信息写错）不新开合并单，改为并入下一张相关票的合并单，或由负责人走一次性的批量账本合并单（此类单须在标题标注「批量账本」，不绑定单票）。

## 5. 任务票与合并申请单一一对应规则

| 规则 | 说明 |
|---|---|
| **R1 · 一票一单** | 一张任务票有且仅有一个交付合并单。定义、实施、收口全部内容都在其中。 |
| **R2 · 显式绑定** | 合并单正文中必须包含 `#<票号>`，合并即自动关票。禁止靠人工记忆关联。 |
| **R3 · 禁止拆单** | 不得把「文档单」「实施单」「收口单」拆成三个合并单——这正是当前追踪断裂的根因。 |
| **R4 · 一单不跨票** | 一个合并单只解决一张票。跨票的批量账本操作必须标注为「批量账本」且不含功能改动。 |
| **R5 · 单票不并多线** | 一个合并单只从一条任务分支合入。 |

**自动校验建议**：在合并前检查环节加一条断言——同一票号在近 90 天内若已存在已合并的交付单，本单必须被拒绝或显式标注为「返工重开」。

## 6. 并行冲突治理（中心账本问题）

任务登记册与看板是**全局共享的单文件**，多任务并行时必然冲突。这是并行开发的头号工程风险。

**处理口径**：

1. 任务分支**不手工编辑**全局登记册的他人条目，只追加本票条目。
2. 合并时若中心账本冲突：采用「以主干为准 + 脚本重放本票条目」的机械解法，**不允许人工逐行解冲突**（人工解冲突是历史事故来源）。
3. 看板文件由脚本整体重写，禁止手工编辑。

**中期改进方向**（需另立票）：把全局单文件登记册拆为「每票一个登记文件」，从根本上消除写冲突。此项见 §8 决策三。

## 7. 角色职责与检查清单

| 角色 | 职责 |
|---|---|
| 负责人（人） | 拍板需求基线、验收三态、合并授权、例外批准 |
| 定义阶段执行者 | 建票建分支、写规格、确保未决产品事项归零 |
| 施工执行者 | 分支内施工、自验证、提交验收 |
| 收口执行者 | 归档三件套、登记册更新、发起唯一合并单 |

**合并前自检清单**（五项全过才允许发起合并单）：

- [ ] 分支名符合 `task/<票号>-<描述>`
- [ ] 已对齐主干最新成果，无未解决冲突
- [ ] 验收结论为「通过」或「有条件通过」且遗留项已登记
- [ ] 收口三件套齐备
- [ ] 合并单正文含 `#<票号>`，且本票此前无已合并交付单

## 8. 待拍板决策点

### 🔴 决策一：定义阶段产物放在哪里

| 选项 | 成本 | 收益 | 风险 |
|---|---|---|---|
| **A · 定义产物随票走（推荐）** | 需改造一处：让任务调度以远端票标签为施工信号，而非读主干上的登记文件 | 主干立即可做到零污染；一票一单天然成立 | 调度链路需一次改造；远端不可达时任务对本机外不可见 |
| B · 定义产物先合并，施工再开单 | 无需改造 | 任务在主干上立刻可见 | 一票两个合并单，违反 1:1；主干仍被文档改动频繁打扰 |
| C · 维持现状 | 零成本 | 无 | 三个痛点全部保留 |

**推荐 A**：只有它同时解决「主干稳定」与「一票一单」两个目标。

### 🔴 决策二：并行上限

- 选项 1：同机同时激活 ≤ 3 条任务线（推荐）——资源可控，收口边界清晰
- 选项 2：不设上限，仅靠命名空间隔离——吞吐高，但当前 30+ 副本的失控状态会重现

### 🔴 决策三：全局登记册是否拆分

- 选项 1：近期维持单文件 + 脚本重放（推荐先做）——成本低，可立即缓解
- 选项 2：另立一票改造为「每票一文件」——彻底消除冲突，但需专门工期

---

## 9. 迁移步骤（建议分三步走）

1. **第一步（立即，无改造）**：统一分支命名 + 合并前自检清单 + 并行上限。这一批动作不依赖任何脚本改造，今天即可执行。
2. **第二步（一周内）**：切换「定义产物随票走」，同步改造调度信号来源（决策一 A）。
3. **第三步（排期）**：历史存量分支清理（按票号反查，无法反查的限期清理）+ 决策三的登记册改造。

---

## 10. 与现有规则的关系

- 本规范**不改变**任务状态机、验收三态、自动返工上限、证据链要求。
- 本规范**改变**的是：定义产物的落点与合并时机、分支命名、合并单数量。
- 需求分析阶段「规格必须入库」的硬要求**依然有效**，只是入库时机从「定义完成时进主干」改为「随交付单合并进主干」；施工期间规格同时可从任务票与任务分支读到。
