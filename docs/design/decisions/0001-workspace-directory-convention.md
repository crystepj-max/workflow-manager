# 0001. 采用多工作区并行开发的目录组织约定

## 状态

accepted（2026-09-12）

## 背景与约束

本仓库采用「一任务一分支一独立工作区（git worktree）」的并行开发模式，工作区由脚本与 AI Agent 自动创建。运行数周后出现四类问题（实测，2026-09-12）：

1. 工作区分散在 **6 个根目录**（仓库内 `.scratch/worktrees/`、三处 DSH 运行时 workspaces、编辑器 worktrees、系统临时目录），`git worktree list` 达 31 条；
2. 每个工作区内部各自再生一份过程产物目录，产物随工作区数量线性复制；出现工作区套工作区；
3. 过程产物无生命周期，单个在制任务（LOC-013）的过程产物已达 **1.3 GB**；
4. 有过程产物漏网入库（`.scratch/` 下 5 个被跟踪文件）；另有孤儿登记与指针错乱目录各一处。

根因不是命名不整齐，而是三条：**缺少单一锚点**（用相对路径推导产物位置，而工作区是仓库完整副本）、**没有生命周期**（任务终态与产物删除之间无因果关系）、**约束分散且互不覆盖**。

约束：

- 项目已被外部运行时的**十余个工作区以绝对路径指回主检出**（`gitdir:` 绝对路径实测）；
- 外部代码托管暂不可用（无法创建 PR），但恢复后需补登完整记录；
- 仓库使用 **squash 合并**（合并提交父数=1），分支祖先判定不可作为合并依据；
- 已有收口角色 `dsh/roles/closeout.md` 与 `scripts/cwf-*.mjs` 等既有机制，不应另起并行体系。

## 决定

1. **工作区根采用相邻容器**：主检出路径不变，全部工作区平铺于 `../workflow-manager-worktrees/`。禁止嵌套、禁止位于仓库目录内。
2. **命名全部派生**：`TASK_ID`（`LOC-<序号>` / `CWF-<issue号>`）为唯一键，`RUN_ID = <task_id 小写>-r<n>`，分支 `dev-<run_id>`，工作区目录名 = 分支名；过程产物落 `<主检出>/.task-runs/<TASK_ID>/<RUN_ID>/`。
3. **过程产物锚定主检出**：不论从哪个工作区执行，产物一律写回主检出（用 `git rev-parse --git-common-dir` 解析）。工作区因此完全可丢弃。
4. **产物分三级**：过程产物（收口即删）／证据（合并后留摘要，明细保留 7 天）／最终产出（永久入库）。
5. **到期清理用机会式 + 机器闸门**，不用定时任务：挂在「开工顺带清 / 收口顺带清 / 校验命令失败」三个触发点上。
6. **收口分两阶段**：托管暂停期「删工作区、留分支 + 归档必要文档六件」；托管恢复期「完整同步后删分支、免留过程记录」。判据是**工作区可再生、分支不可再生**。
7. **归档位置唯一**：`docs/tasks/archive/<TASK_ID>/`（任务卡 + 规格终版 + 证据摘要三件）；`docs/tasks/specs/` 内容并入后废弃。
8. **约定本身与项目无关**：以通用标准模板 + 项目实例化说明两份文件维护；校验项 D-1~D-10 由 `scripts/validate-workspace.mjs` 机器执行。

## 后果

**正面**

- 一个任务的产物物理上只有一份，可定位、可备份、可整体删除；工作区可随时重建，删除不损失不可替代内容。
- 嵌套在机制上不可能再发生（创建路径也走同一锚点）。
- 保留期的正确性不依赖「有人记得」，也不依赖「定时器活着」。
- 约定可被机器检查，不依赖人工自觉；且换项目只需替换占位符。

**代价 / 新增的负担**

- 需要改造既有脚本（路径解析、归档件数、收口编排），并保持一版向后兼容。
- 创建与回收入口需从当前的「2 个创建入口 + 4 个回收入口」收敛为各一个入口，属跨脚本改动。
- 新增 D-1~D-10 校验会先**大面积报错**（现存违规），需先给出违规基线、再按批次收敛；在收敛完成前不宜直接接入 `npm run validate` 的阻断路径。

**风险与缓解**

- 🟡 **迁移期误操作**：缓解——只读报告 → 人工确认 → 每批 ≤5 个 → 执行后复核登记数与磁盘一致；删除工作区用 `git worktree remove`，不删分支。
- 🟡 **并发作业覆盖**：实测发生过「同一工作区另一会话正在作业，导致清理目标被先行删除、对登记册的修改被重写覆盖」。缓解——涉及共享文件或共享工作区的批次，必须在无并发写入时执行。
- 🟡 **误删唯一副本**：实测发生过「工作区检查为 0 未提交改动、内部却躺着 21 个未归档证据文件」（过程产物目录被忽略规则排除，对 `git status` 不可见）。缓解——删除前必须单独做「内部过程产物 ↔ 归档位置」核对（存在性 + 条目数一致），未归档的先补归档。

## 被否决的备选

- **容器下沉布局（`<容器>/base/` + `<容器>/worktrees/`）** —— 否决：会改变主检出绝对路径，而外部运行时创建的十余个工作区均以绝对路径指回主检出（`gitdir:` 实测），迁移后全部失效需逐个修复。相邻容器以零迁移成本获得同样收益。
- **保留工作区于仓库内（`.scratch/worktrees/`）** —— 否决：不解决嵌套根因（相对路径仍会被解析到错误位置），且 GB 级产物长期留在仓库目录内。
- **到期清理由定时任务执行** —— 否决：失败是静默的（调度挂了无人知），且跨机器与多运行环境难以覆盖。
- **统一用分支祖先关系判定「是否已合并」** —— 否决：本仓库使用 squash 合并，该判定会把已合并任务误报为未合并。改用登记册记录的合并提交是否在主分支上。
- **为每套工作流单独实现工作区隔离** —— 否决：该机制不属于任何单一工作流。v0.1 产品规格已将「执行入口」列为四套工作流的**共享能力**，实测四套蓝图内亦无任何分支/工作区创建逻辑（创建在蓝图之外的脚本层）。应作为共享契约维护。
- **让工作区隔离机制依赖某单一 Agent 的能力** —— 否决：同一个 Run 的多个节点本就由不同 Agent 执行，机制必须 Agent 中立；跨 Agent 的适配（规则投递方式、权限模式、资源隔离）作为接口约定由各使用者自行解决。
