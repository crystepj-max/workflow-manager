# VWF 开发模式 / 产品模式双轨

状态：Accepted for v0.1.0  
关联：[Issue #53](https://github.com/crystepj-max/workflow-manager/issues/53)

## 1. 目标

VWF 使用同一份 `packages/dsh-visual-workflow/src/` 同时服务两种不同目的：

| 模式 | 目的 | DSH Home | 插件形态 | 可否作为发布证据 |
|---|---|---|---|---|
| 开发模式 | 版本内快速反馈 | `~/.dsh-workflow-dev` | 进程临时动态插件 | 否 |
| 产品模式 | 证明版本可发布 | 产品 `$DSH_HOME` | 正式组合包 | 完整验收后可以 |

核心原则是：开发模式负责快，产品模式负责真；物理隔离保证净。两者不能互相替代。

## 2. 设计决策

### 2.1 采用方案 A：独立开发 DSH Home

开发 DSH 的 `web` Profile 由 DSH 默认模板在首次启动时初始化，不安装正式
`dsh-visual-workflow` 组合包，不自动复制产品环境的凭据、私有配置或运行状态。产品 DSH
保留现有正式安装，开发过程中不修改其插件配置。

该方案避免正式版与动态版同时注册入口、RPC 或工具，也使发布验证天然发生在没有开发态残留的
另一进程中。开发环境与产品环境可能存在配置差异，所以产品 E2E 不能省略。

### 2.2 不采用方案 B：同一 Profile 来回切换

在产品 Profile 中反复卸载正式包、挂载动态包再恢复正式包，虽然实现少，但容易产生双挂载、
状态污染和错误恢复，还会影响复用该产品环境的其他应用。

### 2.3 不采用方案 C：只生成正式包并刷新 UI

该方案只能缩短部分 client 迭代，host 更新仍属于产品安装流程，无法建立完整的动态双半包闭环。

### 2.4 v0.1.0 范围收敛

第一版不实现“源码一保存，本地命令立即操控 DSH 动态插件”。DSH 公开稳定的动态插件能力存在于
DSH 会话中，因此 `npm run dev:plugin` 只负责：

1. 固定并检查独立开发 Home；
2. 拒绝显式指向产品 Home；
3. 报告 web Profile、正式包冲突和开发进程状态；
4. 根据当前 host + client 生成联合版本标识；
5. 给出使用公开 Cordis 工具完成同步与清理的步骤。

文件监听、未公开接口和本地自动远程控制均不在 v0.1.0 范围。链路稳定后可另行评估自动化。

## 3. 开发模式生命周期

### 3.1 首次进入

```text
npm run dev:plugin
  → 确认 Home 隔离且开发 Profile 无正式 VWF
npm run dev:plugin -- start
  → DSH 用默认模板初始化开发 web Profile
  → 进入 DSH Cordis 动态插件开发会话
```

开发入口只向 `~/.dsh-workflow-dev` 写入启动所需状态和 PID 标识，不读取或修改产品 Profile。
如果 shell 显式设置了其他 `DSH_HOME`，入口立即失败，防止误连产品环境。

### 3.2 每次源码修改

```text
读取当前 src/host.js + src/client.js
  → 计算 vwf-dev-<联合哈希>
  → cordis_define 在同一个 Package 中提交 host + client
  → cordis_run 整体更新
  → cordis_inspect_self 核对当前 Package / Run 版本
  → 查看界面和宿主行为
```

联合哈希是开发版本标识，不是产品版本号。任一半变化都会得到新标识，从而能识别旧版本或只更新
一半的错误。Cordis update 会停止旧 Run，因此 host 和 client 必须始终属于同一个 Package；
禁止分别定义或更新。

一个版本期间开发 DSH 保持运行。连续修改只替换动态 Package，不重启进程。

### 3.3 停止与清理

在开发会话中对当前联合版本执行公开的 `cordis_stop`，再执行 `cordis_undefine`。动态插件为
进程临时能力，开发 DSH 重启后消失属于正常生命周期。开发 Home 中不持久安装正式 VWF，因此
无需改动产品安装配置，也不会在产品模式形成双挂载。

## 4. 产品模式与发布闸门

`npm run release:verify` 顺序复用现有规则：

1. `npm run generate`；
2. VWF `npm run build`；
3. VWF `npm run check:dist`；
4. 根 `npm test`；
5. 根 `npm run validate`。

任一步骤失败都会终止并返回非零退出码，且指出失败阶段。全部通过只说明源码、正式产物和机器
校验一致，状态为发布候选；命令不会宣布 Release Ready。

随后必须：

```text
关闭开发 DSH
  → 完整关闭产品 DSH 的旧进程
  → 从产品 $DSH_HOME 重新启动
  → 确认正式 VWF 从真实安装路径加载
  → 验证模板库、编辑器、看板和本版本功能
  → 完成至少一次真实工作流 E2E
  → 人工验收
```

只有机器闸门、干净产品进程、真实安装加载、E2E 和版本功能验收全部通过，才可认定
Release Ready。

## 5. 产品验收失败回退

产品模式发现问题后，当前候选及其验收证据立即失效：

```text
产品验收失败
  → 回开发模式修改 src/
  → 用新的联合动态版本快速验证
  → 重新执行 release:verify
  → 重新启动产品 DSH
  → 重新执行完整产品验收
```

禁止直接修改 `dist/`、刷新产品页面后沿用原验收，也禁止把动态开发态结果补作发布证据。

## 6. 验收口径

### 快

- 同一开发 DSH 进程中连续完成至少五次“修改 → 联合更新 → 查看”，不重启；
- 至少包含一次纯 client 界面修改和一次 host 行为修改；
- 每次核对联合版本，host 与 client 不错配。

### 净

- 开发 Profile 没有正式 VWF 组合包；
- 可明确停止、清理动态插件，重启后动态态消失；
- 产品 Profile 的插件安装配置在开发周期内保持不变；
- 产品 DSH 中没有动态版与正式版双挂载。

### 真

- 正式产物由当前 `src/` 重新生成且新鲜度检查通过；
- 完整项目校验通过；
- 全新产品 DSH 进程从真实安装路径加载正式 VWF；
- 真实工作流 E2E 与版本功能验收通过；
- 至少演练一次产品验收失败后的完整回退与重新验收。

真机演练证据由测试 / 验收环节在受控环境中记录，机器脚本不能代签。
