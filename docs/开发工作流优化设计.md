# 开发工作流优化设计：GitHub Issue 驱动的双分支开发流程

> 本文档描述基于 gold-band 现有开发工作流的优化方案。适用于希望「需求先人工确认、issue 驱动、自动开发、超限回人工」的软件开发场景（如 sts2-autotest 这类项目）。
>
> 关联交付物（本仓库已统一为蓝图单一事实源，见 `docs/design/blueprint-schema.md`）：
> - 工作流模板：[`templates/dev-workflow-2-0.json`](templates/dev-workflow-2-0.json)（蓝图，生成器产出双入口）
> - 调度节点角色提示词：`dsh/roles/dispatcher.md`（DSH 侧，原 gold-band `src/prompts/...` 已迁移）
> - 人工验收报告要求：`dsh/roles/accept.md`

---

## 1. 设计目标

针对 sts2-autotest 项目实际运行暴露的三个问题做优化：

1. **需求沟通与自动开发耦合**：原工作流首个节点是「需求访谈」（AI 扮演访谈者澄清需求），需求模糊时 AI 反复追问，占用工作流轮次、效率低。改为：需求沟通剥离为工作流外的人工环节，确认好的需求以 GitHub issue 为输入。
2. **打回无上限**：原工作流审核/测试不通过打回开发，轮次无上限，任务可能无限循环。改为：打回上限 9 轮，超限回到调度节点分析，由人工判断拆分或介入。
3. **收口与验收边界不清**：原收口环节也会触发打回。改为：收口不打回，仅人工验收不通过时例外；人工验收时输出通俗验收报告，降低验收门槛。

🟢 **用户收益**：需求确认环节回到人工掌控；自动开发有明确的失败出口（9 轮超限即停止，不再无限烧轮次）；验收报告通俗易懂，非技术人员也能验收。

## 2. 工作流总览

```
[人工环节] 需求沟通确认
    │  沟通确认后的需求在 GitHub 创建 issue（须含三要素）
    ▼
[调度节点] dispatcher ──三要素齐全──▶ [开发节点] dev
    │                              │
    │ 三要素缺失                     │ 完成
    ▼                              ▼
 打回人工（任务失败，           [分流判定] route
 补齐 issue 后重新调度）          │ 需要集成测试 │ 无需
                          ▼            ▼
                    [测试] test      [审核] review
                      │ 通过          ▲ 通过
                      │              │
                      ▼              │
                  [审核] review ─────┘
                      │ 通过
                      ▼
              [人工验收] accept ──通过──▶ [收口] closeout ──▶ 结束
                      │ 不通过（唯一例外，打回开发）
                      ▼
                   [开发] dev
```

**两条分支**（由调度节点判定）：
- 需集成测试：`开发 → 测试 → 审核 → 人工验收 → 收口`
- 无需集成测试：`开发 → 审核 → 人工验收 → 收口`

**打回规则**：
- 测试不通过 → 打回开发修复
- 审核不通过 → 打回开发修复
- 人工验收不通过 → 打回开发修复（唯一例外，见 §4）
- 三要素缺失 → 打回人工（补齐 issue 后重新调度）
- 收口不因 AI 判定打回，正常完成即结束

## 3. 节点职责

| 节点 | 类型 | 职责 | 判定方式 | 思考强度 |
|------|------|------|----------|----------|
| 调度（dispatcher） | worker | 以 GitHub issue 为输入，校验三要素（任务目标 / 涉及范围 / 验收标准），判定是否需要集成测试；超限重调度时给出拆分建议；兼任分流转发 | AI 输出验证：`complete == true` 即通过 | 高 |
| 开发（dev） | worker | 独立分支 + 测试驱动实现，满足质量闸门，产出 dev-report.md | 默认成功（完成后才被下游判定） | 中 |
| 分流（route） | worker | 读取调度结论，输出是否需要集成测试（共用调度角色） | AI 输出验证：`need_integration_test == true` | 低 |
| 测试（test） | worker | 执行集成测试，证据驱动判定，产出 test-report.md | AI 输出验证：`result == true` | 高 |
| 审核（review） | worker | 对照验收标准独立双轴审查（需求符合性 + 代码质量），产出 review-report.md | AI 输出验证：`result == true` | 高 |
| 人工验收（accept） | worker | 产出通俗验收报告 acceptance-summary.md + 严格报告 accept-report.md，等待人工确认 | 人工 check（manual_check） | 中 |
| 收口（closeout） | worker | 一致性收口、交接产物汇总（cleanup-report.md）、临时工作区清理 | 默认成功（不打回） | 低 |

**三要素定义**（调度节点校验标准）：
- **任务目标**：这个任务要交付什么结果？一句话说清，不含歧义。
- **涉及范围**：改动影响哪些文件/模块/服务？哪些明确不做？必须有边界。
- **验收标准**：怎样才算完成？必须可操作、可验证、可复现。

🔴 **决策点已确认**：调度节点对三要素缺失的处理是「如实判定缺失并打回人工」，不自行追问补齐（与旧「需求访谈」节点的本质区别）。

## 4. 关键机制

### 4.1 三要素门禁（需求 1、2）

- 工作流输入 = GitHub issue（人工沟通确认后创建）。
- 调度节点读取 issue 原文，逐项校验三要素。
- **任一缺失** → 调度节点判定失败 → 任务以失败结束，失败原因明确列出缺失要素与补齐建议 → 人工补齐 issue 后重新调度。
- **全部满足** → 进入开发环节，调度结论（目标/范围/验收标准）作为开发节点的输入。

🟢 **用户影响**：需求不合格时不会浪费自动开发轮次，直接在调度节点被拦下。

### 4.2 双分支 + 9 轮打回（需求 3）

- 调度节点在分析时判定「是否需要集成测试」。
- 需要 → 走 `开发→测试→审核→人工验收→收口`；不需要 → 走 `开发→审核→人工验收→收口`。
- 测试/审核不通过均打回开发修复，**最大 9 轮**（工作流控制层 `max_attempts = 9`）。
- **9 轮仍不通过** → 任务以「修复轮次超限」失败结束，完整保留失败记录。
- 人工重新调度或拆分任务后，调度节点会自动读取历史失败记录，在分析中给出「失败归因 + 拆分建议 + 人工介入建议」（见 §4.4）。

🔴 **决策点已确认**：9 轮超限采用「失败后人工重新调度」方案（零开发、纯配置），不新增「超限自动跳回调度节点」的产品能力。当前 gold-band 的能力边界是「超限即任务失败并保留记录」，人工在任务列表重新调度或拆分即可。

🟡 **风险提示**：若未来需要「超限后工作流内自动回到调度节点分析」的无人工触发版本，需要给 gold-band 增加「超限后跳转指定节点」的流转能力，属于产品开发，不在本次配置范围内。

### 4.3 人工验收前置 + 收口不打回 + 通俗验收报告（需求 4 的 2、3 条）

- **人工验收独立成节点**：审核通过后先进入人工验收（accept 节点，人工 check 判定），验收通过才进入收口；验收不通过 → 打回开发修复。
- **收口环节不打回**：收口（closeout）只做一致性收口、交接产物汇总、临时工作区清理，默认成功，不设置打回边。
- **仅人工验收不通过时例外**：从验收环节打回开发是唯一允许的打回路径。
- **人工验收报告**：accept 节点产出两份报告：
  - `accept-report.md`：面向 AI 的严格验证报告（逐条验收标准状态 + 证据来源 + 裁决 PASS/FAIL/INCOMPLETE）。
  - `acceptance-summary.md`：**通俗版验收报告**，包含三部分：
    1. **任务目标**：一句话说明要解决什么问题。
    2. **达成情况**：逐条验收标准标注 ✅/⚠️/❌，附人话解释。
    3. **人工验收可以这样确认**：给出「打开看 / 动手试 / 跑一下 / 看证据」等可操作的确认方式。

🟢 **用户收益**：验收不再依赖技术背景，按报告给出的确认方式操作即可判断是否通过；收口环节不被 AI 判定打回，流程更快收敛。

### 4.4 思考强度可配置（需求 4 的 1 条）

每个节点在模板中通过模型参数指定思考强度（思考强度 = 模型在回答前投入多少推理计算量，档位越高推理越深、耗时越长、成本越高）：

| 节点 | 思考强度 | 理由 |
|------|----------|------|
| 调度 | 高 | 三要素校验与拆分建议需要深入分析 |
| 开发 | 中 | 常规实现，避免过度思考拖慢进度 |
| 分流 | 低 | 只转发调度结论，无需深度推理 |
| 测试 | 高 | 判定通过/失败需要严格证据 |
| 审核 | 高 | 质量门禁需要严格审查 |
| 人工验收 | 中 | 汇总报告，平衡质量与成本 |
| 收口 | 低 | 一致性收尾，机械整理 |

该能力基于 gold-band 已有的模型配置能力（无需开发），节点级配置落在模板 JSON 的 `config_options.reasoning_effort` 字段。

### 4.5 节点权限模式（与 Agent 匹配）

每个节点还需要配置「权限模式」（权限模式 = 该节点驱动的 Agent 在本次执行中允许自动执行的操作范围，例如自动批准文件改动）。**权限模式必须与节点绑定的 Agent 支持列表匹配**，否则工作流保存/启动会报「权限模式不属于当前 Agent」。

| 节点 | Agent | 权限模式 | 说明 |
|------|-------|----------|------|
| 调度 | kimi | yolo | kimi 全权限模式 |
| 开发 | claude | bypassPermissions | claude 全权限模式 |
| 分流 | kimi | yolo | 与调度一致 |
| 测试 | cursor | agent | cursor 自动执行模式 |
| 审核 | kimi | yolo | 与调度一致 |
| 人工验收 | claude | bypassPermissions | 人工 check 节点 |
| 收口 | claude | bypassPermissions | claude 全权限模式 |

⚠️ **换 Agent 时必须同步换权限模式**：`bypassPermissions` 属于 claude 系、`agent` 属于 cursor 系、`yolo` 属于 kimi 系、`agent-full-access` 属于 codex 系。只换提供商/模型而保留旧权限模式，会直接触发「权限模式不属于当前 Agent」校验错误。

## 5. 与现有默认工作流的差异

| 维度 | 现有默认工作流 | 优化后工作流（2.0） |
|------|----------------|--------------|
| 入口 | 需求访谈（AI 引导澄清） | GitHub issue（人工确认后创建） |
| 首个节点 | interview（访谈） | dispatcher（调度校验三要素） |
| 分支 | 单链 | 双分支（需/无需集成测试） |
| 打回上限 | 无限制 | 9 轮，超限回调度分析 |
| 收口 | accept 失败开新 Round 重来 | 人工验收独立节点 → 收口不打回，仅人工验收不通过例外 |
| 验收产出 | 仅面向 AI 的验证报告 | + 通俗验收报告（acceptance-summary.md） |
| 思考强度 | 不指定 | 每节点按需指定 |
| 角色 | 内置角色 | 2.0 独立角色（pf2-*，职责/流程/约束/产出统一） |

## 6. 使用步骤

### 6.1 导入角色提示词（一次）

「开发工作流 2.0」使用独立角色体系（存于 `~/.gold-band/context/profiles/`），共 6 个角色：

| 角色文件 | 角色 id | 服务节点 |
|----------|---------|----------|
| `dispatcher-2.0.md` | pf2-dispatcher | 调度 + 分流 |
| `dev-2.0.md` | pf2-dev | 开发 |
| `test-2.0.md` | pf2-test | 测试 |
| `review-2.0.md` | pf2-review | 审核 |
| `accept-2.0.md` | pf2-accept | 人工验收 |
| `closeout-2.0.md` | pf2-closeout | 收口 |

这些角色已直接落盘到用户级角色库，重启 gold-band 后即可在「角色管理」中看到；若在全新环境，复制上述文件到 `~/.gold-band/context/profiles/` 即可。

### 6.2 导入工作流模板

1. 打开工作流编辑器，选择「导入模板」。
2. 选择 `templates/dev-workflow-2-0.json`（蓝图，经 `npm run generate` 生成 vwf/DSH 双入口；原 gold-band 模板已归档 `.scratch/retired-goldband/`）。
3. 为每个节点绑定 Agent（调度/开发/测试/审核/人工验收/收口建议分别使用不同 Agent 以保持角色隔离，可参考 sts2-autotest 经验：开发与审核使用不同 Agent）。

### 6.3 创建任务

1. 在 GitHub 创建 issue，确保包含三要素：任务目标、涉及范围、验收标准。
2. 在 gold-band 创建任务，输入 issue 内容（或 issue 链接），选择「开发工作流 2.0」。
3. 启动任务，工作流从调度节点开始自动执行。

### 6.4 失败处理

| 失败形态 | 处理方式 |
|----------|----------|
| 三要素缺失 | 补齐 issue 后重新调度 |
| 测试/审核反复不过（9 轮超限） | 查看失败记录 → 重新调度（调度节点会给出拆分建议）或拆分任务 |
| 人工验收不通过 | 查看通俗验收报告确认问题 → 打回开发修复（自动）或人工介入 |
| 环境/需求阻塞 | 人工介入 |

## 7. 待办与后续建议

- 🟡 若需「超限自动回调度」能力，向 gold-band 提产品需求：控制层增加超限后跳转指定节点的边类型。
- 🟡 可考虑将「三要素缺失打回」从「任务失败」升级为「暂停等待人工补齐」（需 gold-band 支持人工补料后继续的机制）。
- 🟢 建议在 sts2-autotest 项目上试点运行本模板，积累 2-3 个 issue 后再回填调整（如 9 轮阈值、思考强度档位）。
