# 开发工作流 2.0 · DSH / vwf 统一引擎与模板同步需求规格

> 本文档基于 `docs/通用问题分析.md` 的逐条核实结论，以及对其隐含期望的澄清访谈整理而成。
> 文档目标：给出**可追溯到问题、可直接用于后续开发**的需求规格。
> 配套核实记录见 §2；分期与优先级见 §6；已知风险见 §7。

---

## 1. 背景说明

### 1.1 现状
当前"开发工作流 2.0"存在**两套独立的定义入口**：

- **文字入口（DSH）**：`dsh/skill/SKILL.md` → `dsh/workflow/dev-workflow-2.0.mjs`，`分流` 为脚本内 `if`（`dev-workflow-2.0.mjs:10,290-291`），模型经运行时 `args.models` 注入。
- **图形入口（vwf）**：`packages/dsh-visual-workflow/src/host.js:29-74` 内嵌 `TEMPLATES['dev-workflow-2-0']`，`分流` 为 route 节点（host.js:43），模型硬编码在模板里。

经核实，**运行时引擎其实已经统一**：DSH 的 `.mjs` 本身就是 `workflow` 工具的 `script`；vwf 在 `host.js:588` 也是把 DSL 编译成 `script` 后交给同一个 `workflowEngine.start` 执行。两边殊途同归到同一引擎。

### 1.2 核心矛盾
真正的问题不是"引擎不统一"，而是**定义源分裂 + 校验/基建缺失**：

1. 同一工作流有两份手写定义，改一处须手动同步另一处，且无一致性保障（B）。
2. 文档存在失效引用与口径矛盾（C1–C5）。
3. 草稿与编译产物混杂在 `.scratch/`（D）。
4. 缺根级清单与统一校验，无 CI（E）。
5. 两份 SKILL 门面并存，gold-band 遗留产物未清（F）。
6. （相邻已确认）`host.js` 默认模型全 `deepseek-official`，dev/review 同 provider，违反"异源异模型"硬规则，且 save/validate 不校验（见 §7 风险）。

### 1.3 目标
建立**单一事实源（蓝图）**，由生成器产出两份入口；支持自然语言同源调用（v1）与对话式模板创作（v2）；清理遗留、补齐根基建与 CI。

### 1.4 范围
- **动**：`dsh/`（编排脚本、skill、roles）、`packages/dsh-visual-workflow/`（插件）、仓库基建（根 `package.json`/`README`/CI/`.gitignore`）、文档修链。
- **清理（不修复）**：gold-band 专属产物（根 `SKILL.md`、`workflows/*.json`、`profiles/*`、`evals/evals.json`）。
- **分期**：v1（P0+P1）先夯实地基与同源调用；v2（P2）做对话式创作与异源 enforcement。

## 3. 功能性需求（FR）

> 每条 FR 标注：来源问题（追溯）、优先级、关联验收标准（§5）。

### FR-1 单一事实源（蓝图）　【来源：B】　优先级：P0
- 所有工作流定义为**蓝图 JSON**，集中存放于仓库 `templates/`（建议将现有 `workflows/` 重定位至此）。
- 蓝图字段：`id`、`displayName`（中文名，如"开发工作流 3.0"）、`name`（英文名/模板 id，如 `dev3.0`）、`entry`、`control.maxRounds`、`nodes[]`（`id`/`label`/`profile`/`goal`/`output.schema`/`output.successCondition`）、`edges[]`（`from`/`to`/`on`/`when`）。
- **模型分配与"分流"实现方式作为 per-entry 绑定配置**，不写死在拓扑核心；生成器据此分别编译出 DSH 的 `if` 分支与 vwf 的 route 节点。
- 现有 `dev-workflow-2.0` 必须首先被抽取为一份蓝图，保证 v1 不丢能力。

### FR-2 生成器（蓝图 → 双入口）　【来源：B、Q1】　优先级：P0
- 提供生成命令/脚本，遍历 `templates/` 下每个蓝图，生成：
  1. **vwf 注册**：`host.js` 改为从目录加载内置 + 用户蓝图（**废除 `host.js:29-74` 硬编码 `TEMPLATES`**）。
  2. **DSH skill 包装**：在 `dsh/skills/<id>/SKILL.md` 生成，内含薄 runner（编译蓝图→mjs 脚本→调用 `workflow` 工具），不再手写 mjs。
- 生成须**幂等、可重跑**；生成物受 NFR-1 约束（不可手改、gitignore）。

### FR-3 模板持久化（vwf.save 落盘）　【来源：Q1 前置、核实新增】　优先级：P0
- `vwf.workflows.save`（`host.js:442-448`）改为将用户蓝图**写入 `templates/`**（或用户模板目录），替代当前仅内存 `userWorkflows` Map；`vwf.workflows.list/remove` 同步基于目录；重载不丢失。
- 这是"图形新增模板 → 跨会话 → 同步文字版"的必要前提。

### FR-4 根级基建与统一校验　【来源：E】　优先级：P0
- 增加根 `package.json`（`workspaces` 指向 `packages/*`）。
- 增加根 `validate` 脚本，执行：① 校验 `templates/` 每个蓝图 DSL 结构合法；② 运行 `packages/dsh-visual-workflow` 测试；③ 幂等重生成 vwf/DSH 条目。
- 增加根 `README.md`：指向 `dsh/` 与 `packages/`，给出工作流开发/新增指引。
- 增加最小 **GitHub Actions**：push/PR 跑 `validate`。
- 注：原文档想要的"DSH↔vwf 一致性断言"在 FR-1/FR-2 同源生成下已**由构造保证**，无需单独对拍测试。

### FR-5 gold-band 产物清理与 DSH 文档修链　【来源：F、C1–C3、核实新增】　优先级：P0
- 删除：根 `SKILL.md`、`workflows/*.json`、`profiles/*`、`evals/evals.json`；`dsh/skill/SKILL.md` 成为唯一入口。
- 删除前确认无运行时依赖（已核实 DSH 用 `dsh/roles/*.md`，不加载根 `profiles/`/`workflows/`）。
- 修复因删除产生的死链：
  - `dsh/README.md:5,55` 改指向 `dsh/workflow/` + `dsh/roles/`；
  - `dsh/workflow/dev-workflow-2.0.mjs:7` 注释更新（不再引用 `workflows/dev-workflow-2.0.json`）。

### FR-6 自然语言同源调用 + 文档口径/死链修复　【来源：Q1、C4、C5、核实新增】　优先级：P1
- 生成的 DSH skill 触发词须含蓝图 `displayName`（中文）与 `name`（英文）及常见别名，使"用开发工作流3.0完成需求""dev3.0"等都能路由到同一 `templateId`；文字与图形入口解析到**同一工作流**。
- 修复《工作流状态机》"六个核心状态"→"七个"（与实际 7 节点一致）。
- 修复《开发工作流优化设计》死链（C4 修正归属至该文档 L6；L190/L220 的 `docs/gold-band/...` 与 `工作流模板/...` 指向新 `templates/` 路径）；`src/prompts` 引用改为实际角色位置 `dsh/roles/`。

### FR-7 对话式新增/改模板（v2）　【来源：Q2】　优先级：P2
- 提供"创建/修改工作流模板"能力：用户在会话用自然语言描述，AI 编写蓝图 JSON 写入 `templates/`，调用生成器重生成双入口，并运行 `validate`（结构合法）后方可接受。
- 修改须编辑蓝图（源），**禁止编辑生成物**（NFR-1）。
- 前置：FR-1 的蓝图 schema 须在 v1 确立并文档化，供 AI 编写。

### FR-8 异源异模型 enforcement（v2）　【来源：相邻异源核实】　优先级：P2
- 在引擎 save/update 入口强制 `dev ↔ review` 异源（不同 provider；至少不同模型），同 provider 即拒并返回明确错误。
- 过渡期在 `host.js` 的 `save`/`validate` 加双保险拒同 provider。
- 作用范围：**仅 `dev ↔ review`**（按《异源问题核实》现状）。

### FR-9 CI 细化（v2）　【来源：E 延伸】　优先级：P2
- 在 v1 轻量 Actions 基础上，按需增加：生成物新鲜度检查（若提交生成物）、异源校验集成、多模板回归。

### FR-10 `.scratch` 分层治理　【来源：D】　优先级：P1
- 将 `.scratch/dsh-visual-workflow-p0/` 的设计稿（`requirements-analysis.md`、`issues/*`）迁移至 `docs/design/`（明确分层）；编译产物（`compiled/*.gen.mjs`、`meta.json`）gitignore 且不入库；`prepare-deploy.mjs`、`deploy-payload.json` 归类为部署/临时产物单独管理。
- 根 `.gitignore` 补充编译产物与 `.scratch` 临时项。

## 4. 非功能性需求（NFR）

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-1 | 生成物不可手改 | 由生成器产出的 mjs / vwf 内嵌 / DSH skill 包装必须 gitignore、只读、改动即重建；人工只编辑蓝图。 |
| NFR-2 | 蓝图校验门禁 | 任何蓝图（新增/修改/生成）须通过 `validate`（DSL 结构 [v1] + 异源 [v2]）才可被 save/接受。 |
| NFR-3 | 向后兼容 | v1 不得破坏现有 DSH 会话以 `dev-workflow-2.0` / "开发工作流2.0" 调用既有流程的能力（生成器须为现有 2.0 也产出等价 skill/模板）。 |
| NFR-4 | 单一入口无歧义 | 删除根 `SKILL.md` 后，`dsh/skill/SKILL.md`（及生成出的 `dsh/skills/*`）为唯一自然语言入口。 |
| NFR-5 | 可追溯 | 每个 FR 可追溯到 §2 问题编号；规格与实现变更同步维护。 |

## 6. 优先级与分期

### v1（本期）

## 7. 已知风险与待办

1. **异源违规跨 v1 持续**：当前 `dev/review` 同 provider 违规在 v1 不被封堵，直到 v2 FR-8。v1 至少保留 `host.js` 现有 warning（不降级），并在文档标注为已知风险。
2. **蓝图 schema 须先确立**：FR-7（v2 对话式创作）依赖稳定、文档化的蓝图 schema；该 schema 须在 v1（FR-1）确立并写入 `docs/design/`，作为 AI 编写契约。
3. **自然语言路由依赖 skill 发现机制**：生成 skill 落 `dsh/skills/` 后需被 agent harness 加载识别；实现时须验证触发词路由生效，否则 FR-6 不成立。
4. **分析文档自身需修正**：C4 归属错误（《开发工作流2.0需求规格》:6 → 实际《开发工作流优化设计》:6），建议在 `docs/通用问题分析.md` 注明或在本次清理中一并修正。
5. **生成物是否入库**：NFR-1 默认生成物 gitignore；若团队选择提交生成物，则 FR-4 的 `validate` 须增加"生成物新鲜度"diff 检查（归入 FR-9）。
