# Graph Engineering（《Stop Chaining Your Agents》）对 workflow-manager 的参考价值

> 来源：@seeconvm，X 长文《Graph Engineering: Stop Chaining Your Agents》，2026-08-14
> https://x.com/seeconvm/status/2088199384580108339
> 分析日期：2026-09-10 · 对照基线：本仓 `CONTEXT.md` + `templates/construction-full-feature.json`（main）

## 0. 适用边界（先说清楚）

原文基于 Claude Code 的 dynamic workflows 写作，`parallel()` / `pipeline()` / worktree /
按节点换模型均为该平台能力。本仓引擎有等价物（钩子五件套 agent / parallel / pipeline /
phase / log、fanout 节点、蓝图声明式路由）。**思想可直接搬，机制必须翻译成本仓语言。**

原文第 14 条「让 AI 自己画这张图」与本仓产品主张冲突（蓝图是唯一事实源、人写机器跑），
不采纳；可借鉴的只有「运行时动态扇出」，不是「运行时动态构图」。

## 1. 原文核心观点

1. **诊断**：几乎所有多步 Agent 都是队列；约一半的「然后」不构成依赖——下游没有读上游产出，
   等待是纯浪费。
2. **主张**：提示词是句子，循环是圈，harness 是地板，而**工作的形状是图**。节点思考，边搬运结果。
3. **经济账**：编排是代码不是对话，协调 N 个 Agent 成本 = 0 token。边免费，节点付租金。
   「每条边都放 Agent 的图，是在为自己的管线付房租」。

## 2. 14 步 → 6 个可复用模式

| # | 模式 | 原文要点 |
|---|---|---|
| 01/02 | 依赖真实性审计 | 每个「然后」问：下一步真读了上一步产出吗？没有即无边。线性脚本 = 退化的最差图（无冗余，C 卡住 D 永不发生） |
| 03/04 | 双层契约 | 节点：有界输入/有界输出/一件事，schema 强校验，验证在工具层发生（模型重试而非人肉解析）。边：按数据命名不按顺序命名，交换两端节点不动全图 |
| 05/06/07 | 菱形拓扑 | 扇出 → 归约（纯代码，免费）→ 综合（一个 Agent 写答案）。归约用代码：扁平化/去重/过滤。barrier 只在「真需要全部结果」时才付代价 |
| 08 | 运行时条件路由 | 路由判断可由模型做，路由执行必须是代码 → 同输入同结果，没有「Claude 今天决定跳过审查」的意外 |
| 09 | 边上的验证器 | ① 对抗式证伪（N 个怀疑者，多数存活才保留）② 多视角透镜（正确性/安全/可复现）③ 评委团（N 个方案并行打分，胜者 + 嫁接亚军优点） |
| 10/11/12/13 | 隔离·收敛·分层·拓扑即成本 | worktree 隔离（仅当节点真并行写文件）；循环「跑到干为止」，**去重必须对「所有见过的」而非「确认过的」**；按判断含量分层配模型；pipeline 优先 barrier |

## 3. 对照本仓现状：三档判断

### 🟢 A 类 — 已领先，原文只是印证

| 原文主张 | 本仓现状（更强） |
|---|---|
| 边免费，别用 Agent 做管线 | **分流折叠**：布尔双出边折叠为脚本内 if，零 LLM |
| 路由执行必须确定性 | **outcomePath 必须可穷举**（enum/const/oneOf/boolean，自由字符串拒绝，#91）——比 if/switch 更硬 |
| 节点契约 | `output.schema` + 文件契约机器核对 + 错误带 `fieldKey` 坐标 |
| 节点隔离 | worktree 纪律已在 `AGENTS.md` |
| pipeline 优先 barrier | fanout 编译器**已用 pipeline 执行** |

### 🔴 B 类 — 真缺口

| # | 缺口 | 证据 |
|---|---|---|
| B1 | **引擎有扇出，模板一次都没用** | `templates/` 全文无 fanout 节点；引擎侧已具备 pipeline 执行、per-item schema、`failOn`（any/all/N）、结果包装 `{total, okCount, failedCount, items}`、4096/1000 cap |
| B2 | **审核只有一个节点** | heteroCheck 只保证「两人不同」；原文的「多透镜 + 对抗式证伪」是下一层 |
| B3 | **去重对象错误（按轮次而非按内容）** | 现用 `maxRounds`/`FAILED_MAX_ROUNDS` 防死循环；缺 finding 指纹去重 → 可能付费重复掉进同一个坑 |
| B4 | **人工门禁无默认动作** | 有 `onMaxRounds: return｜auto-reschedule`，但人工挂起未找到超时策略。对应评论区 HMICsource：「杀死图的是等人类的那个节点——无报错、无超时，只是静默挂起。门禁要么有默认值，要么就是泄漏」 |
| B5 | **模型是绑定不是分层** | `bindings` 是节点配模型，不是按「有无判断含量」分层 |

### 🟡 C 类 — 不适用

- 第 14 条「让 AI 自己画这张图」与「蓝图唯一事实源」冲突。
- 原文假设节点无副作用、可随意并行重建；本仓 dev/test 会推代码、开 PR、改 issue，并行隔离成本远高于纯研究任务。
- 人在回路（验收签字）物理上无法并行。

## 4. 落地清单（按 ROI）

| 优先级 | 动作 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| P0 | 依赖审计：逐条问「这条边有数据流动吗」 | 0.5 人日 | 砍掉无谓等待 | 极低，纯分析 |
| P0 | 人工门禁加默认动作（超时 → 放行 / 打回 / 升级提醒） | 1 人日 | 消灭静默挂起 | 🟡 默认放行会有质量风险 |
| P1 | 打回载荷带 finding 指纹；同一问题二次出现即升人工决策 | 1–2 人日 | 消灭空转返工 | 🟡 需改打回契约 |
| P1 | 审核升级为多透镜扇出 + 归约 | 2–3 人日 | 漏检率下降 | 🔴 单次成本 ×3，需便宜模型对冲 |
| P2 | 按判断含量分层配模型（preflight/test/closeout 便宜，dev/review 贵） | 1 人日 | 直接省钱，不动拓扑 | 低 |
| P2 | 内置蓝图首次引入 fanout 节点 | 3–5 人日 | 打开并行产能 | 🔴 #89 已锁：fanout 禁止 `outcomePath`/`completionPath`/`outcome` 边，需先定放置位置 |

## 5. 待核实项（未下结论）

- fanout 结果包装要求「按原序聚合」——是否真的流式，还是隐含一次 barrier？与「pipeline 优先」
  的主张是否冲突，需看 `scripts/generate.mjs` 编译产物。
- 人工门禁超时：仅在 `CONTEXT.md` 与 `docs/design/blueprint-schema.md` 层面检索，未在运行时代码中确认。

## 6. 一句话结论

**当前瓶颈不是模型，也不是引擎能力，而是「模板还没用上引擎已经有的能力」。**
优先做零分析成本的依赖审计与人工门禁默认值，再谈扇出。
