## 2. 需求目标与验收标准

**目标：**审核、测试、UAT 引用同一份真实候选成果；成果变更后旧证明不得为新成果放行。

**业务规则与边界：**

- 定义宿主生成的 candidate_ref：包含资源类型、作用域清单和不可变版本。Git 至少记录仓库身份、HEAD 与受审工作树内容摘要；有未提交变更时不能仅凭 HEAD 放行。非 Git 以声明文件集合、相对路径和内容摘要标识；忽略项显式声明，不默认忽略待交付内容。
- 在审核/测试开始前捕获候选，结束时重读；两者不一致则本次证明无效。模型自报 HEAD 仅作为诊断信息，权威版本来自宿主。
- 建设和诊断在进入后续关口前检查证明所指候选等于当前候选；任何已存在的集成同步和重跑门禁继续保留。

**可检查的验收条件：**

- [ ] AC-01：审核旧 HEAD、测试另一旧 HEAD、当前新 HEAD 时不进入 UAT/收口，并指出具体不匹配证明。
- [ ] AC-02：同一 HEAD 下受审文件发生未提交修改也被发现；不相关且已声明排除的临时证据文件不会使源码候选失效。
- [ ] AC-03：非 Git 文档集合任一纳入文件修改、增删或更名均改变候选标识；排序变化不改变摘要。
- [ ] AC-04：审核期间被审成果变化时不签发有效证明；对完全相同候选的正常审核、测试可通过。

**代表验收路径：**用 Git 小仓库和非 Git 文档目录各跑一轮：先生成通过证明，再改交付文件且不更新证明；请求下一关口应被拦截，重审当前版本后放行。
