## 2. 需求目标与验收标准

**目标：**在不改变用户行为的前提下，让状态与恢复规则有单一、可直接测试的实现位置。

**业务规则与边界：**

- 以状态转换与恢复检查点判定为一个完整切片，提取无宿主 I/O 的纯逻辑；生成脚本与宿主通过薄适配调用/打包。输入解析、记录提交只建立清晰边界，不在本条同时重写所有子系统。
- 先记录当前公开行为和有意修复后的既有语义，保持工具名称、输入输出、事件含义、快照恢复兼容及构建产物形式。保留 DSH 必需的 VM/子进程适配。
- 不新增远程服务、第二套引擎或通用插件框架；只有消除实际重复规则的抽取才纳入。行数下降不是验收标准。

**可检查的验收条件：**

- [ ] AC-01：状态/恢复的权威规则只有一处实现，生成器和宿主不再各自维护相同转换表或条件分支。
- [ ] AC-02：正常、返工、人工等待、受阻恢复、取消及旧快照兼容的行为对照用例一致。
- [ ] AC-03：Node 环境可直接测试纯逻辑；实际 DSH 打包入口仍加载成功，VM/子进程边界无新增宿主依赖泄漏。
- [ ] AC-04：提交清单列出被消除的重复规则与调用方，未混入新的业务行为或未经本需求包约定的状态改名。

**代表验收路径：**对同一组保存的状态事件序列，分别运行重构前与重构后实现；比较公开输出，并在产品安装路径跑一次等待后恢复。

## 4. 影响范围与建议优先级

**影响对象：**生成器与宿主的内部状态/恢复维护方式；对外行为应保持一致。

**功能边界 / 非目标：**不进行全文件拆分运动，不改变四模板拓扑，不将所有协议重做为抽象类层级。

**优先级理由：**以降低长期维护成本或验证投入收益为主，避免挤占已证实正确性缺口的修复。

**风险与兼容：**与 WR-001/006/009/011 同改核心文件，属于合并风险而非业务硬依赖；建议单独实施窗口与行为对照。
