## 2. 需求目标与验收标准

**目标：**建立能捕捉真实交接错误的验证体系，分别报告机器契约、真实宿主运行和人工业务验收结果。

**业务规则与边界：**

- 测试从生产者真实结构化输出开始，经编译输入解析、宿主提交/恢复到消费者接收，不直接伪造最终“已收到”结果。纳入 7 个原始复现并记录对应修复需求。
- 四类固定代表任务：建设一个有明确行为验收的小功能；非 Git 文档/配置优化；具备可重现故障的诊断修复；有反证和不足分支的开放研究。每类固定输入、实际角色、必需产物与可检查的成功/失败判据。
- 缺陷未修复时回归样例应真实失败或在缺口清单标明 expected failure，不将跳过算通过。可先独立交付夹具与诊断报告；闭环通过状态随对应修复逐项更新。
- 沿用 release:verify 与真实安装路径产品模式验收纪律。真实模型运行记录模型/时间/快照，不以替身计数推断线上发生率；只有实际执行的层级可标 PASS。

**可检查的验收条件：**

- [ ] AC-01：原基线 7 个复现与至少缺文件、旧输入版本、错误类型的负例能被测试体系观察，不因只断言最终路由而漏掉。
- [ ] AC-02：四模板消费方接收到的输入、成果和证明都有可追溯断言；含返工、人工等待、受阻恢复与探索部分失败。
- [ ] AC-03：报告分列自动契约检查、真实安装 DSH E2E、真实模型行为、人工验收及未执行原因。
- [ ] AC-04：测试入口、固定夹具与复跑步骤入库，输出失败能定位到接口和需求 ID；不新增必须部署的 Pact 服务。

**固定样板任务（放在隔离 fixture 项目，不修改正式产品业务）：**

| 工作流 | 输入与任务 | 客观验收 |
|---|---|---|
| 建设 | 小型 Node CLI 原有 `--help`，新增 `--version` 输出 fixture 的 package.json 版本 | 输出与版本一致；退出码 0；既有 help 不回归；独立审核/测试和人工三态有各自证据 |
| 优化 | 非 Git 说明文档含 10 条编号事实；保持事实不变，将正文字符数减少至少 20% | 10 个事实逐项映射仍成立；字符数由脚本计算；不能改评价契约降低门槛 |
| 诊断 | 固定数组汇总函数将最后一项漏计；输入 [2,3,5] 错得 5 | 修改前可稳定复现；修复后得 10；空数组得 0、单项 [7] 得 7；根因与回归证据一致 |
| 探索 | 冻结 6 份本地资料：两份支持 A、两份支持 B、一份揭示共同来源、一份说明缺少成本信息；研究给定选择问题 | 结论引用正确文件/段落，保留反证和来源关联；成本问题无资料时保持缺口，不编造；覆盖部分失败与定向补充 |

以上是验收夹具的建议 V1，字符数按 Unicode code point 计，事实清单及资料正文由本需求执行者一次性写入 fixture 后冻结。测试不得借修改固定答案来迁就实现。

**代表验收路径：**在已安装的候选版本上按四份场景清单实际运行，保存真实产物和报告；与同一基线的替身检查并排查看，确认没有把未执行项目标绿。

## 4. 影响范围与建议优先级

**影响对象：**开发者和验收者使用的四模板测试夹具、运行报告与发布证据清单。

**功能边界 / 非目标：**不代替各需求功能实现、不替用户签验收、不把单次模型运行宣传为统计质量结论。

**优先级理由：**补齐可靠交接、可维护性或运行保障，在关键错误放行问题之后推进。

**风险与兼容：**真实产品环境及模型调用须用隔离样例与已有授权；若环境不可用，交付可复跑材料并如实标注该层未验证。
