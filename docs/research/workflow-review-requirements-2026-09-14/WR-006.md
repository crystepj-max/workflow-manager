## 2. 需求目标与验收标准

**目标：**每次真实节点调用都有独立、可恢复且不重复的执行记录，节点最新结果只是索引。

**业务规则与边界：**

- 调用前持久化 attempt_id，包含 run/node/round、fanout item、segment；成功、失败、取消都写明确状态。结构修复与技术重试也有各自 attempt，逻辑步骤与实际调用分开标识。
- 完成顺序为：保存结果 → 提交正式记录并确认 → 更新最新索引与检查点 → 推进。写入失败保留原专业结论，但不得签发相应有效证明或最终完成。
- 结果提交使用稳定提交键去重；进程中断后重放已确认提交只返回同一记录。存储采用现有本地 Records 能力并处理同 Run 写入冲突，不引入远程事件服务。

**可检查的验收条件：**

- [ ] AC-01：复现的 8 次调用留下 8 个完成 attempts；3 次评估各有可读结果和正式 Revision，最新索引指向第 3 次。
- [ ] AC-02：同一节点跨 segment 再次执行也追加记录；fanout 不同专家与轮次不会碰撞。
- [ ] AC-03：在结果落盘后、确认前及索引更新前分别注入中断，恢复后已确认结果不丢失且不重复生成 Revision。
- [ ] AC-04：模拟写盘失败、重复提交和并发提交，均不能显示“证据有效且完成”却缺少记录；失败可恢复。

**代表验收路径：**优化连续返工两次后成功；在第三次评价提交时中断宿主，再恢复同一 Run，核对所有 8 次执行、评价内容、Revision 与最新索引。

## 4. 影响范围与建议优先级

**影响对象：**全部模板的逐次调用记录、宿主存储、结果查询与中断恢复。

**功能边界 / 非目标：**处理本地执行及正式记录持久化；外部发布等副作用幂等由 WR-012 负责，完整事件溯源平台不在范围内。

**优先级理由：**影响错误放行、虚假完成或失控消耗，建议先于扩展使用范围处理。

**风险与兼容：**旧 Run 无法还原已覆盖内容，只迁移可见记录并标记历史不完整。增加记录量应保留轻量索引，禁止伪造历史 attempts。
