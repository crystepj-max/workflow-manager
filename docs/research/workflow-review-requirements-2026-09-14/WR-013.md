## 2. 需求目标与验收标准

**目标：**12 个角色有清晰一致的能力边界；四模板提供文件、资源和裁决等场景要求，角色不再猜旧工程流程。

**业务规则与边界：**

- dev 允许必要自测与实现相关测试，不自签独立测试证明；review 保持独立判断且不修改候选；test 可写测试和证据，不解决业务源码冲突，发现冲突回开发/集成。
- accept 只整理本模板所需材料；建设按 uat-card.md/acceptance-summary.md 与严格三态，不代签。requirements/designer 不进入实施职责；diagnose 负责故障复现、根因假说及支持/反驳证据，不能把未验证推测写成已确认根因；保留 designer 作为定义/自定义工作流资产。evaluator 服从节点给定裁决与评价标准。
- orchestrator/researcher/synthesizer 保留视角、反证和不确定性职责，枚举与模板一致：探索统筹使用 PLAN_READY，研究 confidence 使用 high/medium/low；研究报告名来自节点声明；closeout 只整理已冻结事实，其外部执行机制归 WR-014。
- 将固定文件名、Git 要求、输出枚举、路径和任务完成条件放到 Node/上下文；优先级明确为宿主安全与授权 → 节点场景契约 → 角色通用能力，不用通用角色覆盖节点基线。

**可检查的验收条件：**

- [ ] AC-01：形成全部 12 角色的职责矩阵与 4 模板节点绑定对照，无 dev 自测禁令与 TDD 要求并存。
- [ ] AC-02：非 Git 文档优化能收到完整执行要求，不要求 dispatch-result、创建 worktree 或 PR 才能完成。
- [ ] AC-03：建设 accept 产物与模板一致，三态不被二态指令覆盖；诊断 test 使用节点声明的回归产物。
- [ ] AC-04：角色加载/编译快照测试验证实际注入文本，不只对 Markdown 做关键词检查；人工抽查四模板各一次代表性角色交接。

**代表验收路径：**分别查看建设开发/验收、文档优化执行、诊断测试、探索专家的真实编译提示；按提示开展小样例，确认无互相矛盾或场景不相关的强制步骤。

## 4. 影响范围与建议优先级

**影响对象：**12 个内置角色文本、四模板节点目标和新运行的编译提示；旧运行继续使用冻结文本。

**功能边界 / 非目标：**覆盖 12 个内置角色与四模板所需文案；不删除 designer，不新增同义角色，不安装或改写用户全局角色副本。

**优先级理由：**影响错误放行、虚假完成或失控消耗，建议先于扩展使用范围处理。

**风险与兼容：**角色文本在编译时冻结，旧 Run 应继续用旧快照；新模板重生成后验证，避免静默改变运行中的职责。
