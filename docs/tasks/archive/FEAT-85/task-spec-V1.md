## 1. 需求背景

正式运行看板当前只能回答「有哪些运行、大概什么状态」：列表主要展示 `taskId / workflow / status / phase / runId`，工作空间、结果类型、完成类型与返工历史没有形成稳定的用户视图；详情里画布、节点表、产物、日志分散在不同区域，用户需要在上下区域之间来回寻找。

同时，多机多 AI 并行的实际使用方式已经形成：同一台机器上会有多个工作空间、多个任务同时推进。用户需要一个能管理**多个工作空间里的多个任务**的列表，以及一个能读懂**同一次运行多轮返工**的详情区。

数据侧已就绪：Logical Run、快照修订、节点尝试、业务结果、控制事件、工作空间上下文均有持久化来源（`vwf.runs.list`、`vwf.logicalRuns.get`、`vwf.run.control`、`wf_run` 续跑参数）。本任务**优先消费现有数据**，不重写运行语义。

## 2. 用户问题（业务语言）

1. **管理不了多空间**——桌面/远程两个工作空间的任务混在一起，看不出哪条属于哪个工作空间，也不能按空间筛。
2. **看不懂一次运行**——列表只给状态；进详情后，节点详情、产物、日志分散在上下两块，来回找。
3. **返工历史被掩盖**——多轮返工看起来像若干个新任务，用户无法分辨「同一次运行的第 N 段」与真正的新任务；上一轮的成果可能被误读成本轮结果。
4. **人工决策要手抄命令**——部分人工决策仍在展示可复制的 `wf_run` 命令文字，用户得离开界面去命令行操作。

## 3. 目标

1. 一个列表管理多工作空间、多任务：分组、空间筛选、状态与结果筛选、分页、返回位置保留。
2. 一个稳定的详情区读懂一次运行：生命周期、当前分段、快照修订、节点尝试、业务结果、完成类型、正式产物、活动记录，且**只有一个选中节点的结果出口**。
3. 返工可读：每个节点显示 attempt / round，退回意见跟随触发它的审查轮次，旧下游结果标为「上一轮成果」。
4. 扇出可读：并行组、子任务独立结果、汇总输入来源、未完成子任务状态清楚可见。
5. 人工决策与受阻恢复在界面内完成：结构化决策卡与恢复卡，由界面提交选项与理由，再用既有运行协议续跑。

## 4. 非目标

- 不修改执行引擎的重试、回环、返工上限或 Logical Run 生命周期语义。
- 不在运行页编辑工作流结构（属 FEAT-84）。
- 不重新设计供应商 / 模型配置；`BLOCKED` 恢复只调用既有 `model_overrides` 续跑语义。
- 不增加「成功 / 失败」二元业务模型。
- 不用新 RPC 替代既有 `vwf.runs.list`、`vwf.logicalRuns.get`、`vwf.run.control` 与 `wf_run` 参数。
- **不新造与 LOC-016 冲突的生命周期定义**（见 §8）。

## 5. 修改前

- 正式看板可列出运行、按页浏览、选择单个 run、显示基础状态、只读画布、节点表、正式产物与日志。
- 列表主要展示 `taskId / workflow / status / phase / runId`；缺工作空间、结果类型、完成类型、返工次数、最近更新时间的稳定视图。
- 详情信息分散：画布、节点表、产物与日志；用户需在上下区域之间来回寻找节点详情。
- 部分人工决策显示可复制的 `wf_run` 命令文字。
- 现有 RPC：`vwf.runs.list`（含 `logical_run_id` / `segment` / `segment_count` / `logical_state`）、`vwf.logicalRuns.get`、`vwf.run.control`（`pause` / `interrupt` / `guidance`）、`wf_run` 续跑参数（`decision_id + user_choice`、`resume_paused`、`model_overrides`）。
- **`LOC-016` 的呈现层实现已存在于未合并分支 `dev-loc-016-r1`**（该分支当前停在人工验收）。本任务的修改前状态因此有两种可能基线，须在开工时确认（见 §11）。

## 6. 修改后

- 运行列表按工作空间分组，支持空间 / 状态 / 结果 / 完成类型筛选与分页；返回后保留分组、筛选与列表位置。
- 同一 Logical Run 的多个 segment 只呈现为一个用户任务，可展开查看每一段。
- 详情工作区：左侧运行定位（工作空间、模板、当前阶段、状态），中间单一选中节点详情，「结果 / 检查 / 活动」页签切换。
- 返工路径可读：实现第 1 次 → 审查退回 → 实现第 2 次 → 审查通过 → 测试 → UAT → 等待人工决定。
- 多视角探索运行可展开并行研究组，看到每个子任务结果与汇总输入来源。
- `WAITING_HUMAN` 显示业务选项（接受 / 增加预算 / 停止）、理由输入与影响说明；提交后仍留在同一个 Logical Run。
- `BLOCKED` 显示阻塞原因与当前 Run Provider / Model 的恢复入口；恢复后出现新 Snapshot Revision，历史修订仍可查。
- 工作空间信息面板显示 mode、repository、branch、当前 / base HEAD、集成状态、活动锁与清理状态。

## 9. 业务规则

- **一个 Logical Run 就是一个用户任务**：多 segment 不得呈现为多个新任务；`superseded` 记录不得当作新用户任务展示。
- **业务结果分层**：Lifecycle、Node Business Outcome、Completion Type 三层分别展示，不得塌缩为成功 / 失败徽标。
- **上一轮成果必须显式标识**：返工前已完成的下游结果必须标为「上一轮成果」，不得冒充当前轮结果。
- **扇出部分完成不得冒充完成**：未完成子任务时汇总节点显示等待。
- **协议优先**：列表读 `vwf.runs.list` 并按 `logical_run_id` 与 `segment / segment_count / logical_state` 合并段位；详情读 `vwf.logicalRuns.get`；控制走 `vwf.run.control`；决策与恢复走既有 `wf_run` 续跑参数。
- **UI 不得拼接让用户复制的命令**：UI 只负责把选项映射为 `decision_id / user_choice / model_overrides`。
- **来源分段标注**：运行日志、正式产物与节点结果必须标注来源分段与 attempt。
- **不伪造成功**：若宿主尚未暴露结构化决策提交入口，把缺口登记为运行协议依赖，不在客户端伪造成功状态。
- **读取失败不冒充事实**：工作空间注册表或锁状态读取失败时显示明确的未知 / 不可用状态与重试，不把过时缓存当作当前事实。
- **按钮名对应实际 action**：暂停 / 立即中断 / 指导 / 恢复的名称必须与真实行为一致。
- **不新造生命周期**：`LOC-016` 是运行看板语义权威；本任务不得另造与之冲突的生命周期定义。

## 10. 用户操作路径

1. 打开运行列表 → 看到按工作空间分组的任务。
2. 用空间筛选与「待处理 / 进行中 / 已完成」筛选 → 列表仍显示所属模板、状态、返工次数、最近更新时间。
3. 选择一条任务 → 进入大工作区详情；返回后保留原分组、筛选与列表位置。
4. 在详情中切换「结果 / 检查 / 活动」页签 → 同一区域内容切换，不同时重复展示同一节点详情。
5. 选择第 1 次与第 2 次执行 → 分别看到对应输入、成果与退回意见。
6. 对等待人工决定的运行 → 选择业务选项、填写理由、查看影响说明并提交 → 仍留在同一 Logical Run。
7. 对 `BLOCKED` 运行 → 看到阻塞原因 → 修改当前 Run 的 Provider / Model → 提交 → 出现新 Snapshot Revision，历史修订仍可查。
8. 展开多视角探索运行 → 看到并行研究组、各子任务结果与汇总输入来源。
9. 打开工作空间信息 → 查看 mode、repository、branch、当前 / base HEAD、集成状态、活动锁与清理状态。

## 16. UAT 场景

### UAT-01 多工作空间列表与筛选

- 执行时机：裁决前可观测
- 验收目的：确认列表能管理多个工作空间里的多个任务。
- 前置条件：
  1. 存在至少两个工作空间的运行记录（每个空间至少两条任务）。
- 操作步骤：
  1. 打开运行列表。
  2. 应用空间筛选，再应用状态筛选。
  3. 记录当前列表位置，进入某条任务详情，再返回。
- 预期结果：
  1. 任务按工作空间分组，组标题可辨识。
  2. 筛选后仍显示所属模板、状态、返工次数与最近更新时间。
  3. 返回后分组、筛选与列表位置保持不变。
- 建议人工关注：`superseded` 记录是否被误当作新用户任务。

### UAT-02 Logical Run 分段与返工历史

- 执行时机：裁决前可观测
- 验收目的：确认一次运行的多轮返工不被掩盖成多个任务。
- 前置条件：
  1. 存在一条经过「实现 → 审查退回 → 实现 → 审查通过 → 测试 → UAT」的运行。
- 操作步骤：
  1. 在列表中定位该运行，确认它只占一条任务。
  2. 进入详情，选择第 1 次执行与第 2 次执行。
  3. 查看每一段的输入、成果与退回意见。
  4. 查看下游节点在返工前的产物标识。
- 预期结果：
  1. 多 segment 呈现为一条任务的连续分段。
  2. 每轮成果与退回意见正确对应。
  3. 返工前已完成的下游结果显示为「上一轮成果」，未被当作当前轮结果。
- 建议人工关注：第 2 次实现的输入是否包含第 1 轮的退回意见。

### UAT-03 扇出与汇总可读性

- 执行时机：裁决前可观测
- 验收目的：确认并行研究组与汇总输入来源可见。
- 前置条件：
  1. 存在一条包含多视角探索（扇出）的运行。
- 操作步骤：
  1. 展开并行研究组。
  2. 查看每个独立研究子任务的成果。
  3. 查看汇总节点的输入来源。
  4. 制造或找到「部分子任务未完成」的状态，观察汇总节点。
- 预期结果：
  1. 并行组与子任务可辨识。
  2. 每个子任务有独立结果。
  3. 汇总节点的输入来源清楚。
  4. 部分未完成时汇总节点显示等待，不冒充完成。
- 建议人工关注：未完成子任务是否有明确状态而非空白。

### UAT-04 人工决策卡与受阻恢复

- 执行时机：裁决前可观测
- 执行者（仅「收口后观测」时填）：不适用
- 验收目的：确认人工决策与恢复在界面内完成，且不伪造成功。

  1. 打开 `WAITING_HUMAN` 运行，查看选项、理由输入与影响说明。
