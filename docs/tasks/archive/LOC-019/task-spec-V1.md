## 1. 需求背景

四套正式内置模板的默认模型绑定仍以 `openai-codex / gpt-5.6-luna` 与非最新 DeepSeek 模型混搭，而用户环境以 DeepSeek 为主且已确认 `deepseek-flash`（DeepSeek V4.1 Flash）有效。同时本机 `~/.dsh` 下已存在用户整份副本与模型覆盖，其中 diagnose 的覆盖把修复与审核改成同一模型，导致该模板校验失败、无法发起运行。

来源：2026-09-13 LOC-014 产品 UAT 验证反馈（用户会话决策）。

## 2. 用户问题

拿到内置模板后，默认模型不是自己能用的，必须逐个节点手改才能真正跑起来；并且当前 diagnose 模板受已有模型覆盖影响，直接发起运行会被校验拒绝。

## 3. 目标

交付后用户获得：四套内置模板的默认模型绑定全部 DeepSeek 化，模板库所见即开箱默认，无需手改即可发起运行；且因用户数据遮蔽而失效的内置改动被解除。

## 4. 非目标

- 不引入异源档位字段（关/弱/强）与相关校验改造 —— 归 LOC-021；
- 不做编辑器 UI 改造（含校验失败时的明确报错与一键修正） —— 归 LOC-021；
- 不调整异源判定逻辑与运行时异源日志识别口径 —— 归 LOC-021；
- 不批量迁移非内置模板（用户自定义模板的绑定不动）；
- 不做运行中模型切换/修订路径（#79）。

## 7. 功能范围

1. 调整四套 `templates/*.json` 的 `bindings.models` 至第 6 节映射表；
2. 重新生成并使其进入实际加载路径（生成命令 + 产品模式重启，生成物本身不入库）；
3. 交付步骤内执行一次用户数据清理：**只删除与内置逐字节相同的同 id 整份副本**（确定性冗余），并复核删除后该 id 回到内置；
4. 模型覆盖文件**不自动删除**：把 diagnose 覆盖导致的运行阻塞以显式清单形式呈递给用户处置（用户可直接使用模板库既有的「清除覆盖」能力，或按建议把 review 改为差异化模型）；
5. 复核四套模板的内置默认绑定通过校验；插件包测试 + 根目录 `npm test`、`npm run validate`、`npm run release:verify` 全绿。

## 8. 不修改范围

- 异源判定逻辑、异源档位字段、编辑器工作流控制区（归 LOC-020）；
- 运行时异源日志识别口径（归 LOC-020）；
- 非内置（用户自定义）模板与新蓝图默认值；
- 模型覆盖层的合成语义与优先级（LOC-014 已定）；
- #79 运行中模型修订路径；
- `.generated/` 不入库的口径不变（不把它加进版本控制）。

## 9. 业务规则

- 「验证角色」判定口径（已确认）：承担**独立验证或回归职责**的节点 —— 收敛审查、审核、测试、回归验证、评估。不含 `preflight`（实施前门禁检查）、`uat`（人工验收准备）、`closeout`（收口）；
- 验证角色统一使用 `deepseek-v4-flash`，其余节点统一使用 `deepseek-flash`；
- 异源约束沿用现状默认弱档语义（本次不引入档位字段）：同 provider 不同 model 通过并给出弱异源警告；provider 与 model 完全相同则拒绝；
- 自检结论（已推算，待施工复核）：完整功能开发 dev=flash / review=v4-flash、诊断 fix=flash / review=v4-flash → 均满足弱档；快速迭代与探索无开发/审核节点 → 异源校验跳过。四套模板均可在弱档下保存与运行；
- 内置结构仍只读；用户仍可通过模型覆盖层改绑定；
- 模型 id 均为有效值：`deepseek-flash` = DeepSeek V4.1 Flash（支持文本+图片），`deepseek-v4-flash` = 纯文本模型，二者同属 provider `deepseek-official`。

## 10. 用户操作路径

模板库 → 打开任一套内置模板 → 看到 DeepSeek 默认绑定（含差异化验证模型）→ 直接发起运行 → 各节点按新模型执行 → 如需自定义，仍走既有模型覆盖入口。

清理路径（交付一次性）：交付回报列出被删除的冗余副本与被保留的覆盖文件 → 用户确认后，diagnose 覆盖按其选择处置（清除 / 改差异化模型 / 保留）。

## 11. 异常和边界场景

- 用户整份副本与内置内容**不同** → 视为用户自定义资产，**不删**，该 id 维持用户副本优先（并在交付回报中列出）；
- 用户整份副本与内置内容**相同** → 判定为确定性冗余，删除；
- 模型覆盖文件损坏/非法 → 既有容错语义不变（忽略并留痕）；
- diagnose 覆盖未处置时 → 该模板仍无法发起运行；交付回报必须显式列出，不得声称四套模板均可运行；
- 生成物未重新生成 → 运行时仍读旧内联模型，必须在验收步骤中显式核对生成物内联模型；
- 清除冗余副本后若用户希望保留该自定义副本 → 需自行重新另存（一次性清理不可逆，交付前须列出清单）。

## 16. UAT 场景

### UAT-01 模板库默认绑定核对

- 验收目的：内置默认绑定已 DeepSeek 化且可见；
- 前置条件：交付已重新生成并重启产品模式；
- 操作步骤：
  1. 打开模板库，逐套查看四套内置模板的节点绑定；
  2. 与第 6 节映射表逐项对照。
- 预期结果：四套模板逐节点绑定与映射表一致；审查/测试/回归/评估节点为 `deepseek-v4-flash`，其余为 `deepseek-flash`。
- 建议人工关注：完整功能开发是否仍显示「已覆盖」标记（若已产生覆盖）。

### UAT-02 开箱可运行

- 验收目的：默认绑定可直接发起运行；
- 前置条件：UAT-01 通过；
- 操作步骤：对完整功能开发、快速迭代、探索各发起一次最小运行（可至探针通过即停）。
- 预期结果：三套均可成功创建运行；运行快照 Rev 1 冻结的是新默认绑定；无因模型不可用导致的 BLOCKED。
- 建议人工关注：探针是否真用新模型（而非缓存旧模型）。

### UAT-03 遮蔽解除核对

- 验收目的：内置改动对用户侧真正生效；
- 前置条件：一次性清理已执行；
- 操作步骤：
  1. 核对 `~/.dsh/visual-workflow/templates/` 下是否已无与内置同内容的整份副本；
  2. 重新打开模板库，确认该 id 显示的是内置默认绑定。
- 预期结果：冗余副本已删除；模板库该 id 走内置并显示新默认绑定。
- 建议人工关注：内容不同的用户副本必须仍被保留。

### UAT-04 诊断模板可运行性

- 验收目的：现存覆盖造成的阻塞被显式处置；
- 前置条件：交付回报已列出 diagnose 覆盖清单；
- 操作步骤：
  1. 在模板库对诊断模板尝试清除覆盖（或按建议把 review 改为差异化模型）；
  2. 发起一次最小运行。
- 预期结果：清除或修正后，诊断模板可成功创建运行；运行时校验不再报「dev 与 review 模型相同」。
- 建议人工关注：这是现存用户数据造成的既有限制，非本次改动引入。

## 17. 风险

- 🟡 一次性清理误删用户资产 → 判定条件收紧为「与内置逐字节相同」，且交付前必须输出删除清单；内容不同者一律保留；
- 🟡 生成物未重新生成导致「改了但没生效」的误判 → 验收条件中单列生效链路核对项；
- 🟡 用户覆盖未处置时诊断模板仍不可运行 → 交付回报必须显式声明，不得声称四套全部可运行；
- 🟡 差异化模型（`deepseek-v4-flash`）能力弱于默认模型，可能影响验证质量 → 属用户已确认取舍；后续可经模型覆盖层调整；
- 🟡 一次性清理不可逆 → 清理前输出清单；如用户希望保留自定义副本，需在清理前明确。

## 18. 已知限制

- 本切片不提供编辑器内「校验失败即报错并一键修正」的能力（归 LOC-020），因此模型覆盖造成的冲突仍需用户手动处置；
- 内置默认绑定对已存在整份自定义副本的 id 不生效（属产品既定优先级语义，非缺陷）；
- 本次不改变「模型覆盖层不校验 provider/model 是否存在」的既定语义。
