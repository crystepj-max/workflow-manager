## 1. 需求背景

2026-09-20 产品模式真机跑 `wf-explore` 时，`evaluate` 节点绑定的 `deepseek-official/deepseek-v4-flash` 报 `MODEL_NOT_CONFIGURED`，被 #74 运行前探针拦下进入 BLOCKED；用户此前已删除 v4-pro / v4-flash 配置、仅保留 v4.1-flash，按 #74 恢复路径手工覆盖后才跑完。

**根因修正（本会话复核，修正票面「LOC-019 漏网」定性）**：LOC-019（`f410900`，2026-09-13）**有意**将验证角色节点设为 `deepseek-v4-flash`（当时有效），提交信息与映射表测试 `scripts/test/builtin-template-model-defaults.test.mjs` 均为证。真实根因是**其后用户模型配置漂移（删除 v4-flash），而仓库没有任何机器闸门核对「模板默认绑定 vs 当前可用模型」**，漂移静默发生直至真机起跑才暴露。因此预防的正解是补闸门，而非复查 LOC-019 覆盖。

**过期面实测（修正票面「仅 evaluate」认知）**：四套正式内置模板共 **6 个验证角色节点**绑定已删除的 `deepseek-v4-flash`：construction 的 `review`/`test`、diagnose 的 `review`/`regression`、explore 的 `evaluate`、optimize 的 `evaluate`。其余 11 个节点为 `deepseek-flash`，真机 UAT 已实际跑通，有效。新环境或他人机器上四套模板开箱即不可运行。

**闸门设计约束（取证结论）**：「deepseek-official 当前可用模型目录」没有磁盘配置文件可读，权威事实源在产品 DSH 运行时内部（`llm.listProviders()/listModels()`，运行前探针即以此判定 `MODEL_NOT_CONFIGURED`）。

## 2. 用户问题

一句话：模型配置一变，四套内置模板默认绑定就静默过期，每次都要真机起跑才炸、再手工覆盖。

## 3. 目标

四套内置模板在现配置下开箱可跑（6 个验证角色节点默认绑定指向现存模型）；且今后配置再漂移时，发布前机器闸门会给出逐节点失败清单，不再靠真机起跑发现。

## 4. 非目标

- 不修仓外同类过期（如 `~/.dsh/settings.yaml` 的 `subagent-model-selection.allowedModels` 仍指 v4-flash——DSH 应用侧配置，不属本仓库）。
- 不改运行前探针 BLOCKED + `model_overrides` 恢复语义（#74）。
- 不涉及 #233 的形态误判修复（独立在途任务）。
- 不改编辑器 UI（闸门段不新增界面）。
- 不重议 LOC-019「验证角色与执行角色异模型」的两层设计（本次基线已确认保持）。
- 不动两套历史模板（default-workflow / dev-workflow-2-0，已迁用户自定义资产）。

## 5. 修改前

6 个验证角色节点默认绑定指向已删除的 `deepseek-v4-flash`：四套模板开箱即探针 BLOCKED；「默认绑定 vs 当前配置」无任何机器核对，漂移只能真机发现。

## 6. 修改后

四套模板 24 节点默认绑定全部指向现存模型，开箱可跑；`release:verify` 新增检查段在产品 DSH 可达时输出逐模板逐节点核对清单，存在过期绑定即失败并列明「模板 / 节点 / 当前绑定 / 目录实况」；不可达时显式跳过留痕。

## 7. 功能范围

**切片① 默认值修复**
- `templates/` 四套蓝图 6 个验证角色节点：`deepseek-v4-flash` → `deepseek-v4.1-flash`（走蓝图重新生成，`npm run generate`；禁止手改 `.generated/`）。
- `scripts/test/builtin-template-model-defaults.test.mjs` 映射表同步（`VERIFY_MODEL` 更新；弱异源警告断言保持成立，见 §9）。

**切片② 默认绑定机器闸门（双层，方案 A）**
- 仓库层：切片① 的映射表测试即仓库层锚点（默认值 = 已认可映射）。
- 真机层：`scripts/release-verify.mjs` 新增检查段「内置模板默认绑定 vs 当前可用模型」——产品 DSH 可达时逐模板逐节点核对默认绑定是否 ∈ llm 模型目录（目录成员判定口径与运行前探针一致），输出核对清单与明确失败清单；不可达时显式跳过并留痕。核对核心逻辑做成可注入目录 stub 的形态，正负路径均可单测。

## 8. 不修改范围

- `.generated/` 直接手改（一律重生成）；两套历史模板；仓外 DSH 应用配置；探针恢复语义；#233 在途修复；编辑器 UI；异源档位三态语义（LOC-021）。

## 9. 业务规则

- 默认绑定更新只能走 `templates/` 蓝图 + `npm run generate`（票面要求 3）。
- 验证角色（review / test / regression / evaluate）与执行角色**异模型**的两层设计保持（LOC-019 决策，本次基线确认）：执行角色 = `deepseek-flash`，验证角色 = `deepseek-v4.1-flash`。
- 弱异源三态语义（LOC-021）不受影响：同 provider 异 model → construction / diagnose 仍应产生弱异源警告。
- 闸门段两条硬规则：失败必须输出可读的逐节点失败清单；不可达必须显式跳过留痕——不得静默绿、不得环境缺失误报红。

## 10. 用户操作路径

主路径：用户（或发布流程）执行 `npm run release:verify` → 检查段输出四套模板逐节点绑定核对清单；配置再漂移时，该段在发布前变红并列出具体节点，用户按清单更新蓝图默认值或恢复模型配置。

## 11. 异常和边界场景

- CI / 无产品 DSH 环境：仓库层测试全绿，真机层段显式跳过留痕，`release:verify` 整体不因环境缺失失败。
- 产品 DSH 可达且绑定全有效：清单全绿。
- 可达但存在过期绑定：检查段失败 + 逐节点失败清单（负路径以目录 stub 单测固化，UAT-01 可选真机复演）。
- 用户未来再删模型：下一次 `release:verify` 拦截。
- `v4.1-flash` 实际不可选（前提不成立）：闸门 / UAT 核出 → 回到基线重议（风险 §17 已声明）。
- 运行期探针语义不变：即使闸门全绿，运行前探针仍按 #74 独立判定（闸门是发布前核对，不替代运行时保护）。

## 16. UAT 场景

### UAT-01 真机绑定核对清单

- 验收目的：验证检查段在真实产品 DSH 上输出正确清单并拦截真实过期。
- 前置条件：
  1. 切片① 已落地；按 AGENTS.md 完整重启产品 DSH（3080）；
  2. 产品 DSH 配置中存在 `deepseek-flash` 与 `deepseek-v4.1-flash`（决策 2 前提的最终确认点）。
- 操作步骤：
  1. 执行 `npm run release:verify`（或单独触发检查段）；
  2. 查看逐节点核对清单；
  3. （可选负路径）临时将某节点绑定改回 `deepseek-v4-flash` 重跑 → 应失败并列出该节点 → 还原。
- 预期结果：
  1. 清单显示 24 节点默认绑定全部 ∈ 当前模型目录，检查段绿；
  2. 负路径复演时检查段红且清单指认准确。
- 建议人工关注：`v4.1-flash` 在 DSH 模型选择器中确实可选（决策 2 前提）。

## 17. 风险

- 决策 2 前提风险：`v4.1-flash` 若在产品配置中实际不可选，闸门 / UAT 会核出，需回基线重议（已在前置条件显式设卡）。
- 通道施工风险：脚本侧读取 DSH llm 目录的传输方式（RPC / 服务直读）施工时定，验收按行为写不锁实现；若成本超预期，可先交付「不可达显式跳过」形态再增强，但 AC-04 的 stub 单测不可省。
- 覆盖面错觉风险：本票只管四套正式模板；仓外同类过期（settings.yaml subagent 白名单）仍在，需读者知悉（§4）。
