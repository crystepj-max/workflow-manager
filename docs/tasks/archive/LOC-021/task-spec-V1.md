## 1. 需求背景

异源约束（同一工作流内「开发」与「审核」不得使用同一模型）目前是**全局强制**且只有一个隐含档位：同 provider 不同 model 已放行（弱异源 + 警告），只有 provider 与 model 完全相同才拒绝。编辑器工作流控制区里那个「异源检查 ON/OFF」开关**不影响校验**，只影响运行时日志注入——用户看到开关却控制不了行为。用户希望按需把异源收紧为真异源（provider 必须不同），或明确关闭。

来源：2026-09-13 LOC-019 需求分析会话（D1/D1-b/D2/D3/D6 决策），源自 LOC-014 产品 UAT 反馈。

## 2. 用户问题

用户无法提高或降低异源要求的强度：想严格时没有「provider 必须不同」的档位，想放开时也无法关闭；而现有开关与真实校验行为不一致，容易误解。

## 3. 目标

交付后用户获得：在工作流控制区用「关 / 弱 / 强」三档表达异源要求，随蓝图保存并真实生效——弱档（默认）等同现状，强档要求 provider 必须不同，关档不做校验；旧蓝图行为零变化。

## 4. 非目标

- 不扩大校验配对范围：只拦「开发↔审核」一对，`开发↔测试`、`执行↔评估` 不纳 入强制校验（默认值差异化在 LOC-019 已定，不受影响）；
- 不做「一个工作流内多组异源配对」的配置模型；
- 不改内置模板的默认模型绑定（归 LOC-019）；
- 不做运行中档位切换（档位是蓝图属性，运行中不可变）；
- 不改模型覆盖层语义。

## 5. 修改前

- 蓝图字段 `heteroCheck` 为布尔值，仅 `true` 时要求存在开发与审核节点；对校验强度没有表达能力；
- 校验内核：凡含「开发」与「审核」节点的蓝图一律强制校验，与开关无关——任一方缺绑定 → 拒绝；provider 与 model 完全相同 → 拒绝；同 provider 不同 model → 通过 + 弱异源警告；provider 不同 → 通过；
- 编辑器「工作流控制」区只有 ON/OFF 开关，文案明说「硬规则全局强制，与开关无关」；
- 运行时异源日志按节点 id 写死取 `dev` / `review`，导致诊断模板（开发节点 id 为 `fix`）的异源日志完全不触发；
- 契约文档与测试把「全局强制、与开关无关」写成正式约定。

## 6. 修改后

- 蓝图档位字段支持三态：**关 / 弱 / 强**；**缺失 或 旧值 `true` → 弱**（与现状行为完全一致）；旧值 `false` → 关；
- 校验语义：
  - 关档：不做异源校验，不拦截；
  - 弱档（默认）：同 provider 不同 model → 通过 + 弱异源警告；provider 与 model 完全相同 → 拒绝；
  - 强档：provider 必须不同，否则拒绝（即使 model 不同也拒）；
- 拒绝时的错误信息含实际 provider/model 与修复指引；
- 编辑器工作流控制区的开关升级为三档选择器，文案改写为档位说明，随蓝图保存、重开不丢；
- 四套内置模板显式声明弱档；
- 运行时异源日志的识别口径统一为「按节点 id 或角色」，并按当前档位输出；诊断模板的异源日志恢复触发；
- 契约文档与既有测试同步修订。

## 7. 功能范围

1. 蓝图档位字段三态化 + 旧数据兼容读入（缺失/true → 弱，false → 关）；
2. 校验内核按档位判定（关 / 弱 / 强三套语义）；
3. 蓝图与编辑视图之间的投影支持三态双向透传（保存、重开不丢）；
4. 编辑器工作流控制区：现有 ON/OFF 开关升级为三档选择器 + 文案同步（中/英）；
5. 运行时异源日志识别口径统一为「按节点 id 或角色」，并输出当前档位；诊断模板日志恢复；
6. 四套内置模板显式声明弱档；
7. 契约文档同步：蓝图字段语义、硬规则条款、等价性检查清单中异源一行、决策票（修订或替代）；
8. 测试：三档正反例、旧数据兼容、投影往返、模板档位声明、诊断模板日志触发；插件包测试 + 根目录 `npm test`、`npm run validate`、`npm run release:verify` 全绿。

## 8. 不修改范围

- 校验配对范围（仍只「开发↔审核」）；
- 内置模板默认模型绑定（LOC-019）；
- 模型覆盖层与「清除覆盖」语义；
- 运行中模型修订路径（#79）；
- 现有自定义模板的行为（除档位缺失按弱档处理外，无变化）。

## 9. 业务规则

- 默认档 = 弱；**任何未声明档位的蓝图按其原有行为运行**（现状即弱档判定）；
- 三档语义互斥且穷举：关 / 弱 / 强；
- 档位不影响「开发与审核节点是否存在」这一结构要求之外的其他校验；
- 关档下开发与审核使用相同模型属用户显式选择，系统不提示——**这是已知取舍**；
- 档位是蓝图属性，随蓝图保存与迁移；运行中的运行不受后续档位改动影响（快照语义不变）；
- 错误信息必须可读、可定位、含修复指引（沿用现有错误结构，逐字段标红 + 定位首个问题节点）；
- 旧数据兼容优先级高于新语义：存量蓝图行为不得因本次改动改变。

## 10. 用户操作路径

打开编辑器 → 工作流控制区 → 从「关 / 弱 / 强」中选择 → 保存 → 校验按所选档位执行（不合规时按现有错误展示方式给出问题与定位）→ 重开编辑器时档位保持。

运行路径：发起运行时按蓝图当前档位校验，不合规则拒绝并给出指引。

## 11. 异常和边界场景

- 档位缺失或旧值 `true` → 弱档；旧值 `false` → 关档；无法识别的非法值 → 按弱档处理并给出校验错误；
- 无「开发」或「审核」节点的蓝图 → 三档下均跳过异源校验（结构要求仅在存在该对时才有意义）；
- 有开发与审核节点但任一方缺绑定 → 弱档与强档下拒绝（无法证明异源）；关档下不校验；
- 强档下同 provider 不同 model → 拒绝，错误需明确说明档位为「强」；
- 诊断模板（开发节点 id 为 `fix`，角色为「开发」）：识别口径统一后，弱档运行时日志应正常输出异源比对结果；
- 档位切换后重新保存 → 立即按新档位校验（无需重启）。

## 16. UAT 场景

### UAT-01 三档选择与持久化

- 验收目的：档位可选、可存、可重开；
- 前置条件：LOC-019 已交付；插件已加载；
- 操作步骤：
  1. 打开任一套内置模板（或新建工作流），在工作流控制区把档位依次设为关 / 弱 / 强并保存；
  2. 每次保存后关闭编辑器重新打开，查看档位值。
- 预期结果：三档均可选择、保存后重新打开仍显示所选档位。
- 建议人工关注：四套内置模板默认显示为「弱」。

### UAT-02 强档拦截

- 验收目的：强档真正收紧到 provider 级；
- 前置条件：某工作流含开发与审核节点；
- 操作步骤：把档位设为强 → 把开发与审核都设为同一个 provider（model 不同）→ 保存。
- 预期结果：保存被拒，问题定位到模型绑定处，错误信息说明「强档要求 provider 不同」并给出实际值。
- 建议人工关注：错误信息是否可直接照做修正。

### UAT-03 弱档与关档

- 验收目的：默认档与关闭档语义正确；
- 前置条件：同 UAT-02 工作流；
- 操作步骤：
  1. 档位设为弱 → 开发与审核同 provider、不同 model → 保存并运行，观察是否出现弱异源警告；
  2. 档位设为关 → 开发与审核设成完全相同的 provider 与 model → 保存并运行。
- 预期结果：1 通过并给出弱异源警告；2 不报错、可保存可运行。
- 建议人工关注：关档下系统确实不再提示——这是用户显式选择。

### UAT-04 旧蓝图兼容

- 验收目的：存量工作流行为不变；
- 前置条件：存在档位字段缺失或为旧布尔值的工作流；
- 操作步骤：打开该工作流 → 观察档位显示 → 不做修改直接保存 → 发起运行。
- 预期结果：缺失或旧值 `true` 显示并表现为弱档；旧值 `false` 表现为关档；运行结果与改动前一致。
- 建议人工关注：保存前后不应出现新的校验错误。

### UAT-05 诊断模板异源日志

- 验收目的：识别口径统一后日志恢复触发；
- 前置条件：诊断模板档位为弱，修复与审核为同 provider 不同 model；
- 操作步骤：发起一次诊断模板的最小运行，查看运行日志中的异源检查输出。
- 预期结果：日志按角色识别出「修复」与「审核」并输出现行档位与比对结论。
- 建议人工关注：日志中应能看出识别的是角色而非节点名。

## 17. 风险

- 🟡 「关」档会让开发与审核使用同一模型而系统不再提示 → 属用户已确认取舍；文案需明确说明后果；
- 🟡 旧数据形态迁移可能引入行为回归 → 兼容口径以「缺失/true → 弱」为锚，必须有显式回归用例；
- 🟡 既有测试与契约文档把「全局强制、与开关无关」写成正式约定，本次要推翻 → 需同批修订文档与断言，避免文档与实现再次漂移；
- 🟡 编辑器控件升级涉及界面渲染与本地化文案 → 需重建插件产物并重启产品模式后才可见效果；
- 🟡 强档可能与用户已保存的模型覆盖组合出新的拒绝场景 → 错误信息必须能定位到具体节点与档位，避免用户无法自行修复。

## 18. 已知限制

- 只支持「开发↔审核」一组配对，不支持为不同节点对配置不同档位；
- 档位是工作流级属性，不支持节点级异源要求；
- 关档下不提供替代性的独立性提示；
- 编辑器不提供「一键修正为差异化模型」（如 LOC-019 交付回报中提及的临时处置仍为手工）。
