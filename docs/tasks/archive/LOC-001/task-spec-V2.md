## 1. 需求背景

V1（LOC-001）已把「业务结果路由」搬进编辑器：节点侧第 4 态给 `outcomePath` 文本输入 + schema JSON 编辑，边侧给 outcome 名文本输入。V1 交付后用户在真实编辑中提出 4 条反馈，暴露出"能用但不好用"：

1. 路由档切到其它档再切回来，业务结果路径丢失，必须重填；
2. `$.field` 的 JSON 路径格式对不熟悉 DSL 的使用者门槛过高；
3. 节点的业务结果路径与边强耦合，但界面上看不到"哪个取值有没有对应边"；
4. 边的 outcome 名应当从节点声明的取值中选，而不是手打。

## 2. 用户问题

不熟悉 DSL/JSON 的使用者无法顺利完成一条业务结果路由：需要同时理解 `$.field` 路径语法、`output.schema` 的 enum 语义、以及"每个取值必须恰好有一条 outcome 边"这条隐含规则；模式往返还会丢数据，边与取值的对应关系只能靠肉眼比对，容易做出保存不了或语义不完整的图。

## 3. 目标

把「业务结果路由」的录入收敛成三步可观察操作：**填参数名 → 增删取值 → 在边上选值/按图标补齐**。用户不需要写 `$.`、不需要手写 enum、不需要记忆边与取值的对应关系；模式往返不丢已录入内容；与取值不匹配的边在录入当场就被指出。

## 4. 非目标

- 不改 DSL / 内核 / 投影 / 生成器契约：**不新增 `output.resultMode`**，模式仍由 `output.outcomePath` 的存在性推断
- 不改内核对业务结果路由的校验规则（枚举穷举、每个取值恰好一条 outcome 边、禁 success/failure 边与 when、禁 successCondition）
- 不做 `$human-decision` 的 result / 子序列字段编辑；不自动为节点创建 success/failure 边
- 不托管 boolean 型路由字段的参数项列表（该形态仍由 JSON 编辑器编辑，界面给只读提示）
- 不改画布渲染规则（本切片不新增画布元素；边标签沿用 V1 行为）

## 5. 修改前

- 节点「业务结果路由」档：`outcomePath` 手写 `$.field`；schema 以 JSON 文本编辑；取值枚举只存在于 JSON 里，界面不呈现
- 离开该档：`outcomePath` 被清空（V1 规格范围第 3 条"进入/离开该态显式清理字段"），切回来必须重填
- 边「业务 outcome」：outcome 名手打；该取值是否与节点声明一致、是否已被同节点其它边占用，界面不提示
- 边与取值的缺口只能等保存时由内核报错（如「枚举值 X 缺少对应 outcome 出边」）

## 6. 修改后

- 节点路由档呈现三件套：
  1. **业务结果字段**：只填参数名（如 `route`），粘贴 `$.route` 自动归一；提供 schema 中已有可穷举属性名的候选。`$.` 前缀属实现细节，界面不展示（V2 修订，按用户 UAT 反馈）
  2. **业务结果取值**：可 `+` / `-` 的参数项列表，一行一个取值（取值、状态图标与操作在同一行）
  3. 每个取值行尾显示**边存在性图标**：✅ 已存在对应该取值的 outcome 边；⚠️ 尚无（tooltip「无对应边」），点击 ⚠️ 一键补一条 outcome 边（默认目标 `$end`，建后选中可改目标）
- 列表下方给出**反向告警**：图中存在 outcome 取值未在参数项中声明的边（列出边与取值）
- 边表单：源节点处于路由档时，outcome 字段变为**下拉**，选项 = 该节点声明的取值；已被同一节点其它边占用的取值加标注；源节点非路由档时保持文本输入；手写/历史取值仍可见（下拉中标注"未在节点声明"，并在节点侧触发告警）
- 模式往返：路由档 ↔ 输出校验/人工验收/无 ↔ 路由档，参数名与取值列表**不需要重填**

## 7. 功能范围

- F1 友好路径录入：参数名输入（固定 `$.` 前缀、粘贴归一、已有可穷举属性名候选）
- F2 取值参数项列表：`+` / `-` 增删；写入 `schema.properties.<name>.enum` 与 `required`，不破坏 schema 其它属性与 `output.files`
- F3 边存在性图标：✅ / ⚠️，⚠️ 可点击一键补边
- F4 反向告警：边取值未在参数项声明
- F5 边 outcome 下拉：源节点声明取值优先 + 占用标注 + 非路由档回退文本输入
- F6 模式往返保留：进路由档自动恢复参数名与取值
- F7 删除保护：删除仍有边的取值被拦截并提示；无边取值可直接删
- F8 i18n（zh/en）、dist 重建、包内测试与根校验通过

## 8. 不修改范围

校验内核 / 宿主 RPC 面 / 引擎 / 生成器 / 既有模板数据 / 画布渲染 / 模板库 CRUD / 运行看板 / 角色库。

## 9. 业务规则

- **R1 写入契约不变**：参数名 `N` → `output.outcomePath = '$.N'`；取值列表 `[v1..vn]` → `output.schema.properties[N] = { type: 'string', enum: [v1..vn] }`，且 `output.schema.required` 包含 `N`；schema 的其它属性、`output.files`、`successCondition` / `manualCheck` 等既有字段不被破坏
- **R2 参数名**：`[A-Za-z_][A-Za-z0-9_]*`（单段路径）；空名不写 `outcomePath`（保持空串=路由档编辑中）
- **R3 取值**：非空、同一字段内唯一；"每个枚举值恰好一条 outcome 边 / 无重复 outcome 边"仍由内核保存校验兜底
- **R4 删除保护**：某取值仍存在对应 outcome 边时禁止删除（提示先改边）；无边时可删
- **R5 模式语义不变**：切到非路由档仍清空 `outcomePath`（DSL 不留休眠字段），"不丢"靠 R6 + schema 存活实现
- **R6 进档恢复**：进入路由档且 `outcomePath` 为空时——① schema 中恰有一个可穷举 string 属性 → 预填该字段名；② 多个 → 给候选下拉（默认选 `required` 中的第一个）；③ 无 → 留空等输入，取值列表空
- **R7 边存在性判定**：对取值 `v`，"有边" ⇔ 存在 `from === 本节点 id` 且 `outcome === v`（严格字符串相等）的边
- **R8 一键补边**：新增 `{ from: 本节点, to: '$end', outcome: v }`（不带 `on` / `when` / `countRound`），建边后选中该边
- **R9 反向告警**：只读提示，不改数据

## 10. 用户操作路径

主路径（新建一条业务结果路由）：

1. 选中节点 → 「结果判定方式」选「业务结果路由」
2. 「业务结果字段」填 `route`（界面显示 `$.route`）
3. 取值参数项 `+` 两次，填 `pass`、`block`
4. 两行均显示 ⚠️ → 点 `pass` 行 ⚠️ 补边并把目标改为节点 2；点 `block` 行 ⚠️ 补边（默认 `$end`）
5. 两行转为 ✅ → 「保存工作流」成功

往返路径：切到「输出校验」再切回「业务结果路由」→ 字段名与两个取值原样还在。

边侧路径：选中该节点出边 → 类型选「业务 outcome」→ outcome 下拉中选 `pass`。

## 11. 异常和边界场景

| 编号 | 场景 | 期望 |
|---|---|---|
| E1 | schema 中无可穷举字段 | 不预填，等用户输入参数名 |
| E2 | schema 有多个可穷举字段 | 给候选下拉；未选定前不写 `outcomePath` |
| E3 | 该字段不可穷举（无 enum/const/oneOf/boolean） | 取值区提示「该字段不可穷举，无法作为业务结果路由」，保留 JSON 编辑兜底 |
| E4 | boolean 型路由字段 | 只读提示（V2 不托管），JSON 编辑器可改 |
| E5 | 图中 outcome 取值未在列表声明 | 该边仍可查看/保存；节点侧告警行提示；边下拉标注"未在节点声明" |
| E6 | 同一取值被两条边占用 | 取值行图标显示"重复"告警；保存由内核拦截 |
| E7 | 删除仍有边的取值 | 拦截并提示（R4） |
| E8 | fanout 节点 | 保持 V1 行为：禁止 `outcomePath`，切 fanout 时删字段 |
| E9 | 参数名改名 | 同步改 `outcomePath` 与 schema 属性键；目标名已存在则拦截提示 |
| E10 | 切换模板 / 切换选中节点 | 编辑器态不残留（会话记忆不跨模板） |

## 12. 已确认的关键决策及原因

| 决策主题 | 选择 | 原因 | 确认人 | 确认时间 |
|---|---|---|---|---|
| D1 模式往返保留的实现方式 | 编辑器侧「进档恢复 + schema 存活」，**不新增 `output.resultMode`** | 新增契约字段要动内核/投影/生成器/既有模板，属 Target 变更，本轮不值得；A 方案零契约变更且覆盖主用路径 | 用户（会话确认交付路径时采纳推荐 A 方案） | 2026-09-10 |
| D2 取值列表的权威 | `output.schema` 是唯一真源，参数项只是它的编辑器（写入即合并、JSON 改动后重新读回） | 内核已以 schema 为权威，另立字段会造成双源 | Agent 建议，随基线确认 | 2026-09-10 |
| D3 删除有边的取值 | 拦截并提示，而非静默允许 | 内核要求每个枚举值有边；允许删除会把用户推进"保存不了还得回查"的状态 | Agent 建议，随基线确认 | 2026-09-10 |
| D4 参数名录入 | 只填名字；`$.` 前缀属实现细节，界面不展示 | 满足"普通用户不写 JSON 路径"；V2 修订：按用户 UAT 反馈进一步去掉前缀展示，帮助文案改为解释字段作用 | 用户（第 2 条反馈 + UAT 反馈） | 2026-09-10 |
| D5 无人值守许可 | 允许 | 沿用 V1 | 用户 | 沿用 V1 |

## 15. 验收条件

- [ ] 路由档下只填参数名即可（`$.` 前缀属实现细节，界面不展示）；粘贴 `$.route` 自动归一为 `route`；字段旁帮助文案说明该字段的作用
- [ ] 取值行内「取值输入 / 状态图标 / 建边 / 删除」**在同一行**展示（不折行）
- [ ] 参数项可 `+` / `-`；保存的 DSL 中 `outcomePath` 与 `schema.properties.<name>.enum` 与列表一致，`required` 含该字段，schema 其它属性与 `files` 未被破坏
- [ ] 每个取值显示边存在性图标；无边取值的图标可一键补边（默认 `$end`），补边后转为"已有边"
- [ ] 图中存在未声明的 outcome 取值时，列表下方出现告警行
- [ ] 删除仍有边的取值被拦截并提示；删除无边取值直接生效
- [ ] 选中路由节点的出边时 outcome 为下拉且选项 = 该节点声明取值；已被其它边占用的取值有标注；源节点非路由档时仍是文本输入
- [ ] 路由档 → 输出校验 / 人工验收 / 无 → 回路由档：参数名与取值列表**无需重填**（本项是对 V1「显式清理字段」行为的修改）
- [ ] fanout 节点、boolean 路由字段、旧模式节点与 success/failure/when 行为不回归
- [ ] zh/en 文案齐全；包内测试新增断言并通过；`npm run build` 后 dist 一致性检查通过；根 `npm test`、`npm run validate` 通过

## 16. UAT 场景

### UAT-01 新建业务结果路由（主路径）

- 验收目的：普通用户不写 JSON 也能从零建成一条业务结果路由
- 前置条件：编辑器打开任一模板；有一个 2 节点以上的图
- 操作步骤：节点切「业务结果路由」→ 参数名填 `route` → 取值 `+` 出 `pass`、`block` → 点 `pass` 行 ⚠️ 补边并改目标 → 点 `block` 行 ⚠️ 补边 → 保存
- 预期结果：两行图标转为"已有边"；保存成功；DSL 中 `outcomePath = "$.route"`、`schema.properties.route.enum = ["pass","block"]`
- 建议人工关注：`$.` 前缀是否只读显示、取值行间距与图标辨识度

### UAT-02 模式往返不丢

- 验收目的：V1 反馈第 1 条被消除
- 前置条件：UAT-01 的节点
- 操作步骤：切「输出校验」→ 再切回「业务结果路由」
- 预期结果：参数名与两个取值原样还在，不需要重填
- 建议人工关注：schema 里该字段的 enum 是否被清空

### UAT-03 边侧下拉与自检

- 验收目的：V1 反馈第 3、4 条被消除
- 前置条件：UAT-01 的节点与边
- 操作步骤：选中 `route → 节点2` 的边 → 类型选「业务 outcome」→ 观察 outcome 字段；再手写一个不存在的取值
- 预期结果：outcome 为下拉且含 `pass` / `block`；已被占用的取值有标注；手写值触发参数项区告警行
- 建议人工关注：占用标注的可读性

### UAT-04 删除保护

- 验收目的：删除路径不会把用户推进不可保存状态
- 前置条件：UAT-01 的节点
- 操作步骤：点 `pass` 行的 `-`
- 预期结果：被拦截并提示"该取值仍有对应边，请先处理边"
- 建议人工关注：提示文案是否指出是哪条边

## 17. 风险

- 参数项与 JSON 编辑器双入口可能互相覆盖：以 D2 约束（写入即合并、JSON 改动后列表重算）；UAT-03 覆盖
- 一键补边默认指向 `$end`，用户若需指向中间节点要手动改目标（可接受，UAT-01 覆盖）
- 会话记忆不跨模板：极端路径（切档 → 切模板 → 切回）仍需重填，记入已知限制

## 18. 已知限制

- 不新增 `output.resultMode`：若用户在非路由档把 schema 里那个可穷举字段删掉，切回路由档无法自动恢复（需重填）——这是 D1 的代价，B 方案可彻底解决，留待 Target 版本
- boolean 型路由字段不提供参数项列表
- 会话记忆不落盘，仅在同一次编辑会话内有效
