## 摘要（三要素）

**目标：** 同一次运行从第一次调用到最后一次调用读到的角色正文是同一份；快照能回答「本 Run 用的是哪一版角色」。

**范围：** 做——生成器把「本图实际引用到的自定义角色」正文一并内联并加尺寸闸门、Rev1 快照记角色身份与内容摘要、读不到/超限时显式降级并留控制事件。不做——改内置角色内联机制、删产物旁角色包、改角色库编辑语义、提供「运行中切角色」入口。

**验收标准：**

- [ ] AC-01：起一个用到 `dispatcher` 的运行，等待期间改写 `dsh/roles/dispatcher.md`，恢复后节点角色正文仍是运行时那一版。
- [ ] AC-02：同一运行重复恢复三次，三次读到的角色正文完全一致。
- [ ] AC-03：新建运行读到修改后的角色正文（冻结只作用于已存在的运行）。
- [ ] AC-04：内置角色不回归（现有生成物比对与 `role-manifest` 用例保持通过）。
- [ ] AC-05：构造「角色文件读不到」，运行仍继续且摘要记未内联并有控制事件。
- [ ] AC-06：`npm run generate && npm run validate` 不因本改动新增失败项。

## 成立性判定（本会话复核结论）

**部分成立，但命中面比原票更具体。**

- 已修的一半：内置角色正文在编译期内联进冻结脚本（`ROLE_DEFS`），等待期间改文件不影响本 Run；Rev1 存脚本且续跑恒用 Rev1。
- 未修的一半：快照 `roles` 只有可变路径 `role_dir`，自定义角色（`builtin:false`）运行期仍是**工作区路径优先**读文件。
- 命中的真实范围：唯一自定义角色是 `dispatcher`（`builtin:false`），被 `dev-workflow-2-0` 与 `default-workflow` 两套已发布模板的 `dispatch`/`route` 节点使用；而 `.generated` 产物旁没有 `roles/` 包（实测），`findRoleDir` 返回空时打包路径与工作区路径重合——**只剩一个可写目录内的可变路径**，冻结形同不存在。
- 需要如实标注的一点：这条读文件路径是当年**有意保留**的兼容取舍（宿主注释「兼容角色（builtin:false，不内联）靠它走读文件路径」；生成器注释「自定义先工作区再打包快照，编辑种子到工作区后对 bundled run 生效」）。因此本切片等于**重新决定一项已确认取舍**，不能当作疏漏直接修——本会话已按决策 3=A 由人工确认撤销该取舍。
- 成本核对：正文内联不会撞编译上限（角色最大 9KB、合计 64KB；编译输入上限 120KB、输出上限 1MB，现有生成物 133–151KB）。「拷贝目录」方案则要新增每 Run 私有角色目录的生命周期与回收。
