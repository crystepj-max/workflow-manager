# Integration Gate 自动重跑闸门（LOC-017）

| 元数据 | 值 |
|---|---|
| 需求基线版本 | V2 |
| 对应 Issue | 无（本地轨道；GitHub 同步 = pending） |
| 优先级 | P1 |
| 前置依赖 | LOC-008（已合并） |
| 无人值守许可 | 允许 |
| 定义时间 | 2026-09-11 |
| 当前状态 | 待确认 |

> V1 → V2 变更原因：V1 三要素把「载体」推迟到施工期，且「重算受影响依赖」超出了运行时现状。本次分析核查出 3 项未决产品事项与 1 项闸门误放行缺口，经用户确认后升版。

## 1. 需求背景

`docs/design/v0.1-parallel-development-plan.md` §9.3 规定 PR 合并前必须走 Integration Checkpoint 六步。目前只有内核算法（观测目标 HEAD、判定 Proof 覆盖、集成锁）和一份**手工** Bootstrap CLI（`scripts/cwf-checkpoint.mjs`），六步中的「sync/rebase/merge」与「重跑受影响 Review/Test」**没有任何代码路径**，靠人和 Agent 自觉执行；`assertIntegrationAllowed` 除单测外没有调用者。

结果是：多个 Run 从同一 base 派生、其中一个先合并时，其余 Run 的旧 Proof 可能被当成仍然有效，闸门形同虚设。

## 2. 用户问题

并行开发的 Run 在集成时，我需要人工判断「main 是否已经前进、我的证明是否还有效、要不要重跑」。一旦遗漏，就会出现「Test 证明验的是旧 HEAD，却给新的集成放了行」——用户拿到的是没有在当前代码基线上验证过的结果。

## 3. 目标

建设流程在进入人工验收前，**自动**完成 §9.3 的第 1–5 步：观测目标 HEAD → 目标已前进则自动同步 → 产生新的产物版本 → 自动重跑受影响的审核/测试 → 全部证明覆盖当前版本后才放行集成；否则拦截并给出原因。用户不再需要手工跑 checkpoint 命令或自行判断证明是否失效。

## 4. 非目标

- 不改 git merge/rebase 策略本身（沿用仓库既有做法）。
- 不做跨仓库 / 多目标集成。
- 不做 Container / Remote Provider。
- 不重写 `scripts/workspace-isolation.mjs` 与 `scripts/formal-records.mjs` 的算法与语义。
- 不新增 UI（看板呈现归 LOC-016）。
- 不改 `scripts/local-task-merge.mjs` 的合并闸门（见 §18 已知限制）。
- 不做精确受影响子集的重算（见 §12 决策 2）。

## 5. 修改前

- 未前进 / 已前进、证明是否失效，全部由人或 Agent 自行判断。
- 需要人工执行 `node scripts/cwf-checkpoint.mjs <runDir>`，并靠 `--proofs-rerun` **自述**已重跑；该命令只校验声明，不触发任何重跑。
- 目标前进后，sync 与重跑 Review/Test 无代码支撑。
- checkpoint 结果只打印到终端，写进证据包靠人工粘贴。
- 集成锁的 RPC 已注册但没有任何编排代码调用。

## 6. 修改后

- 建设流程在「测试通过」与「进入人工验收」之间自动执行集成闸门，用户无需操作。
- 目标前进时：自动获取集成锁 → 自动同步 → 自动产生新的产物版本 → 自动重跑本 Run 的审核与测试 → 全部证明覆盖当前版本后自动放行并进入人工验收。
- 目标未前进时：闸门直接放行，不额外重跑。
- 无法获取集成锁时：Run 进入 BLOCKED 并提示占用方；锁释放后可在同一逻辑运行上继续。
- 闸门判定结果落盘可追溯，人工验收时能看到「闸门何时跑的、目标 HEAD 是什么、重跑了什么」。

## 7. 功能范围

1. **集成闸门编排**：串接既有内核 `observeTargetHead` / `computeIntegrationCheckpointFromRepo` / `recordSourceSync` / `coverageStatus` / `assertIntegrationAllowed`，落在产品运行时（决策 1）。
2. **自动同步**：目标前进时自动 sync/rebase/merge 工作分支到目标最新 HEAD，并 `recordSourceSync` 刷新 Source Revision。
3. **新产物版本的产生**：同步后按新 Source Revision 重签本 Run 的产物记录，产生新的 Record Revision，使旧 Proof 被 `coverageStatus` 判为 `not_covering_current`（补齐 V1 未写明的必要环节，见 §9 B4）。
4. **自动重跑**：自动重跑本 Run 的审核与测试节点，回收新 Proof（决策 2 = 保守全量）。
5. **集成锁**：闸门窗口内全程持有集成锁并心跳刷新（决策 3）。
6. **门禁与生命周期**：放行 / 拦截 / BLOCKED 三种结果与既有 Logical Run 生命周期的衔接。
7. **结果落盘**：判定与重跑事实写入运行记录与证据包。
8. **E2E 与回归测试**：双 Run 场景真机验证。

## 8. 不修改范围

- `scripts/workspace-isolation.mjs` 的算法实现（只调用，不重写）。
- `scripts/formal-records.mjs` 的内核语义（追加式 Store、Revision 分配规则）。
- `scripts/cwf-checkpoint.mjs` 的既有纯函数与 CLI 行为（Bootstrap 路径保持可用；`computeCheckpoint` 仍被内核复用）。
- 四套正式模板的业务语义与节点结论词表。
- `templates/*.json` 的既有节点与边（若施工选择以模板节点承载闸门，只允许新增、不得改动既有转移语义，并须重跑 `npm run generate`）。
- 生成产物 `.generated/`（只通过重新生成更新）。
- `docs/design/` 与 `specs/` 的契约正文。

## 9. 业务规则

- **B1 闸门的触发范围**：仅 Git 支撑的 `ISOLATED_WRITE` 运行（建设、优化-git、诊断）。`ISOLATED_READ`（探索）与 `SANDBOX` 运行不触发集成闸门。
- **B2 触发时机**：建设流程中「测试通过」之后、「进入人工验收」之前自动执行，对应 §9.3 第 1–5 步；第 6 步人工验收/合并保持人工，AI 不代签。
- **B3 未前进即放行**：目标当前 HEAD 等于本 Run 的集成基线时，不重跑、不额外耗时，直接放行。
- **B4 同步必须产生新产物版本**：目标前进时，同步后必须产生新的 Record Revision。若同步未产生新版本，**不得放行**，也**不得**报告 `rerun_completed`。原因：`assertIntegrationAllowed`（`scripts/workspace-isolation.mjs:437-459`）只比对 Proof 依赖的 Record Revision，版本未变时旧 Proof 仍判 `COVERING`，闸门会放行且谎报已重跑。
- **B5 重跑范围 = 本 Run 全部审核/测试**：不计算精确受影响子集。理由：`recordSourceSync` 改的是整个 workspace 的 Source Revision，本 Run 全部 Proof 同时失去背书，「受影响」在本场景就等于「整个 Run」。
- **B6 重跑必须真正执行**：`proofs_state` 只能由实际重跑产出新 Proof 得出，不得由「无 stale Proof」推定。
- **B7 旧 Proof 不删除**：被替代的 Proof 保留在 Store 中并标记 stale（沿用既有口径）。
- **B8 重跑结论具约束力**：重跑后审核或测试判 `RETURN_DEV` 时，闸门不得放行，按既有转移语义回到开发节点并计入既有轮次语义。
- **B9 集成锁全程持有**：锁在「获取 → 同步 → 重跑 → 判定 → 放行」整个窗口内有效，期间按 TTL 心跳刷新；不得在重跑期间释放。
- **B10 锁冲突不破坏运行**：抢不到集成锁时 Run 进入 BLOCKED 并提示占用方；锁释放或过期后，可在**同一逻辑运行**上继续，不新建逻辑运行、不消耗回退额度。
- **B11 锁的粒度**：键为 `repo:<repository>:target:<ref>:integration`，不同目标的 Run 可并行集成。
- **B12 结果必须落盘**：闸门判定（目标 HEAD 观测值、是否前进、重跑了哪些节点、最终结论）写入运行记录与证据包，不得依赖人工粘贴。
- **B13 fail closed**：观测目标 HEAD 失败（仓库不可读、ref 不存在、Git 元数据损坏）时拒绝放行，不得回落调用方自报 HEAD。

## 10. 用户操作路径

1. 用户在建设流程里正常跑到「测试通过」。
2. 系统自动执行集成闸门（用户无需操作）：
   - 目标未前进 → 直接进入人工验收。
   - 目标已前进 → 自动获取集成锁 → 同步 → 产生新产物版本 → 重跑审核与测试 → 通过后进入人工验收。
   - 目标已前进但审核/测试重跑后判 RETURN_DEV → 回到开发节点，不进人工验收。
   - 集成锁被别的 Run 占用 → Run 显示 BLOCKED 并说明占用方。
3. 用户做人工验收，此时看到的证明全部对应集成当下的代码基线。
4. 用户放行后进入收口与合并。

## 11. 异常和边界场景

| 场景 | 期望行为 |
|---|---|
| 目标在闸门执行期间再次前进 | 本次结果作废，重新观测；不得用过期观测放行 |
| 同步产生 rebase 冲突 | fail closed：不放行，Run 进入需人工介入的状态并说明冲突文件 |
| 仓库不可读 / ref 不存在 | fail closed 拒绝放行（B13） |
| 集成锁被占用且未释放 | BLOCKED；锁 TTL 过期后可自动接管继续 |
| 重跑期间锁 TTL 到期 | 心跳刷新续期；刷新失败按 fail closed 处理并在运行记录留痕 |
| 重跑过程中进程中断 | 恢复后从正确位置继续；已产出的新 Proof 不得回退为旧 Proof 背书 |
| 同一 Run 已有更晚的同步结果 | 不得重复同步；已有新版本时直接重新判定 |
| 非 Git 运行（探索 / sandbox） | 不触发闸门（B1） |

## 13. 功能切片关系

- 本切片：集成闸门从「被拦」到「自动重跑后放行」的完整闭环，单一可独立 UAT 的切片。
- 兄弟切片：无（不拆分）。
- 拆分原则：最小可独立 UAT 的完整功能切片。
- **不拆分的理由**：「只判定拦截、不自动重跑」正是决策③已否掉的半自动形态，不应作为独立交付物出现。

## 15. 验收条件

- [ ] E2E：Run A 与 Run B 同 base 派生，A 先合并；Run B 集成被拦 → 自动 sync → 受影响审核/测试自动重跑 → 重验通过才放行
- [ ] 旧 HEAD 的 Test Proof 不为新集成背书（集成前任一 Proof 判 `not_covering_current` 即拒绝）
- [ ] 同步未产生新产物版本时拒绝放行，且不得报告 `rerun_completed`（B4/B6）
- [ ] 重跑结论为 `RETURN_DEV` 时不放行，按既有语义回到开发节点（B8）
- [ ] 集成锁被占用 → Run 进 BLOCKED 且提示占用方；锁释放后可继续同一逻辑运行；锁在整个闸门窗口内有效，无第二方插入（B9–B11）
- [ ] 闸门判定结果落盘可追溯（运行记录事件 + 证据包字段），无需人工粘贴（B12）
- [ ] 目标未前进时不触发重跑、不额外耗时（B3）
- [ ] `workspace-isolation` 既有测试不改断言全绿；`npm test`、`npm run validate` 全绿

## 16. UAT 场景

### UAT-01 双 Run 集成：被拦 → 自动重跑 → 放行（主场景）

- 验收目的：确认目标前进后闸门自动完成 §9.3 第 1–5 步，且重验通过才放行。
- 前置条件：
  1. 有可写 Git 仓库与可用的产品 DSH 运行环境。
  2. Run A 与 Run B 从同一 `base_commit` 派生，各自有实现产物与审核/测试证明。
- 操作步骤：
  1. 让 Run A 先完成并合并到目标分支。
  2. 让 Run B 走到「测试通过」，进入集成闸门。
  3. 观察 Run B 的运行记录与最终状态。
- 预期结果：
  1. 闸门观测到目标 HEAD 已前进，Run B 集成被拦。
  2. 自动获取集成锁，自动同步到目标最新 HEAD。
  3. 产生新的产物版本，旧 Proof 被标 `not_covering_current`（保留不删）。
  4. 自动重跑审核与测试，产出对应新版本的新 Proof。
  5. 全部 Proof 覆盖当前版本后放行，进入人工验收。
  6. 全过程无需人工执行任何命令。
- 建议人工关注：重跑的是否只是本 Run 的审核/测试；目标 HEAD 观测值是否来自真实仓库。

### UAT-02 旧 HEAD 的证明不为新集成背书（反例）

- 验收目的：确认不变量成立——Test Proof 验的是 H1、实际集成 HEAD 是 H2 时，旧 Proof 不得显示为当前有效。
- 前置条件：Run B 已有绑定 H1 的审核/测试 Proof；目标 HEAD 前进到 H2。
- 操作步骤：
  1. 触发 Run B 的集成闸门。
  2. 检查闸门判定与 Proof 状态。
- 预期结果：
  1. 绑定 H1 的 Proof 被判 `not_covering_current` 并标记 stale。
  2. 在未产出覆盖 H2 的新 Proof 前，闸门拒绝放行。
  3. 不存在「未重跑却报告已重跑」的情况。
- 建议人工关注：`proofs_state` 是否与实际重跑事实一致。

### UAT-03 集成锁被占用（BLOCKED 与恢复）

- 验收目的：确认锁冲突不破坏运行，且可在同一逻辑运行上继续。
- 前置条件：另一 Run 已持有同一目标的集成锁。
- 操作步骤：
  1. 让本 Run 进入集成闸门。
  2. 观察状态；再释放另一 Run 的锁。
  3. 让本 Run 继续。
- 预期结果：
  1. 本 Run 进入 BLOCKED，提示锁被占用及占用方。
  2. 锁释放后可在同一逻辑运行上继续，不新建逻辑运行、不消耗回退额度。
  3. 整个闸门窗口内锁无第二方插入。
- 建议人工关注：BLOCKED 期间是否仍有后台写操作。

### UAT-04 重跑判 RETURN_DEV

- 验收目的：确认重跑结论具有约束力。
- 前置条件：同步到新 base 后，审核或测试重跑会判 `RETURN_DEV`（可用可控注入构造）。
- 操作步骤：
  1. 触发集成闸门，让重跑发生。
  2. 观察流程走向与状态。
- 预期结果：
  1. 闸门不放行，不进入人工验收。
  2. 按既有转移语义回到开发节点，轮次语义与既有 `countRound` 一致。
- 建议人工关注：是否出现「判 RETURN_DEV 但仍放行」的路径。

### UAT-05 目标未前进（快速路径）

- 验收目的：确认无谓重跑不会发生。
- 前置条件：目标 HEAD 等于本 Run 的集成基线。
- 操作步骤：让 Run 走到集成闸门，观察。
- 预期结果：直接放行，不重跑审核/测试，无额外等待；判定结果仍落盘。
- 建议人工关注：是否仍产生了新的产物版本（不应产生）。

## 17. 风险

- **R1 同步语义变化只由审核把关 🟡**：因为不重跑开发节点（决策 2），rebase/merge 冲突解决若引入语义变化，唯一把关是重跑的审核。缓解：审核重跑为强制项，不可跳过；审核结论按 B8 具约束力。
- **R2 重跑耗时与锁长期占用 🟡**：全量重跑最长，锁靠心跳续期。缓解：TTL 兜底释放；刷新失败 fail closed 并留痕（§11）。
- **R3 目标在闸门执行期间再次前进 🟡**：缓解：每次放行前重新观测，不得复用过期观测。
- **R4 非 Git 运行误触发 🟡**：缓解：B1 明确适用范围，并有对应测试。
- **R5 与 LOC-010 建设模板正式化的相互影响 🟡**：若施工选择以模板环节承载闸门，需与已验收的正式建设模板保持一致，并重跑 `npm run generate` / `npm run validate`。
- **R6 过程不可见导致人工验收失去依据 🟡**：缓解：B12 要求落盘，看板呈现由 LOC-016 承接。

## 18. 已知限制

- `scripts/local-task-merge.mjs` 的合并闸门不校验集成结果，本地轨道的合并仍可绕过闸门。本任务不修改它；闸门的效力通过运行生命周期（未放行即不进入收口/合并）体现。建议后续独立任务处理。
- Bootstrap shim 路径（`scripts/cwf-checkpoint.mjs`）保持现状，不升级为自动编排；外部 Agent 手工路径在本轮不享受自动化。
- 精确受影响子集的重算不在本轮（决策 2），全部审核/测试都会重跑。
- 不做跨仓库/多目标集成。
