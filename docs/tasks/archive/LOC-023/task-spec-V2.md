## 1. 需求背景

仓库采用「一任务一分支一独立工作区」的并行开发模式，工作区口径由 `docs/design/workspace-directory-convention.md`（通用标准模板 v1.0）与已接受决策 `docs/design/decisions/0001-workspace-directory-convention.md` 定义。

LOC-019 收口（2026-09-13）实测发现：交付链多处文字与已被接受的决策 0001 第 6 条相悖，且机器校验器在工作区内运行时给出错误结论，导致 `npm run validate` 在正常交付节奏下必然失败。

## 2. 用户问题

交付操作者（人）与交付执行体（AI）在收口时会看到两条互相否定的指引：

- 交付链文字（runbook、公共契约、离线轨道说明、任务目录说明、合并脚本提示与测试断言）说「已合并任务的工作区与分支**暂不删除**」；
- 机器校验器 D-7 说「终态任务的工作区**必须已清理**」。

结果是：按文字执行 → 校验失败；按校验器执行 → 与文字冲突。**正常交付节奏下 `npm run validate` / `npm run release:verify` 永远无法全绿**，发布前机器闸门失去可信度。

同一个校验器在链接工作树内运行时，还会把主检出误判为「治理区工作区」，并读取分支内的旧登记册快照，得出与主检出侧不一致的结论。

## 3. 目标

交付操作者获得一个**口径唯一、两侧结论一致、在正常交付节奏下可全绿**的工作区校验闸门：

1. 「终态任务的工作区何时必须清理」在文档与校验器之间有唯一答案，不再互相否定；
2. 校验器在主检出与任一链接工作树内运行，对同一仓库给出**同一组结论**；
3. 收口动作自动完成工作区清理（分支保留），无需人工补一步；
4. `npm run validate`、`npm run release:verify` 在主检出侧全绿；根目录 `npm test` 全绿。

## 4. 非目标

- 不改 `.generated/`、`.agent-runs/`、`.task-runs/` 不入库的口径；
- 不处理 GitHub / CNB 远端凭据问题（另案）；
- 不动 LOC-021 的异源档位范围；
- 不改动在制任务的工作区（LOC-020 / LOC-021）；
- 不删除或迁移 `/Users/chris/.codex/worktrees/**`（外部运行时资产）；
- 不引入新的定时任务或常驻调度。

## 7. 功能范围

1. **口径收敛**：修订 6 处交付链文字（runbook、公共契约仓库内 + skill 副本、离线轨道说明、任务目录说明、合并脚本头注释与 `cleanup_hint`）与 1 处测试断言，统一为「删工作区、留分支」。
2. **校验器定位修正**：`scripts/validate-workspace.mjs` 分离两个角色——**锚点**（登记册 / 归档 / 过程产物根，唯一真源在主检出，由 `git rev-parse --git-common-dir` 的父目录解析）与**被校验集合**（排除主检出的全部工作区，含调用方自身所在的工作树）。
3. **例外区补齐**：`EXEMPT_PATH_SEGMENTS` 增补 `.codex/worktrees`（外部运行时工作区，按约定 §1.10 计警告不计失败）。
4. **收口动作补齐**：`scripts/local-task-merge.mjs` 在证据锚定与摘要生成之后、且通过干净性检查的前提下自动删除本次任务工作区；同时自动写入 `branch_retained = true`。
5. **数据补齐**：为 LOC-014 / LOC-019 补 `branch_retained = true`；按归档任务卡考出的真实分支名回填 LOC-005（`dev-loc-005-r1`，分支已不存在 → `branch_retained = false`）；LOC-001 从未有分支记录，保持 `null` 并由 D-10 显式标注为不可核验（不伪造数据）。
6. **存量清理**：清理 `dev-loc-014-r1`、`dev-loc-019-r1` 两个终态工作区（**保留分支**）。
7. **回归用例**：见 §15。

## 8. 不修改范围

- 不改变工作区的命名派生规则（目录名 = 分支名）、相邻容器布局、产物锚定主检出规则；
- 不改变 D-1~D-10 的检查项目集合与判定语义（除 §7.3 的例外区清单与 §7.2 的锚点/集合分离）；
- 不改变在制任务的处理方式（约定 §3.2：在制工作区保留，不强制回改）；
- 不改变两阶段收口中「阶段二（托管恢复后）删分支」的口径。

## 9. 业务规则

| 编号 | 规则 |
|---|---|
| R-1 | 终态任务的**工作区必须清理**，**分支必须保留**（阶段一口径）。判据：工作区可再生（`git worktree add`），分支不可再生（补 PR 的唯一载体） |
| R-2 | 校验器的「数据锚点」永远是**主检出**（登记册、归档目录、过程产物根只有一份，在主检出）；「被校验集合」= 登记的全部工作区**去掉主检出**，其余全部纳入（含调用方自身所在的工作树） |
| R-3 | 外部运行时 / 编辑器创建的工作区属**例外区**，只计警告不计失败（约定 §1.10）；本仓库已登记：DSH 三处 workspaces、Cursor worktrees、**Codex worktrees（本轮新增）** |
| R-4 | 自动删除工作区的硬约束（无人值守前置）：仅当①登记册状态为已合并/已取消 ②归档三件套核对通过 ③证据明细已按锚定规则落主检出 ④工作区无未提交改动 同时满足才删；**禁止使用 `--force`**；删除失败只登记为遗留，不阻塞合并 |
| R-5 | 工作区删除后必须追加 `git worktree prune` 兜底注销失效登记 |
| R-6 | 涉及登记册 / 看板等共享文件的动作必须在**无并发写入**时执行（约定 §2.5 / §3.3） |
| R-7 | 已接受的决策记录永不修改；如需改变 0001 第 6 条须新写决策条目并标注 `Superseded by`（本轮不涉及） |
| R-8 | 已合并但**无分支记录**的任务，D-10 必须给出**非失败**的显式说明（列出任务与原因），不得以「静默跳过 + 输出全部一致」的方式掩盖不可核验项（V2 新增） |
| R-9 | 登记册数据只按**已存在的事实**回填（归档任务卡、合并提交、证据摘要）；不得为凑覆盖率伪造分支名或字段值（V2 新增） |

## 10. 用户操作路径

**路径 A · 交付操作者验证闸门（主要路径）**

1. 在主检出目录执行 `npm run validate:workspace`；
2. 期望：D-1~D-10 全部 ✅，退出码 0，无终态任务工作区残留；
3. 在任一链接工作树内执行 `node scripts/validate-workspace.mjs --repo <工作树路径>`；
4. 期望：结论与第 2 步逐项一致（D-2 / D-3 / D-4 / D-5 不再出现「主检出被当作工作区」的条目）。

**路径 B · 收口**

1. 任务通过人工验收（accept / conditional_pass）；
2. 执行 `node scripts/local-task-merge.mjs --task <任务标识> --branch <分支> --decision accept ...`；
3. 期望：脚本完成归档三件套 → 登记册改「已合并」并写 `branch_retained = true` → 删除本任务工作区 → `git worktree prune`；
4. 期望：分支仍存在（`git branch --list <分支>` 有输出），可用 `git worktree add` 重建工作区；
5. 期望：收口后立即执行 `npm run validate:workspace` 通过，无需人工补动作。

**路径 C · 存量收敛**

1. 先执行只读核对：工作区未提交改动数、被忽略内容清单、证据明细是否已在主检出、归档三件套是否齐备；
2. 核对通过后逐个删除两个终态工作区（保留分支）；
3. 期望：`git worktree list` 只剩主检出与 2 个在制工作区 + 例外区工作区；D-7 通过。

## 11. 异常和边界场景

| 场景 | 期望行为 |
|---|---|
| 收口时工作区有未提交改动 | **拒绝删除**（不用 `--force`），删除失败登记为遗留项，合并主路径不阻塞 |
| 收口时归档三件套或证据摘要生成失败 | 跳过工作区删除（R-4 前置未满足），登记遗留，合并不阻塞 |
| 校验器在链接工作树内运行 | 读取主检出的登记册与归档；被校验集合排除主检出、包含当前工作树自身 |
| 校验器在非 git 仓库目录运行 | 现有行为：报错退出码 2 |
| 例外区工作区违反命名规则 | 计警告（⚠️），不计失败；不影响退出码 |
| `branch_retained` 与分支实际存在性不一致 | D-10 报失败（现有语义不变） |
| `main` 分支尚未包含某任务的合并提交 | D-7 只认登记册状态，不改判定依据 |
| 并发会话正在写登记册 / 看板 | 收口类动作应择时执行（R-6）；被覆盖时以登记册真源为准重跑 |
| 存量工作区内存在被忽略但未归档的内容 | 删除前必须逐项核对；测试夹具（`.scratch/ws-isolation-tests`）属可再生，可删 |
| **已合并任务无分支记录**（如 LOC-001） | D-10 输出**非失败**说明行，列出该任务与原因（「历史上未登记分支，口径不可核验」），不计入 failures，不伪造分支名（R-8 / R-9） |
| **调用方所在工作树自身含已跟踪的过程产物漏网** | 该侧 D-6 报失败、主检出侧报通过——属 R-2 保留的合并前自查能力，不算两侧不一致（V-3 前提） |

## 16. UAT 场景

### UAT-01 主检出侧闸门全绿

- 验收目的：确认正常交付节奏下工作区闸门可全绿（对应 V-2 / V-12）
- 前置条件：
  1. 存量清理已完成（V-9）；
  2. 仓库无并发写入（R-6）。
- 操作步骤：
  1. 在主检出目录执行 `npm run validate:workspace`；
  2. 执行 `npm run validate`；
  3. 执行 `npm run release:verify`。
- 预期结果：
  1. 第 1 步输出 D-1~D-10 全部 ✅、退出码 0；终态任务残留项为空；
  2. 第 2、3 步退出码 0。
- 建议人工关注：D-7 的报告行是否仍把对外部运行时工作区的判断写成「失败」而非「警告」。

### UAT-02 工作树内运行与主检出侧结论一致

- 验收目的：确认校验器定位口径修正（对应 V-3 / V-4）
- 前置条件：
  1. 存在至少一个在制任务的链接工作树（当前为 `dev-loc-020-r1` / `dev-loc-021-r1`）。
- 操作步骤：
  1. 在主检出执行 `node scripts/validate-workspace.mjs --json > /tmp/main.json`；
  2. 在工作树内执行 `node scripts/validate-workspace.mjs --repo <工作树路径> --json > /tmp/wt.json`；
  3. 逐项比对两份 JSON 中各检查项的 `ok` 字段。
- 预期结果：
  1. 各检查项 `ok` 逐项一致；
  2. 工作树侧输出中不再出现 `/Users/chris/workspace/workflow-manager  目录名=...  分支=...` 一类把主检出当工作区的条目；
  3. 工作树侧仍报告该工作树自身的 D-2 / D-3 / D-4 结论。
- 建议人工关注：两侧读到的登记册终态任务条数应一致（修改前实测为 16 vs 17）。

### UAT-03 收口自动清理与安全门

- 验收目的：确认收口闭环与删除安全门（对应 V-6 / V-7）
- 前置条件：
  1. 任务已通过人工验收；
  2. 该任务工作区先处于「干净」状态执行一次；再制造未提交改动执行一次。
- 操作步骤：
  1. 干净状态下执行 `local-task-merge.mjs`（可用 `--dry-run` 先看计划）；
  2. 查看工作区是否被删除、分支是否存在、是否执行了 prune；
  3. 在另一任务上制造工作区未提交改动后执行收口。
- 预期结果：
  1. 第 1 步：归档三件套先入库，随后工作区被删除；分支保留；`git worktree prune --dry-run` 输出为空；
  2. 第 3 步：删除被拒绝，收口输出中登记该遗留项，合并本身仍完成（或按脚本既定口径中止并说明），**未使用 `--force`**。
- 建议人工关注：收口输出中的遗留项是否被如实记录、未谎报已清理。

### UAT-04 例外区与存量收敛

- 验收目的：确认例外区口径与存量清理结果（对应 V-5 / V-8 / V-9）
- 前置条件：
  1. `.codex/worktrees` 下存在工作区（当前存在 1 个）。
- 操作步骤：
  1. 执行 `npm run validate:workspace` 观察 D-2 的警告行；
  2. 执行 `git worktree list` 核对存量收敛结果；
  3. 执行 `node -e "..."` 或直接查看 `docs/tasks/registry.json` 核对 LOC-014 / LOC-019 的 `branch_retained`。
- 预期结果：
  1. Codex 工作区以 ⚠️ 警告形式出现，不计失败；
  2. `git worktree list` 仅含主检出、2 个在制任务工作区、例外区工作区；无终态任务工作区；
  3. LOC-014 / LOC-019 的 `branch_retained = true`，两任务分支仍存在。
- 建议人工关注：被删除的工作区对应分支是否仍可用于 `git worktree add` 重建。

## 18. 已知限制

- 例外区工作区仍违反命名派生规则（外部运行时不遵守本约定命名），只计警告；这是约定 §1.10 的既有取舍，不在本轮改变。
- 存量清理只覆盖本仓库当前 2 个终态工作区；其他并行项目是否存在同类残留不在本轮范围。
- `release:verify` 中「生成 / 构建 / 产物新鲜度」等阶段是否通过取决于仓库当时状态，本任务只保证工作区闸门不再是阻塞原因。
- **LOC-001 的收口口径永久不可核验**（该任务先于 Run 证据链机制落地，从未有分支），D-10 只能显式标注，无法补齐（R-9 禁止伪造）。这是本任务验收 V-8 的天花板：覆盖率上限 15/16。
- V-12 的「主检出侧」验证只能在合并到 `main` 之后完成——候选校验脚本本身位于任务分支，未合并前主检出运行的仍是旧版脚本。
