## 1. 需求背景
架构评审候选 7：execution-plan 的批次状态机（快照/排序/fill 补位/释放三态路由/autoPhaseDone/汇总）0 导出，测试只能「测试 → spawn m3-check → spawn plan」两层壳端到端打（仅 2 场景）；M4 验收脚本用源码正则防止复制内核——module 形态缺席的直接症状。

## 2. 用户问题
补位/释放分支（释放非 RUNNING 静默忽略、未知释放状态报错、queue 空短路）无法单测；扩规模前缺乏护栏。

## 3. 目标
状态机成为可导入导出（同文件 export + main guard）；新增直测覆盖上述分支；CLI 与 trigger 的进程边界保持不变。

## 4. 非目标
- 不让 trigger 改为进程内 import（M4 到点开跑的进程隔离是刻意设计）
- 不改 m4-check 的 regex 看门（重构后自然继续成立，防回归复制）
- 不改批次语义/字段/退出码

## 5. 修改前
execution-plan 214 行 0 导出，状态机全部顶层；测试仅 2 个端到端场景。

## 6. 修改后
导出 `createBatchState` / `fillCapacity` / `applyRelease`（命名施工定）；CLI 逻辑置于 main guard；直测直接驱动状态机。

## 7. 功能范围
1. execution-plan 导出状态机函数 + main guard 化。
2. 新增直测（fill 短路/补位、释放三态、非法释放、autoPhaseDone）。

## 8. 不修改范围
scheduled-trigger、m4-check、batch.json/events 格式、LOC-001 在途文件。

## 9. 业务规则
1. CLI 行为逐字节兼容（stdout 汇总结构、退出码）。
2. 状态机导出为纯状态变换（输入状态 + 事件 → 新状态），不做 IO。

## 10. 用户操作路径
无用户可见变化；开发者直测状态机分支。

## 11. 异常和边界场景
释放事件指向不在 RUNNING 的任务：维持静默忽略 + stderr 提示现状；未知 `to` 值：维持报错退出现状。
