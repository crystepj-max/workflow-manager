## 摘要（三要素）

**目标：** 同一任务的新启动在入口即互斥——后到的调用立刻拿到明确回执，不再出现两条运行同时跑同一任务，也不再出现「把健康运行误判为崩溃残留」。

**范围：** 做——宿主启动入口的同步占位与释放、崩溃残留判定收口、拒绝回执文案、同 tick 并发用例。不做——改派生（`#2`）语义、跨机器/跨进程协调（属 #185/#187）、允许同任务并行的产品方向变更、重写 LOC-032 幂等账本。

**验收标准：**

- [ ] AC-01：同一 `taskId` 两次新启动同 tick 发起 → 恰好一次进入执行，引擎 `start` 只调一次，另一次收到可读拒绝回执。
- [ ] AC-02：第一次启动在编译/校验阶段失败后，第二次发起不被历史占位挡住（占位无残留）。
- [ ] AC-03：真实崩溃残留仍按现状判 FAILED 并派生 `#2`（现有用例 `logical-run.test.mjs:300` 保持通过）。
- [ ] AC-04：不同 `taskId` 并发仍全部放行（#19 T1/T2 不回归）。
- [ ] AC-05：拒绝回执人工可读，用户不看代码就知道该换 taskId 还是等前任结束。
- [ ] AC-06：`npm run generate && npm run validate` 不因本改动新增失败项。

## 成立性判定（本会话复核结论）

**成立，且比原票描述更严重。** 原票说「第二调用可能误判崩溃残留并派生 #2」；本会话用仓库既有测试替身做隔离探针（未改任何产品文件）实测：同 `taskId` 连发两次新启动 → **引擎实际启动 2 次**，并落盘 `task-race`（RUNNING）与 `task-race#2`（RUNNING）两条逻辑运行。派生 `#2` 只能出自 `host.js:3249-3256` 的「崩溃残留」分支，即该分支确实被走到；对前任写入的 `FAILED / RUNTIME_RESTARTED` 随后又被仍在运行的前任自己覆盖回 RUNNING——同一条记录在一次启动里被写两次，最终值取决于竞态。

现有测试为何没抓到：`assertMutexBlocked`（`host.test.mjs:1460`）与 #19 T2（`:1523`）都先等前任引擎已 `start` 才发第二次调用，正好绕开了「登记前」的窗口。

原票把它归为「main 既有互斥架构边界」——边界定性成立，但「架构边界」不等于不可修：进程内同步占位即可闭合，成本主要在语义决策。
