## 摘要（三要素速览）

### 任务目标

消除「合并后保留工作区」与「终态任务工作区必须清理」之间的规则矛盾，使 `npm run validate` / `npm run release:verify` 在正常交付节奏下可以全绿；同时修正 `validate-workspace` 在链接工作树内运行时的扫描定位口径。

### 涉及范围

- 做：
  1. 裁决并统一两条规则的口径（见决策点），同步修订 `docs/design/workspace-directory-convention.md`、`scripts/validate-workspace.mjs`（或 runbook 所在文档）；
  2. 修正 `validate-workspace` 在链接工作树内运行时的扫描范围（D-2/D-3/D-4 误把主检出当作治理工作区比对：主检出目录名 ≠ 分支名、分支 = main、含 `.agent-runs`）；
  3. 补回归用例：在链接工作树内运行 `validate-workspace` 应只判工作树自身；终态任务工作区的清理判定按裁决后口径执行；
  4. `npm run validate`、`npm run release:verify` 在主检出与工作树两侧都能按新口径得出一致结论。
- 不做：不改变 `.generated/` / `.agent-runs/` 不入库的口径；不处理 GitHub/CNB 远端凭据问题（另案）；不动 LOC-021 的异源档位范围。

### 验收标准

- [ ] 规则口径唯一：文档与校验器对「终态任务工作区何时必须清理」给出一致答案，不再互相矛盾
- [ ] `validate-workspace` 在主检出运行：终态任务工作区按新口径判定，LOC-014 / LOC-019 保留工作区不再被误报（或按新口径被正确要求清理）
- [ ] `validate-workspace` 在链接工作树内运行：D-2/D-3/D-4 不再误扫主检出，结论与主检出侧一致
- [ ] `npm run validate` / `npm run release:verify` 在主检出侧全绿（除非存在按新口径确应清理而未清理的真实违例）
- [ ] 根目录 `npm test` 全绿

## 背景（矛盾证据，LOC-019 收口实测）

| 规则 | 内容 | 后果 |
|---|---|---|
| runbook §7.4（construction-bootstrap / local-task-merge） | 「🔴 工作区与分支**暂不删除**，保留供 GitHub 恢复后补 PR；`GitHub 同步` 保持 pending」 | 已合并任务（如 LOC-014、LOC-019）的工作区被**要求保留** |
| `validate-workspace` D-7 | 「终态任务（已合并/已取消）工作区已清理」 | 保留的工作区被**判为违例**，`npm run validate` / `release:verify` 永远失败 |

实测（2026-09-13）：主检出侧 `npm run validate:workspace` 唯一失败项即 D-7（LOC-014 已合并但工作区按 §7.4 保留）；工作树侧额外多出 D-2/D-3/D-4 三项，均为「在链接工作树内运行只读校验时把主检出误判为治理工作区」（主检出目录名 `workflow-manager` ≠ 分支 `main`、分支 = main、含 `.agent-runs`），在主检出侧运行则这三项全部通过。

## 🔴 待决策点（进入需求分析会话时关闭）

1. **口径归属**：三选一——
   - A：改 `validate-workspace` D-7——本地轨道（`GitHub 同步 = pending`）的已合并任务，其工作区在证据保留期内（当前 7 天）允许保留，过期后再强制清理；
   - B：改 runbook §7.4——合并即清理工作区与分支，「补 PR」改为从归档三件套 + 标签重建；
   - C：折中——保留工作区但必须登记保留理由与期限，D-7 只对「超期未清理且无登记」报警。
2. **保留期与证据期的关系**：是否直接复用证据保留期（默认 7 天，起算点 = 合并时间）作为工作区保留期。
3. **扫描定位口径**：`validate-workspace` 在链接工作树内运行时，治理区集合应如何取（建议：只判当前工作树自身 + 主检出的登记记录，不把主检出当链接工作区比对目录名/分支名）。
