## 2. 推荐方案及取舍

**方案 A（推荐）：接受表内 V1 及各规格的明确规则。** 收益是范围有限、材料可直接交接，沿现有入口推进；投入集中在本仓库。代价是 CNB 自动发布和所有 Profile 的隔离不在本期承诺内；LOC-041 的真实宿主组合仍可能技术受阻。已有质量与人工验收门保留。

**方案 B：本轮增加 CNB 运行时交付适配及多 Profile 强制隔离。** 收益是更广的直接可用范围；需要补充外部动作适配、跨平台安全策略和真实环境验收，扩大当前分析/开发量。若选择此项，仅调整 LOC-037/041 的候选版本与依赖，其他条目的决定可保留。不得让 agent 在施工时自行选择 A/B。

探索耗尽终态、有限 Schema 子集、缺产物处理及指标缺值等具体规则同样属于本次确认对象；如修改，指出任务 ID 和变化内容即可，不必重做其他需求。

## 3. 环境与执行许可提案 D-BATCH

- 每条任务使用自身 ID 的**独立环境组**与 `codex/loc-xxx-<slug>` 分支。跨组依赖先完成并合入启动基线，不加入或改写已经批准的 P0 环境组。
- **环境规则冲突需随本次明确确认**：本轮提供的 AGENTS 要求建设 Run 独占 DSH Home；当前 [construction-bootstrap runbook](../../dsh/skills/construction-bootstrap/runbook.md) 已实现唯一开发实例 9527、共享 Home、按 Run namespace 隔离。两者不能同时照做。本提案建议按当前已实现的共享宿主、每 Run 独立命名空间/工作区安排；用户明确接受 D-BATCH 后才以该安排执行本批。此前不操作任何 DSH。若选择继续严格独占 Home，需先解决分配器与规则不一致，本批环境就绪仍受阻，不能悄悄照共享方式运行。
- 资源由实际分配记录确定，不停止或清理其他 Run；LOC-041 的 SDK 子进程 Home 是该节点隔离配置的一部分，不冒充把共享开发宿主改成独占部署。参考配置探针使用隔离开发资源，不触碰产品凭据。
- 拟允许确认后无人值守执行实现、必要测试、内部 review、有限返工和 UAT 材料准备，**止于人工验收关口**；沿项目已有返工上限。需求确认不等于验收、发布授权或远端合并授权。
- 本轮只做定义；即使现在确认，也仅回填定义状态、许可与门禁检查，不立即开始开发。
- 候选清单保守设置并发 **1**：当前 runbook 明确同一时刻只允许一个任务激活插件，切换活跃任务可能重启共享 DSH。执行前必须确认槽位空闲；发现其他任务活跃就等待资源或记录受阻，不调用会抢占它的 `start --task`。命名空间隔离不代表可以同时运行两个开发插件。此清单不是定时任务，本轮没有建立夜间自动化。

## 4. 批量能力与前置门禁

当前 `ai-task-execution-plan.mjs` 会排除任何有依赖的候选；它本身输出计划/状态快照，不是启动真实开发 agent 的完整执行器。

- 确认后可进入现有无依赖候选的有：**LOC-036、038、039、040、041、042**。仍需实际入口验证环境；LOC-041 尤其不能以“无任务依赖”推断宿主可用。
- **LOC-034、035、037、043** 需等待表中 P0 合入，再经单任务入口分阶段启动。依赖已经完成也不代表现有批量脚本会接纳它们。
- 执行者必须同时核验前置登记册交付状态、合入提交及 `git merge-base --is-ancestor <前置合入commit> HEAD`。仅“本地已定义”、UAT 待验收或工作区里存在文件，都不算前置已满足。
- 当前独立环境计划器不会自动核验跨组业务依赖，故由受托执行者在创建 Run 前核验并记录证据；LOC-038 将完善入口一致性，但不是本批偷偷新增的前置任务，也不是本轮已完成能力。
- 不允许把候选卡片“前置依赖”临时改成“无”以骗过调度器。需要未来真正自动依赖调度时另行定义。

因此，本批分析不承诺“确认后现有夜间脚本就能把 10 条自动开发完成”。材料获取、需求已定义、环境可执行、调度器支持、开发通过和人工验收是分别核验的事实。
