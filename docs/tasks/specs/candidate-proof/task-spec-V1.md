## 9. 业务规则

- 定义宿主生成的 candidate_ref：包含资源类型、作用域清单和不可变版本。Git 至少记录仓库身份、HEAD 与受审工作树内容摘要；有未提交变更时不能仅凭 HEAD 放行。非 Git 以声明文件集合、相对路径和内容摘要标识；忽略项显式声明，不默认忽略待交付内容。
- 在审核/测试开始前捕获候选，结束时重读；两者不一致则本次证明无效。模型自报 HEAD 仅作为诊断信息，权威版本来自宿主。
- 建设和诊断在进入后续关口前检查证明所指候选等于当前候选；任何已存在的集成同步和重跑门禁继续保留。

**接手者可直接采用的实现边界：**复用宿主工作区真实路径与安全文件读取，形成 captureCandidate/compareCandidate；审核、测试开始和结束捕获，UAT/收口前比较。现有 Integration Gate 的同步/重跑路径必须调用相同候选核验。

**接口与数据约定：**candidate_ref 固定字段：kind、resource_id、scope_manifest、version={head?,content_sha256}。scope_manifest 为授权根下相对文件路径、类型、摘要；包含已跟踪文件及声明交付的未跟踪文件，排除显式证据/构建临时区。路径排序后按规范 JSON 计算摘要；拒绝越界符号链接。相同 HEAD 下的业务文件改动必须改变摘要。WR-005 消费此接口。

本条拥有 candidate_ref 捕获/比较和 proof 的候选引用；WR-005 引用该对象，WR-007 处理其失效依赖。测试替身不得由模型输出冒充宿主实际版本。

**兼容方式：**新运行使用本条新规则；已启动运行保持其冻结快照。无法补证的旧历史明确 legacy/unverified，不改写成已验证完成。若其他 P0 已合入，复用其公共接口并运行集成检查；没有硬依赖的条目允许通过既有接口完成自身切片，不能自行等待整个需求包。

## 16. UAT 场景

### UAT-01 主路径与关键反例

- 验收目的：验证 §3 用户目标与 §15 全部 AC。
- 前置条件：对应候选源码在隔离 worktree；Node.js 24 与所需依赖可用；真实产品模式验证按既有发布规则使用安装产物。
- 操作步骤：隔离 Git fixture：审核版本 A、随后不提交地改业务文件为 B，要求旧证明不能进入 UAT；非 Git fixture 对声明文件增加/删除/更名各验证一次。
- 预期结果：正常输入达成目标；非法/缺失/过期输入按 §9 和 AC 拒绝；结果状态、产物和原因一致。
- 人工关注：界面/报告能看懂通过或受阻原因，不把测试替身结果当成用户已经接受。

### UAT-02 恢复与兼容

- 前置条件：保存一个旧快照与一个新规则 Run 的中间状态；仅在隔离环境制造中断。
- 操作步骤：分别恢复旧快照、新运行，再执行一次同请求重放或同内容重读；核对输出与证据。
- 预期结果：旧快照不静默迁移；新运行不丢有效成果、不伪造历史证明；本条涉及的非法条件仍被拦截。
- 证据要求：输出日志/实际产物/状态快照与候选 HEAD；不能只附最终 PASS 字样。
