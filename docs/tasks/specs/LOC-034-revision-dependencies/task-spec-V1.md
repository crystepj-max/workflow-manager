## 9. 业务规则

1. 新记录的 dependencies 只取该 attempt 的 resolved_inputs 中实际解析成功的正式引用，以及显式声明的候选/评价基线引用；自记录版本沿袭放 based_on，不自动成为业务依赖。禁止从当前 Store 全量推导。
2. 引用身份为 logical_run_id + record_id + record_revision；本期仅同 Run，提交前检查存在、正式性、可读性与无环。解析与提交之间输入更新也不得把固定引用改为 latest。
3. 更新 A 时保留历史 A1/B1/Proof1 的正文与依赖；当前覆盖视图将依赖 A1 的 B1 及传递下游标为 stale，并给出最短原因链。尚未消费 A 的 C 保持有效。新 attempt 显式解析 A2 才能重新形成覆盖证明。
4. 旧记录缺消费依赖时标记 dependency_coverage=incomplete、不可据此签发新的当前覆盖证明；历史仍可查。错误使用 missing_ref/cross_run_ref/nonformal_ref/dependency_cycle，拒绝整个本次提交，不留下半条有效依赖。

输入输出和归属：输入消费 LOC-024 的 resolved_inputs 与 LOC-029 的稳定 attempt_id、已提交 Revision；输出精确依赖和当前覆盖判断。本条拥有依赖图语义；LOC-029 继续拥有持久化事务，LOC-024 继续拥有绑定解析。

## 11. 异常和边界场景

- **只重验真实下游**：创建 A1、独立 C1、消费 A1 的 B1 和消费 B1 的 Proof1。 处理结果必须为：B1、Proof1 对当前成果失效；C1 更新前仍有效；C 的更新不再新增该 Proof 的失效原因。
- **历史引用与恢复**：准备 A1/A2 及显式绑定 A1 的旧 attempt。 处理结果必须为：旧 attempt 始终读 A1，新 B 读 A2；恢复前后依赖集合相同。
- **探索局部补充**：准备 E1/E2 两份专家结果，综合 S 只消费 E1。 处理结果必须为：E2 不影响 S；E1 更新使实际消费链失效，无关专家报告保持有效。
- **拒绝不可靠引用**：准备缺失引用、跨 Run 引用、临时引用和 A/B 循环四组输入。 处理结果必须为：四组均给出对应错误与路径，无部分有效记录；旧无依赖记录显示 incomplete。

共同恢复规则：证据不足写 BLOCKED/UNVERIFIED 并保留失败输入、恢复位置；同一原因重试不改变基线，不因无人值守降低验收。旧 Run 使用冻结快照；范围外变化另行记录，不静默迁移历史。

## 15. 验收条件

- [ ] AC-01：A→B→Proof 更新 A 后，B 与 Proof 失效；独立 C 仍有效。更新 C 不影响该 Proof。
- [ ] AC-02：同一成果有两版时消费者仍能读取其绑定旧版；新执行明确使用新版，不悄悄改写历史引用。
- [ ] AC-03：并行专家一人补充只使实际读取其旧结果的综合/终评失效，不使无关专家报告失效。
- [ ] AC-04：缺失引用、临时引用用于正式 Proof、循环依赖均被拒绝；恢复后依赖集合不扩大为所有当前记录。
