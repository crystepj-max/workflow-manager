# Requirements Analysis · FEAT-77（M5 夜间批次调度器实现）

## 1. 背景

夜间批次是"无人值守把一批待办任务在夜窗内施工"的能力。旧形态由一条长提示词驱动单个 AI 会话：会话内既做调度（筛选/排序/补位）又做施工（每任务经 subagent）。实测暴露三类问题：

1. **规则漂移**：筛选/排序/补位语义写在散文里，每晚 AI 重新理解，跨机器/跨 AI 工具（ZCode / Codex / DSH）口径不一致；
2. **雪崩风险**：单会话承载整批，会话中途崩溃或上下文溢出会拖垮全部任务；
3. **维护成本高**：规则变更要改提示词散文，难以测试与回归。

## 2. 用户/系统需求

| 需求 | 来源 | 说明 |
|---|---|---|
| 调度确定性 | 多轮夜间批次事故复盘 | 筛选/排序/补位由脚本机械执行，可单测 |
| 故障隔离 | 单会话雪崩教训 | 每任务独立执行上下文，单任务失败不影响整批 |
| 跨工具一致 | ZCode/Codex/DSH 并存 | 行为边界固化在渲染后的会话提示词，跨工具同一份 |
| 可观测 | 夜间无人值守 | 每会话产出结构化释放事件，调度器聚合成报告 |

## 3. 方案对比

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A. 每任务独立 CLI 会话（**选定**） | 调度器为每个任务 spawn 独立 AI CLI 会话，渲染专属提示词 | 故障隔离彻底；上下文小；会话可并行 | 同时存活会话数受机器资源约束，需并发上限 |
| B. 单会话 + subagent | 维持旧形态 | 改动最小 | 不解决漂移与雪崩；上下文随批次膨胀 |
| C. 单会话串行施工 | 同会话内逐任务做，不并 subagent | 简单 | 无并发、无隔离，夜窗时长不够 |

选定 **方案 A**（与 DT-01 裁定一致）：把"调度"与"施工"彻底分离——调度器只管编排，施工下沉到每任务的独立会话。

## 4. 关键设计决策

- **并发模型**：`maxConcurrency` = 同时存活的独立会话数；会话结束（写释放事件或看门狗超时）才释放名额补位。
- **会话隔离**：每任务独立工作树/run 目录，物理隔离；调度器渲染 `<runDir>/session-prompt.md` 注入机器配置的 agent 命令。
- **结束契约**：`release-event.json` 三态（`WAITING_HUMAN` / `BLOCKED` / `COMPLETED`），调度器轮询解析，超时（看门狗默认 120 分钟）记 `BLOCKED` 并释放。
- **不回填提示词**：原长提示词的调度散文已下沉脚本，调度层提示词（`.scratch/night-batches/night-batch-prompt-v2.md`）只做"对账前置 + 唤起调度器 + 读报告"三件事。

## 5. 假设与约束

- 假设：目标机器已配置 `machine.json`（AI CLI 命令模板、权限档、现场创建命令），不入库；
- 约束：调度器不写账本、不建现场（现场由会话内的 cwf-run-init 建）；
- 约束：验收裁决永远留人，会话停在 `WAITING_HUMAN`。

## 6. 验收链路

- 单测：`ai-task-candidate-collect-m5.test.mjs`（采集闸门 6 项）、`ai-task-night-dispatch-m5.test.mjs`（调度器端到端 6 项）；
- 真链路（已在 ZCode 实测，见 `docs/design/night-batch-dispatcher.md`）：真实 cwf-run-init + 真实 ZCode 会话 → 释放事件 → 报告定位表。
