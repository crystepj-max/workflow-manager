## 9. 业务规则

- 调用前持久化 attempt_id，包含 run/node/round、fanout item、segment；成功、失败、取消都写明确状态。结构修复与技术重试也有各自 attempt，逻辑步骤与实际调用分开标识。
- 完成顺序为：保存结果 → 提交正式记录并确认 → 更新最新索引与检查点 → 推进。写入失败保留原专业结论，但不得签发相应有效证明或最终完成。
- 结果提交使用稳定提交键去重；进程中断后重放已确认提交只返回同一记录。存储采用现有本地 Records 能力并处理同 Run 写入冲突，不引入远程事件服务。

**接手者可直接采用的实现边界：**通过已有 workspace/records RPC 通道增加逐次 attempt 提交接口；将段末扫描变成兼容回退，新运行在每次实际调用前后提交并获得确认。结果、索引与检查点按固定顺序推进，正式证据失败使放行等待恢复。

**接口与数据约定：**attempt_id 由宿主在调用前分配并持久化；result_commit_id 与 attempt_id 唯一对应。相同键同内容重放返回同一 Revision，不同内容拒绝。并发提交使用每 Run 串行提交队列和磁盘互斥/原子替换，不能只用一个共享 .tmp 名称抵抗并发。断线后查询提交键再决定是否重放。

本条拥有 attempt_id、result_commit_id、逐次事件和节点最新索引；对外提供按 Run/Node/Attempt 获取记录的稳定接口。WR-007/008/020 消费，不直接写底层文件。

**兼容方式：**新运行使用本条新规则；已启动运行保持其冻结快照。无法补证的旧历史明确 legacy/unverified，不改写成已验证完成。若其他 P0 已合入，复用其公共接口并运行集成检查；没有硬依赖的条目允许通过既有接口完成自身切片，不能自行等待整个需求包。
