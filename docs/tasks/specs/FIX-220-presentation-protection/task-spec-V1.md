## 1. 需求背景

契约的可审计性建立在一条前提上：**人工签收的对象，就是当初呈递给他的那份内容**（§3.6）。PR #125 交付 `cwf-record` 时按这条做了 acceptance_package 一层，另两层留作未修意见。#123 的时间序子项同属「呈递过的事实能不能被机器验证」，且因 JSON Schema 无法表达跨字段比较，只能落在引擎——一并归入本片。

## 2. 用户问题

同一次 attempt 内，把 design package 从「未决」刷成「已决」时可以顺带换掉呈递的问题与候选集；把基线从 `draft` 刷成 `confirmed` 时可以顺带改掉呈递过的目标/范围/验收标准。事后仅凭记录本身，看不出人工答的是不是眼前这份。

再加一条已被真实数据证实的：**签收时间可以随便填**。`.agent-runs/cwf-74-r1` 的一条验收包，其 `decided_at` 既早于本工具在写入瞬间打的 `created_at`（早 5h39m），又早于它所绑定的那个提交（早 4h48m）——两处倒挂没有任何机器拦住，最后是 2026-09-20 UAT 里专家手工识别出来、判定该时间戳不可作时刻证据并把它从定论链剔除。这个判断本票要接过来。

## 3. 目标

交付后，「刷新成熟态」这一动作无法改变已呈递内容（除非显式声明换版），并且时间序与 conditional_pass 的 feedback 由引擎在磁盘记录上复核——绕过写入工具也躲不掉。

## 4. 非目标

- 不改 schema 约束强度（片 1）。
- 不在写入路径做任何新增拒写（片 3 #221 题域）。⑩ 两档一律只在引擎侧评估；⑩-a 按 D-1 只报提示，本票不在 `cwf-record` 里拦。
- 不碰 `文件 mtime` 类判据与屏幕物证——已登记 GitHub #214（CHORE-75 收口护栏），本票只做 schema 与校验器能机械断言的部分（R-6 边界）。
- 不追溯校验已归档历史记录；不重写历史。
- 不改 acceptance_package 那半条已落地的保护逻辑。

> 事故样本的两点额外价值：① 它是**可直接固化的失败用例**（真实数据形状，不用编造）。② 本会话一度推断「不依赖 git 的那条探测器更强」——**该推断已被全量归档复算否掉**：`created_at` 是 `cwf-record.mjs:89` 写文件的时刻，成熟刷新必然晚于人工签收，所以「`decided_at` 早于 `created_at`」是正常形态。真正站得住的只有「签收早于所验提交」这一条。

**全量复算结果（`.agent-runs/*/acceptance_package*.json`，2026-09-21）**

| 判据 | 实测 |
|---|---|
| `decided_at ≥ created_at` | 32 条可比样本中 **25 条不满足**，中位偏离 0.00h → 当硬判据会误伤 78% 正常记录，**废弃**（松哥裁定 D-1 改为反向软判） |
| `提交时刻 ≤ decided_at` | 25 条正常 / **7 条倒挂（分属 4 个 run）** / 56 条不可评估（缺字段或提交不在本地）；正常边际中位 +2.42h |

| run | 倒挂 | `decided_at` 形态 | author 与 committer |
|---|---|---|---|
| cwf-74-r1（本票靶子） | 289 分钟 | `09:30:00` 整分 | 相同 |
| 另一 run | 212 分钟 | `06:40:00.000` 整分 | 相同 |
| 其余三个 run | 36 / 17 / 13 分钟 | 带秒（机器钟） | 相同 |

**4 例 author 与 committer 日期全部相同**，据此排除「rebase/amend 重写 committer 日期」造成的假阳性。小时级伴随手写整分值（真回填特征），分钟级更像跨机时钟偏差——但松哥裁定 **D-2：不设阈值，一律判失败**，分钟级噪声同样阻断（该风险已在 §17 如实登记，不粉饰）。历史这 4 个 run 按 **D-3：只写进本规格存档**，不追溯改写、不另立票。

## 6. 修改后

- 同 attempt 把 design 刷成带 `decision`：若已存在旧记录，其 `decision_request` 必须原样保留（问题文本、候选集、推荐项逐项等值），否则拒写并指明差异字段。
- 同 attempt 把 baseline 刷成 `confirmed`：已存在旧 `draft` 记录时，`goal/scope/acceptance` 必须等值；确需变更须显式绑定旧 Revision（换新 `baseline_revision` 并前进 attempt），此时允许内容不同但必须可追溯到被替换的那一版。
- 时间序按**两档**落地（⑩）：
  - **⑩-b 跨系统档（主判据·硬不可能）**：签收所验的提交必须在签收时刻**之前或同时**已存在，即 `author/committer date(verified_head) ≤ decided_at`。人不可能验过一个当时还不存在的提交，故违反即不可能为真。取不到该提交（归档、浅克隆、跨仓）时判 **「无法评估」并在 detail 显式说明**，不得静默算通过。**不设时间容差（D-2）**：任何分钟级倒挂同样判失败。
  - **⑩-a 记录内档（次判据·反向软判，只报不拦）**：断言方向改为 `created_at ≥ decided_at`——记录不得早于它所记载的签收事件。违反时**只输出偏离提示并列出两个时间戳，不拒写、不改变整链结论**（D-1）。原方向 `decided_at ≥ created_at` 已实测废弃，实现与用例都不得沿用。
- 引擎新增判定 ⑪：`decision=conditional_pass` 时磁盘记录必须带非空 `feedback`（补 schema 之外的磁盘复核，覆盖绕过 `cwf-record` 的落盘）。
- 引擎⑥补一条：`decision.question` 与 `decision_request.question` 等值。
- 失败输出必须**指明被推翻的是哪个字段、依据的是哪一档权威源**，让人一眼看出「这个时间戳不能当时刻证据」——这正是 cwf-74-r1 UAT 里专家手工做出的判断，本票要把它变成机器判断。

## 7. 功能范围

1. `cwf-record` 写路径两条呈递保护（复用 `deepEqual`，与已有 assembled 保护同一模式与同一拒绝风格）。
2. 引擎⑥扩一条文本等值断言。
3. 引擎新增⑩（b 主判据硬失败 + a 次判据软提示）与⑪判定，输出结构与前九项一致（`id/name/ok/detail`）；⑩-a 只提示、不参与 `ok` 计算。
4. 负例先行：每条各一个「加固前能通过、加固后被拒」的用例。
5. 契约 §5.3/§8.3 相应文字与变更史；runbook 无需改（引擎仍人工执行，接线是片 3）。

## 8. 不修改范围

九项既有判定的语义；schema 文件；`cwf-record` 其他子命令；attempt/额度/回退语义；归档与清理链路；acceptance_package 既有保护。

## 9. 业务规则

- R-1 保护只在**同 attempt 覆盖同一文件**时触发；跨 attempt（回退重跑、reverify）本就落新文件，不受约束。
- R-2 内容确需变更时的唯一通道是**前进 attempt**（`--attempt N+1`）：旧修订文件按 §8.5 原样保留，呈递过的内容因此在磁盘上可追溯。🟡 施工核对发现 schema 内**没有** `supersedes`/`revised_from` 一类字段（`handoff.schema.json` 全检索为空），原「显式绑定旧 Revision」的写法需要新增 schema 字段、越界到 #219 题域，故按此等价通道落实；不新增字段。
- R-3 时间序比较的是**同一 run 链路内**可得的成对时间戳，不做绝对时钟可信性判断（不引入 NTP 假设，不判「谁的时间准」）。
- R-4 比较**必须先解析为时刻再比**，禁止字符串比大小：记录内时间戳是 `isoDateTime` pattern 下的 UTC `Z` 串（小数秒可选），而 git 提交日期带本地时区偏移（如 `+08:00`）——本票的锚点样本两侧偏移恰好不同，字符串比较会得出错误结论。
- R-6 **权威时刻分层**（2026-09-20 cwf-74-r1 UAT 结论，作为断言取值与报告口径的依据）：
  `git 自证（提交对象自身携带的日期）` ＞ `契约强制的 verified_head 提交时刻` ＞ `created_at（写入瞬间由工具打戳）` ＞ `人工回填字段（decided_at / confirmed_at 等）` ＞ `派生叙述（正文里的时间描述）` ＞ `文件 mtime`。
  两档探测器冲突时以高层为准；报告时须写明「推翻了哪一档、依据是哪一档」。
  🟡 **边界**：`文件 mtime` 一档**不属本票**——归档 mtime 与屏幕物证缺失已登记 GitHub #214（CHORE-75 收口护栏），本票只做 schema 与校验器**能机械断言**的部分，不重复施工。
- R-5 ⑪的「非空」与片 1 的下限解耦：本票只断言存在且非空白，长度下限属片 1 题域。

## 10. 用户操作路径

① Controller 呈递 design 待决包给松哥 → 松哥答 A；② Controller 写 `package_ready` + `decision`，但顺手把 `decision_request.options` 改成 A/B' → 立即拒写，报「呈递候选集被替换」；③ 恢复原呈递内容后重写通过。

## 11. 异常和边界场景

- E-1 首条 design 记录就同时带 `decision_request` 与 `decision`（无历史可保护）→ 允许写入，由引擎⑥保证自洽。
- E-2 旧记录无 `decision_request`、新记录有 → 属于「补呈递」而非替换，须放行还是拒绝？裁定：**放行**（缺呈递记录本就是⑥要抓的，补上是改进；保护的是「不替换」，不是「不许补」）。
- E-3 `options` 顺序变化但集合相同 → 按 R-1 之外的口径：顺序影响呈递外观，判为替换、拒写。
- E-4 baseline `draft` 从未呈递（无 gaps、一次性 confirmed 写入）→ 无旧文件可比，放行。
- E-5 `decided_at < created_at`（cwf-74-r1 即此形态，早 5h39m）→ **正常，不判失败**：成熟刷新的 `created_at` 天然晚于人工签收，实测 25/32 样本如此。反向（`created_at < decided_at`）才由 ⑩-a 报偏离提示。
- E-6 引擎⑩遇到引用记录缺 `created_at`（理论被 schema 挡住，但磁盘手改可能缺）→ 判失败，不得静默跳过。
- E-7 提交不可达（归档 run 的 `verified_head` 已被 rebase 丢弃、浅克隆、跨仓 SHA）→ ⑩-b 输出 `无法评估` + 原因，整链结论不得因此被算作通过；⑩-a 仍独立生效（不需要 git）。
- E-8 两档结论不一致（⑩-a 仅提示而 ⑩-b 倒挂）→ 整链结论以 ⑩-b 的失败为准（R-6 取 git 自证一档），detail 同时列出两个比较对，不隐藏任一侧。

## 16. UAT 场景

### UAT-01 呈递替换攻击

## 17. 风险

- 🟡 保护过头会挡住正常纠错（E-2、E-4）。缓解：V-3 显式要求「应放行」的正例。
- 🟡 引擎从九项变十一/十二项，任何按项数硬编码的消费方需同步。缓解：实施前全仓检索 `checks.length` / `九项` 字面量并一并更新文案。
- 🟡 **D-2「零容差」的已知代价（如实登记，不粉饰）**：⑩-b 不设阈值，实测归档中 13 / 17 / 36 分钟三例若发生在未来会被同样判失败，而它们的时间戳带秒、更像跨机时钟偏差而非手写回填。后果是签收/收口可能被分钟级时钟漂移阻断，需要人工判断后走 reverify 或改绑正确提交。缓解：detail 必须打印两个时间戳与偏离分钟数，让人一眼分辨量级；小时级与分钟级在报告里同格式呈现，不做隐性降级（那等于绕开裁定）。
- 🟡 ⑩-a 反向偏离同样受时钟偏差影响，因此按 D-1 只做提示；若未来升级为硬判据，须先重新量化误伤率。
- 🟡 ⑩-b 依赖提交可达；归档/浅克隆场景会退化为「无法评估」。缓解：E-7 强制显式报告，绝不静默通过；⑩-a 不依赖 git，仍可独立生效。
- 🟡 与片 1 同改测试文件的冲突。缓解：本片只新增用例段落，不改夹具取值。
