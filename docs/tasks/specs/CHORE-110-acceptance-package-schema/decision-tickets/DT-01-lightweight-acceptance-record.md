## 背景（为什么必须决定）

`acceptance_package` 的 `assembled` 是**必填**，且强制要求五类前置记录引用（baseline / design / dev_handoff / **review_proof** / **test_proof**）+ `integration_checkpoint`。走**轻量路线**的任务没有独立评审 / 测试节点，因此 `review_proof` / `test_proof` 根本不存在 → **登记不了验收包** → 归档证据摘要里 `decision` / `decided_by` / `decided_at` **恒为 null**。

实测样本：`docs/tasks/archive/CHORE-106/evidence-summary.json` 与 `CHORE-37` 三字段全为 null。本批任务**全部**走轻量路线，所以这不是个例，是常态。

要决定的核心问题是：**轻量路线的验收签署，应以什么形态被记录下来？**

同时必须挡住的坏解法：为了「凑齐」必填项而伪造 `review_proof` / `test_proof`——那等于伪造独立评审，比缺字段严重得多。

## 方案

| 方案 | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A · 验收包分层（推荐）** | `acceptance_package` 增「轻量变体」：`assembled` 按路线二选一——正式路线仍须五类引用；轻量路线只需 `dev_handoff_ref` + 路线标识，并**强制**记录 `decided_by` / `decided_at` | 中——schema + 契约 + `cwf-validate` 校验分支 | 直接命中根因（必填结构与路线现实错配）；签署人留痕恢复；正式路线标准不降 | schema 放宽后有被误用于正式路线的风险 → 须以路线标识 + 校验分支锁死 |
| B · 独立轻量记录类型 | 新增记录类型（如 `acceptance_note`），只记签署人 / 时间 / 结论 / 依据清单；正式验收包原样不动 | 中高——新增类型 + 摘要取值分支 + 契约新增一节 | 不动正式契约，改动隔离 | 两套「验收」概念并存 → 长期语义分叉；本项目已有「两套同名实现争夺同一文件」的历史教训（LOC-016） |
| C · 不放宽，改口径 | 契约写死：走轻量路线即不产生结构化签署；摘要三字段以显式「不适用」值标记并附原因 | 低——仅改契约说明 + 摘要取值 | 改动最小，立即消除「静默 null」的误导 | **放弃**「谁验收的」可追溯性——把审计缺口制度化而非消除；而本批任务恰恰全部走轻量路线 |

## 推荐

**倾向 A。** 三条理由：

1. **对症**——断链根因是「必填结构与路线现实错配」，分层直接命中；C 只是把缺口写成规范。
2. **不引入第二套语义**——B 会让「验收」出现两种并行概念，与本项目已踩过的「两套同名实现」坑同型。
3. **审计价值不对称**——`decided_by` / `decided_at` 是链上最不可再生的一环（代码可重跑、测试可重跑，但「当时谁签的字」事后补记即为伪造），值得为它调结构。

## 共同底线（不随方案变化）

无论选哪一种，以下三条都必须在 CHORE-110 中落实：

1. 明文**禁止**为满足校验而伪造 `review_proof` / `test_proof` 或冒充独立评审。
2. 轻量路线的验收签署**必须可追溯到人**（真实 `decided_by` / `decided_at`），或被显式标记为「不适用」——两者不得含混。
3. 正式路线的五类引用强制校验**不得放宽**。
