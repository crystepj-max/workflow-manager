## 1. 缺陷现象（可复现）

合并远端最新 `main`（`9b4bfee`）后运行 `npm test`，`scripts/test/generate.test.mjs:339` 的 S6 用例失败：

```
not ok - S6 内联仅限蓝图引用内置角色：最小图产物 < 宿主 64KB stdout 捕获上限，且 12 角色均可加载
  error: 最小图编译产物 < 64KB（宿主 runNode maxBytes:64*1024，host.js:137）
```

## 2. 实测证据

| 观测项 | 实测值 | 来源 |
|---|---|---|
| 最小图（`hello-blueprint`）编译产物体积 | **77,101 字节 = 75.3 KB** | `compileBlueprint(mini).script` 的 UTF-8 字节数 |
| 宿主捕获上限 | 65,536 字节 = 64 KB | `host.js:137` `runNode maxBytes` |
| `dsh/roles/dev.md` 体积 | 4,589 字节 | 文件大小 |
| `dsh/roles/orchestrator.md` 体积 | 5,025 字节 | 文件大小 |

> 关键判断：单个被内联的角色文件都远小于上限，超限来自**编译产物骨架本身**在近期合并后增长，而不是某个角色文档变大。

## 3. 任务目标

最小图编译产物回到宿主 64KB 捕获上限以内，使 S6 用例恢复通过；能力面（12 个内置角色均可加载）不得削弱。

## 4. 涉及范围

- **做**：
  1. 定位编译产物骨架中体积增长的具体来源（对比合并前后的产物构成）；
  2. 在保持蓝图语义、节点行为、能力面完全不变的前提下压缩体积；
  3. 若体积增长确属必要功能所致，则按既有先例（`e854f20` 曾按实测把载荷预算上调至 200KiB）**以实测依据**同步调整宿主上限与断言，并在交付证据中给出依据。
- **不做**：
  1. 不改动任何模板的节点语义与边；
  2. 不删除、不裁剪内置角色的能力内容来凑体积；
  3. 不放宽断言而不留任何依据。

## 5. 验收标准

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | `npm test` 全绿 | 完整测试套件通过（当前 601 项，以修复时的实际总数为准） |
| 2 | 体积断言与宿主真实上限一致（不得与宿主代码事实矛盾） | 断言依据指向有效位置，且给出实测字节数 |
| 3 | 12 个内置角色均可加载 | `loadBuiltinRoleDefs(loadBuiltinRoleIds())` 返回 12 项 |
| 4 | 全 12 角色各一节点的图仍在宿主 1MB 上限内 | S6 用例后半段断言通过 |
| 5 | 存在防膨胀闸门 | 体积上限按实测值定值，并保留「新增载荷优先瘦身」的约束 |

## 6. 诊断结论（2026-09-16，A 方案定位结果）

### 6.1 产物体积构成（最小图，`936c60e` 实测）

| 构成 | 字节 | 占比 |
|---|---|---|
| 内联角色定义（`dev.md` 一份） | 4,653 | 6% |
| **运行时骨架** | **72,448** | **94%** |
| 合计 | 77,101（75.3 KB） | 100% |

> 结论一：超限与角色文档无关（`dev.md` 仅 4.6KB），**体积几乎全部来自运行时骨架**——骨架承载了全部功能实现，与蓝图规模无关，最小图也必须完整携带。

### 6.2 增长曲线（沿 `scripts/generate.mjs` 历史实测）

| 提交 | 产物字节 | 说明 |
|---|---|---|
| `b6c2311`（09-14） | 58,536 | 低于上限 |
| `fbaf844`（09-15） | 64,449 | **距上限仅余 1,087 字节** |
| `ce8cdb8`（09-15，LOC-031 并入） | 65,375 | 余量降至 161 字节 |
| `d3165bd`（09-16，合并主干） | **77,101** | 当前值 |

> 结论二：LOC-031（技术重试/超时/无进展循环）自身只增加约 0.9KB，**真正把产物推高的是 LOC-024~031 一系列功能持续往骨架里累积**；`fbaf844` 时距上限已不足 1.1KB，突破是时间问题。

### 6.3 A 方案（压缩骨架）的实测可行性

| 项 | 字节 | 换算 |
|---|---|---|
| 当前产物 | 77,101 | 75.3 KB |
| 需要削减 | 11,565 | 11.3 KB（15.0%） |
| 可压缩空间（全部注释 + 缩进） | 4,531 | 4.4 KB（5.9%） |
| **压缩后仍缺口** | **7,034** | **6.9 KB** |

> 结论三：**A 方案不足以解决**。即使把产物里所有注释与缩进全部去掉（会显著牺牲可读性），仍差 6.9KB；剩下的缺口只能靠削减真实功能代码或改变自包含策略，代价与风险都远高于收益。

### 6.4 决定性事实：断言的前提已经失效

| 观测 | 事实 |
|---|---|
| 宿主默认捕获上限 | `host.js:119` `runNode` 默认 `maxBytes: 64*1024` |
| **宿主编译路径的实际上限** | `host.js`（编译调用点）显式使用 **`maxBytes: 1024 * 1024`**，并附注释：「编译输出上限 1MB：全内置角色内联的图约 66KB，**默认 64KB 会静默截断**」 |
| 测试断言的依据 | 写作「宿主 runNode maxBytes:64*1024，host.js:137」——该行号当前指向 DSH_HOME 探测代码，**引用已失效**（功能合并导致行号漂移） |

> 结论四：宿主早已为编译路径显式放宽到 1MB，并在代码注释里承认「默认 64KB 会截断、全内置角色图约 66KB」。也就是说：**「最小图必须 < 64KB」这条断言与其所依据的宿主事实已经相互矛盾**，它保护的是一个已被宿主主动放弃的旧约束。

### 6.5 建议：采用 B（按实测修正断言 + 保留防膨胀闸门）

依据链（四条独立证据）：

1. 宿主编译路径的真实上限是 1MB，且注释明确说明 64KB 默认值会截断；
2. 宿主注释已实测「全内置角色内联的图约 66KB」，本就超过 64KB；
3. S6 断言引用的行号已失效，属于陈旧依据；
4. 已有先例 `e854f20`：按合并终态实测量化，把载荷预算从 198KiB 一次性上调至 200KiB（人工裁决），并写明「后续新增载荷应优先瘦身」。

B 的具体做法（不得简化成单纯放宽）：

| 步骤 | 内容 |
|---|---|
| 1 | 把 S6 第三条断言的上限从其依据（宿主默认值 64KB）改为**编译路径真实上限**，并修正注释中的失效行号引用 |
| 2 | 同时以当前实测值定一个**回归闸门**（建议 96KB，留出约 20KB 余量），防止体积继续无约束增长 |
| 3 | 在代码注释中写明「新增载荷优先瘦身」的约束（沿用 `e854f20` 的既有写法） |
| 4 | 保留 S6 后半段「全 12 角色图 < 1MB」的最坏情况断言不变 |

风险与缓解：放宽单点上限会降低越界输出的发现能力 → 由回归闸门 + 后半段最坏情况断言共同兜住；若后续骨架继续增长触及闸门，则应优先瘦身而非再次上调。

### 6.6 实际落地情况（2026-09-16 13:55 核实）

本任务的修复**未由本任务自身交付**，而是随 LOC-032（PR #67，合并提交 `51739d6`）的收口链进入主干：S6 断言已按「**128KB 体积卫生口径**」修正，注释引用宿主编译路径真实上限（1MB），与本规格 §6.5 建议的 B 方案实质相同（两个会话平行得出同一结论；诊断建议的闸门值为 96KB，实际落地取了更宽的 128KB）。

与 §6.5 建议的逐项对照：

| §6.5 建议 | 实际落地 | 判定 |
|---|---|---|
| 断言上限改为编译路径真实上限，修正失效引用 | 断言改为 128KB 体积卫生口径，注释写明「宿主编译捕获实际 maxBytes 1MB」 | 一致（口径定值 128KB，介于旧 64KB 与真实 1MB 之间，保留了防膨胀意义） |
| 按实测设回归闸门 | 128KB（当时实测 77.1KB，余量约 51KB） | 一致 |
| 写明「新增载荷优先瘦身」 | 断言注释含「体积卫生口径」表述 | 基本一致 |
| 保留「全 12 角色图 < 1MB」最坏情况断言 | 保留 | 一致 |
