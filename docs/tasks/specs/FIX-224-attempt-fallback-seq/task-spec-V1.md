## 1. 需求背景

LOC-029（WR-006，2026-09-15 合并 `4bdd595`）已经把「每次真实节点调用留一条独立执行记录」在主路径上落地：编译脚本在每次调用前后输出 `[vwf-attempt]` 事件行，宿主按「段号 + 调用序号」分配 `attempt_id` 并逐次提交到 Formal Records Store。

但 LOC-029 保留了一条**兼容回退**：早于 2026-09-15 创建、其 Rev1 冻结脚本里没有事件行的逻辑运行，续跑（含暂停恢复、中断后恢复、崩溃后重跑）时仍走「段末扫描」——按结果键收集，同一节点被重入多次只留一条，且条目没有 `attempt_id`。

这条残留正是 #183 项 1 判定的 B 类：**不影响新运行的证据正确性，只影响旧运行续跑后的可读性**。

- 主路径：[scripts/generate.mjs](../../../../scripts/generate.mjs:363)（事件发射）、[scripts/attempt-ledger.cjs](../../../../scripts/attempt-ledger.cjs:37)（宿主分配 `attempt_id = 'a<段号>k<序号>'` 并串行提交）、[scripts/records-host.mjs](../../../../scripts/records-host.mjs:443)（Store 逐次入库并回填索引）
- 残留路径：[packages/dsh-visual-workflow/src/host.js](../../../../packages/dsh-visual-workflow/src/host.js:988)（`recordNodeAttempts` 段末扫描）

## 2. 用户问题

打开一个 2026-09-15 之前创建、后来又续跑过的运行，「完整经过」里同一个节点只有一条记录，看不出它实际被调用了几次；这条记录也没有序号，无法回答「第几次尝试」。用户会把它误读成「这个节点只跑了一次」。

## 3. 目标

旧运行的续跑记录**不再冒充逐次证据**：兜底条目带段内顺序号与明确的来源标注「段末扫描记录（不保证逐次）」，用户不会再把它当成完整调用史。

## 4. 非目标

- 不改动已落地的新运行逐次链路（事件协议、Store 提交键、Revision 链）。
- 不为历史运行**重建**丢失的逐次记录——段末扫描发生时信息已经不可恢复（结果被 `results[nodeId]` 覆盖）。
- 不涉及并发互斥窗口（另一切片）与角色正文冻结（第三切片）。

## 6. 修改后

已确认口径（决策 1 = B）：

1. 旧脚本段的记录仍来自段末扫描，但每条带上**可判定来源**的标记与段内顺序号，例如 `attempt_id: 'a3s2'` + `evidence_source: 'segment_scan'`。
2. 运行详情的「完整经过」对该段显示「段末扫描记录（不保证逐次）」，用户不会误读为完整调用史。
3. 新脚本段行为与现在完全一致，逐字不变。
4. 历史运行**不做补偿回填**——只在其下次续跑产生新记录时按上述口径标注。

## 7. 功能范围

- 宿主段末扫描入档时补齐顺序标识与来源标记（[host.js:988-1022](../../../../packages/dsh-visual-workflow/src/host.js:988)、[host.js:3558-3566](../../../../packages/dsh-visual-workflow/src/host.js:3558)）。
- 运行详情对该来源的呈现（[client.js:3384-3397](../../../../packages/dsh-visual-workflow/src/client.js:3384) 及执行链视图）。
- 对应宿主侧用例（新增，覆盖「无事件行脚本段」与「有事件行脚本段」两种入档）。

## 8. 不修改范围

- 不改 `[vwf-attempt]` 事件协议、不改 Store 的提交键与 Revision 规则、不改 Formal Record 的 Proof 签发。
- 不改新运行的任何用户可见行为。
- 不批量改写历史 `.agent-runs/`、DSH Home 下已落盘的运行记录（除宿主在下次续跑时自然追加的字段）。
- 不把段末扫描升级为「真正的逐次证据」——事件未产生即无法复原。

## 9. 业务规则

1. 顺序标识必须**只依赖段内已确定事实**（扫描顺序、完成时间），不得推测被折叠掉的调用次数。
2. 段末扫描条目必须可被机器区分：`evidence_source` 存在且非 `per_call`，任何据「attempt 条数」计数的展示都必须显式降级说明，不得静默等同逐次记录。
3. 新脚本段（有事件行）继续以 Store 为权威，本任务不得让段末扫描重新参与提交（保持 [attempts-runtime.test.mjs:171](../../../../packages/dsh-visual-workflow/tests/attempts-runtime.test.mjs:171) 断言成立）。
4. 一条记录的来源标记一旦写入不得在后续 Revision 中翻转（防同一条记录一次显示逐次、一次显示兜底）。

**实现边界（供接手者直接采用）：** 改动集中在 `recordNodeAttempts` 的条目构造与中断补录分支，以及 client 的来源呈现；生成器与 Store 无需改动。宿主与插件客户端必须同一版本交付（`src/host.js` + `src/client.js` 是一整个版本）。

## 10. 用户操作路径

1. 用户打开一个 2026-09-15 前创建、之后续跑过的运行详情。
2. 展开「完整经过」，看到该段每个节点一条记录，旁边标注「段末扫描记录（不保证逐次）」，并显示段内顺序号。
3. 打开一个 2026-09-15 后创建的运行，看到的内容与今天一致：每次调用一条，可切换「第 N 次尝试」。

## 11. 异常和边界场景

| 场景 | 要求 |
|---|---|
| 同一段既有事件行又有段末扫描（异常混合） | 以 Store 为准，扫描条目不得覆盖逐次条目 |
| 段内无新完成节点（纯等待/纯门禁） | 不追加条目，与现状一致 |
| 中断发生在旧脚本段 | 中断条目同样带来源标记与顺序号 |
| 记录被 UI 之外的消费者读取（Formal Records / 质量成本） | `attempt_id` 格式必须与逐次口径不冲突（逐次为 `a<段>k<序号>`，兜底使用可区分的不同前缀） |
| 用户希望「旧运行也补齐真实逐次」 | 明确不可能：事件行未产生即不可复原；只能标注，不能补造 |

## 16. UAT 场景

### UAT-01 旧运行续跑后，记录来源可辨识

- 验收目的：用户不会把兜底记录误读为完整调用史。
- 前置条件：
  1. 备一个 Rev1 冻结脚本不含 `[vwf-attempt]` 行的逻辑运行（可按 §11 用测试夹具构造，或用 2026-09-15 前的真实运行）。
  2. 该产品 DSH 已完成本版本验收组合包安装（不用动态开发态作发布证据）。
- 操作步骤：
  1. 对该运行发起一次续跑，使同节点被重入两次。
  2. 打开运行详情 → 「完整经过」。
- 预期结果：
  1. 该段的记录每条都有段内顺序号，且整体被明确标注为「段末扫描记录（不保证逐次）」；同节点重入两次仍只有一条，**不会**出现凭空补出来的第二条，也不会被展示成完整的调用史。
  2. 新创建的运行同一视图不出现该标注。
- 建议人工关注：标注措辞是否用户可读（不要出现 node_attempt/segment_scan 等术语，口径见 FIX-107）。

## 18. 已知限制

- 段末扫描发生时，被折叠的调用次数已不可恢复；本任务只能提升「可辨识度」，不能恢复事实。
- 该回退路径的存在前提是「Rev1 冻结脚本恒用于续跑」这条冻结纪律（[host.js:3277-3279](../../../../packages/dsh-visual-workflow/src/host.js:3277)）；只要不重新生成旧运行的冻结脚本，回退就不会自动消失。
