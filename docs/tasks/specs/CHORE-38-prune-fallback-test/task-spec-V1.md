## 1. 需求背景

收口脚本在删掉本任务工作区之后，会再跑一次「清理失效登记」的兜底动作（第八步）。它存在的理由是一个真实的坑：**删掉父工作区，不会连带注销它内部嵌套的子登记**——那些登记会变成指向已不存在目录的幽灵条目，目录约定里记着这个缺口历史上复现过三次。

LOC-023 人工验收为「有条件通过」时的优化意见③指出：这个兜底动作的结果**没有任何一条用例断言**，端到端用例也没覆盖它。

## 2. 用户问题

兜底动作是不是真的在干活，现在没人知道——它悄悄退化了也不会有任何红灯亮起，只会留下越来越多指向空目录的幽灵条目。更麻烦的是，收口脚本的收尾提示**无条件**宣称「失效登记已清理」，即使清理失败也照这么说：报告读起来一切正常，实际问题被藏起来了。

## 3. 目标

1. 给这个兜底动作补上可复现的自动校验——让它退化了有人立刻知道；
2. 让收尾提示按真实结果说话——清理成功说成功，失败说失败并给出人工补救命令。

## 4. 非目标

- 不改动清理动作本身的逻辑与执行时机；
- **不新增「清理失败」的故障注入用例**——该异常保护行为本票不改，为它造故障的改动面与复杂度不成比例（取舍理由见分析摘要 §7）；
- 不改收口流程的其他判定（合并门禁、归档、分支保留等）；
- 不处理与本票无关的既有红灯（治理闸门中的 LOC 系列归档缺口、未收口工作区等）；
- 不改动其他任务的测试。

| 对象 | 目标态 |

| 收尾提示 | 按真实结果分叉：已清理 → 写明已清理；未清理 → 写明**未能**清理，并给出人工补救命令 `git worktree prune` |

## 7. 功能范围

1. **补两条断言类用例**（同一测试文件内，沿用现有临时仓库夹具的写法）：
   - 用例 A：正常收口路径，断言清理结果字段为「已清理」；
   - 用例 B：构造幽灵登记场景（在任务工作区内再建一个子工作区，随后直接删除其目录，只留下登记），跑收口后断言工作区清单中**不再包含**该子工作区路径。
2. **收尾提示按结果分叉**（一处文案，两分支），失败分支给出人工补救命令。

## 8. 不修改范围

| 对象 | 理由 |

| 异常保护（清理失败只登记、不阻塞合并） | 既有行为，本票不改、也不为它造故障 |
| 现有 10 个用例的断言 | 全部有效，只新增不改写 |
| 收口脚本的其他返回字段 | 与本票无关 |
| 治理闸门既有红灯（LOC 系列） | 属其他任务缺口 |

## 9. 业务规则

| 编号 | 规则 |
|---|---|
| R-1 | 断言必须指向**真实结果**：清理论断只能来自收口返回的结果字段，不得用「跑过命令就算通过」糊弄 |
| R-2 | 必须覆盖兜底动作真正要解决的那一类问题——**幽灵登记**（父工作区删掉后残留的子登记），而不只是重复验一遍「父工作区已删」 |
| R-3 | 收尾提示不得谎报：清理成功与失败必须给出**不同**的说法；失败分支必须给出可执行的人工补救命令 |
| R-4 | 异常保护行为保持不变：清理失败仍只登记、不阻塞合并 |

## 10. 用户操作路径

1. 执行收口 → 脚本删工作区 → 跑清理兜底 → 输出收尾提示；
2. 读提示：正常时看到「已清理」；异常时看到「未能清理」与补救命令；
3. 日常跑测试：清理兜底一旦退化，新增用例立刻变红，而不是静默失效。

## 11. 异常和边界场景

| 场景 | 处置 |
|---|---|
| 任务工作区内嵌套了子工作区，父删子留 | 清理兜底应注销该幽灵登记；本票用用例 B 锁定这一行为 |
| 清理动作本身失败（git 报错） | 提示如实写明未清理并给出补救命令；合并不阻塞（既有异常保护，R-4） |
| 构造场景时子工作区目录删除后登记仍在 | 这正是用例 B 要复现的前提；若实测中 git 会自动注销，需在用例中改用能稳定复现的构造方式并在报告中说明 |

## 16. UAT 场景

### UAT-01 新增用例确实在保护这个动作

**执行时机**
裁决前可观测

**验收目的**
确认补的不是「跑过就算」的装饰性断言，而是真能抓住退化。

**前置条件**
1. 位于任务工作区，分支 `dev-chore-38-r1`
2. 新增用例已提交

**操作步骤**
1. 跑 `node --test scripts/test/local-task-merge.test.mjs`，确认全绿
2. 临时把清理动作改成不执行（或把结果强制为「未清理」），再跑同一命令
3. 恢复改动，再跑一次

**预期结果**
1. 第 1 步全绿
2. 第 2 步新增用例**变红**（证明断言咬得住）
3. 第 3 步恢复全绿

**自动验证结果**
待施工后回填

**建议人工关注**
若第 2 步不变红，说明断言是空转的，必须重写——这是本票唯一的实质风险。

### UAT-02 收尾提示不再谎报

**执行时机**
裁决前可观测

**验收目的**
确认清理成功/失败两种情形下，提示说法不同，失败时给出可执行的补救命令。

**前置条件**
1. 收尾提示已按结果分叉

**操作步骤**
1. 查看脚本中收尾提示的构造处，确认两个分支的说法
2. 跑一次正常收口路径，查看输出中的提示文案
3. 与 UAT-01 第 2 步（强制未清理）的输出提示做对照

**预期结果**
1. 正常路径提示写明已清理
2. 未清理路径提示写明**未能**清理，且包含 `git worktree prune` 补救命令
3. 两种说法不同，不存在无条件声称成功

**自动验证结果**
待施工后回填

**建议人工关注**
文案长度与语气是否顺手——提示是给人读的，别为了准确变成机器腔。

## 17. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 🟡 幽灵登记场景在实测中难以稳定复现（git 可能自动注销） | 用例 B 可能退化为空转 | V-4 强制做「变红验证」；若实测无法复现，如实报告并改用能稳定复现的构造方式，不得伪造通过 |
