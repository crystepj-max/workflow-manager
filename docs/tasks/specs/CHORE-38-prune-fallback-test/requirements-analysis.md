## 3. 调查事实（2026-09-17 实测，main `8cacb03`）

### 3.1 被保护的动作是什么

收口脚本第八步做一次「清理失效登记」的兜底动作（第 371–374 行），原因是：**删掉一个父工作区，不会连带注销它内部嵌套的子登记**——那些登记会变成指向已不存在目录的幽灵条目，目录约定里明确记着这个缺口历史上复现过三次。

它把结果写进返回对象的顶层字段（第 403 行）。

### 3.2 缺口在哪

| 观察 | 事实 |
|---|---|
| 现有用例数 | `scripts/test/local-task-merge.test.mjs` 共 **10 个用例，实测 10/10 全绿** |
| 对清理结果的断言 | **0 处** |
| 端到端用例覆盖了什么 | 只断言「本任务工作区已删除」「分支保留」「磁盘上不存在」「工作区清单里不含该路径」 |
| 没覆盖什么 | 清理兜底真正要解决的那一类幽灵登记（父工作区删掉后残留的子登记） |

也就是说：现有用例是把结果字段旁边的行为顺便验了一遍，**没有一条能证明清理兜底真的干活**。它退化了也不会有人知道。

### 3.3 顺带发现的真实性缺陷（松哥裁定一并修）

收口脚本第 411 行的收尾提示**无条件**宣称「失效登记已清理」——即使清理动作失败、结果字段为「未清理」，提示照样这么说。这与 LOC-023 立的「不得谎报已清理」是同一类问题：报告读起来一切正常，实际留下了幽灵登记。

## 7. 关于「清理失败要不要补用例」的取舍

清理动作外包在一层异常保护里，失败只登记不阻塞。要为「失败场景」写用例，需要人为注入故障，改动面与复杂度都会上升，而该保护行为本身没有变化、也不是本票要解决的问题。

故本票**不新增故障注入用例**，只对「成功清理」与「幽灵登记被真正注销」两类做断言；异常保护保持既有行为、不动它。这条取舍已写进规格的不做项，避免后续误判为遗漏。
