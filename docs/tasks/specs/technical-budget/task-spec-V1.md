## 9. 业务规则

- 建立技术失败分类：输出结构错误可有限修复；暂时服务错误可退避重试；权限拒绝、必需输入缺失、业务契约冲突不自动重跑有副作用节点。所有实际模型调用计入统计。
- V1 建议默认：同一节点、同一输入版本的一次激活最多 3 次模型尝试，包含首次和格式修复；重试等待 1 秒、2 秒。单次调用截止 30 分钟，Run 累计自动运行时间上限 4 小时；人工等待不计时。配置可收紧或显式调整时间上限，启动时展示并冻结，恢复不得自动清零技术消耗。业务额度沿用模板/M2，不改变建设的常量 3。
- 不计业务额度的回边，以节点、实际输入内容摘要、评价基线内容及目标摘要识别进展；仅改变 Revision 序号或 attempt_id 不视为进展；连续 2 次返回相同签名且无新有效成果则受阻。停止原因指出预算种类、已用量与下一步，不再主要依赖 AGENT_CAP。
- 费用仅在模型价格和实际用量可知时计算/限制；未知显示 unavailable，不能当 0。本条必须实现调用次数和时间硬界限，精细成本看板归 WR-020。

**接手者可直接采用的实现边界：**在统一模型调用边界统计每次调用，格式修复和技术自环共用一次激活预算；使用可注入时钟测试 deadline。配置写入快照，checkpoint 保留已耗用量；输出结构化失败分类而非拼文字判断。

**接口与数据约定：**retry_policy={max_attempts:3,backoff_ms:[1000,2000],attempt_timeout_ms:1800000,run_auto_time_ms:14400000,no_progress_repeats:2}。一次激活包括同节点同实际输入因技术原因的全部重入；同内容仅换 Revision 不重置。人工等待不计自动时间，Run 自动时间按时间区间并集统计，fanout 不把并行墙钟重复相加。提额必须显式记录增量与原因，禁止通用恢复清零。

本条拥有 retry_policy、技术计数、deadline 与 no_progress 判定；向 WR-009 输出可恢复受阻原因，向 WR-020 输出用量事件；WR-012 负责外部动作重试安全。

**兼容方式：**新运行使用本条新规则；已启动运行保持其冻结快照。无法补证的旧历史明确 legacy/unverified，不改写成已验证完成。若其他 P0 已合入，复用其公共接口并运行集成检查；没有硬依赖的条目允许通过既有接口完成自身切片，不能自行等待整个需求包。

## 15. 验收条件

- [ ] AC-01：持续无效输出最多调用 3 次即停止；内部格式修复和技术自环不能各自偷偷获得额外 3 次。
- [ ] AC-02：暂时错误按可控时钟验证退避；不可重试错误最多调用 1 次即停止；超时后停止发起新调用并尽力取消当前调用。
- [ ] AC-03：业务返工计数不因技术重试增加；同一受阻 Run 恢复不重置已耗预算，人工明确新技术额度后才能继续。
- [ ] AC-04：相同目标的无进展重新确认连续 2 次后受阻；真正的新目标/新基线不被误判。
- [ ] AC-05：用户可查看冻结的次数/时间限制及实际消耗；无法强制终止的外部调用标明取消能力限制。

这些勾选框代表未来实现验收，当前全部未执行；Definition Check 通过不自动勾选功能验收。

## 16. UAT 场景

### UAT-01 主路径与关键反例

- 验收目的：验证 §3 用户目标与 §15 全部 AC。
- 前置条件：对应候选源码在隔离 worktree；Node.js 24 与所需依赖可用；真实产品模式验证按既有发布规则使用安装产物。

- 预期结果：正常输入达成目标；非法/缺失/过期输入按 §9 和 AC 拒绝；结果状态、产物和原因一致。
- 人工关注：界面/报告能看懂通过或受阻原因，不把测试替身结果当成用户已经接受。

### UAT-02 恢复与兼容

- 前置条件：保存一个旧快照与一个新规则 Run 的中间状态；仅在隔离环境制造中断。
- 操作步骤：分别恢复旧快照、新运行，再执行一次同请求重放或同内容重读；核对输出与证据。
- 预期结果：旧快照不静默迁移；新运行不丢有效成果、不伪造历史证明；本条涉及的非法条件仍被拦截。
- 证据要求：输出日志/实际产物/状态快照与候选 HEAD；不能只附最终 PASS 字样。
