## 1. 需求背景

契约 §8.3 要求 Controller 在**呈递或签收前**校验证据链，九项引擎（PR #132）已具备这个能力，但它是一个需要人主动执行的独立 CLI：`runbook.md:143` 里写明了这一步。忘记执行、或在执行后又改了记录，整链就从未被机器校验过也能签收。

#123 原文给的形态是「做成仓库脚本**或** CI 检查」，仓库脚本已交付；本片把「什么时候必须跑」也变成机器保证。

## 2. 用户问题

签收这个动作可以在整链不成立的情况下完成——只要没人跑那条命令。

## 3. 目标

交付后，`acceptance_package` 与 `closeout_summary` 两类记录的写入，在落盘前自动执行整链校验，任一不通过即拒写；不跑命令也无法跳过。

## 4. 非目标

- 不为其余五类记录加整链校验（链路此时本就不齐）。
- 不加「告警放行」旁路开关（裁定见 §12）。
- 不改引擎判定语义（片 2 题域）。
- 不改 CI 与工作流蓝图。

## 5. 修改前

`cwf-record.mjs` 的 write 依次做：schema 校验（`:106`）→ Proof 绑定比对（`:115-128`）→ 已终结态与 assembled 保护（`:133-146`）→ closeout 引用双重校验（`:151-172`）。全程不引用 `verifyEvidenceChain`；九项判定只在人工执行 `cwf-evidence-verify.mjs` 时发生。

## 6. 修改后

- 写 `acceptance_package` 且 payload 为 `decided` 形态：落盘前对**当前 run 目录**跑整链，不通过则拒写、不落盘、不更新 `index.json`/`run.json`。
- 写 `closeout_summary`：在既有双重校验之后同样跑整链。
- 拒写时打印未通过项 `id + name + detail`，与独立 CLI 输出同构。
- `awaiting_decision` 形态的验收包（呈递时刻）**不跑整链**——此时 review/test proof 可能尚未齐，跑必然失败；呈递前的校验由人工/CLI 承担，本片只把「签收」这个契约明确要求校验的时刻接上。

## 7. 功能范围

1. `cwf-record.mjs` 引入 `verifyEvidenceChain`，在两个写入分支调用。
2. 调用时机与失败行为（拒写、退出码 1、不落盘）。
3. 归档态/离线导致实况不可得时的行为（E-2）。
4. runbook §6 相应步骤文案降为「兜底复核」，并说明现在写入路径已自动跑。
5. 负例先行：整链不成立时签收必须被拒；且证明记录确实没落盘。

## 8. 不修改范围

九项引擎本体；其余五类记录写入路径；回退/额度/attempt 语义；`--offline` 等不存在的开关（不得新增）。

## 9. 业务规则

- R-1 只有 `decided` 形态与 `closeout_summary` 触发整链，其余一律不触发。
- R-2 整链失败 = 拒写。无告警放行、无环境变量旁路、无 `--force`。
- R-3 校验必须读**落盘前**的 run 目录状态：新验收包自身尚未写盘，引擎的 `ap` 来源需明确为本轮待写 payload（见 §17 实施约束）。
- R-4 幂等：同一条已通过的签收记录重写，仍会重跑整链，不因「上次过了」跳过。

## 10. 用户操作路径

① 集齐五类引用后写 `acceptance_package`（decided）→ 内部自动跑整链 → 若 test proof 的 HEAD 已过期，拒写并指明第④项失败 → 按提示 reverify 重跑 proof → 再写成功。② 写 `closeout_summary` 同理。

## 11. 异常和边界场景

- E-1 引擎因缺文件而无法评估（`index.json` 无验收包指向）→ 视为不通过、拒写，detail 说明缺哪一类；不得静默跳过。
- E-2 归档态/离线：引擎④/⑤的实况比对在取不到 git 信息时本就有回退路径（`liveState` 返回 null 时退回 `run.json` 缓存）。裁定：**沿用引擎既有语义**，写入路径不因「读不到实况」额外放行或额外拒绝。
- E-3 待写 payload 与盘上既有 `acceptance_package.aN.json` 同时存在（成熟刷新）→ 以本轮 payload 为验收包评估，不用旧文件。
- E-4 `closeout_summary` 引用的是另一 attempt 的验收包 → 按引用路径实际评估。
- E-5 run 目录不可读/payload 非法 → schema 阶段已拒，不进整链。

## 16. UAT 场景

### UAT-01 忘记跑命令也躲不过校验

- 验收目的：本片存在的理由——校验时机不再是人治。
- 前置条件：隔离 worktree 内一条链路完整、已签收过一次的 run。
- 操作步骤：① 人为让 test proof 失效（在新 commit 上重跑或改 HEAD）；② **不执行任何校验命令**，直接尝试写 `acceptance_package(decided)`；③ 修复后再写。
- 预期结果：② 被拒且指出失效项；③ 成功；全程无需人工执行 `cwf-evidence-verify`。
- 建议人工关注：拒写信息是否给了下一步该做什么（reverify / 重跑 proof）。

## 17. 风险与实施约束

- 🔴 **引擎入参与「未落盘的待写 payload」不匹配**：`verifyEvidenceChain(runDir)` 从 `index.json` 读验收包，而待写记录此刻还在内存。实施需支持注入待评估的 ap 对象或先写临时文件再评估后决定去留——**不得**用「先落盘、失败再删」的实现（中途崩溃会留下无效证据记录）。这是本片最主要的设计点，必须在施工时以可评审的实现解决，不改变 R-2 的拒写语义。
- 🟡 循环依赖：`cwf-evidence-verify.mjs` 顶层有 `main()` 守卫，被 import 时不执行，确认可安全引入。
- 🟡 签收变慢（多跑一次引擎与若干 git 调用）。影响可接受。
- 🟡 与片 2 同改 `cwf-record.test.mjs` → 串行合并即可。
