## 1. 需求背景

2026-09-19 执行 CHORE-106 收口时，实测发现 `scripts/local-task-merge.mjs`（本项目**唯一在用的收口脚本**，本批任务全部经它合入主干）存在两处口径缺陷：一处在**流程副作用**上（收口后把主检出弄脏，会阻塞并行会话），一处在**记录质量**上（收口提交携带的任务范围字段恒为无意义值）。

两处都不影响「代码是否合入主干」这个主结果，因此长期未被发现；但它们都在**每次收口时必然发生**，属于系统性口径缺陷而非偶发。

## 2. 用户问题

### 缺口①：收口后主检出残留未提交改动

收口脚本的硬前置是「主检出不得有未提交改动」（`checkMerge` 在主检出视角校验）。脚本自己在提交完成后才回写 `merge.commit`，于是**每次收口结束都会在主检出留下一个未提交改动**。后果是：

- 下一次收口（尤其**并行会话**的收口）会被自己的残留产物挡住，表现为莫名其妙的 `checkMerge` 失败；
- 只能靠人工发现并补一次提交收尾（CHORE-106 即由人工补了 `7e8e8ba`）。

这是**自我阻塞**：工具给使用者制造了一个必须先清理、而清理动作又不在工具内的循环。

### 缺口②：收口提交的「任务范围」字段恒为废值

抽取正则 `### 涉及范围[\s\S]*?\n\n` 在标准任务卡形态下只匹配到标题字面，于是所有收口提交里都写着 `任务范围: ### 涉及范围`。这条字段本应让人**从 git 历史直接读出本次改了什么范围**，现在等于没有——而 git 历史是收口后最主要的回溯入口。

## 3. 根因（实测证据）

| 缺口 | 根因 | 证据 |
|---|---|---|
| ① | **写入排在提交之后**：顺序为 `update(..., {merge_commit:'PENDING'})` → `writeBoard` → `git commit` → `git rev-parse HEAD` → `update(..., {merge_commit: 真实哈希})`。最后一步的写入没有任何提交承接 | `local-task-merge.mjs` L308–L316（置 PENDING 并写看板）、L318–L323（commit）、L326（rev-parse）、L329（回写真实哈希） |
| ② | **正则假设标题后无空行**：`[\s\S]*?` 为非贪婪，任务卡里标题后紧跟空行，故匹配在空行处即终止，整体匹配退化为标题本身 | `local-task-merge.mjs` L237 `card.match(/### 涉及范围[\s\S]*?\n\n/)`；任务卡实际形态为 `### 涉及范围` + 空行 + `- 做：` |

## 4. 目标

1. 收口流程结束时，主检出处于干净状态，不需要任何人工补提交。
2. 收口提交中的 `任务范围` 字段是任务卡「涉及范围」小节的真实正文。
3. 两处均有单测守住，避免回归。

- 不改动 `delivery-closeout-host.mjs`（引擎蓝图路线）与 WR-014 适配层。

## 7. 修改后

1. **缺口①**：在回写真实哈希之后，**由脚本自动追加一次「回写提交」**（仅含登记册/看板路径），使收口结束时主检出干净。
   - 保持既有语义不变：登记册 `merge.commit` 记录的是**收口合并提交**（即代码合入的那一次），回写提交只做登记册与看板落账。
   - 回写提交消息采用固定形态，便于识别与检索：`docs(tasks): <任务标识> 回写收口 merge_commit（收口脚本提交后才写入，需补一次提交）`。
   - 若回写提交无任何待提交内容（例如登记册未被改动），则跳过且不报错。

2. **缺口②**：修正抽取逻辑——从标题行之后取内容，**直到下一个同级或更高级标题或文末**；并抽为可导出函数（如 `extractRangeText(card)`）以便单测。
   - 结果需去掉 markdown 列表标记与多余空白；卡片无该小节时回退为既有默认文案（`（详见任务卡）`）。

3. 两处各补一条单测；缺口②的单测**必须复现「标题后紧跟空行」的原缺陷形态**。

## 8. 验收标准

1. 一次完整收口结束后，主检出 `git status --porcelain` 为空（不计本任务以外的并行会话在制产物）；登记册该任务 `merge.commit` 为真实 40 位哈希，非 `PENDING`。
2. 收口提交（或紧随的自动回写提交）中 `任务范围:` 字段为任务卡「涉及范围」小节的正文，不含 `###` 标题字面与 markdown 列表标记。
3. `extractRangeText`（或等价导出函数）对「标题后紧跟空行」的卡片返回正文而非标题；对无该小节的卡片返回空串或既定回退值。
4. `scripts/test/local-task-merge.test.mjs` 全绿，未引入新失败。

## 9. 风险与取舍

| 风险 | 说明 | 处置 |
|---|---|---|
| 收口主路径改动 | 本票改的是**每次任务收口都要走**的脚本，回归代价高 | 改动收敛在收口末尾的落账动作与一个纯函数；不动判定口径；受影响测试文件单独跑并用主检出对照实验判定失败归属 |
| 收口提交数由 1 变 2 | 历史回溯时多一次 bookkeeping 提交 | 提交消息固定形态，便于识别；语义上「代码合入」与「账本落账」分离，反而更清晰；与 CHORE-106 人工补提交的既有做法一致 |
| 正则放宽后误取 | 改为「取到下一个标题」可能纳入超出预期的内容 | 单测覆盖标准卡片与边界卡片（小节在文末、小节后紧跟其他小节） |
| 并行会话冲突 | 收口脚本为共享资产，改动期间有并行会话在跑收口 | 改动前确认无并发收口；改动后 `git status` 复核，不留未提交残留 |
