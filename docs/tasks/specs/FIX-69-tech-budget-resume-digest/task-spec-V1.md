## 1. 缺陷现象（可复现）

远端 LOC-031 实现（PR #34，`ce8cdb8`，已合并 cnb/main）中，Run 因激活预算耗尽受阻后，若业务输入（`feedback`）修订再恢复，引擎沿 `takeActivationKey` 的恢复分支无条件沿用冻结激活键（旧输入版本的键），`actRemain(key) = 0` 导致 **0 次新调用立即再次受阻**——新输入没有获得全新激活预算。

复现方式：`.scratch/loc-031-f01f02-verification/probe.mjs`（修复前输出「❌ 缺陷复现：新业务输入未获得全新激活预算（0 次新调用即再受阻，继承已耗尽预算）」）。

违反契约：`scripts/generate.mjs` 激活机制注释「激活=同节点+同输入版本；首次/格式修复/技术自环重入共用 max_attempts 预算（AC-01）」——输入版本已变，不应共用旧键预算。

## 2. 实测证据

| 观测项 | 修复前 | 修复后 |
|---|---|---|
| 新输入恢复后的新调用数 | 0（立即 `TECHNICAL_BUDGET_EXHAUSTED`） | 3（消耗全新预算后按场景结果收束） |
| 恢复后的激活键 | `evaluate\|c1y7gr#2`（沿用旧键） | `evaluate\|11y75rr#0`（新键） |
| 原样恢复（AC-03 不重置） | 0 次新调用，再次受阻 ✅ | 同左，保持 ✅ |

来源：移植校验会话 2026-09-16（`.scratch/loc-031-f01f02-verification/VERIFICATION.md`，含探针与逐场景输出）。

## 3. 根因

冻结激活键 `stage|inputDigest(stage, feedback)#visitSeq` 的 digest 是**进入节点时刻**的值；受阻时 `feedback` 已被技术失败反馈文本覆盖。恢复时无论比较「键内 digest vs 现算 digest」还是直接沿用，都无法区分「原样恢复」与「业务输入真实修订」：

- 无条件沿用（远端现状）→ 业务修订继承已耗尽预算（本缺陷）；
- 比较键内 digest（第一版修复，已回退）→ 原样恢复也被判为新输入，破坏「AC-03 受阻恢复不重置」（实测 3 次新调用）。

## 4. 修复方案

在预算快照与恢复沿用之间建立**受阻时刻输入摘要**基准：

1. `technicalBudgetSnapshot` 新增 `resume_digest`：受阻时刻对受阻节点现算 `inputDigest(stage, feedback)` 冻结入快照；
2. 恢复端读入 `tbResumeDigest`；
3. `takeActivationKey` 恢复沿用分支增加校验 `tbResumeDigest === inputDigest(stage, feedback)`——一致（原样恢复）沿用冻结键；不一致（业务输入修订）落入新键分支，获得全新预算（恢复携带的 grant 亦挂新键）。

无进展签名 `noProgressBase` 已含 `inputDigest`，输入变化自动刷新，无连带改动。

## 5. 涉及范围

## 7. 方案取舍

- **采纳**：快照冻结受阻时刻摘要（`resume_digest`）——精确区分「原样恢复」与「输入修订」，两个方向语义同时成立，改动面最小（3 处）。
- **否决**：比较键内 digest——无法区分技术失败反馈覆盖后的原样恢复与真实修订（见 §3，实测破坏 AC-03）。
- **否决**：无条件沿用（远端现状）——业务修订继承已耗尽预算，本缺陷本体。
- **否决**：业务/技术反馈分离建模（本机退役版 F-02 的 `bFb/bizFbOf` 思路）——需重构 feedback 单变量模型，超出缺陷修复边界；若后续需要再立需求任务。
