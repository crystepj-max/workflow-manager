## 1. 需求背景

2026-09-16 CHORE-36 重入时第四次出现同型现象：FIX-72 已把工作区命名尺子修好（`TASK_ID_RE` / `RUN_ID_RE` 认 FEAT/FIX/CHORE），但**用尺子的人没对齐**——并行会话持续产出违规现场与缺口：

- 非 `dev-<run_id>` 命名的工作区（`fix-65-compile-output-size`、`chore-73-registry-reconcile`），D-3 两次转红；
- 经 CNB 合并请求收口的任务不走本地归档/轻量归档，13+ 个任务缺归档，D-8 四次转红，每次靠人工回填。

## 2. 用户问题

**护栏在事后，纪律靠自觉。** 现在只有 `validate-workspace` 这类事后检查能发现问题，且发现后要人工回填；开工时点没人拦，收口时点没人强制。结果是每次并行会话跑完都要补一轮账。

## 4. 修改前：`registry-reconcile` 的识别盲区（2026-09-19 实测）

`scripts/registry-reconcile.mjs` **只认「主干 merge commit 尾注」这一个信号**，导致两类真实工作它都看不见：

1. 分支上已自建、尚未合并的工作；
2. 经 CNB PR 合入、但合并提交没带任务尾注的提交。

这正是 #76 / #77 / CHORE-38 状态滞后的直接根因——代码已合入主干，对账脚本认不出来，登记册状态就停在「定义中」。该盲区不修，账实不符会反复出现（2026-09-19 已人工补关 18 个 issue）。

## 6. 目标

1. 开工时点拦住非规范工作区命名，不让违规现场产生后再靠人工发现；
2. 收口时点强制产出轻量归档，不依赖人工回填；
3. 补上 `registry-reconcile` 的识别盲区，让「分支自建工作」与「无尾注的 CNB 合并」都能被对账认出；
4. 把 §5 的 4 行纪律条文落到三条 SKILL.md，并使各会话规则分发一致。

## 7. 非目标

- 不重做 `registry-reconcile` 的例行对账集成（已被 CHORE-73 + FIX-76 覆盖）；
- 不改动 FEAT-84/85/86 相关的工作流 UI 交互（由 ZCODE 推进）；
- 不处理与本票无关的既有红灯；
- 不改动 FIX-72 已修好的命名尺子本身（`TASK_ID_RE` / `RUN_ID_RE`）。

## 8. 验收标准

1. 以非规范命名启动 `cwf-run-init`（或等价环境登记）时，被拒绝或自动纠正为规范命名；规范命名不受影响。
2. 经 CNB 合并请求收口的任务，收口完成后具备轻量归档产物；缺归档时有显式红灯而非静默通过。
3. `registry-reconcile` 能识别出「分支上已自建未合并的工作」与「经 CNB PR 合入但无任务尾注的提交」两类事实，输出中可见；既有对账结果不回归。
4. §5 的 4 行条文逐字落在对应 SKILL.md 中，且安装态副本同步（`scripts/sync-ai-task-skill-set.mjs`）。
5. 既有测试全绿，新增用例覆盖上述 1–3。
