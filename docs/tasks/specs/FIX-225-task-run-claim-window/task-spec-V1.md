## 1. 需求背景

#79 Logical Run 给同一任务（`taskId`）规定了串行互斥：一个任务同时只允许一个进行中的运行，同任务再启要么被拒、要么在终态后**派生**新运行（`taskId#2`）。

互斥判定由 `taskHolder(taskId)` 完成，但它只查「已经登记在册的引擎运行」。而一次新启动从**通过互斥检查**到**把引擎运行登记在册**之间，要经过 DSL 校验、子进程编译、模型探针、工作区准备、引擎 `start()` 等多个耗时步骤。两个针对同一 `taskId` 的新启动如果落在这个空隙里，彼此看不见，于是都放行。

这不是理论推断：本会话在隔离探针环境中实测到同一 `taskId` 两次新启动**都成功起了引擎**（见 §5）。

- [packages/dsh-visual-workflow/src/host.js:1839](../../../../packages/dsh-visual-workflow/src/host.js:1839)（`taskHolder` 只遍历已登记运行）
- [host.js:3118](../../../../packages/dsh-visual-workflow/src/host.js:3118)（放行点）→ [host.js:3469](../../../../packages/dsh-visual-workflow/src/host.js:3469)（登记点 `ensureRun` + `live.add`）
- 结论：**全仓没有同步抢位逻辑**（`claim` / `reserve` / 串行化入口均无命中）

## 2. 用户问题

同一个任务被并发发起两次（例如调度器重发、Agent 误以为失败后重试），结果不是「第二次被拒」，而是**两条运行同时在跑**；其中一次还会把另一条已建的运行记录按「崩溃残留」处理，写成失败后派生 `#2`——用户看到同一个任务凭空多出两条运行，且分不清哪条是真的。

## 3. 目标

同一 `taskId` 的新启动在**入口即互斥**：后到的调用立刻拿到明确的拒绝回执（说明谁占着、处于什么阶段、该怎么办）；不再出现两条运行同时跑同一任务，也不再出现「把健康运行误判为崩溃残留」。

## 4. 非目标

- 不改「终态后再启派生 `#2`」的既有语义（R8）。
- 不改跨机器/跨进程的协调（那是 #185 / #187 的流程与环境侧，与本票互补不重叠）。
- 不做「同一任务允许多个运行并行」的产品方向变更（需另立需求）。
- 不重写 LOC-032 幂等账本（其职责是防重复**外部动作**，见 §5 末）。

5. 现有测试为何没抓到：`assertMutexBlocked`（[host.test.mjs:1460](../../../../packages/dsh-visual-workflow/tests/host.test.mjs:1460)）与 #19 T2（[host.test.mjs:1523](../../../../packages/dsh-visual-workflow/tests/host.test.mjs:1523)）都**先等到前任引擎已 start** 再发第二次调用，覆盖的是「登记之后」的互斥，正好绕开了这个窗口。
6. LOC-032 幂等账本不覆盖：账本按 runId 分文件（[scripts/operations-host.mjs:79](../../../../scripts/operations-host.mjs:79)）、以 `operation_id` 去重（[operations-host.mjs:73](../../../../scripts/operations-host.mjs:73)），防的是「同一 Run 内重复外部动作」，Run 还不存在时无从谈起。

## 6. 修改后

已确认口径（决策 2 = A · 立即拒绝）：

1. 新启动在通过互斥判定的**同一同步步骤内**占位（占位记录 `taskId → 本次启动`），后续耗时步骤都发生在占位之后。
2. 后到的同 `taskId` 新启动立即收到拒绝回执，回执指出占用方是谁、处于什么阶段、下一步该怎么办（沿用现回执文案，补「正在启动中」这一形态）。
3. 启动成功 → 占位移交给引擎运行登记；启动失败/异常 → 占位必须释放，不得把任务永久锁死。
4. 任何情况下不再出现「两条运行同时跑同一 `taskId`」，也不再出现「对健康运行写 FAILED 后派生 `#2`」。

## 7. 功能范围

- 宿主启动入口的同步抢位与释放（[host.js:3105](../../../../packages/dsh-visual-workflow/src/host.js:3105) 起的 `wf_run.execute` 全流程）。
- 拒绝回执文案与状态提示（含「正在启动中」与「崩溃残留」两种形态的区分）。
- 崩溃残留判定改为只在**确认无在途启动**时进行。
- 新增并发用例：两次同 `taskId` 新启动在同一 tick 发起（正好是现有测试缺口）。

## 8. 不修改范围

- 不改续跑/恢复（`decision_id`、`entry`、`resume_paused`）的接管语义。
- 不改 `latestLogicalRunForTask` / `nextLogicalRunId` 的命名与派生规则。
- 不改引擎本身（worker 线程/子进程）与 Formal Records Store。
- 不引入跨进程文件锁（决策 2 已定为拒绝口径，进程内同步占位即可闭合本窗口）。

## 9. 业务规则

1. 占位与互斥判定之间**不得有 await**：判定通过即占位，否则窗口依旧。
2. 占位必须成对释放：成功登记（转交 `live`）、启动失败、启动抛错、启动前返回错误四条路径都要释放；进程内任何退出路径不得留下幽灵占位。
3. 占位只用于「新启动」；续跑沿用同一逻辑运行，是否受占位约束统一处理为：续跑与恢复不新增运行，不参与新启动抢位，但仍受同任务串行门禁（决策 2=A 下的既定口径）。
4. 崩溃残留判定（写 `FAILED / RUNTIME_RESTARTED`）只能在**没有活跃占位且引擎未在册**时执行，且必须落在真实终态记录上，不得被后续启动流程覆盖成 RUNNING 而无声丢失。
5. 拒绝回执必须可操作：告诉用户占用方标识、当前阶段、以及三条既有出路（带 `decision_id` / 带 `entry` / 换 `taskId`）。

**实现边界（供接手者直接采用）：** 本切片只需改 `src/host.js`（入口同步占位 + 崩溃残留判定收口）；`src/client.js` 仅在需要新增「正在启动中」呈现时参与——若需要，两者必须同一版本交付，禁止只改一半。持久层不动：占位是进程内生命周期，重启后由「回载 + 崩溃残留判定」负责，不得把占位写盘（否则进程被杀会留下无法自愈的死锁）。

## 10. 用户操作路径

1. 用户对同一任务连续发起两次启动（或调度器重发）。
2. 第一次正常开始执行。
3. 第二次**立刻**收到拒绝回执：说明该任务已被哪次运行占用、当前处于「正在启动」还是「执行中」，并给出下一步。
4. 运行看板只有一条进行中的运行；没有多出来的 `#2`。

## 11. 异常和边界场景

| 场景 | 要求 |
|---|---|
| 第一次启动在编译阶段失败并返回错误 | 占位释放；用户可立即重试，不被幽灵锁定 |
| 第一次启动成功、进入人工等待后再次发起 | 沿用现状（按停机态判定，带 `decision_id`/`entry`/`resume_paused` 才放行） |
| 宿主机重启，前任是真实崩溃残留 | 仍按现有语义判 FAILED 并派生（不得因本改动被拒） |
| 同一 `taskId` 两次调用**完全同一毫秒**发起 | 只允许一个进入启动流程（AC-01 的判定就是这个用例） |
| 两个不同 `taskId` 并发 | 不受影响，必须仍并行放行（防回归） |
| 占位持有者异常退出（未走正常释放） | 必须有兜底（超时或随引擎登记自动失效），不得永久锁死任务 |

## 16. UAT 场景

### UAT-01 并发发起同一任务

- 验收目的：验证抢位窗口关闭，且不产生重复运行。
- 前置条件：
  1. 产品 DSH 已安装本版本验收组合包（动态开发态不作发布证据）。
  2. 一个可用的正式模板（如 `wf-construction-full-feature`）与一个从未用过的 `taskId`。
- 操作步骤：
  1. 在同一个 Agent 回合内连续发起两次 `wf_run`（同 `taskId`，不等待第一次回执）。
  2. 打开运行看板/运行列表查看该任务。
- 预期结果：
  1. 只有一次真正开始执行；另一次立即返回拒绝回执，回执点名占用方与下一步。
  2. 看板该任务下只有一条进行中的运行；没有 `#2`，也没有被误标失败的记录。
- 建议人工关注：回执措辞是否用户可读；「正在启动中」是否被表达成用户能理解的说法（口径见 FIX-107）。

### UAT-02 失败后可立即重试

- 验收目的：确认占位不会把任务锁死。
- 前置条件：一个会在启动前失败的场景（如故意用不存在的 `templateId`，或让 DSL 校验失败）。
- 操作步骤：
  1. 发起一次注定失败的启动，收到错误回执。
  2. 用正确参数再次发起同一 `taskId`。
- 预期结果：
  1. 第二次正常启动，不被「已有进行中的运行」挡住。
- 建议人工关注：是否需要用户手工清理什么（不应需要）。
