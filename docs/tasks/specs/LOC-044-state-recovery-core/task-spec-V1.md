## 2. 用户问题

同一状态或恢复约定需要在生成脚本和宿主间多处维护，修改容易漏掉一个入口，造成暂停、等待或恢复表现不一致。

## 3. 目标

状态与恢复约定具有一处可直接测试的实现，调用者通过薄适配使用；用户已有工具、状态和恢复行为保持一致。

验收须逐项对应 §15 四项 AC 与 §16 四组 UAT；研究得出“不采用”可以是有效结论，但没有执行的实验不是已验证收益。

## 4. 非目标

不重写引擎，不拆分整个 host/client，不改四模板拓扑、状态名或人工权限，不接管记录事务、输入绑定、精确失效和技术预算。

## 9. 业务规则

1. 开工先冻结 behavior_baseline_commit、四模板摘要和至少六类公开事件序列，列出规则→当前生产者/消费者→抽取后唯一所有者的清单。已有 P0 状态修复若已合入则保留其新行为；尚未合入的目标不能当作当前实现。
2. 本条只拥有：状态/完成结果的规范化与映射约定、检查点字段与恢复载荷构造/校验的纯函数。计时、随机 ID、日志读取、文件访问、AbortController、模型调用和记录提交仍在适配层；时间/ID 需要时作为输入注入，纯函数不得修改调用方对象。
3. 生成脚本包含从同一源构建的自包含纯逻辑；宿主按现有打包/加载边界消费同一源。允许构建时复制产物，禁止再维护手写副本或依靠 toString 隐含闭包。Node 可直接导入测试，DSH VM 中不新增 fs/process/宿主服务依赖。
4. 共享字段约定至少覆盖 entry/results/history/round-feedback、budgetUsed/maxRounds/decisionSeq 与旧字段映射。抽取不统一这些字段背后不同的业务含义：正常结束、人工等待、外部 BLOCKED、主动 PAUSED、取消等仍按既有基线分别处理。
5. 旧冻结脚本恢复继续遵守其检查点形态；损坏检查点、缺失现场、$end 伪入口、非法 decision_id/choice 和待生效基线修订的处理与基线一致。不得为对照通过而静默删除错误信息、历史事件、候选/证明引用或预算字段。
6. 行为比较允许归一化时间戳、临时绝对路径、随机 run/engine ID，但保留引用间关系和顺序；状态、原因码、有效入口、已完成结果、预算、人工作用及副作用请求必须逐项相同。不能整段忽略 resume/result 来掩盖差异。
7. projection-core 已有单一职责，不搬入运行状态引擎；只有新的共享模块确实改变打包引用时才调整其消费者接缝。抽取候选若没有实际重复，不为凑减行量强行创建抽象；最终列清消除的重复及已复用的既有单源。

接口与数据归属：输入为冻结 Blueprint/当前状态摘要、既有事件或已解析检查点、显式上下文；输出为规范结果、恢复载荷或结构化拒绝事实。对外 wf_run/wf_control 参数、结果与事件字段保持兼容。纯逻辑的内部函数命名由实现者按现有模块风格选择，不因此扩大公开 API。

## 11. 异常和边界场景

- **单源及调用方**：同规则只维护一处源，三入口结果一致，清单能指出具体消除了哪份副本。
- **六类公开行为对照**：所有对外语义一致；缺失/损坏检查点和非法选择与基线同样拒绝，不增加模型或外部动作。
- **真实打包与恢复**：无宿主依赖泄漏、无缺模块，实际恢复到原入口；机器测试与真实安装证据分别记录。
- **范围与并行合入**：无额外业务行为变更；每项抽取可追溯；已有修复保留，未运行的真实检查不标通过。

旧快照不能识别或真实打包缺模块时保留失败现场，按冻结前行为拒绝/降级；不得静默丢弃现场并派生一个伪装为恢复的新Run。
