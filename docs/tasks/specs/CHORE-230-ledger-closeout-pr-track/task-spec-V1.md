## 1. 背景

2026-09-19 主源从 CNB 切到 GitHub，`main` 由 repository ruleset `main protect`（id `21234444`，enforcement=active，bypass_actors=0）保护，**只能通过 PR 合并**。

任务流程原本不是这么设计的：`local-task-merge.mjs` 把任务分支 squash 并进**本地** main，顺手在同一个提交里写完账本（归档三件套、登记册状态、看板）。账本写入和主干推进是同一个动作，所以零额外开销。

主源切换后，主干由 GitHub 的合并动作推进，账本写入失去了载体。

## 2. 用户问题

1. **每收口一个任务要多开一个 PR。** 实测：CHORE-111 的代码走 #223，账本走 #229，两个 PR 内容零重叠，后者纯属流程开销。
2. **新任务的材料进不了主干。** FIX-224 / FIX-225 / FIX-226 的任务卡与规格至今是未跟踪文件，主干上不存在；`validate:task-context` 因此长期挂 3 项红。干净检出或远端克隆后，这些任务"有号无规格"，无法开工。
3. **门禁处于两难。** 它现在把"规格未入库"判成硬失败，而这个窗口在 PR-only 流程下必然存在（材料要先经评审才能入库），于是门禁长期红、真问题被噪音淹没。
4. **误发号的暴露面变大。** 本票立项过程中，在一次执行 `allocate` 的工作区落后 4 个提交，旧代码把号发到了 CNB 灾备镜像（`cnb#116`）。只要"账本和规则要过闸门、工作区容易落后"这个结构还在，同类误操作就会再来。

## 3. 目标

让「立票 → 施工 → 收口」在 PR-only 主干上闭环自洽：**账本与立票材料随任务自身的 PR 入库，每任务 1 个 PR，且账本的可追溯性与既有校验不降级**。

非目标见 §5。

## 5. 非目标

- **不改历史任务的 `task_id` / `remote` / `merge` 值**，含存量字符串形状的 `merge`（FIX-108、CHORE-104）与 8+ 条不规范 `remote`——判据只读兼容（D-05）。
- **不给 `main` 增加 ruleset bypass 或专用机器人直推通道**：ruleset 的 bypass 只能按身份+ref 生效、无法限定路径，等于重开刚建立的 PR 闸门。
- **不把账本搬出 Git**（GitHub Projects / issue 字段）：会推翻「任务卡、登记册、看板必须入库，克隆即可离线开工」这条现行硬规则，代价与收益不成比例。
- 不改编号契约语义（`<TYPE>-<号>` 由远端服务端分配、禁止本机自增）。
- 不改 GitHub 收口适配器的动作形态（`close-task` 走真实 `gh`、`create-review`/`merge` 登记效果）。
- 不修 CI born-red（`LOC-042 consumer_chains`、`dsh-visual-workflow` 包测试、M5 挂钟依赖）——在途于 #218，本票不承接。
- 不改 FEAT-84/85/86 的 UI 交互与 `.github/workflows/mirror-cnb.yml`。

## 6. 方案

### 6.1 合并事实：记 PR 号，哈希本地解析回填

```
任务 PR（含账本）             合并（GitHub 产生 merge commit）      下一次任意脚本运行
  merge.pr = 223     ──────►   PR #223 = MERGED      ──────►   resolveMergeCommit(repo,223)
  status = 等待验收                                             → sha + merged_at 回填 merge.commit
                                                                → 看板/前置判据视其为「已合并」
```

要点：合并前账本里**没有任何先于事实的断言**（只写"这个任务的收口挂在这个 PR 上"）；合并后事实自动出现，无需第二个 PR。哈希没有被丢弃，只是不再要求人在合并前知道它——这保住了 §4.4 两处依赖逐字哈希的校验。

### 6.2 立票材料的入库载体

复用 §4.3 第 6 项的同一条路线：定义阶段产出的卡 + 规格 + Definition Check 提交到任务分支，随任务 PR 合入；门禁按 §4.4 第 11 项分级，使"评审中"不再是红。

### 6.3 拆分与顺序

单票两个可独立验证的交付面，建议按序提交（不拆成两票，理由见 §10 D-01）：
- 面 A（§4.1–§4.2、§4.4 第 9/10 项）：账本字段、解析、状态推导与判据兼容。
- 面 B（§4.3、§4.4 第 11/12/16 项、§4.5）：`--via-pr` 收口与立票路线、门禁分级、推送目标、文档。
面 B 依赖面 A 的字段；两面各自都能独立写出可观察的 UAT。

## 7. 验收标准

1. **收口一个任务只产生 1 个 PR**：用 `local-task-merge.mjs --via-pr <n>` 收口一个真实任务后，主干上该任务的代码、任务卡、规格、归档三件套、登记册与看板全部到位，`git log` 中不存在只为补账本而开的第二个 PR。
2. **账本不含先于事实的断言**：任务 PR 合并前，登记册该记录只有 `merge.pr`、没有 `merge.commit`；解析函数在 PR 未合并时返回 null 且调用方不误判为失败。
3. **合并事后可追溯**：PR 合并并 fetch 后，`resolveMergeCommit` 解析出的 sha 与 `gh pr view <n> -q .mergeCommit.oid` **逐字相同**，并回填进 `merge.commit`；`validate-workspace` 的 D-8 归档一致性继续通过。
4. **前置判据不倒退**：`ai-task-preflight-check` 对「已合并前置」判定通过、对「未合并前置」仍失败；存量字符串形状 `merge`（FIX-108 那条）不再被误判为缺少合并证据。
5. **立票材料不再长期悬空**：新任务的材料随其 PR 合入主干；`validate:task-context` 对「规格存在但未跟踪」输出警告与待提交清单且退出码为 0，对「已具开工资格却无规格文件」仍返回非 0。
6. **历史值零改动**：`git diff docs/tasks/registry.json` 中既有任务的 `task_id`/`remote`/`merge` 值不被改写（推导只在读取或看板生成时起效；回填 `merge.commit` 仅发生在含 `merge.pr` 且已合并的记录上）。
7. **误发号与误推均有提示**：① 工作区落后于 `origin/main` 时执行 `allocate`，stderr 出现明确警告，不落后时无噪音，离线（fetch 失败）不阻断；② 收口与立票路线的推送动作显式指向主源远端，在 `remote.pushDefault=cnb` 保持不变的机器上执行时推送不落到 CNB；实际目标与主源不一致时 stderr 告警。
8. 新增单测覆盖：解析正确性（含 PR 未合并、未 fetch、sha 不在本地三种情形）、状态推导、门禁分级、`--via-pr` 账本落盘、历史值不变；既有测试套件失败集与开工基线逐名一致。

## 8. 实施要点

- 与 `FIX-109` 在 `local-task-merge.mjs` **强重叠**（它改 `merge_commit` 回写时机与 `extractRangeText`，正是本票 §4.3 的同一区域）。FIX-109 在途于 `dev-fix-109-r1`。判定：**不设硬前置依赖**（"它未完成则本票无法开始"不成立），但开工前先 rebase 到含 FIX-109 的主干，避免同文件反复冲突；若 FIX-109 已被本票覆盖，需在卡面记录其能力未丢失。
- 推导必须是**只读优先**：`renderBoard`/preflight 可以在内存里用推导值，落盘回填只在明确调用 `set`/收口路线时发生，避免"跑一下看板就改写了账本"的意外 diff（多会话共用登记册时尤其重要）。
- `resolveMergeCommit` 不得联网：只用本地 `origin/main` 引用；未 fetch 到时应返回 null 而非报错。
- 解析依赖 GitHub 默认合并信息格式 `Merge pull request #<n> from <branch>`。若该格式变化（如 squash 或自定义模板），必须有兜底：解析不到 → 保留显式值并告警，绝不误判未合并。
- 门禁分级不得削弱既有断言：`validate-workspace-archive.test.mjs` 的 V-6 负例（merge.commit 与登记册不一致即失败）必须继续通过。
- 工作在本票自己的任务分支与新 worktree，不在共用的主检出施工。

## 11. UAT 场景

### UAT-01 收口只产生一个 PR

- 验收目的：证明流程开销归零。
- 前置条件：存在一张已验收、代码已在任务分支上的真实任务。
- 操作步骤：
  1. `node scripts/local-task-merge.mjs --task <ID> --branch <b> --decision accept --via-pr <n>`；
  2. 建 PR 并合并；
  3. `git log --oneline origin/main -5` 与 `gh pr list --search "<ID>"`。
- 预期结果：
  1. 主干一次合并即含代码 + 卡 + 规格 + 归档 + 登记册 + 看板；
  2. 不存在第二张只为账本的 PR；
  3. 登记册该记录 `merge.pr=<n>`，其 `merge.commit` 在下一次解析后与 `gh pr view` 一致。
- 建议人工关注：合并前账本里不应出现任何"已合并"字样。

### UAT-02 三态解析

- 操作步骤/预期：① PR 未合并 → 解析 null、判据报「未合并」而非崩溃；② 已合并且已 fetch → sha 与 `gh` 一致、D-8 校验通过；③ 已合并但本地未 fetch → 不误判、给出可执行提示。

### UAT-03 门禁分级

- 操作步骤：造两种任务——A 有规格文件但未跟踪、B 已具开工资格但无规格文件。
- 预期：A 输出警告与待提交清单且退出码 0；B 仍非 0 且点名原因。

### UAT-04 历史账本不变

- 操作步骤：跑完上述场景后 `git diff docs/tasks/registry.json`。
- 预期：FIX-108 / CHORE-104 等存量 `merge`（含字符串形状）与所有 `task_id`/`remote` 零改动。

### UAT-05 推送目标显式主源

- 验收目的：证明推送不再依赖机器本地的 `pushDefault`。
- 前置条件：机器保持 `remote.pushDefault=cnb`（**不修改配置**）。
- 操作步骤：
  1. 在任务分支上执行一次收口 / 立票路线的推送动作；
  2. 核对 GitHub 上该分支是否已更新（`git ls-remote origin <分支>`）；
  3. 核对 CNB 侧同名分支是否未被本次动作更新。
- 预期结果：GitHub 分支已更新；CNB 侧无新提交；全程无需人工指定远端。
- 建议人工关注：首次执行时确认「目标与主源不一致」的告警确实触发。

## 12. 已知限制

- 推导与回填依赖本地 `origin/main` 引用足够新；机器长期不 fetch，账本会停在"只有 PR 号"的中间态（可接受：事实仍可按需解析，且不产生错误结论）。
- 存量字符串形状 `merge` 不在本票内改写，D-8 对这类记录仍只能按回落值比对。
- GitHub 轨道的证据来源依赖 CHORE-110 的验收包 schema；该票未落地前，`--via-pr` 路线对无验收包的任务如实不生成 `evidence-summary.json`。
- CI `validate` 的 born-red 不由本票修复；本票只保证不新增失败。
- 机器本地 `remote.pushDefault=cnb` 不被本票修改（D-07）：第 16 项只在收口 / 立票路线的推送动作中显式指定主源；人工在其他位置执行不带远端的 `git push` 仍会落到 CNB。
