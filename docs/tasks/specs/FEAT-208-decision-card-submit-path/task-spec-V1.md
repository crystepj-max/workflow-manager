# 决策卡提交路径闭环（UI 续跑接原运行）

## 1. 需求背景

运行详情的决策卡（WAITING_HUMAN）与恢复卡（BLOCKED 改模型恢复）由 FEAT-85 交付：界面、字段映射、DT-01 受阻路径呈现均已验收。其提交路径当时按 LOC-016 的开放决策票 `DT-01-ui-resume-attribution` 如实受阻。2026-09-19 松哥对该票作出裁决（UI 续跑接在原运行上继续），提交路径具备闭环条件，立本任务实施。

## 2. 用户问题（业务语言）

用户在运行详情看到「需要你的决定」的卡片，能看懂选项，但点了没有下一步——任务停在原地，必须离开产品回到会话/终端里手工操作才能继续。恢复卡同理。用户要的是：在页面上做完决定，任务就真的动起来。

## 3. 目标

- 决策卡点选选项（可附理由）提交后，原 Logical Run 追加段/attempt 续跑，详情页与链路实时反映。
- 恢复卡改模型恢复同口径闭环。
- 系统如实记录「这次续跑由界面触发」（provenance）。

## 4. 非目标

- 不改执行引擎语义、工作流模板、校验器。
- 不重构决策卡/恢复卡的呈现层（FEAT-85/102/103 已验收形态保持）。
- 不覆盖 LOC-016 片2 的其余增强项（进度呈现等已有能力不动）。
- 不处理 DT-02（token 统一，已裁定 B 观察期）。

## 5. 修改前

- 决策卡呈现选项/理由/影响/锁定与 DT-01 受阻字段映射，提交动作按受阻口径不可用（或点击无实际效果）。
- 恢复卡呈现原因/Provider·Model 前后值，提交路径同样受阻。
- 用户必须离开产品，经会话/CLI 按 guidance 手工续跑。

## 6. 修改后

- 决策卡提交 → 经 `vwf.run.control`（扩展动作）向**原 Logical Run** 追加段/attempt 续跑；提交后卡片转为对应状态，详情页/链路/attempt 列表实时更新。
- 恢复卡改模型提交 → 原运行按新 Provider/Model 恢复，同口径更新。
- 每次提交在 provenance 中如实记录「UI 触发」来源。
- 交付后 FEAT-85 验收项 UAT-04/07 中「提交路径受阻」的口径转为「已闭环」。

## 7. 功能范围

1. 决策卡提交动作（选项 + 理由）→ 原运行续跑。
2. 恢复卡提交动作（改模型恢复）→ 原运行恢复。
3. `vwf.run.control` 动作扩展：新增续跑/决策类动作与 initiator（UI 触发来源）字段（增量、可加法，不改变既有 pause/interrupt/guidance 行为）。
4. 提交后的详情状态联动（卡片态、attempt 列表、链路）。

## 8. 不修改范围

- 既有 pause/interrupt/guidance 动作行为。
- 运行详情呈现层结构（页头/状态条/三栏工作台/链路弹窗）。
- 执行引擎、工作流模板、校验器、数据契约既有字段（仅增量）。

## 9. 业务规则

1. UI 续跑**接在原运行上继续**：同 Logical Run 追加段/attempt（DT-01 裁决），不新开运行。
2. provenance 如实记录 UI 触发来源，不冒充会话内触发。
3. 提交失败（通道错误、宿主拒绝、运行状态已前进）→ 如实报错并可重试，**不伪造成功状态**。
4. 提交后执行仍按运行引擎既有规则进行（快照版本记录承载工具与实现变更）。

## 10. 用户操作路径

1. 打开含 WAITING_HUMAN 门禁的运行详情 → 决策卡呈现。
2. 点选选项（可填理由）→ 点击提交。
3. 详情页状态实时转为对应状态，链路/attempt 列表出现新执行段。
4. BLOCKED 运行 → 恢复卡改模型 → 提交 → 原运行恢复。

## 11. 异常和边界场景

| 场景 | 行为 |
|---|---|
| 提交时运行已被其他途径推进 | 以宿主裁决为准如实呈现（不覆盖、不回滚他人推进） |
| 提交通道失败 | 报错可重试，不伪造成功 |
| 重复提交（双击） | 幂等或明确提示，不产生重复段 |
| 决策卡与恢复卡并存 | 按运行实际状态只呈现其一（既有规则保持） |
