## 1. 需求背景

#75 §4 要求编辑器支持渐进式配置 Business Outcome Routing 与 Completion Mapping。Business Outcome Routing 的界面已经随 `FEAT-84` 落地（「结果与去向」段），Completion Mapping 从来没有对应控件。四套内置模板靠手写 JSON 声明完成映射，例如 `templates/wf-diagnose.json` 的 closeout 节点写着 `output.completionPath = "$.completion_type"`；用户自建的工作流没有这条路。

## 2. 用户问题

1. **完成类型永远为空**：用户自建工作流跑完，运行详情里的「完成类型」显示不出来，因为他没有任何入口声明「完成原因取自结构化结果的哪个字段」。同一个 Run 在内置模板下有值、在自己的工作流下没值，用户无法解释也无法排查。
2. **改结果字段会悄悄吃掉手写路径**：运行层与校验层都支持多层字段路径（`scripts/validate-core.cjs:123` 的 `JSON_PATH_RE` 接受 `$.a.b`，宿主 `host.js` 的 `readOutcomePath` 按 `.` 逐层取值），但编辑器面板只认单层字段名（`client.js:5552` `routingNameOf` 的正则限死 `$.<单段>`）。用户手写的 `$.result.decision` 在面板里显示成「未配置」，此时只要在该面板改任何东西，`applyRoutingWrite`（`client.js:5600-5618`）会把 `outcomePath` 整体改写成 `$.<新名>` —— 原多层路径静默丢失，且 schema 里对应的旧属性不会被清理。

## 3. 目标

用户在编辑器里，不打开 JSON 就能：

1. 给自定义工作流的收口节点声明完成映射（选字段、看候选值、保存即写回 `output.completionPath`），保存后运行的完成类型能正常出现在运行详情；
2. 让多层结果字段路径在「结果与去向」面板中如实回显、如实编辑，改任何一项都不再覆盖用户已写的路径层级。

## 4. 非目标

- 不做面板分层重排：定稿 §4.2 已确认**三层（基础 / 结果与去向 / 高级）就是 v0.1 形态**，完成映射作为「结果与去向」层的一等能力补入，不拆第四段。
- 不引入插件运行入口：DT-01 已裁 **A——Skill / Chat 仍是唯一正式运行入口**，本票不新增任何发起运行的按钮或路径（实测 `client.js` 现无运行入口，须保持）。
- 不做 Outcome Preset 纠偏与选择器：`outcome-presets.json` 三条 preset 的 `outcomePath` 全为 `$.verdict`，与正式模板实际的 `$.route` / `$.status` 不符，属定稿 **S-2**；本票只在候选值来源上与之划清（见 §9）。
- 不改运行详情 / 看板的呈现与筛选（属定稿 S-4、`LOC-016`、`FEAT-208`、`FIX-107/108`）。
- 不改运行时读取逻辑（`host.js` 的取值实现已支持多层，本票不动）。
- 不改四套内置模板的任何声明；内置模板结构只读规则不变。
- 不把 `COMPLETED_OBSERVING` 等无生产者的完成类型加进候选值（2026-09-19 裁定：v0.1 明确不做）。

## 5. 修改前

- 「结果与去向」段：字段名输入框 + 取值列表 + 一键补边；字段名只接受单层名；多层路径显示为空。
- 「完成映射」：编辑器内不存在该概念（`client.js` 中 `completionPath` 出现 0 次）；只能在高级 JSON 里手写。
- 校验：`validate-core` 已对 `completionPath` 施加六条规则，但只在保存/校验管道里报错，面板不预告，用户靠试错发现。

## 6. 修改后

- 「结果与去向」段新增「完成映射」区：字段路径输入 + 当前 schema 中的候选取值 + 明确的「未声明」态；写回 `output.completionPath` 并保持 schema 为取值真源。
- 多层路径在面板中回显为完整路径（例如 `result.decision`），编辑取值只改取值集合，不动路径层级；改路径本身是显式动作。
- 面板即时反映校验内核的六条规则（哪条不满足、为什么），不再依赖保存后试错。

## 7. 功能范围

1. 完成映射字段的编辑与写回（含候选值来自 schema 的 `enum` / `const`）。
2. `outcomePath` 与 `completionPath` 的多层路径表达、回显与保真写回。
3. 校验内核既有六条 `completionPath` 规则的前端同源提示（不改规则本身，只把已有规则映射到界面文案）。
4. 投影与往返：多层路径经 `projection-core` 蓝图 ↔ DSL 双向不丢字段。
5. 回归测试：多层路径保真、取值编辑不覆盖路径、六条校验规则的界面态。

## 8. 不修改范围

`scripts/generate.mjs` 的编译语义、`host.js` 的运行时取值与 `wf_run` / `vwf.*` RPC 契约、`.generated/` 生成物（只重新生成不改写）、`templates/`、运行详情与看板的展示层。

## 9. 业务规则

以下均为已存在的内核规则，界面必须与之内核同源，不得各自演化：

| 规则 | 内核出处 |
|---|---|
| schema 是业务结果取值的唯一真源，界面列表只是它的编辑器 | `client.js:5548` 注释 D2；`applyRoutingWrite` 写回 schema |
| `outcomePath` / `completionPath` 必须是 `$.` 开头的字段路径，可多层 | `validate-core.cjs:123` |
| 声明 `completionPath` 时 `output.schema` 必填 | `validate-core.cjs:866` |
| 完成类型路径必须在 `output.schema` 中已声明 | `:868` |
| 完成类型叶子节点必须是 string | `:870` |
| `completionPath` 只允许声明在有结构边指向 `$end` 的节点上 | `:874` |
| fanout 节点禁止 `outcomePath` 与 `completionPath` | `:695`、`:698` |
| 业务结果路径必须可穷举（enum / const / oneOf 常量或 boolean） | `:898` |
| 新模式（有 `outcomePath`）禁止 `on: success/failure` 出边与 `when` | `:905`、`:908` |

其它约束：

- 一个 Logical Run 的完成原因只有一个：Completion Type 是 `COMPLETED` 的业务原因，不是运行状态，不得与 Lifecycle 混用或压进同一个状态字符串（`docs/design/workflow-design-principles.md` 原则 12）。
- 完成类型枚举真源是模板/蓝图自己的 schema 声明，不是产品规格 §3.3 的全量枚举（`LOC-016` 规格 §4 已确认该口径；定稿 §5 R-6 同调）。
- 候选值只来自当前节点自己的 `output.schema`。`docs/design/outcome-presets.json` 在本票中**不作为任何默认值来源**——它三条 preset 的路径与正式模板不符（定稿 R-2），纠偏完成前接入会给用户错默认值。
- 内置模板的结构性内容只读；本票全部编辑能力只对自定义工作流开放。
- 载荷闸门：`packages/dsh-visual-workflow/scripts/build-bundle.mjs:276` 限定 `host + client ≤ 284 KiB`（290816 B），而定稿 §5 记录现值已达 **289230 B，余量约 1.6 KB**。本票任何新增都必须随卡附瘦身评估，且默认**不得**上调闸门。

## 10. 用户操作路径

1. 编辑器新建/打开一个自定义工作流 → 选中收口节点（该节点需有结构边指向 `$end`）。
2. 配置栏停在「结果与去向」段 → 在「完成映射」区选字段路径（默认建议 schema 中已声明的 string 字段）→ 界面显示该字段在 schema 里的候选取值。
3. 保存 → 生成与校验管道按内核规则通过；若节点没有指向 `$end` 的结构边，界面在保存前就说明原因。
4. 运行该工作流至收口 → 运行详情显示完成类型，与内置模板表现一致。
5. 另一条路径：在高级 JSON 里手写 `outcomePath: "$.result.decision"` → 回到「结果与去向」段，路径完整回显 → 增删取值 → 保存 → JSON 中该路径逐字未变，只取值集合变化。

## 11. 异常和边界场景

- 所选完成类型字段不在 schema 中 / 不是 string / 节点无指向 `$end` 的结构边 → 界面按内核同口径提示，保存不产生半成品蓝图。
- fanout 节点 → 完成映射与结果路由两个区都不提供编辑入口（不是报错后才告知）。
- 已有手写多层 `completionPath`（如内置模板形态）→ 回显完整路径；改取值不得降层。
- 从单层改多层、从多层改单层 → 都是显式编辑路径的动作，需同步维护 schema（旧属性清理，不留孤儿字段）。
- schema 无候选值（只 `type: string` 无 enum）→ 界面不得编造候选，如实显示「未穷举，保存会被校验拒绝」并指向可穷举的写法。
- 用户把 `completionPath` 与 `outcomePath` 指到同一字段 → 按内核现状处理并在界面标注冲突，不静默二选一。
- 内置模板节点 → 两个区只读展示当前声明，不可编辑。

## 16. UAT 场景

### UAT-01 自建工作流完成类型不再为空

- 验收目的：证明用户不用手写 JSON 也能得到和内置模板一致的完成类型呈现。
- 前置条件：
  1. 按仓库双轨规则使用开发 DSH（固定 9527）并登记本任务为激活任务；或产品 DSH 已完成正式安装；
  2. 已有一个自定义工作流：至少 目标确认 → 执行 → 收口，收口节点有结构边指向 `$end`，收口 schema 含 string 字段 `completion_type`。
- 操作步骤：
  1. 打开收口节点 → 「结果与去向」段 → 声明完成映射字段 `completion_type`；
  2. 保存；
  3. 用该工作流发起一次运行并跑到收口完成；
  4. 打开运行详情查看完成类型。
- 预期结果：
  1. 保存无校验错误；打开高级 JSON 可见 `output.completionPath` 已写入；
  2. 运行详情显示完成类型值，与收口节点结构化结果一致；
  3. 与同结构内置模板（诊断）的运行相比，完成类型呈现位置与措辞一致。
- 建议人工关注：完成类型为空时是否还有其它原因（节点未指向 `$end`）被如实告知。

### UAT-02 多层路径不被面板吃掉

- 验收目的：消除已确认的静默覆盖。
- 操作步骤：
  1. 在高级 JSON 把某节点写成 `output.outcomePath = "$.result.decision"`，并在 schema 声明 `result.decision` 为可穷举 string；
  2. 回到「结果与去向」段，确认路径回显为多层；
  3. 增删一个取值、补一条边；
  4. 重新打开高级 JSON 核对。
- 预期结果：
  1. 第 2 步面板显示完整 `result.decision`，不再呈现为「未配置」；
  2. 第 4 步 `outcomePath` 逐字未变，schema 中旧位置无孤儿属性残留；
  3. 校验与生成结果一致，`npm run validate` 通过。
- 建议人工关注：从多层改单层这一显式动作是否有清楚确认，不误触。

### UAT-03 规则前置提示同口径

- 操作步骤：分别制造四种非法态——① 字段不在 schema；② 叶子非 string；③ 节点无指向 `$end` 的结构边；④ fanout 节点。逐一尝试保存。
- 预期结果：四种都在界面得到与内核一致的原因说明；第 ④ 种不提供入口；不出现界面放行而内核拒绝（或反之）的分歧。

### UAT-04 内置模板只读不受影响

- 操作步骤：打开任一内置模板的收口节点。
- 预期结果：两个区均只读展示当前声明，无编辑控件；结构锁定提示不变。

## 17. 风险

- **载荷余量几乎为零（高）**：闸门 290816 B，集成收口实测现值 289230 B，余量约 1.6 KB（`docs/tasks/closeout-20260919-integration-round.md:30`、`:36`）；本票要新增一个配置区与多层路径回显，按体量必然超限。而且 `CHORE-104` 的 −14028 B 瘦身**尚未正式并入 main**（分支保留待整合，同一收口记录 `:21`）。处置：开工前先跑一次构建实测当前值，超限即回报为独立阻塞项交 `CHORE-104` 处理，**不得**自行放宽 `build-bundle.mjs:276` 的阈值，也不得把瘦身改动悄悄并入本票范围。本票很可能需要串行两轮（先瘦身腾空间，再加能力）。
- **与定稿 S-4 / `LOC-016` 抢同一文件（中）**：三者都改 `client.js`。缓解：本票范围严格限制在「结果与去向」段与其写回函数，不碰看板与详情；`client.js` 是 5600+ 行单文件，跨卡并行时按仓库规则用隔离工作区串行。
- **界面与内核分叉（中）**：若前端自行「友好化」规则（例如放宽叶子必须 string），会产生界面放行、保存即失败的假通过。以 §9 同源表和 UAT-03 为闸门。
- **误当成发布门槛（低）**：本票不在 `LOC-018` 的 v0.1 发布清单内，收口时不得反向写成门槛。

## 18. 已知限制

- 完成映射字段与业务结果字段指向同一 schema 位置时，本票只做「标注冲突」，不做自动分离或改写。
- 多层路径的数组下标、通配等 JSONPath 扩展语法不在范围内（内核正则 `validate-core.cjs:123` 本身也不接受）。
- 完成类型的业务语义仍然完全由收口节点 schema 决定；本票不引入完成类型字典或跨工作流的统一枚举，也不接 `outcome-presets.json`。
- 运行时「完成类型为空」的既有历史 Run 不做回填。
