## 决策 1 · 主题 token 的权威来源

**必须决定什么**：编辑器、运行页、角色页要共用一套语义色。新造一套 token、沿用 DSH alias、还是以原型的设计文档为准？

| 方案 | 成本 | 收益 | 风险 |
|---|---|---|---|
| **A** 以 `DESIGN.md` 的 A 编排台基础色与排版基线为唯一权威，映射为语义 token | 定义阶段一次对齐 | 与 FEAT-84 / FEAT-85 的契约统一；并行施工时不会各造一套 | 中：`DESIGN.md` 是原型文档，正式实现仍需施工方映射为 CSS 变量 |
| B 完全沿用现有 DSH alias，不新增 token | 最低 | 不动宿主 | 中高：现有 alias 缺焦点、遮罩等成对语义；缺失处仍会退化成硬编码 |
| C 新造一套独立 token | 中 | 命名最自由 | 高：与另外两个切片和宿主三套并存，收口必然返工 |

**裁定：A**。依据 —— handoff 明确要求「沿用 A 编排台的雾蓝语义系统」「不重新选择一套与 A 编排台冲突的美术方向」。缺失项按 §7 要求新增时**必须同时提供浅 / 深值与对比度证据**，不得在单一主题硬编码黑 / 白。

## 决策 2 · 内置 / 自定义来源如何判定

**必须决定什么**：badge 的来源判定依据。

| 方案 | 成本 | 收益 | 风险 |
|---|---|---|---|
| **A** 按 `builtin` 布尔字段判定 | 零 | 与业务语义一致，误判为零 | 低 |
| B 通过角色名 / 命名约定推断 | 零 | 无需字段 | 高：角色可复制改名，推断必然误判 |

**裁定：A**。依据 —— handoff §6「如果内置 / 自定义 badge 缺字段，按 `builtin` 布尔语义映射；不要通过角色名猜来源」。字段缺失时按「缺字段」处理并如实交接，不改用推断。

## 决策 3 · 无 summary 时长摘要如何处理

**必须决定什么**：真实角色没有 summary 字段，但职责极长。是回写 summary 到存储、在显示层生成、还是不显示摘要？

| 方案 | 成本 | 收益 | 风险 |
|---|---|---|---|
| **A** 显示层生成两行摘要，不写回 | 低 | 不触碰角色数据；列表可控 | 低 |
| B 生成后回写角色存储 | 中 | 后续读取更快 | **高**：改写用户角色原文，属越权数据变更 |
| C 不显示摘要，只显示名称 | 零 | 无风险 | 中：用户仍需打开详情才知道角色用途，正是当前痛点 |

**裁定：A**。依据 —— handoff §6「客户端可从 content 生成显示摘要，但不能写回或覆盖角色原文」。摘要必须支持中文与无空格连续长串的断词 / 换行。

## 决策 4 · 窄屏拥挤如何解决

**必须决定什么**：390×844 下信息放不下时，缩字号、隐藏内容、还是折行 + 独立滚动？

| 方案 | 成本 | 收益 | 风险 |
|---|---|---|---|
| **A** 折行 + 独立滚动 + 保留固定操作；弹层安全边距 | 中 | 可读性优先；与 DESIGN.md「避免靠缩小文字塞进更多信息」一致 | 低（需要更多纵向滚动） |
| B 缩小正文字号 | 零 | 视觉信息密度高 | 高：直接违反 handoff §4 禁止项与 WCAG 目标 |
| C 隐藏次要文字 / 只留图标 | 低 | 省空间 | 高：无障碍与可理解性双降；状态不能只靠颜色 / 图标 |

**裁定：A**。依据 —— handoff §4「不以降低正文字号、隐藏文字或降低对比度来解决窄屏拥挤」。
