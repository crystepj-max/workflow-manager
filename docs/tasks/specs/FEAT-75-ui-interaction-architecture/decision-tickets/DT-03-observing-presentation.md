## 1. 必须决定什么

**呈现形态其实已经定了，缺的是"这个标签由谁产生"。** 目标规格 §5 已明确写下：

> OBSERVING 不是 Lifecycle。缺陷可 `COMPLETED` 后显示"已完成 · 观察中"；复发创建新缺陷 Run，不重新打开旧 Run。
> —— `docs/design/workflow-manager-v0.1-final-product-spec.md:119-121`（原则 §3.2 `workflow-design-principles.md:226` 重申"`OBSERVING` 不是 Lifecycle 值"）

所以本票不问"要不要做成标签"（要，且规格已定），只问：**一个已完成的 Run，凭什么被标成"观察中"？**

## 2. 为什么必须现在决定

- 全仓实测：`OBSERVING` 只出现在文档，`templates/`、`scripts/`、`specs/`、`packages/` **命中 0**；看板 Completion 筛选是按实际生产者动态生成的（`client.js:3602-3610`）。这意味着现在若照 #75 §10 字面验收，会出现**永不命中的空档**——同 LOC-016 附带发现 C4（诊断模板 `completion` 恒 null）是同一种坑。
- 这条不是纯 UI 缺口：**没有生产者就没有可呈现的事实**。若在 UI 侧硬造，等于把"观察中"变成界面自说自话，违反"UI 不改写 Runtime 语义"的分层铁律。
- 它决定 S-5 是否存在、以及是否要动契约（跨模板/校验/Skill 全链），是本卡三票里唯一牵动契约面的一张。

## 3. 候选方案

**方案 A · v0.1 不呈现，显式移出范围（推荐）**
把「Observing 呈现」从 #75 §10 的 v0.1 完成标准里显式摘出，标注"无生产者，属目标规格未落地项"，规格原文保留不动。
- 成本：零（本卡文档层面一句话，S-5 取消）。
- 收益：验收面与现实一致，不交付空档；不碰契约、不占载荷；把决策推迟到"缺陷观察期"真有业务流程承接时。
- 风险：读规格的人可能以为已上线（需在架构文档 §5 台账里写明，本文已写）。

**方案 B · 人工标注（不碰契约）**
在已完成 Run 上给用户一个"标记观察中 / 取消观察"的只读标签位，标注动作由人做，复发时按规格新建 Run 并在描述里关联旧 Run。
- 成本：中。需要一个新的可写维度（Run 级人工标签）+ 一个写入口——而**看板当前没有任何续跑/写入口的执行通道**（同一技术前提见 DT-01 方案 C 与 LOC-016 DT-01 §2 取证），FEAT-208 正在解决决策卡的这半，但标签通道不在其范围。
- 收益：完全符合规格"不是 Lifecycle、作为完成后事项/标签呈现"的原意；不改 Runtime 语义；用户拿到真实的观察诉求。
- 风险：又是一次"UI 要写状态"的宿主能力扩张；与 FEAT-208 抢同一区域文件；标签若不成体系（无查询、无统计）价值有限。

**方案 C · 把它做成 Completion Type 的一个正式枚举**
补生产者：模板收口节点可产出 `COMPLETED_OBSERVING`，一路穿到校验（`scripts/validate-core.cjs`）、投影、看板筛选。
- 成本：高。跨模板 + 契约 + 校验 + UI 四段，且载荷预算贴线（余量约 1.6KB）。
- 收益：观察期进入正式结果模型，可筛选可统计。
- 风险：🔴 **与规格和原则直接冲突**——两处权威都写明 `OBSERVING` 不是 Lifecycle；把它塞进 Completion Type 虽名义不同，实为把同一概念重新变成一个结果枚举值，日后难拆。不推荐，列出只为留痕。

## 4. 关闭判据

产品经理择一；选 A 时须确认"规格 §5 的 OBSERVING 段保留、但 v0.1 不验收"这一表述；选 B 时须一并确认标签是否需要可查询/可统计（决定范围大小），并接受它依赖一条新的宿主写入口。

## 5. 产物

- 结论回写架构文档 §5 R-6 与本卡 §功能切片 S-5；
- 选 A：S-5 取消，#75 §10 的对应完成标准标注"裁定为 v0.1 不做"；
- 选 B：S-5 施工卡基线 + 一张宿主写入口的探路记录（可与 DT-01 §4 探路合并做）。
