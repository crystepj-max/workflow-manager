## 3. 候选方案

**方案 A · 维持"保留推进"，CHORE-113 收窄**
#75 保持 open 作为 UI 伞票；`CHORE-113` 的关票条款删除，只保留其三件实事（stale 指向修正、LOC-036 取代记录、规格口径回写）。
- 成本：低——改动是一份卡的范围描述。
- 收益：与本轮指令一致；preset 等规划中需求有明确承接位。
- 风险：CHORE-113 指出的"伞票持续误导"问题**没有解决**，后续会话仍可能拿 #75 旧正文否定已上线能力。

**方案 B · 采纳 CHORE-113，#75 关票**
本卡（FEAT-75）与本文档并入其计划的对账文档，#75 在获得授权后关闭。
- 成本：中——要合并两份对账表并迁移权威落点；本轮已落盘的文档需重命名或降级为附录。
- 收益：单一对账权威，伞票不再悬空。
- 风险：🔴 **与产品经理本轮明确给的前提相反**；且 `outcome-presets.json` 选择器在 CHORE-113 的 14 项判定里**没有任何一张卡认领**（其第 5 项把 Outcome Preset 与多层路径一起塞给 FEAT-114，而 FEAT-114 自己声明"不新增 Preset 库"）——关票等于把用户点名"仍在规划阶段"的 preset 需求丢在地上。

**方案 C · 合并：#75 保留 open，但收窄成"三件未裁事项"，两份对账合一（推荐）**
- #75 不关，但正文的 14 项逐条标注归属（用 CHORE-113 的对账内容 + 本文 §5 的 R-1…R-12 合并成一张表，权威落点唯一 = 本文档）；
- `CHORE-113` 保留，范围收窄为"stale 指向修正 + LOC-036 取代记录 + 规格口径回写 + 在 #75 上回写归属标注"，**不再包含关票**；
- `FEAT-114` / `FEAT-115` 保留为已拆出的施工卡；本卡派工面收缩为 **S-2（preset 纠偏 + 选择器）、S-4（看板字段补齐）、S-1/S-5（挂 DT-01/DT-03）**，不再主张 S-3；
- Timeline 与 Observing 的"已实现/未实现"分歧按 §4 单独裁。
- 成本：中——需要做一次对账表合并（约半天，纯文档），并同两侧会话的 registry 描述。
- 收益：既守住用户"保留推进 + preset 仍在规划"的判断，又消掉 CHORE-113 指出的"伞票误导"根因；唯一权威、无重复施工面。
