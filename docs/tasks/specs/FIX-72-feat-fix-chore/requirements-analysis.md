## 1. 问题的本质

编号迁移（d34f618，2026-09-16 上午落地：CNB 远端发号 FEAT/FIX/CHORE-<n> + 定义入库 `docs/tasks/specs/`）**只改了「账本」，没改「门口的尺子」**——工作区命名核心与闸门的判定规则仍只认旧世界（LOC/CWF），导致每一个用新号开工的任务都会撞上工作区闸门的假红灯；同时闸门未适配「CNB 合并」这一新收口形态，历史账目（归档、分支保留标记）与现实脱节。

## 2. 实测证据（2026-09-16 13:45，main == cnb/main @ 98dad77，主干干净）

`node scripts/validate-workspace.mjs` → ❌ 4 项失败 + 2 项警告：

| 检查项 | 失败内容 | 根因 |
|---|---|---|
| D-3 | `fix-65-compile-output-size` 工作区（分支同名，FIX-65 的活跃现场，属主另一会话，1 个诊断提交） | 分支命名不走 `dev-<run-id>`；**无任何文档定义新号任务的工作区命名形态** |
| D-5 | `.agent-runs/chore-36-r1` ← 非 TASK_ID/RUN_ID | `workspace-convention-core.cjs` 的 `TASK_ID_RE=/^(?:LOC\|CWF)-\d+$/`、`RUN_ID_RE=/^(?:loc\|cwf)-\d+(?:-s\d+)?-r\d+$/` 不认新前缀 |
| D-8 | 10 个已合并任务无归档目录：LOC-024..027、029..033、FIX-69 | 全部经 **CNB 合并请求**合入，未走本地收口流程；`cnb/main` 上同样无归档（`git ls-tree cnb/main docs/tasks/archive/` 命中 0）→ 本地与远端都不可考 |
| D-8 ⚠️ | `docs/tasks/specs/` 仍存在（决策五：归档位置统一到 archive/） | **决策五已过时**：2026-09-16 新规把 `docs/tasks/specs/` 复位为「定义入库家」，与决策五「删除 specs/」直接冲突 |

**关键层位事实**：命名规则存在**三层不一致**——
1. 生成器 `cwf-run-init`：`assertRunIdSafe` 接受任意净化小写串（`chore-36-r1` 能建），分支名 = `dev-<run_id>`（未随迁移改动）；
2. 判定器 `workspace-convention-core.cjs`：只认 `LOC|CWF`（未随迁移改动）；
3. 实际现场：FIX-65 属主自创了第三种形态 `fix-65-compile-output-size`（无 dev- 前缀、带 slug）。

→ 即：**新号任务的「工作区/分支/Run 目录」命名形态目前没有权威定义**，这是本任务必须先钉死的产品口径。

## 3. 影响面

- **阻断性**：每个用 FEAT/FIX/CHORE 新号开工的任务，其 run 目录都会让 D-5 失败 → `npm run validate` 红 → 收口被阻（CHORE-36 已因此挂起）。FIX-65 自身收口也会被 D-3 拦。
- **历史账目**：10 个已合并任务在本地与远端均不可考（无归档），违反「归档三件套」契约的本意。
- **波及文件**：`scripts/workspace-convention-core.cjs`、`scripts/validate-workspace.mjs`（D-3/D-5/D-8 警告/D-10 文案）、登记册数据（branch_retained 回填）、`docs/design/workspace-directory-convention-instance-workflow-manager.md`（决策五）、可能的约定文档（新命名形态的落笔处）。

## 5. 决策卡（3 张，全部影响产品口径，必须人工裁定）

### 决策卡 1 · 新号任务的命名基准（D-3/D-5 的判定依据）

**A（推荐）· 单轨延伸**：run_id = `<type小写>-<n>[-s<k>]-r<n>`（如 `fix-65-r1`、`chore-36-r1`），分支 = `dev-<run_id>`，工作区目录名 = 分支名。`TASK_ID_RE` 扩为 `(?:LOC|CWF|FEAT|FIX|CHORE)-\d+`，`RUN_ID_RE` 扩为 `(?:loc|cwf|feat|fix|chore)-\d+(?:-s\d+)?-r\d+`。生成器不动（`dev-<run_id>` 派生已兼容）。FIX-65 现场由其属主重建为 `dev-fix-65-r1`（1 个提交，成本极低）。
- 成本：改 1 个核心文件 + 既有测试断言；协调 FIX-65 属主重建现场。
- 收益：命名单轨、单射、与生成器零冲突；`dev-` 前缀继续承担「治理区工作区」识别职责。
- 风险：低。

**B · 双轨承认**：额外承认 `<type>-<n>-<slug>`（如 `fix-65-compile-output-size`）为合法工作区形态。
- 成本：regex 两套并存 + D-3 需区分两种派生。
- 风险：中——双轨长期并存会让「工作区名 → run 目录 → 登记册」的映射出现歧义，正是本任务要消灭的那类漂移。

**C · 只放行 Run 目录**：D-5 认新前缀，D-3 维持 `dev-` 强制（fix-65 现场仍红，等属主自行处置）。
- 成本：最小。风险：闸门对 FIX-65 的在制期持续报红，验收标准「交付节奏全绿」不可达。

### 决策卡 2 · 10 个 CNB 合并任务的归档缺口

**A · 本地全量回填**：从 CNB issue 正文 + 合并提交 + 登记册重建每个任务的归档三件套（10 任务 × 3 件，脚本半自动 + 逐个核对）。
- 成本：高（且 CNB issue 上未必留有规格终版，部分内容只能写「以 CNB#n 为源」的指针）。
- 收益：D-8 按原语义真实闭环。

**B · 修改 D-8 语义认「远程收口」**：登记册含 `remote` + `merge.commit` 即视为已归档（在远端）。需新决策记录（改「归档三件套」契约）。
- 成本：最低。风险：这 10 个任务在本地**永久不可考**，契约被掏空。

**C（推荐）· 本地轻量归档 + 远程指针**：本地补建归档目录，含三件中的「证据摘要」（记录 merge commit、CNB#n 链接、状态）+ 一份指向 CNB 的任务卡存根；规格正文以 CNB 侧为源不复制。D-8 增加对「轻量归档」的认可（存根形态入契约，不改三件套对**本地收口任务**的要求）。
- 成本：中（一次脚本批量 + 抽查）。
- 收益：本地可考（有指针可循）、契约语义清晰分层（本地收口=全套；远程收口=存根+指针）。
- 风险：低——需在约定文档里写明两种收口形态。

### 决策卡 3 · 决策五与 `docs/tasks/specs/` 的口径冲突

**A（推荐）· 决策五范围收窄 + 校验器警告条件更新**：实例文档决策五标注「2026-09-16 起定义入库使 `docs/tasks/specs/` 复位为定义家；决策五收窄为『归档位置统一到 docs/tasks/archive/』」（不改写原决策，只追加范围说明，符合 R-7）；D-8 的 specs/ 警告改为仅当 `docs/tasks/archive/` 出现同名漂移时告警。
- 成本：文档 1 处 + 校验器 1 处。
- 收益：警告不再永久误报。
- 风险：低。

**B · 维持决策五原文，把定义入库迁到别的目录**（如 `docs/tasks/definitions/`）。
- 成本：迁 24 个目录 + 改门禁脚本 + 改所有既有引用。风险：新规刚落地就再迁一次，制造第三次漂移。不推荐。
