## 1. 需求背景

交付链的验收清单（规格 §16 UAT 场景 + UAT 验收卡）隐含假设「所有验收项都能在人工裁决前观测」。但有一类验收项，结果只有在**收口合并之后**才可能存在（例：主检出侧发布闸门全绿、本任务工作区已自动删除且分支保留）。

2026-09-15 LOC-023 的人工验收，交付操作者按清单字面执行，第 2、3 步必然失败，得到一个「看起来像缺陷、实际只是时机不对」的结论，差点触发一轮无意义返工。

同一缺口在归档的 LOC-020 已出现过一次（§15 与 UAT-03「收口回收与残留如实上报」，前置条件写作「一个已完成验收、准备收口的任务」），当时靠措辞绕过。

## 2. 用户问题

**验收清单没写清「这一条什么时候才能跑」。** 交付操作者照单执行 → 遇到依赖合并后状态的条目必然看到失败 → 由此可能做出错误的验收裁定。

一句话：**不是被测的东西坏了，而是清单没说清什么时候看；清单可信度因此受损。**

## 3. 目标

验收清单成为**照着执行不会产生假红灯**的清单：

1. 每条验收项声明「执行时机」：**裁决前可观测** 或 **收口后观测**；
2. 收口后项与裁决前项**分区呈现**，裁决依据只取裁决前项；
3. 收口后项**必须被实际执行并回填结果**，不得静默跳过；
4. 定义阶段的检查清单能拦住「时机未声明」的验收项；
5. 该规则在模板、交付文档、契约、执行手册、机械检查之间**只有一份口径**。

## 4. 非目标

- 不改人工验收严格三态（通过 / 退回 / 有条件通过）与其语义；
- 不改自动返工上限 3；
- 不改 `handoff.schema.json` 的记录类型与字段，不新增证据记录类型；
- 不改 M2 主链状态机（不新增 Run 阶段或状态）；
- 不做「按自由文本逐条解析验收项」的校验器；
- 不追溯回改历史卡与历史规格（含已归档的 LOC-020 / LOC-023）。

## 9. 业务规则

| 编号 | 规则 |
|---|---|
| R-1 | 每条验收项（规格 §16 与 UAT 卡）必须声明**执行时机**，取值恰好一个：**裁决前可观测** / **收口后观测** |
| R-2 | 「收口后观测」项集中在**独立分区**「收口后复核」，并显式标注**不是**人工裁决的依据；人工裁决依据只取「裁决前可观测」项 |
| R-3 | 收口后项必须**实际执行并回填**（至少含：执行时间、命令、实际结果要点、结论）；不得留空、不得静默跳过 |
| R-4 | 收口后项复核**失败不静默**：结果如实写入 UAT 卡回填区与收口摘要；若判定为真缺陷 → 另立任务（不在本轮静默修） |
| R-5 | 前置条件必须自洽：不得引用裁决之后才存在的状态（例：「主检出已包含本修复」）；确实依赖时该项必须标为「收口后观测」 |
| R-6 | Definition Check §9.5 增补两条可判定检查项：① 每条验收项均已声明执行时机 ② 收口后项已写明执行者与结果回填位置。未通过 → 不得进入「待确认」 |
| R-7 | 若某收口后项在收口后仍不可观测（如依赖托管恢复补 PR），必须写明原因与后续触发条件，并列入「已知限制」——**不得写成能跑的样子** |
| R-8 | 一张卡必须至少有一项「裁决前可观测」项作为裁决依据；若全部验收项都无法在裁决前观测，视为需求定义不完整 → 退回定义阶段，不得进入等待验收 |
| R-9 | 规则只有一份口径：模板、交付文档、契约、执行手册、机械检查之间不得出现互相否定的表述（同类漂移是本任务的直接病因） |

## 10. 用户操作路径

**路径 A · 定义阶段（需求分析）**

1. 写规格 §16 时，逐条给 UAT 项标「执行时机」；
2. 属「收口后观测」的，写明执行者（默认：执行体）与结果回填位置；
3. 跑 Definition Check，§9.5 新增两条必须通过；
4. 期望：不通过则回定义阶段，不得呈递基线确认。

**路径 B · 交付阶段（生成卡 → 裁决 → 收口）**

1. 自动阶段完成后按新模板生成 UAT 卡（每条含时机、收口后项独立分区）；
2. 交付操作者**只对「裁决前可观测」项**执行与裁决；
3. 裁决通过（或有条件通过）→ 收口合并；
4. 执行体在收口后**立即**执行「收口后复核」区各项，把结果回填卡片与收口摘要；
5. 期望：裁决阶段不会因收口后项出现假红灯；收口后复核区有实际结果。

**路径 C · 复核失败**

1. 如实记录失败（命令、输出要点、结论）；
2. 若为真缺陷 → 另立任务，本任务不静默修；
3. 若为「环境/时机不成立」→ 写明原因与后续触发条件，列入已知限制（R-7）。

## 11. 异常和边界场景

| 场景 | 期望行为 |
|---|---|
| 收口后项在收口后仍不可观测（如依赖托管恢复补 PR） | 写明原因与后续触发条件，列入已知限制；不得写成可执行 |
| 收口后项复核失败且判定为真缺陷 | 如实记录 + 另立任务；不阻塞本任务收口流程的完成性记录 |
| 收口后项复核失败但属环境不具备 | 写明原因与再次触发条件，不谎报通过 |
| 前置条件引用裁决后才存在的状态 | R-5：必须改标为「收口后观测」；定义检查按 R-6 拦截 |
| 一张卡的全部验收项都是收口后项 | R-8：不得进入等待验收，退回定义阶段 |
| 模板缺「执行时机」字段 | 机械断言失败（指名「执行时机」），M2 机械验收不通过 |
| 机械断言只测字段存在性、语义仍写错 | 已知限制；由定义检查的人工项与 UAT-02 的演示兜底 |
| 历史卡 / 历史规格（含已归档） | **不追溯回改**；新规则只对生效后新建的卡与规格生效 |
| 运行态 skill 池副本仍为旧版 | 不在本任务范围；收口后在遗留事项中提示需按既有流程同步 |

## 16. UAT 场景

### UAT-01 「时机」在清单上一眼可辨

- **执行时机**：裁决前可观测
- 验收目的：确认新模板让执行者不必猜「这条现在能不能跑」。
- 前置条件：
  1. 已按本任务改动落盘模板。
- 操作步骤：
  1. 用新模板写一张最小卡：一条「裁决前可观测」项 + 一条「收口后观测」项；
  2. 观察两处的字段与分区归属。
- 预期结果：
  1. 两条都能看到明确的「执行时机」；
  2. 「收口后观测」项落在独立分区「收口后复核」，并标注不是裁决依据；
  3. 裁决清单里不会出现收口后项。
- 建议人工关注：一眼能否分辨「现在该跑哪几条」。

### UAT-02 按旧写法必红的条目，在新写法下不再误导裁决

- **执行时机**：裁决前可观测
- 验收目的：确认本任务的直接病因被消除（用真实反例验证，不用假想例子）。
- 前置条件：
  1. LOC-023 归档规格与验收卡可读（`docs/tasks/archive/LOC-023/`）。
- 操作步骤：
  1. 取 LOC-023 规格 UAT-01 原文（第 2、3 步依赖合并后状态）；
  2. 用新模板改写为一条「裁决前可观测」项 + 一条「收口后观测」项；
  3. 检查改写后的裁决清单是否只含前者。
- 预期结果：
  1. 依赖合并后状态的那部分是「收口后观测」项，不再出现在裁决清单里；
  2. 每条都写明了执行者与回填位置；
  3. 按新写法，裁决阶段不会出现「修好了却报红」的结论。
- 建议人工关注：改写后的措辞是否让非技术读者也能看懂「为什么它现在不该跑」。

### UAT-03 机械断言真的会咬

- **执行时机**：裁决前可观测
- 验收目的：确认「模板再漏字段」会被机器挡下，而不是靠自觉。
- 前置条件：
  1. 已可运行 `scripts/ai-task-deliver-m2-check.mjs`。
- 操作步骤：
  1. 正常跑一次检查，记录退出码；
  2. 在临时副本目录中删掉模板里的「执行时机」字段；
  3. 对临时副本再跑一次检查。
- 预期结果：
  1. 第 1 步退出码 0；
  2. 第 3 步退出码非 0，且错误信息包含「执行时机」；
  3. 原始仓库文件未被修改。
- 建议人工关注：失败信息是否足以让人立刻知道要补什么。

### UAT-04 收口后复核被真实执行并回填

- **执行时机**：**收口后观测**（本条自身即受 R-1～R-3 约束）
- 执行者：执行体（AI）在收口合并后立即执行
- 结果回填位置：本任务 UAT 卡「收口后复核」区 + 收口摘要
