## 1. 需求背景

交付链的「验收清单」（规格 §16 UAT 场景 + UAT 验收卡）**隐含假设所有验收项都能在人工裁决前观测**。但存在一类验收项，其结果只有在**收口合并之后**才可能存在——例如「主检出侧发布闸门全绿」（合并前主检出跑的仍是修复前的代码）、「本任务工作区已自动删除、分支保留」。

2026-09-15 LOC-023 的人工验收实测，正是这一类项按字面执行导致的假红灯。

## 2. 用户问题（业务语言）

**验收清单没写清「这一条什么时候才能跑」。** 交付操作者照着清单逐条执行，遇到依赖合并后状态的条目必然看到失败，于是得到一个**看起来像缺陷、实际只是时机不对**的结论；由此可能做出错误的验收裁定（本轮差点按「验收退回」重做一整轮）。

一句话：**清单可信度受损——不是被测的东西坏了，而是清单没说清什么时候看。**

## 3. 目标

验收清单成为**可以照着执行而不会产生假红灯**的清单：

1. 每条验收项都声明「执行时机」：**裁决前可观测** 或 **收口后观测**；
2. 收口后项与裁决前项**分区呈现**，不得混在人工裁决所依据的清单里；
3. 收口后项的结果**必须被实际执行并回填**，不得静默跳过；
4. 定义阶段的检查清单（Definition Check）能拦住「时机未声明」的验收项。

## 4. 非目标

- 不改人工验收严格三态（通过 / 退回 / 有条件通过）；
- 不改自动返工上限（3）；
- 不改 `handoff.schema.json` 的记录类型与字段（本轮不新增证据记录类型）；
- 不改 M2 主链状态机（不新增 Run 阶段/状态）；
- 不引入按自由文本逐条解析验收项的校验器（脆弱、误判成本高）。

## 7. 必须人工决策的事项（决策卡）

### 决策卡 1 · 规则的强度与落点

**需要决策**：这条规则只写在模板与检查清单里（靠人遵守），还是同时加一条机器断言？

- **方案 A（推荐）模板 + 定义检查 + 一条最小机器断言**
  - 成本：改 5 处真源文档 + 1 处机械检查 + 1 处测试（同一会话可完成）
  - 收益：模板**不可能再漏**「执行时机」字段；断言只测模板存在性，不引入自由的文本解析
  - 风险：低（若将来字段改名，断言会失败——但那时本就该同步改检查）
- **方案 B 只改模板与定义检查（纯文字）**
  - 成本：最低
  - 收益：零破坏风险
  - 风险：**靠自觉**——本任务本身就是因为「模板漏了字段」才发生的，不加机器断言则有再次漂移的空间
- **方案 C 全机器化**：机器逐条校验每份卡/规格的每个验收项都有时机标注，未标注即拒绝
  - 成本：最高（卡与规格是自由文本，需约定可解析格式）
  - 风险：高——解析脆弱、误判多，收益不抵成本。不推荐

**推荐**：A。**推荐原因**：这条规则的价值在于「以后不再发生」，而只靠文字的历史记录显示它会漂移（副本已漂移一行即为证）；同时把机器介入限制在「字段存在性」这一稳定断言上，避免脆弱解析。

### 决策卡 2 · 「收口后观测」项的地位与失败处置

**需要决策**：这类项是**保留为正式验收内容**（只是换个分区与时机），还是一律降级为「已知限制/未覆盖项」？

- **方案 A（推荐）保留为正式验收内容，独立分区 + 必须回填 + 失败不静默**
  - 成本：模板加一个分区 + 定义检查加一条
  - 收益：最有价值的证据被制度化保留（本轮「合并后闸门全绿」正是最强证据）；失败时如实报告，若属真缺陷则另立任务
  - 风险：低
- **方案 B 一律降级为「已知限制/未覆盖项」**
  - 成本：最低
  - 风险：把「能验的事」改成「不验」，长期降低闸门可信度；且与本轮已发生的最有价值证据相矛盾
- **方案 C 写进清单但允许「裁决前不可观测」并存、不要求回填**
  - 成本：低
  - 风险：中——**这正是本轮 LOC-023 的现状**（写了但没说清何时跑），同一个坑会复现

**推荐**：A。**推荐原因**：验收清单的目的是「让机器闸门可信」，而不是「让清单好看」；把可验证项排除在外只会让闸门继续失真。

### 决策卡 3 · 收口后复核的执行主体与主链位置

**需要决策**：收口后复核由谁执行、算不算 M2 主链的一步？

- **方案 A（推荐）由执行体（AI）在收口后立即执行并回报，结果写入收口摘要 + 回填 UAT 卡；不改主链状态机**
  - 成本：改交付文档 §7 收口 + 卡模板回填区
  - 收益：闭环、有痕、不依赖人的记性；不牵动状态机
  - 风险：低
- **方案 B 由人工在收口后手工跑**
  - 成本：低（只写文字）
  - 风险：中——人容易忘，且结果没有落点
- **方案 C 把「收口后复核」升为 M2 主链的显式节点**
  - 成本：高（改产品可见主链，可能牵动状态机与证据记录类型）
  - 收益：制度最强
  - 风险：中高——目前只有一到两个真实案例，过早扩状态机不划算

**推荐**：A。**推荐原因**：机械动作（跑命令、看退出码）本就应该由执行体做，人工只应在结果异常时介入；等案例积累到足够多再考虑升为主链节点。
