## 1. 目标与判据

**目标**：`validate` 在 CI 上达到**稳定全绿**，从而具备被设为「必要状态检查」的资格。

**判据（三条同时成立才算收敛）**：

1. CI 引擎层与包测试失败数为 **0**；
2. 连续 **≥3 次**运行（含一次满载时段）无「偶发红」；
3. 本地与 CI 结论一致——不存在「本机绿 / CI 红」或反之的环境性差异。

## 2. 机制明细与修法方向

### M1 · git 提交身份缺失 ✅ 已修（对照基线）

- **现象**：`local-task-merge` 系列 7 项报 `Command failed: git commit -F /tmp/loc-merge-*.txt` + `Author identity unknown`。
- **根因**：产品代码执行 git 时不覆盖子进程 env（`scripts/local-task-merge.mjs:50`），身份只能来自运行环境；Ubuntu runner 不配身份，macOS 会自动推导。
- **处置**：FIX-254（PR #256）在 `validate` 工作流补 `git config --global user.name/user.email`。**CI 双臂对照：失败数 15 → 8。**

### M2 · 端口核验工具缺失（`dev-plugin` 2 项）— P1

- **现象**：`❌ 无法核验端口 19527 占用情况；已停止，避免误判。`
- **根因（定位到行）**：`scripts/dev-plugin.mjs` 的 `lsofBin = process.env.VWF_DEV_LSOF_BIN || (existsSync('/usr/sbin/lsof') ? '/usr/sbin/lsof' : 'lsof')`；`listeningProcesses()` 执行 `lsof -nP -iTCP -sTCP:LISTEN -Fpcn`；`inspect()` 在 spawn 失败或非 0 退出时返回 `null` → 端口占用返回 `null` → `resolvePortState()` 按**设计**主动失败（fail-closed，本身是正确的产品行为）。runner 上无 `lsof`，故必然触发。
- **修法方向（二选一，倾向 ②）**：
  - ① CI 侧装 `lsof`（`sudo apt-get install -y lsof`）：一行，但把「测试能否通过」继续绑在环境上。
  - ② **测试侧注入替身**：代码已支持 `VWF_DEV_LSOF_BIN` 环境变量覆盖，用例注入一个确定性的假探针，使测试不依赖宿主机工具。符合「测试应当自足」。
- **验收**：`dev-plugin.test.mjs` 在**无 `lsof`** 的环境下通过。

### M3 · 治理区扫描依赖真实工作区布局（`validate-workspace-context` 4 项）— P0

- **现象**：D-2/D-3/D-4/D-10 一条违规都没报出（`治理区违规仍应报出` 失败、`D-2 应报出目录名 ≠ 分支名` 失败、断言得到 `[]`）。
- **根因（已实证）**：`scripts/validate-workspace.mjs` 的 `EXEMPT_ABS_PREFIXES = ['/private/tmp/', '/tmp/']` 把 `/tmp` 全域划为**例外区**（只计警告不计失败）；而测试夹具用 `os.tmpdir()` 建临时仓库——macOS 的 `os.tmpdir()` 是 `/var/folders/…`（**不在**豁免前缀内，被判治理区，测试通过），Linux runner 的 `os.tmpdir()` 就是 `/tmp`（**落在**豁免前缀内，全体降级为例外区，测试失败）。
- **复现证据**：macOS 上设 `TMPDIR=/tmp` 后，该文件**恰好 4 项失败**，与 CI 输出逐项一致。
- **修法方向**：夹具不再落在豁免区——用显式的、非 `/tmp` 的临时根（例如仓库同级容器或 `TMPDIR` 之外的确定路径）；或让用例显式传入自己的豁免清单而非吃全局默认值。**不得**通过删豁免前缀来「修绿」，那会削弱真实防护。
- **验收**：`TMPDIR=/tmp` 下该文件全绿，且豁免区行为本身有独立用例覆盖。

### M4 · M4 机械验收脚本失败（1 项）— P1（待定位）

- **现象**：`scripts/ai-task-scheduled-m4.test.mjs:9` 断言 `scripts/ai-task-scheduled-m4-check.mjs` 退出码为 0，CI 上非 0，提示 `M4 检查失败：`（后续明细被输出裁剪）。
- **已排除**：本地默认环境、`TMPDIR=/tmp`、`HOME` 替换、`gh` 未登录（`GH_CONFIG_DIR` 指向空目录）、无 `gh`——以上模拟**均通过**。
- **下一步（须先取证再动手）**：在 CI 上单独运行该脚本并**保留完整 stdout/stderr**（该脚本把错误逐条 `console.error(' -', e)` 输出，完整输出即可直接定位是文档断言、触发脚本断言，还是报告内容断言失败）。
- **注意**：不得凭猜测改断言；先拿到原始输出。

### M5 · 告警条数断言被新增告警打破（1 项）— P0（回归）

- **现象**：`gh 不可达时降级 TMP 并告警（验收 2）` 报 `Expected values to be strictly equal`。
- **根因（已实证）**：该用例把 `console.error` 临时替换为收集器，并断言 `warnings.length === 1`（意在证明「降级只告警一次、无额外噪声」）。FIX-245 在 `allocate` 新增了「未识别到 agent 身份」告警，同一路径因此产生**第二条**告警。
- **证据**：含 FIX-245 的主干代码 + 移除宿主指纹 → 该文件 16 项中 **1 项红**；FIX-245 之前的提交 `7a8ae6a5` + 同样环境 → **16 项全绿**。故系 FIX-245 引入。
- **修法方向（倾向 ①）**：
  - ① 用例断言改为**针对降级告警本身**（过滤后计数），保留「恰好一条降级告警」的原意，同时不再被正交告警干扰；
  - ② 产品侧把身份告警**去重为每进程一次**（本身也是体验改进），但该做法依赖用例执行顺序，**不作为单独修法**。
- **验收**：有/无宿主指纹两种环境下该文件均全绿。

### M6 · 挂钟依赖（脆弱性，当前未红）— P2

- **代码证据**：
  - `scripts/test/ai-task-night-dispatch-m5.test.mjs:137` `assert.ok(elapsed < 20_000, …)`；
  - 同文件 `:67` `spawnSync(…, { timeout: 60_000 })`；`:130` `watchdogMinutes: 0.03`（约 1.8 秒）；
  - `packages/dsh-visual-workflow/tests/evaluation-baseline-runtime.test.mjs:48` `until(…, ms = 8000)`，5ms 轮询。
  三处均围绕**真实进程生成 + 轮询**设定硬阈值。
- **本地实测**：造 24 个 CPU 满载进程（load average 升至 20）后，M5 文件仍 6/6 通过（4.7s）→ **本地未复现假超时**，阈值在 10 核机器上尚有余量；但 CI runner 为 2 核，相对争用高一个量级，风险显著更大。
- **修法方向**：把「等待」改为**事件驱动或可注入时钟**（例如允许注入 poll 间隔与超时），断言改为「业务结果正确」而非「在 N 秒内完成」；至少把硬阈值改为可配置并给 CI 留足余量。
- **为何必须在设为必需检查前解决**：偶发假超时会让闸门变成**误报源**，比红灯更伤信任。

### M7 · 跑测试改写 51 个被跟踪基准产物 — P2

- **现象（已量化）**：跑一次引擎层测试即改写 `scripts/benchmark/loc-045/` 下 **51 个被 Git 跟踪的文件**，345 增 / 345 删。
- **改动性质**：不只是时间戳——`config/freeze-manifest.json` 的 `template_digests` / `script_digest` **也变了**，说明冻结夹具已与当前模板脱钩（模板自 2026-09-16 冻结后已被多次修改）；报告类文件的「生成时间」同步变化。
- **危害**：任何跑过测试的工作树都会凭空背上一批未提交改动，多会话并行时极易被误当成他人在途工作**清掉或误提交**。
- **修法方向（三选一，需产品决策）**：
  - ① 重新冻结并入库一次（使 digest 与当前模板对齐），同时让测试路径**只读校验、不重写**；
  - ② 把 loc-045 产物移出版本控制（`.gitignore`），保留一份冻结副本作基线；
  - ③ 生成物写到被忽略目录，仅提交「研究结论」类文档。
- **验收**：跑完整测试后 `git status` 在 `scripts/benchmark/` 下为**空**。

### M8 · 收口归档完整性（D-8 / D-9 / D-10）— ✅ **已修**（CHORE-286 / PR #292）｜ 2026-09-21 新增

- **发现方式**：`validate` 链是 `validate.mjs && validate-task-spec-sync.mjs && validate-workspace.mjs`。此前 ③ 段先失败即**短路**，`validate-workspace` 的 D-8/D-9/D-10 **从未被执行**；M4 收敛、引擎层首次全绿后才暴露。换言之它是**被 `&&` 长期掩盖**的一类，与 M1–M7 同属「闸门可信度」，此前未被盘点。
- **三类形态**：
  - **D-8 归档完整性**：每个「已合并」任务须有 `docs/tasks/archive/<ID>/`，内含任务卡 + `task-spec-V*.md` + `evidence-summary.json`；远程收口走「轻量归档」（任务卡存根 + 摘要携带 `archive_form: lightweight-remote`、`merge.commit`、`remote_ref`，缺任一凭据即失败）。
  - **D-9 超期证据残留**：`evidence_expires_at` 已过期而 `evidence_cleared_at` 未清。
  - **D-10 口径一致**：`branch_retained` 须为布尔值，且与 `refs/heads/<branch>` 事实一致；非布尔值者按 R-9 列为「不可核验」，不伪造字段值。
- **历史欠账（2026-09-21 CI 实测）**：D-8 约 30 条、D-9 约 48 条、D-10 约 60 条；主体为 `LOC-028`~`LOC-045`、`FEAT-84`~`FEAT-103`、`FIX-97`~`FIX-108`、`CHORE-104`、`CHORE-111`、`FEAT-237` 等早期任务。
- **本专项自身引入的部分已顺手补齐**：`CHORE-262` / `-264` / `-268` / `-273` / `-276` / `-279` 已随各自收口补齐归档三件套并校准 `branch_retained` 口径。
- **🔴 检查器的环境敏感性（2026-09-21 实测）**：D-10 核验的是**本地** `refs/heads/<branch>`，因此同一提交在本地与 CI 的结论可能**相反**——`branch_retained=false` 的任务在本地会因残留工作分支被判违规，在 CI（只检出单个 ref）则通过；反之 `branch_retained=true` 在 CI 必被判违规。同理 D-8 的「未收口工作区」也以本地 worktree 事实为准。子票 7 须一并裁定该检查的口径（改为核验远端引用，或显式声明环境差异），否则「本地绿 / CI 红」的误判会换个方向重演。
- **修法方向**：逐条补齐或按规则批量回填（仓内已有同类工具 `scripts/backfill-fix72-archives.mjs` 可参考/复用）；D-9 清理超期明细；D-10 逐条核对分支保留口径。
- **验收**：CI `validate-workspace` 的 D-8 / D-9 / D-10 三项全绿。
- ✅ **收敛结果（2026-09-21）**：基线实测 D-8 **33** / D-9 **12** / D-10 **22** 条（父票原估 D-8 ~30 / D-9 ~48 / D-10 ~60 为粗略值，以 CI 实测为准）。CHORE-286（PR #292）逐条收敛后，主干 CI `validate` **首次整体通过**：D-8 ✅（75 个已合并任务）、D-9 ✅（54 条）、D-10 ✅（67 条）。
- 🔴 **D-10 的口径已按实测更正**：原实现核验 `refs/heads`（本地引用），而 CI runner 只检出单 ref ⇒ **任何标「保留分支」的任务在 CI 上必然失败，该检查在 CI 上不可能通过**。22 条实测分流为「真数据错误 1 条 + 仅本地存在 20 条 + 本地远端均在 1 条」。经负责人两次裁定，最终采**口径 B（以远端共享真值）**：检查器核验 `refs/remotes/origin/<branch>`、CI 显式 fetch 全部分支、登记册 21 条按远端实测校正。
