## 9. 业务规则

1. 测试读取真实编译产物、宿主提交及恢复后的输入引用，断言消费方收到的字段/字节/版本。替身只能替换外部模型或环境，不在每个接口各造一份互不关联的理想结果。
2. 七个基线复现按原证据 ID 保留，再加缺文件、旧引用、错误类型至少三类负例；每个失败映射 WR/LOC、接口、固定输入与预期。已知未修缺陷在独立 known_gaps 报告明确失败，不 skip 后称产品绿色；用故意坏/修复控制夹具证明探针能红能绿。
3. 四固定样板：建设 Node CLI 从 package.json 输出 --version 且保留 --help；非 Git 优化含 10 条编号事实的文档，Unicode code point 长度减少至少20%且事实全保留；诊断 sum([2,3,5]) 从错误5修为10、空数组0、单项7；探索6份本地资料，两份支持A、两份支持B、一份共享来源、一份明确成本未知。开发首次创建夹具后冻结内容及摘要。优化样板将十条编号事实作为十条完整原句固定保存，优化时原句及编号必须逐字保留，只压缩外围说明；初始外围说明足够支持至少20%的缩减，不仅保留事实编号冒充事实保留。长度以完整 UTF-8 文本解码后的 Unicode code point 计，不按字节或 UTF-16 长度计。
4. 覆盖返工反馈、人工等待（注入明确拒绝/通过事件不能代替真人）、受阻恢复和探索部分失败。每模板至少一条生产到消费完整自动路径；真实安装 DSH 以同一夹具按运行说明执行并记录安装路径/版本、模型及 Run。
5. 报告按自动契约、真实安装 DSH、真实模型行为、人工验收四层分别 PASS/FAIL/BLOCKED/UNVERIFIED，未执行写原因；现有产品缺陷可以作为本任务发现结果，但相应产品用例保持 FAIL，不能表示发布已达标。
6. 本任务验收对象是可复跑并能定位真实缺陷的测试体系，要求四模板真实路径均有执行尝试与可复核结果。遇不可用服务可如实 BLOCKED 交接，缺真实执行证据不宣称完成全部验收；产品修复由对应任务承担。

输入输出和归属：消费模板编译器、runtime harness、host 和记录读取接口；输出固定 fixtures、契约断言、运行命令和分层结果 JSON/人读报告，release:verify 引用其机器层状态。既有七探针是输入证据，不是新产品行为实现。

## 11. 异常和边界场景

- **负例能被观察**：准备七历史探针与缺文件/旧引用/错误类型三类负例及修复控制夹具。 处理结果必须为：坏样例准确定位接口与 WR，控制样例转绿；已知缺陷没有被 skip 当 PASS。
- **四个样板完整链**：冻结四夹具摘要，准备真实编译脚本和 host 存储。 处理结果必须为：可追溯输入/产物/证明，覆盖返工、等待、恢复、部分失败，失败可定位具体边。
- **真实路径与证据分层**：按支持的开发/产品模式分别准备 DSH；不冒充已有发布授权。 处理结果必须为：安装路径、模型、Run 和结果可查；自动、实装、模型、人工分列，未执行层无 PASS。
- **异机复跑与发布入口**：复制仓库到另一个临时路径，按 README 准备依赖。 处理结果必须为：不依赖作者路径或私有状态；报告说明已知产品失败不被本任务接管修复。

共同恢复规则：证据不足写 BLOCKED/UNVERIFIED 并保留失败输入、恢复位置；同一原因重试不改变基线，不因无人值守降低验收。旧 Run 使用冻结快照；范围外变化另行记录，不静默迁移历史。
