## 1. 需求背景

产品规格 §2.3 要求：Invocation 与 Runtime 分离，Skill / Chat / 插件入口只能是 Invocation Adapter，最终进入同一个 Logical Run Runtime，不得形成第二套运行体系。§12 Phase C 以本卡（`#83`）作为该要求的落地任务。

当前 DSH 内已存在两条起跑路径：

1. 插件工具 `wf_run`——插件自己编译并起跑，完整接入 Logical Run Runtime（分段、任务归属、完成类型、人工决策续跑、暂停/指导/恢复）。
2. 会话按 runbook 拿编译脚本调用 **DSH 内置 `workflow` 工具**——脚本执行结果只回到会话，插件不在调用链上。

两条 runbook（`dsh/skill/SKILL.md`、生成器产出的模板 SKILL.md）目前都写的是第 2 条。

## 2. 用户问题

在 DSH 里由 Skill / Chat 触发一次模板运行后，看板上那条记录是「残缺」的：没有任务归属、只显示一段、完成类型为空，也不能从看板续跑或暂停——用户无法确认这次运行到底跑完了什么。

## 3. 目标

让 DSH 内 Skill / Chat 触发的工作流运行，与插件入口共享同一条完整运行记录：跨多段（人工决策/恢复）仍是一个 Logical Run，看板可见完整分段与摘要，人工决策可按 `decision_id + user_choice` 续跑，`DONE` 有明确的完成类型。

## 4. 非目标

- 不新建第二套 Runtime；不改 `wf_run` 既有语义。
- 不新增插件工具面（备选方案「结果回灌通道」不采纳，理由见 §12 决策 2）。
- 不为「内置 `workflow` 工具直起」的运行补全记录（保持如实提示的退化态）。
- 非 DSH 执行器接入（v0.4 边界）。

## 5. 修改前

DSH 内 Skill 触发的运行，按 runbook 走内置 `workflow` 工具；插件只能旁观引擎事件流，落一条退化摘要（`task_id=''`、单段、`completion=null`，`host.js:1207`）。

## 6. 修改后

DSH 内 Skill 触发的运行，按 runbook 首选调插件的 `wf_run`；插件是发起方，落完整 Logical Run（任务归属、分段、完成类型、人工决策现场），看板与暂停/指导/恢复均可用。内置 `workflow` 工具退居应急回退，使用时必须如实提示记录将退化。

## 7. 功能范围

1. **生成器 runbook 改造**：`scripts/generate.mjs` 的 `skillWrap`（模板产物 SKILL.md）执行步骤改为「首选 `wf_run`（`templateId` + `taskId` + `entry` + issue/requirement 字段）」，续跑步骤对应改为 `wf_run` + `decision_id`/`user_choice`（Human Decision）与 `entry` + `approved`（残留人工门禁）；编译脚本仅作为回退路径的参数来源保留。
2. **DSH 运行手册同口径改造**：`dsh/skill/SKILL.md` 第 3 步（现「调用 workflow 工具」）与第 5 步（人工门禁续跑）对齐为 `wf_run` 口径。
3. **回退规则写入两份 runbook**：`wf_run` 不可用（引擎/agents 未挂载）时才回退到内置 `workflow` 工具执行编译脚本，且必须在会话输出中显式提示「本次运行记录将退化为单段、无完成类型，且不可从看板续跑」。
4. **args 装配保留 `resource_kind`**：optimize 类模板需要该字段（LOC-009 契约，`host.js:2168`；由模板声明或运行参数传入），runbook 装配步骤需保留并说明。
5. **Current 侧口径修正**：`CONTEXT.md`（D5 执行路径段）、`dsh/README.md`（「wf_run 增强路径」节）、`packages/dsh-visual-workflow/README.md` 对应段落，改为「Skill 入口首选 `wf_run`；内置 `workflow` 工具为回退」，并修正「编辑器点『获取脚本』」这一当前界面已不存在的入口表述（`host.js:1534` 注明面板不再暴露该按钮，`client.js` 无 `vwf.script` 调用）。
6. **真实验证**：在 DSH 内由 Skill 触发一次模板运行，确认实际走 `wf_run`、记录完整（见 §15/§16）。

## 8. 不修改范围

- `wf_run` 与 Logical Run Runtime 的运行语义、数据契约、RPC 面（只消费）。
- 插件客户端 UI（看板详情视图 / 决策卡 / 工作区面板属 LOC-016）。
- 产品规格（Target 文档）正文：其中「当前真实路径仍是……」（`workflow-manager-v0.1-final-product-spec.md:240`）已与实现不符，**本卡不改**，仅在卡上记录该漂移，移交后续 Target 文档维护。
- 非 DSH 环境的技能适用性治理（仅在卡上记录已知事实，见 §18）。

## 9. 业务规则

- **正式入口唯一**：DSH 内 Skill / Chat / 插件触发的运行都必须经 `wf_run` 进入同一 Logical Run Runtime（规格 §2.3）。
- **回退不静默**：仅当 `wf_run` 不可用时才使用内置 `workflow` 工具，且必须如实提示记录退化，不得让用户误以为记录完整。
- **续跑参数单一来源**：Human Decision 续跑一律 `decision_id + user_choice`；残留人工门禁续跑一律 `entry + approved`；两者不得混用（`wf_run` 已有互斥校验，不得绕过）。
- **生成物不可手改**（NFR-1）：SKILL.md 改动必须来自 `scripts/generate.mjs`，改完跑 `npm run generate` 与 `npm run validate`。

## 10. 用户操作路径

1. 在 DSH 会话里说出模板触发词（如「用开发工作流 2.0 跑 issue #N」）→ 技能加载。
2. 会话按 runbook 装配 args，调用 `wf_run`（插件编译并起跑）。
3. 跑到人工门禁 / Human Decision 停住 → 会话呈报告与决策包；用户裁决后按 `decision_id + user_choice`（或残留门禁按 `entry + approved`）续跑**同一逻辑运行**。
4. 收口 `DONE` → 看板该运行显示完整分段、业务结果与完成类型；暂停 / 指导 / 恢复可用。

## 11. 异常和边界场景

| 场景 | 期望行为 |
|---|---|
| `wf_run` 不可用（engine / agents 未挂载，`host.js:2155`、`host.js:2241`） | 回退到内置 `workflow` 工具执行编译脚本，**并显式提示记录将退化**；不得静默降级 |
| 同一 `taskId` 已有进行中的运行 | `wf_run` 按既有互斥规则拒绝，并提示正确的续跑参数（不改既有行为） |
| 技能在非 DSH 环境被触发（缺 `workflow` 工具与插件） | runbook 开头即声明适用范围与自检：所需工具不存在时**停下说明**，不得进入装配步骤后卡死 |
| 会话未按 runbook 使用工具（自行选择内置工具） | 属模型行为风险：runbook 写明首选与判据；验收以真实运行为准（见 §17） |
| 生成物与安装态副本不一致 | 已知限制（§18）：安装态 skill 需重新安装才生效 |

## 15. 验收条件

- [ ] **真实验证**：DSH 内由 Skill 触发一次模板运行，会话实际调用 `wf_run`；运行记录 `task_id` 非空、`trigger=start`，看板显示为同一次运行（而非退化单段记录）
- [ ] Skill 发起的一次任务跨多段执行（人工决策 / 恢复）仍是一个 Logical Run，看板可见完整分段与摘要
- [ ] Skill 路径的人工决策可按 `decision_id + user_choice` 续跑，Decision / Control Record 落档
- [ ] `DONE` 的完成类型（completion）不再为 null
- [ ] **回退不静默**：走内置 `workflow` 工具时会话输出含明确的记录退化提示
- [ ] 既有 `wf_run` 路径回归不变（`scripts/test/runtime-logical-run.test.mjs`、`scripts/test/human-decision-e2e.test.mjs` 断言不改且全绿）；`npm test`、`npm run validate` 全绿
- [ ] 生成物一致性：`npm run generate` 后无差异（`generated-diff` 门禁通过）

## 16. UAT 场景

### UAT-01 Skill 入口完整运行

- 验收目的：确认 DSH 内 Skill 触发的运行进入同一 Logical Run Runtime，看板记录完整且可续跑。
- 前置条件：
  1. 产品 DSH 已安装正式插件，且会话可解析工作流引擎；
  2. 已安装/可加载目标模板的 skill 副本；准备一个可跑通到人工门禁的任务标识。
- 操作步骤：
  1. 在会话中以触发词发起一次模板运行；
  2. 观察首段返回状态与看板记录（任务归属、分段数、完成类型字段）；
  3. 在人工门禁处裁决并续跑；
  4. 跑到 `DONE`。
- 预期结果：
  1. 首段运行记录 `task_id` 非空、`trigger=start`（即经 `wf_run`）；
  2. 续跑后仍为**同一个** Logical Run，分段数 ≥ 2；
  3. `DONE` 时 `completion` 非 null；
  4. 看板无「残缺单段」记录。
- 建议人工关注：会话是否真的调用了 `wf_run`（而非自行改用内置工具）。

### UAT-02 回退路径如实提示

- 验收目的：确认回退不静默。
- 前置条件：构造 `wf_run` 不可用的会话（或按其错误分支模拟）。
- 操作步骤：以触发词发起运行，走到回退分支。
- 预期结果：会话输出含明确的「记录将退化」提示，且未声称记录完整。
- 建议人工关注：提示是否出现在用户可见输出中，而非仅日志。

## 17. 风险

- **模型不遵循 runbook**：会话可能自行选择内置工具。缓解：runbook 写明首选与判据；验收以真实验行为准（UAT-01 第 1 条即为此设）。
- **`wf_run` 在 DSH 内不可用**：前置验证不通过则停下呈报，不得静默降级或改走 B 方案。
- **口径改动扩散**：生成 skill 会分发到安装态目录（`~/.dsh/skills/` 等），改动须重跑生成与校验，且安装态副本需重新安装才生效（见 §18）。
- **文档与实现漂移**：`CONTEXT.md` / 两份 README 现状把内置工具写成正式路径、并引用已不存在的界面入口；本次一并修正，避免实施者被误导。

## 18. 已知限制

- 非 DSH 环境（如 ZCode）可加载同名技能但无法运行（缺 `workflow` 工具与插件；技能描述已声明仅适用于 DSH 会话）——属既有事实，本卡不处理。
- 内置 `workflow` 工具直起的运行仍为退化记录（本卡明确不处理）。
- 安装态 skill 副本不会自动更新，需重新安装后生效。
- optimize 类模板的 `resource_kind` 当前无模板声明（该模板线仍在验收中），runbook 保留该参数说明以待其落地。
