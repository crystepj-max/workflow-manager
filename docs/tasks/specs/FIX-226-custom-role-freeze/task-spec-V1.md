## 1. 需求背景

#79 的冻结纪律是「运行中工作流定义不变，只有 Provider/Model 可改」（R3）。为此，运行摘要的第一版快照（Rev1）保存了冻结脚本，续跑恒用 Rev1 脚本（[host.js:3277-3279](../../../../packages/dsh-visual-workflow/src/host.js:3277)）。

角色正文的冻结情况分两半：

- **内置角色**：编译期内已经把正文内联进脚本（`ROLE_DEFS`），冻结脚本自带正文 → 等待期间改角色文件不影响本 Run。**这一半已经修好了。**
- **自定义角色**（角色清单中 `builtin:false`）：仍然只在运行时告诉 Agent「去读某个路径的文件」。快照里记的是**路径**，不是内容 → 等待期间改掉那个文件，续跑的节点就会读到新内容。**这一半没修。**

当前唯一受影响的自定义角色是 `dispatcher`（调度），而它确实被两个已发布模板用到。

- 内联优先：[scripts/generate.mjs:543-555](../../../../scripts/generate.mjs:543)
- 自定义角色工作区优先读：[scripts/generate.mjs:556-562](../../../../scripts/generate.mjs:556)
- 快照只记路径：[packages/dsh-visual-workflow/src/host.js:823](../../../../packages/dsh-visual-workflow/src/host.js:823)

## 2. 用户问题

一次运行跑到一半停下来等人工（返工确认、验收、暂停），期间有人改了角色文件（或者运行自己的节点在可写目录里改了它）。恢复后节点按新角色行事，但看板上它仍属于同一个「定义已冻结」的运行——用户以为跑的是同一套规矩，实际中途换了。

## 3. 目标

同一次运行从第一次调用到最后一次调用，读到的角色正文是同一份；快照能回答「本 Run 用的是哪一版角色」。

## 4. 非目标

- 不改内置角色的现有内联机制（已经满足冻结，不重复建设）。
- 不提供「运行中主动切换角色」的入口——那是产品方向变更（当前纪律明确禁止定义漂移）。
- 不改角色库的编辑、创建、删除功能（角色库 UI 属 FEAT-101/102 范围）。
- 不动 Provider/Model 修订链。

## 5. 修改前

| 角色类别 | 正文来源 | 等待期间改文件是否影响本 Run |
|---|---|---|
| 内置角色 | Rev1 冻结脚本内联正文 | 否（已冻结） |
| 自定义角色 | 运行时读文件，工作区路径优先 | **是** |

证据（main `5dea84a`）：

1. 自定义角色的读取顺序：`_b = BUILTIN_ROLE_IDS.indexOf(name) >= 0`；`_order = _b ? [_bundle, _ws] : [_ws, _bundle]`（[generate.mjs:554-560](../../../../scripts/generate.mjs:554)，实测产物 `.generated/dev-workflow-2-0/script.mjs` 同形）。`_ws` 是相对路径 `dsh/roles/<name>.md`，落在运行自己的可写 source 目录内。
2. `dev-workflow-2-0` 与 `default-workflow` 两套已发布模板的 `dispatch` / `route` 节点 `profile` 就是 `dispatcher`（实测 `.generated/dev-workflow-2-0/vwf-dsl.json`），而 `dispatcher` 在角色清单里被显式标为 `builtin:false`（`dsh/roles/builtin-roles.json` 的 `compatibilityRoles`），生成的脚本中 `BUILTIN_ROLE_IDS` 也不含它。
3. 对以 `.generated` 为产物根的模板，产物旁没有 `roles/` 目录（实测 `.generated/dev-workflow-2-0/` 只有 SKILL.md/meta.json/script.mjs/vwf-dsl.json），`findRoleDir` 返回空（[host.js:548-554](../../../../packages/dsh-visual-workflow/src/host.js:548)）→ `_bundle` 与 `_ws` 同路径，去重后**只剩这一个可变路径**。
4. 快照侧确实只有路径：`roles: { role_dir: String(info.roleDir || '') }`（[host.js:823](../../../../packages/dsh-visual-workflow/src/host.js:823)），后续修订只是把 `prev.roles` 原样带过去（[host.js:863](../../../../packages/dsh-visual-workflow/src/host.js:863)）。
5. 这条读文件路径是**有意保留的兼容设计**，不是遗漏：宿主注释原文「兼容角色（builtin:false，不内联）靠它走读文件路径，磁盘旧脚本不再复用但角色包必须保留」（[host.js:544-545](../../../../packages/dsh-visual-workflow/src/host.js:544)）；生成器注释亦写明「自定义先工作区再打包快照（如迁移后的 dispatcher，编辑种子到工作区后对 bundled run 生效）」（[generate.mjs:556-557](../../../../scripts/generate.mjs:556)）。🔴 因此本切片是**对一项已确认取舍的重新决定**：已由人工在知情前提下拍板撤销（决策 3 = A，见 §12）。
6. 体积不是硬约束：角色正文最大 9,092 字节（`closeout.md`）、`dispatcher.md` 3,401 字节、全部角色合计 65,568 字节；编译参数上限 120KB、编译输出上限 1MB（[host.js:565-566](../../../../packages/dsh-visual-workflow/src/host.js:565)），现有生成物 133–151KB。

## 6. 修改后

已确认口径（决策 3 = A · 内容内联）：

1. 编译时把**本次图实际引用到的自定义角色**正文一并内联（与内置角色同源同机制），运行期不再依赖工作区文件。
2. Rev1 快照除路径外还记录角色身份与内容摘要（哪几个角色、摘要值），能回答「本 Run 用的哪一版」。
3. 内联失败（文件读不到、超出尺寸闸门）时**诚实降级**为现有读文件路径，并在运行摘要留一条控制事件，不静默假装已冻结。
4. 等待期间修改工作区角色文件，对已开始运行的这一次不再生效。

## 7. 功能范围

- 生成器的角色正文装配范围（从「仅被引用的内置角色」扩到「被引用的全部角色」）与内联尺寸闸门。
- 运行摘要 Rev1 快照的角色条目（身份 + 摘要 + 是否内联）。
- 自定义角色的读取顺序口径（内联命中即不再读文件）。
- 生成器用例 + 宿主侧续跑用例。

## 8. 不修改范围

- 不删 `roleDir` / 产物旁 `roles/` 角色包机制（打包自包含仍服务其他场景）。
- 不改角色库的编辑语义与内置角色只读规则。
- 不改内置角色的内联范围裁剪（现按被引用裁剪，见 [generate.mjs:246-253](../../../../scripts/generate.mjs:246)）。
- 不把运行摘要里已有的工作流定义快照重做一遍。

## 9. 业务规则

1. 冻结单位是**内容**，不是路径：一次运行的所有段（含暂停恢复、崩溃后派生前的续跑）必须读到同一份角色正文。
2. 内联内容必须与快照摘要同源可核对；摘要不一致时必须可见（不得静默用新内容）。
3. 只内联「本图实际引用到」的角色，不得按全量角色内联（历史上全量内联曾把最小临时图撑到 65KB 以上并触发捕获上限，见 [generate.mjs:246-249](../../../../scripts/generate.mjs:246)）。
4. 尺寸闸门失败时的降级必须是**显式**的：留控制事件 + 快照记 `inlined:false`，UI/记录能读出「本 Run 的这个角色未冻结」。
5. 生成物必须由 `npm run generate` 产出，禁止手改 `.generated/`（改权威模板与生成器再重生成）。

**实现边界（供接手者直接采用）：** 权威源码改动集中在 `scripts/generate.mjs`（角色正文装配 + 快照摘要所需信息）与 `packages/dsh-visual-workflow/src/host.js`（快照条目 + 降级留痕）；若新增「未冻结」呈现，`src/client.js` 必须与 `host.js` 同一版本交付。生成后必须 `npm run generate && npm run validate` 验证生成物一致性。

## 10. 用户操作路径

1. 用户用 `dev-workflow-2-0` 起一个运行，跑到 `dispatch` 节点后进入人工等待。
2. 期间用户（或另一个会话）修改了 `dsh/roles/dispatcher.md`。
3. 用户恢复该运行。
4. 后续节点仍按**运行时那一版**调度角色行事；运行详情能看到本 Run 用的角色版本/摘要，与修改后的工作区文件不同。
5. 新起的运行使用修改后的角色（不受影响）。

## 11. 异常和边界场景

| 场景 | 要求 |
|---|---|
| 自定义角色文件在编译时读不到 | 降级为读文件路径 + 留控制事件，运行不因此失败 |
| 内联后编译产物超出尺寸闸门 | 拒绝内联并显式降级（同 9.4），不得静默截断脚本 |
| 角色同名但一处是内置、一处是工作区自定义 | 按现有身份判定（`BUILTIN_ROLE_IDS`）为准，本任务不改变身份切分 |
| 用户在运行中途改角色且**确实想生效** | 当前纪律不允许；唯一出路是重新发起（派生新运行）。若这类诉求成立，属产品方向变更，需另立需求 |
| 旧运行（无内联的 Rev1 冻结脚本）续跑 | 仍走读文件路径；与证据兜底切片同类，只能标注不能补造 |
| 编译时角色内容被塞进脚本后含特殊字符 | 走既有 `JSON.stringify` 内联路径（与内置角色同机制），由生成器用例覆盖 |

## 16. UAT 场景

### UAT-01 等待期间改角色文件，恢复后不换规矩

- 验收目的：验证角色正文随运行冻结。
- 前置条件：
  1. 产品 DSH 安装本版本验收组合包。
  2. 使用 `dev-workflow-2-0`（或 `default-workflow`），其 `dispatch` 节点用自定义角色 `dispatcher`。
- 操作步骤：
  1. 起一个运行，等它过了第一次调度、进入人工等待或暂停。
  2. 在运行可写目录里把 `dsh/roles/dispatcher.md` 改一处显眼的措辞（例如加一行「【已改版】本轮只做只读研究」）。
  3. 恢复该运行，观察后续调度节点的行为与提示词。
- 预期结果：
  1. 后续节点仍按运行时的旧角色正文行事，不出现「【已改版】」的效果。
  2. 运行详情能看到本 Run 使用的角色版本/摘要标识。
  3. 另起一个新运行，能读到改版后的内容。
- 建议人工关注：本切片已按「改角色对已存在的运行不再生效」的既定口径验收（决策 3=A）。若验收时发现这条行为变更在实际使用中不可接受，停在此处回定义，不要让施工方自行放宽。

## 18. 已知限制
