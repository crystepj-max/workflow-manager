## 1. 需求背景

`FEAT-75` 的定稿已经把 P1–P10、9 条缺口台账、S-0…S-5 切片归属、#54–#57 裁定和 `LOC-036` 对探索硬用例的取代全部落档，因此「#75 还剩什么」已经有唯一真源。

仍然没有人负责的是收尾三步：定稿明确写了「不改产品规格正文」「不在 GitHub 上回填或关闭 Issue」，而权威文档里有六处仍在把能力指向一张即将关闭的设计票；目标规格的发布门槛与完成类型枚举也还没按本轮裁定标注实现状态。

## 2. 用户问题

关掉 #75 之后，`docs/design/workflow-manager-v0.1-final-product-spec.md` §11 仍然写着「#75 负责正式 UI/交互架构」，`blueprint-schema.md:145` 与 `CONTEXT.md:254` 仍写着 Preset 选择器「#75 做」——读者顺藤摸到一张已关闭的票，权威链断裂；同时目标规格 §13 的发布门槛、§3.3 的完成类型示例都不带实现状态，容易被读成「v0.1 必须有、已经做好」。

## 3. 目标

让 #75 关闭后，仓库内所有仍指向它的权威引用都落到仍然存在的载具上，并把本轮四项裁定以状态标注的形式写进目标规格，使「目标怎么说」与「v0.1 做到哪」不再靠读者自己推断。

## 4. 非目标

- 不产出第二份 14 项对账表或 9 条缺口台账（主源是 `FEAT-75` 定稿 §5 与其需求分析）。
- 不修改 `docs/design/workflow-ui-interaction-architecture.md`——它是另一会话的未入库在飞文件，其 §3 运行入口结论与 DT-03 的收口由主源自己改。
- 不实施任何 UI 功能（`FEAT-114` = 定稿 S-3）、不做 Preset 纠偏与选择器（定稿 S-2）。
- 不关闭 `#82` / `#83`，不改 `#54`–`#57`，不动任何既有任务卡的业务字段与验收结论。
- 不改运行时、蓝图、模板、生成物。

## 9. 业务规则

- 权威归属按仓库 `AGENTS.md`「权威资料与 Current / Target 边界」：长期原则看 `workflow-design-principles.md`，v0.1 目标语义看 final product spec，Current 看实际 main；本票只加状态标注与新指向，**不得删改任何规范性条文**，也不得以已实现为由否定目标。
- 指向改写后必须仍可追溯：每处保留「原指向 #75」这一事实（就近一句或本票 §5 表），不得静默抹掉历史。
- 关闭 GitHub issue 属对外动作：仅在产品明确授权后执行；未授权时交付正文草稿，验收第 5 条保持未勾选。
- 回写 tracker 的内容以 `> *This was generated by AI during triage.*` 开头。
- 目标规格 §13 的改动只能表达「这条门槛还成不成立、v0.1 做到哪、谁承接」，不得新增或取消门槛条目本身。

## 11. 异常和边界场景

- **定稿尚未入库（未跟踪）**：本票前置依赖 `FEAT-75`；若主源的定稿被大改或改名，指向目标会失效。处置：改指向时以定稿的**文件名 + 章节号**为准，不写行号；主源状态变化时本票退回「定义中」重做 §7 第 1 项。
- **主源正在写同一批文件**：定稿文档与其规格目录由另一会话在飞。处置：本票一律不打开这些文件；如发现主源已自行改了目标规格，本票对应条目记为已被主源吸收并取消，不产生两份改法。
- **GitHub 不可达**：仓库内回写照常交付，关票留待网络恢复，本票不得标为已收口。
- **裁定与定稿结论不一致**：例如定稿 §3 写「是否新增插件运行入口是唯一悬而未决的产品选择」，而本轮 DT-01 已裁 A。处置：由主源改其自己的文档，本票只在目标规格侧按 A 的口径标注，并在 §18 记录这一待主源收口项。
- **并行会话改动同一行**：本检出多会话共用。处置：动 `docs/design/` 与 `CONTEXT.md` 前先重读现值，只改含 `#75` 的那一行，冲突时保留他人内容。
